- 技术方案：[语义分段、对齐与安全复用](technical/translation-cache-optimization.md)。
- 基础方案：[翻译管线 §14](technical/translation-pipeline.md#14-缓存落地方案核心已接入--扩展状态见-149)（稳定阅读：同文件「## 14」；职责边界见技术方案 §1.1）。

## 1. 问题与目标

缓存目前支持整段、连续短句块和单短句复用，但游戏对白常因窗口排版折行，原文与译文也可能采用不同分段方式。优化不能把排版行误认为语义短句，不能因两侧段数相同就认定译文对应。

本需求让翻译库在保留原始定稿的前提下，通过可信语义边界与原译映射提高命中率。最小复用单位仍是完整短句，不做单词相似、任意子串或字符覆盖匹配。

## 2. 真实案例

复核入口：`/translate/cache?q=おっかないんスよねえ`。本次查看到 10 条记录，均显示为导入；仅凭页面不能判断它们是否由历史优化生成。

```text
いや俺ヴェンダンさん実はあんま好きじゃ
　ないんスよ恐いじゃないスかあの人顔イカツイじゃないスか
　おっかないんスよねえ
```

第一处换行截断了 `好きじゃない`，不能按行独立翻译或配对。当前无外壳整段的优化预览没有额外结果；带外层 `「……」` 的版本仅预览去除外层引号。

| 记录                                                  | 结论                                                 |
| ----------------------------------------------------- | ---------------------------------------------------- |
| `おっかないんスよねえ` → `超让人发怵的啊`             | 基本可用；语气强度可人工调整                         |
| `おっかないんスよねえ』つって` → `根本不敢接近啊`     | 增加“不敢接近”的意思，遗漏转述，不宜作为准确复用依据 |
| `おっかないんスよねえ』つって」` → `根本不敢接近啊』` | 同时存在转述遗漏与引号结构不对应                     |

经人工审校可考虑以下分组。表格说明语义边界，不代表已保存映射；原始折行如何对应逻辑正文须由技术方案处理。

| 原文逻辑短句                                       | 参考译文                       |
| -------------------------------------------------- | ------------------------------ |
| `いや俺ヴェンダンさん実はあんま好きじゃないんスよ` | 不是，我其实不太喜欢梵达先生啊 |
| `恐いじゃないスか`                                 | 那人不是挺吓人的吗             |
| `あの人顔イカツイじゃないスか`                     | 他长得不是挺凶的吗             |
| `おっかないんスよねえ`                             | 真让人发怵啊                   |

人名沿用已有译名，正式定稿以术语表为准。不能把本例推广成遇到 `スよ`、`スか` 就自动切分的规则。

## 3. 产品规则

### 3.1 换行与语义边界分开

- 软换行：有提取来源或人工确认，表示窗口排版折行；允许建立逻辑正文视图，原始文本保持不变。
- 硬换行：明确的独立条目、段落或结构边界；禁止跨越它合并匹配块。
- 未知换行：来源不足以判断；保留原样，可整段精确复用，但不能仅凭换行生成可独立复用的短句或缺口。
- **默认 unknown**：图鉴优化 / 已入库定稿若无与原文精确绑定的提取元数据，也无人工换行注解，则文中换行一律按 **unknown** 处理；禁止实现侧猜测为 soft（含「凡 RPG Maker 对白换行都当 soft」）。
- 不全局删除空白。英文词间空格、缩进、控制码和实际换行用途须分别处理（英文 soft 空白策略见技术方案 §4.2）。

### 3.2 整段与连续块优先

下表中的 `a`、`b`、`c` 都是已确认完整的短句。

| 查询         | 缓存                       | 行为                                      |
| ------------ | -------------------------- | ----------------------------------------- |
| `a,b,c`      | 完整 `a,b,c`               | 整段优先                                  |
| `a,b,c`      | 完整 `b,c`                 | 使用连续 `b,c`，仅补译 `a`                |
| `b,c`        | `a,b,c` 且有可信映射       | 提取对应的 `b,c`，不输出 `a`              |
| `b,c`        | `a,b,c` 无可信映射         | 不裁译文，继续查完整 `b,c`，再查 `b`、`c` |
| `b,c`        | 完整 `b,c` 和独立 `b`、`c` | 优先连续块，避免不必要拼接                |
| 无边界 `abc` | 若干单词或子串             | 不复用子串，按完整待译单元处理            |

已有人工区间保护、冲突回退与来源优先级继续生效。覆盖率指完整短句的覆盖比例，不是词相似度；高覆盖率也不能绕过边界和映射校验。

### 3.3 标点与引用

- 保留无标点、句号、问号和感叹号之间的语气区别；全半角等价沿用基础规则。
- 省略号及其位置保留，默认不作为可直接剥除的装饰。
- 只对结构对应的成对外壳建立别名；内部引语、说话人和转述后缀保留。
- `『……』つって` 中的 `つって` 属于正文语义；不能通过剥壳规则删除。
- 引号残片不能自动升级为完整独立句。实际翻译质量与结构完整性需要分别审校。

### 3.4 优化工作流

1. 展示原始定稿、已有映射和候选分组，标出排版换行与语义边界的区别；无提取元数据时明确标为 unknown，并提供「标为软折行 / 硬边界」的人工操作。
2. 自动建议保持待确认状态；两侧段数相同只表示数量一致。
3. 用户可以合并、拆分或调整对应区间，支持一对多、多对一；也可先确认换行注解再确认对齐。
4. 提交前展示可保存项及失败原因；不把后端必然拒绝的候选显示为可直接确认。
5. 确认后保存与当前定稿版本绑定的映射，不批量生成去引号、去折行、去标点的独立译文。
6. 修改译文与确认映射区分操作；先保存译文时，重新验证基于旧译文的候选。

### 3.5 与管线 §14 的关系（产品层）

本需求是 §14「定稿 + 可重建索引 + verified 映射」之上的 **换行证据与逻辑视图扩展**，不推翻：

- 原始定稿主键与正文保留；
- 写入秩 / 双写拒写（低秩不进本作 ndjson）；
- 服务端完整命中 vs 插件 `translateWithLookup` 渐进替换（§2）——本期 **不** 把插件改成「未完整则整段 null」。

细节边界表见技术方案 §1.1。

## 4. 范围与非目标

本期包括：换行分类、可信语义边界、原译区间映射、统一优化预览与运行时规则、服务端与插件一致性、诊断及回归用例。

本期不包括：更换 SQLite、词向量检索、自动重翻全部缓存、批量删除旧记录、消息窗口重排、自动认定模型拆分可信、语序重排后的跨区间拼接、改写管线写入秩或双写契约。

历史问题记录先提供诊断清单；修正原文或译文需要单独操作，不随索引升级自动改写。

## 5. 验收

| 场景                                      | 必须结果                                                             |
| ----------------------------------------- | -------------------------------------------------------------------- |
| `好きじゃ` 与 `ないんスよ` 被未知换行隔开 | 不生成两个独立可复用单元，不按行补译                                 |
| 图鉴优化无提取元数据、无人工换行注解      | 无句末标点的中段换行推断 soft；句末后换行推断 hard；歧义才 unknown   |
| 同一折行经启发式或人工确认为软折行        | 可与无折行正文匹配；原始正文与偏移可追溯                             |
| 英文 soft：`Hel\nlo` / `word\nword`       | 按技术方案 §4.2 空白策略；不删成 `Hello` 误粘或吃掉词间空格          |
| 英文词间空白、URL、控制码                 | 不因折行归一化被删除、拼坏或移位                                     |
| 原译段数相同但含义错位                    | 不自动标记可信；允许人工重组                                         |
| 一句译成两句，或两句译成一句              | 保存完整映射块，只在合法边界提取                                     |
| 带 `』つって` 的残片                      | 不与裸 `おっかないんスよねえ` 等价                                   |
| 无标点、`!`、`?`、省略号变体              | 不因去边缘符号串义                                                   |
| 查询和缓存双向包含                        | 按 §3.2 复用，连续 `b,c` 优先                                        |
| 确认时定稿已修改                          | 拒绝旧映射，保留编辑内容并提示刷新                                   |
| 映射失效或无 soft 注解                    | 整段精确查询仍可用；无证据时不强行 soft 匹配（MVP 不做旧客户端双轨） |
| 预览显示可确认                            | 后端在同一版本与规则下得出相同校验结果                               |
| 插件局内套用                              | 仍允许渐进部分替换（管线 §2）；不因本期改为整段 null                 |

完成标准：上述用例在纯规则、服务端及插件相关路径通过；真实案例回放不产生否定截断、转述遗漏或无来源子译文。命中率与拒绝原因先记录基线，再评估提升，不预设未经测量的收益数字。
