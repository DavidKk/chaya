# AI 开发文档优化需求

- 日期：2026-10-24；有效性：现行；文档优化已实施，二轮 CR 修复见 §5。
- 目标：初始化轻、按需定位准、内容足以约束行为。体积与语义覆盖都要验收。
- 范围：需求、关联技术方案、产品 skill、索引；本次明确要求 CR 初始化上下文，允许等长或缩短修订根入口。
- 技术方案：本轮仅文档治理，不新增独立技术文档、生成器或分发逻辑。未来涉及代码机制再补必要设计。

## 1. 背景与目标

文档过大会增加读取和处理成本；过度压缩则容易遗漏范围、权限、停止条件与验收，导致 AI 偏移。优化应做到：

1. 默认只提供必要规则和精确路由，正文需要时再读。
2. 阅读目标文档时先确认页头有效性与替代关系，再选相关章节。
3. 当前能力、确认目标、冻结范围和历史记录分开；只读摘要不能视为掌握完整约束。
4. 需求与实现关联明确；不为同名配对、行数指标而新建、拆分或归档。

不据本文扩展产品功能、解冻旧需求或改变用户授权边界。

## 2. 初始化与 token 约束

- 根入口保留 Next.js 提醒、约定存放位置、按需技能、文档路由、校验和源文件大小边界。不加入产品能力表、全文导入或“每次必读 docs”。
- 普通功能开发不改 Agent 约定；本次初始化 CR 仅精简 `AGENTS.md` 并补文档路由，保留 `CLAUDE.md` 导入和 `.agents/` 原有规则。
- 索引只列任务关键词、文件与必要章节，不复制正文或实现进度；不超过 60 个非空行、7 KB（UTF-8）。
- 已知路径直读；路径未知且需要文档时才查索引。关联链接不代表递归加载，历史材料、排期和页面译文不进入默认路径。
- 技术细节不足、需求冲突或依据缺失时定向补读原文 / 代码，不为守住字数而猜测。范围、权限、错误语义及验收不能删。
- Skill 描述须为有效 YAML，触发范围可区分。仅任务命中的 skill 加载正文；产品 skill 安装后独立可用，不依赖仓库内索引。
- MCP 优先使用已暴露 schema；工具缺失或清单过期才重新发现，避免重复读取整份目录。
- MCP schema 是否预载取决于客户端；本次目录 52 项序列化约 28 KB，不等于实际请求体积。不用 Chaya 时可在客户端关闭连接，不能只靠缩短文档消除该成本；本轮不改客户端配置。
- 根入口与三个英文 skill 分别不大于二轮 CR 开始时的 1744、2475、2653、3709 字节。体积只是代理，不宣称不同客户端的精确 token、耗时或加载次数已测定。

## 4. 优化事项与验收

保留原清单 1–10 编号；P1 优先处理错误路由与事实边界，P2 处理维护成本。

### 1. 术语统一（P1）

以[运行模式](run-modes.md)为产品词表：local / cloud / plugin。`remote / server / app` 作为实现值保留并说明映射；Microsoft Edge 只指浏览器。验收：RGSS、README、skill 不把 Edge 当 cloud 产品名，不机械替换代码标识。

### 2. MCP 能力同步（P1）

[能力总表](capabilities.md)按 `lib/integration/mcp-catalog.ts`、`mcp-availability.ts`、`lib/webmcp/mode-matrix.ts` 核对；内置权限另查 `lib/game-agent/runtime/capabilities.ts`。验收：现行工具与环境限制一致；新增目标写需求，落地后同步快照。入口保留配置和限制，skill 不复制完整目录。

### 3. 状态与进度分开（P1）

有效性采用草案、现行、冻结、历史；进度另写阶段与未完成范围。验收：混合文档按章节说明替代关系，冻结不等于历史或已完成；需求与技术进度不同须说明原因。

### 4. 按任务索引（P2）

交付 [docs/README.md](README.md)，同时定位需求和技术文件。验收：先看页头再选章节；配置 / 聊天不误导到仅有工具权限的章节；技术细节不足时能找到下一份依据，不凭文件名猜配对。

### 5. Skill 与译文（P1 / P2）

三份英文源先核对，再同步 27 份页面译文。验收：标准 YAML 和仓库读取逻辑均通过；setup 对应安装 / 环境，launch 对应游戏准备 / 启动，mcp 对应连接 / 操作，不因泛称 Chaya 同时拉入三份正文。保留前置条件、权限、操作后验证、原始错误和不可信内容边界；命令标识不翻译。

### 6. 翻译文档职责（P2）

区分调度、缓存、结构化编辑、整句回退、质量和徽标。验收：[调度基线](translation-scheduling.md)覆盖旧全引擎竞速；[并发与徽标](translation-concurrency-and-badges.md)仍保留开关、探活、徽标入口；保留各自限制、示例和验收，不强制合成两篇。

### 7. 产品模式与门禁（P1）

[服务形态需求](requirements-service-modes.md)与[技术设计](technical/service-modes.md)说明实现映射；[补齐需求](capability-supplement.md)保留冻结范围。验收：O2 能力拆分与未验收矩阵的冻结不误写成 O8 命名冻结，不因仅留术语表而丢掉门禁规则。

### 8. 关联补齐（P2）

核对轨迹、集成、服务形态、调度与已有方案的实际覆盖。验收：可表达一对多、多对一、无需独立方案和确有缺口；[轨迹](agent-gameplay-trace.md)关联活动日志与任务分层不代表 Phase 2–3 已完成。仅有影响实施且未覆盖的决策时才补技术方案。

### 9. 长文组织（P2）

CLI、补齐需求、Agent 设计、翻译管线先做章节直达。验收：既有规则与锚点可追溯，能够定向选段；仅职责混杂或重复维护时拆分，不把源码行数限制套成文档硬限制。

### 10. 历史材料（P2）

会议纪要与 MVP 定稿只供追溯；backlog 保留排期；并发篇保留有效章节。验收：核对入链、待办与替代关系后才归档，不按日期迁移；修复路径、章节引用和必要旧入口。

## 5. 执行与 CR 记录

首轮完成索引、术语与状态修正、技术关联、skill 精简和页面译文同步。长文采用章节导航，混合文档保留原位，无需额外技术方案或物理归档。

- 语义覆盖：按下表静态核对核心信息可达。不替代真实客户端的自动选择与模型行为测量，也不代表全部产品功能已实现。
- 二轮验证：三份 skill 的标准 YAML 与仓库解析一致，skill 校验通过；现有读取测试 10 项通过。最终体积、链接与格式结果随本轮交付报告。

## 6. 场景验收

<!-- prettier-ignore -->
| 场景 | 最小必要上下文 | 不应自动加载或推断 |
| --- | --- | --- |
| 已有路径的小改动 | 目标文件；涉及功能边界时才读需求页头 / 章节 | 整个 docs、优化记录、无关 skill |
| Agent 配置与聊天 | 助手页头、配置章节；涉及运行策略再读替代入口 | 仅凭 §9 推导配置；全部 CLI 方案 |
| 调度 / 徽标 | 调度基线或徽标有效章节；必要的技术部分 | 全部翻译文档、旧竞速方案 |
| 安装 Chaya | setup 描述与正文 | launch、mcp 正文，除非后续任务涉及 |
| 已连 MCP 的游戏操作 | mcp、相关 schema；状态 → 操作 → 回读 | setup / launch、反复完整目录、无关历史 |
| 覆盖存档 / 读档 / 退出 | 操作范围、用户授权、破坏性说明与结果验证 | 从摘要自行推定已授权 |

每轮记录实际文件、验证结果与残留风险。文档变更按影响面验证，不新增镜像文案测试，不运行无关全量构建，不触碰用户的并行代码改动。
