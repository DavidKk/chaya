# Chaya 助手与 Agent 配置需求

> 状态：实施中（M1 已完成）  
> 日期：2026-10-04  
> 技术方案：[`technical/game-agent.md`](./technical/game-agent.md)  
> 关联：[`integration.md`](./integration.md)、[`webmcp.md`](./webmcp.md)、[`game-assistance.md`](./game-assistance.md)

## 1. 背景

Chaya 已能通过 MCP 读取游戏状态、调用第一方插件、模拟按键并执行短按键序列。当前仍需要外部 Agent 客户端连接 MCP，玩家不能直接在游戏窗口内提出目标并让 Agent 持续操作。

新增“Chaya 助手”右侧聊天面板，使玩家可以输入目标，由用户配置的 Agent 推理，并通过现有 Chaya 工具完成“观察 → 操作 → 验证”的有限循环。Agent 是独立、可重复配置的实体；当前适配器为 Ollama，名称、接入地址、默认模型和参数不写死在聊天面板或游戏插件中。

App、local server、Edge 和游戏插件使用相同的 Chaya 助手与 Agent 配置组件。Edge 的 Agent 配置存于浏览器本地；执行能力按运行形态显示可用状态。

## 2. 目标

| 目标 | 说明                                                           |
| ---- | -------------------------------------------------------------- |
| G1   | 在任意页面或游戏内唤出独立 Chaya 助手侧栏                      |
| G2   | 输入自然语言 Prompt，获得所选接入实例的流式回答                |
| G3   | Agent 可以读取当前游戏状态、按键游玩并调用允许的插件工具       |
| G4   | 一次任务可执行多轮工具调用，但必须有明确上限和停止条件         |
| G5   | 玩家始终能看到当前动作并立即停止 Agent                         |
| G6   | Agent 操作后必须重新读取状态，不能只根据工具返回假定操作成功   |
| G7   | 模型、会话和游戏隔离；切换游戏不会串用上下文                   |
| G8   | 配置区以列表和详情完成多个 Agent 的新增、查看、编辑和删除      |
| G9   | 游戏插件与本机服务双向同步 Agent，离线修改重连后自动合并       |
| G10  | Chaya 助手可按用户指令管理本地 Agent，且凭证只写不读、加密落盘 |

## 3. 非目标

- 第一版不支持 Edge / Vercel 直接连接本机 Ollama。
- 第一版只交付 Ollama 适配器；配置结构按 provider + profile 设计，后续可以增加其它协议适配器。
- 第一版不让 Agent 使用终端、任意文件系统、任意网络或 `chaya_live_eval`。
- 第一版不让模型无限后台运行，也不在玩家未发起任务时自行操作。
- 第一版不处理只能通过画面识别的谜题；先使用结构化游戏状态和屏幕文字。
- 第一版不承诺所有 Ollama 模型都能游玩；优先使用原生工具调用，模型未返回工具调用时尝试结构化动作决策，失败则明确报错。

## 4. 核心使用场景

### 4.1 问当前状态

玩家输入“我现在在哪里，下一步可以做什么”。Agent 读取当前状态并回答，不操作游戏。

### 4.2 执行短目标

玩家输入“选择第二个选项并继续对话”。Agent 读取状态，执行短按键序列，读取新状态并报告结果。

### 4.3 执行连续目标

玩家输入“帮我走到村长旁边并完成对话”。Agent 在限定步数内循环读取地图、附近事件和对话状态，分段执行移动与确认操作，达成目标后停止。

### 4.4 使用插件能力

玩家输入“打开三倍加速继续走”。Agent 可调用已允许的 ChayaBoost 工具，然后读取状态确认。修改金钱、传送、读档等能力根据权限策略处理。

### 4.5 人工接管

玩家在 Agent 运行中点击停止，或使用停止快捷键。当前请求立即取消，后续工具不再执行，游戏输入恢复给玩家。

### 4.6 管理 Agent 配置

玩家可以要求 Chaya 助手列出、新增、修改或删除本地 Agent，例如“删除名字叫 Flow Local 的 Agent”。名称重复时助手必须先读取列表并使用稳定 id。Token、API Key 等凭证只能作为写入参数，列表、工具结果、聊天记录和日志均不得返回其明文或密文。

## 5. 运行模式

### 5.1 询问（内部策略）

- 默认只开放只读工具。
- Agent 可以读取游戏状态和插件状态。
- 不允许按键和修改游戏。
- 回答完成后立即结束本轮。

### 5.2 游玩（内部策略）

- 开放状态读取、按键和经过允许的插件工具。
- 一次用户消息启动一个有界循环。
- Agent 达成目标、需要玩家决定、连续无进展或达到上限时结束。
- 每次只允许较短的 `chaya_live_play` 操作序列，避免模型一次规划过长而失控。

不增加“完全后台自动玩”模式。长期目标仍由一次显式任务承载，并受轮次和时间上限约束。

玩家直接输入自然语言目标；Host 结合当前状态判断本轮使用只读询问还是有界游玩，不要求玩家预先选择模式或声明场景。游戏辅助的动态规划与典型场景见 [`game-assistance.md`](./game-assistance.md)。

## 6. 游戏内展示

### 6.1 Chaya 助手入口

- App / Web 顶栏右侧增加“Agent”图标工具按钮；游戏内 GameEdit Header 使用相同入口。
- 提供全局快捷键，第一版固定为 `Ctrl/Command + Shift + A`，后续再开放配置。
- Agent 侧栏与 GameEdit 编辑面板独立；关闭编辑面板不应中断正在运行的 Agent。
- 不可用时在面板中央显示原因与“连接”按钮；“连接”进入配置区的 Agent 列表，不在 Composer 底部显示错误。

### 6.2 桌面布局

Agent 使用游戏窗口右侧停靠栏，不作为 GameEdit 的普通 Tab，也不放在居中卡片中。

```text
┌────────────────────────────── 游戏窗口 ──────────────────────────────┐
│                                                       ┌─────────────┐│
│                                                       │ Agent   ■ × ││
│                                                       ├─────────────┤│
│                         游戏画面                      │ 当前目标     ││
│                                                       │             ││
│                                                       │ 对话与动作   ││
│                                                       │             ││
│                                                       ├─────────────┤│
│                                                       │ 当前目标    ││
│                                                       │ Prompt   ▶  ││
│                                                       └─────────────┘│
└──────────────────────────────────────────────────────────────────────┘
```

- 默认宽度 400px，最小 320px，最大 `min(560px, viewport - 160px)`，允许在该范围内拖动。
- 游戏可用宽度不足时改为覆盖式侧栏，但保留一部分游戏画面作为上下文。
- 侧栏采用固定 Header、可滚动 Body、固定 Composer 的三段结构。
- 不把每条消息包成装饰卡片；用户消息与 Agent 回复按对话层级排版。

### 6.3 Header

Header 保持单行稳定高度，包含：

- 标题固定为“Chaya 助手”。
- 运行时显示停止按钮；空闲时显示新会话按钮。
- 关闭侧栏按钮。

接入实例和模型切换放在 Composer 底部工具栏，不占用主 Header。运行中禁止切换。

### 6.8 配置信息架构

- 全局一级导航新增“配置”，与游戏库、修改、翻译、日志、集成并列。
- 配置页使用二级导航；第一项是“Agent”，后续配置类型沿用同一外壳扩展。
- Agent 二级页默认展示 Agent 列表，不直接展示编辑表单。
- 列表支持进入详情、添加和删除；新增与编辑复用同一个详情表单。
- Agent 是多个实体，不设置“默认 Agent”按钮；列表第一项作为默认选择，顺序稳定。
- 每个 Agent 独立保存名称、平台、服务地址、默认模型、Temperature 和 Keep Alive。
- Chaya 助手只负责聊天、会话和选择 Agent / 模型；CRUD 统一进入配置页。
- App、local server、Edge 和游戏插件复用同一套列表、详情与表单组件，仅替换请求和存储适配器。

### 6.9 插件与服务同步

- 插件启动、恢复焦点和运行期间自动与本机服务同步；插件保存后立即同步。
- 初始化必须先合并两边已有数据；缺失缓存和空缓存不能清空另一边。
- 不同 Agent 取并集，同一 Agent 的不同字段分别合并，同字段冲突使用稳定版本号决定。
- 删除必须同步明确的删除记录，离线旧副本不能让已删除 Agent 重新出现。
- 同步暂时失败时保留插件本地修改，重连后继续合并。

### 6.4 当前目标

游玩任务开始后，消息区顶部显示一条紧凑目标栏：

- 用户原始目标的单行摘要。
- 当前循环步数，例如 `4 / 20`。
- 当前阶段：观察、操作、验证、等待玩家或已停止。

目标栏不是聊天消息，滚动消息时保持可见。

### 6.5 消息与动作

消息区同时展示对话和执行进度：

- 用户 Prompt 右对齐。
- Agent 正文左对齐，支持流式增量。
- 工具动作使用紧凑行：工具名称、动作摘要、状态和耗时。
- 连续按键序列合并为一行，例如“向下选择并确认”。
- 工具结果默认折叠，只展示与判断下一步有关的摘要；可展开查看 JSON。
- Agent 的内部推理不展示，只展示面向玩家的简短进度。
- 错误显示在发生位置，并提供重试或结束本轮操作。

### 6.6 Composer

- 移除单独的“询问”标题，输入框、接入实例、模型和发送按钮组成一个圆角 Composer。
- 第一行是多行 Prompt 输入框，第二行工具栏从左到右显示接入实例和该实例的模型，发送 / 停止位于右侧。
- 接入实例显示用户配置的 label；同一种 provider 可以有多个 label 不同的实例。
- `Enter` 发送，`Shift+Enter` 换行。
- 发送按钮使用熟悉的箭头图标并带可访问名称。
- 不要求玩家在发送前选择“询问 / 游玩”；根据目标和当前游戏状态决定本轮工具权限，并在执行动作前展示任务状态。
- 生成期间输入框可继续编辑下一条消息，但发送进入队列的能力放到后续阶段；第一版生成期间禁用发送。
- 运行中主命令变为停止，不允许重复提交同一任务。

### 6.7 焦点与游戏输入

- 侧栏输入框聚焦时，玩家键盘事件不得传入游戏。
- 点击游戏画面或关闭侧栏后，恢复游戏焦点。
- Agent 发送的程序化按键不受侧栏输入焦点影响。
- `Escape` 优先关闭侧栏内浮层；没有浮层时收起侧栏，不退出游戏。
- 停止快捷键在侧栏开关状态下都可用。

## 7. Prompt 组成

用户只编辑本轮目标。实际发送给模型的上下文由系统组装：

1. 固定系统 Prompt：身份、边界、循环规则和停止条件。
2. 当前模式：询问或游玩。
3. 当前游戏与可用能力摘要。
4. 最近会话历史和阶段摘要。
5. 用户本轮目标。
6. 工具定义通过 Ollama `tools` 字段单独提供，不重复塞入正文。

第一阶段不允许模型自主选择工具。Host 在每个询问 Turn 开始前确定性调用一次 `chaya_live_state`，将裁剪后的结果作为受信任的上下文注入 Ollama 请求。第二阶段再启用模型工具调用。

Agent 使用用户本轮 Prompt 的语言回答；无法判断时使用当前 UI 语言。

系统 Prompt 必须要求：

- 操作前先读取状态。
- 每次只执行短操作。
- 操作后重新检查状态。
- 不猜测工具成功，不伪造未观察到的游戏内容。
- 已达成目标时结束，不继续无关操作。
- 需要玩家选择或遇到危险操作时停止并说明。

## 8. Agent 循环

一个游玩任务由 Chaya Host 控制循环，不能依赖 Prompt 让模型自行遵守无限循环边界。

```text
用户目标
  ↓
观察：chaya_live_state
  ↓
模型决定：回答 / 调工具 / 请求玩家 / 完成
  ↓
执行一个或一小组工具
  ↓
验证：读取或使用工具返回的新状态
  ↓
进展判断
  ├─ 已完成 → 总结并结束
  ├─ 需玩家 → 暂停并等待
  ├─ 无进展 → 换策略；连续 3 次无进展后结束
  ├─ 达上限 → 总结当前进度并结束
  └─ 有进展 → 下一轮
```

默认边界：

| 边界                | 默认值                   |
| ------------------- | ------------------------ |
| 单任务最大模型循环  | 20                       |
| 单次按键序列        | 8 个动作                 |
| 单次按键按住 / 等待 | 600 帧以内，沿用工具限制 |
| 连续状态无变化      | 3 次后停止               |
| 单任务最长时间      | 5 分钟                   |
| 同一游戏并行任务    | 1 个                     |

## 9. 工具权限

### 默认允许

- `chaya_live_games`
- `chaya_live_state`
- `chaya_live_plugins`
- `chaya_live_play`
- `chaya_live_press`
- 只读插件工具
- ChayaBoost 的启停与状态

### 第一版不提供

- `chaya_live_eval`
- 游戏库、装壳、清插件、删除翻译等游戏外管理工具
- 任意未列入第一方目录的方法

### 需确认或暂缓开放

- 覆盖存档、读取存档。
- 退出游戏。
- 传送、修改金钱、物品、变量、开关。
- 启动战斗、跳过或清除事件。

第一阶段可以直接不向模型提供这些工具。后续开放时，必须由 Host 在执行前暂停并生成确认请求，玩家本人确认后才继续。

## 10. 状态

| 状态           | UI 行为                           |
| -------------- | --------------------------------- |
| `unavailable`  | 显示原因与“连接”，进入 Agent 配置 |
| `idle`         | 可输入 Prompt、切模式和模型       |
| `starting`     | 创建会话、探测模型能力            |
| `observing`    | 读取游戏状态                      |
| `thinking`     | 等待 Ollama 返回                  |
| `acting`       | 正在执行工具                      |
| `verifying`    | 操作后检查状态                    |
| `waiting_user` | 等待玩家确认或补充信息            |
| `stopping`     | 已请求停止，等待当前执行点退出    |
| `completed`    | 本轮结束，可继续追问              |
| `failed`       | 显示失败原因和可重试动作          |

刷新、关闭侧栏和切换页面不能偷偷丢弃仍在运行的任务。游戏退出时必须中断对应任务。

第一、二阶段会话只保存在服务进程内；刷新 UI 可以重新取得当前 Turn 状态，但服务进程重启后不恢复历史。持久化与重连放在第三阶段。

## 11. 分阶段交付

不建议一步到位。分三个可独立验收的阶段：

### Phase 1：Chaya 助手与 Ollama 对话

- Chaya 助手侧栏、快捷键和焦点处理。
- 一级“配置”导航与二级“Agent”导航。
- Agent 列表与新增 / 编辑详情，支持多个 Ollama Agent 的独立名称、endpoint、默认模型和参数。
- App、local server、Edge 与游戏插件复用 Agent CRUD 组件。
- 根据所选实例动态探测 Ollama 和读取模型列表；失败或临时空列表时保留已保存模型。
- Prompt、流式回答、停止和错误状态。
- 按 `gameId` 建立内存会话。
- 只开放只读状态工具，完成“询问当前状态”。

验收：在 demo 中打开侧栏，询问当前选项，Agent 能读取状态并流式回答；停止立即生效。

### Phase 2：有界游玩循环

- 接入原生 Ollama tool calling。
- 开放 `chaya_live_play` 和安全插件工具。
- Host 控制最大循环、时间、无进展检测和操作后验证。
- 展示工具过程、当前目标和循环步数。

验收：Agent 根据自然语言目标，在 demo 中选择指定选项并确认，最终引用操作后的状态报告完成。

### Phase 3：长期使用

- 危险工具确认与暂停 / 恢复。
- 会话持久化、上下文压缩和游戏阶段摘要。
- 模型能力探测、模型级参数配置和失败降级。
- 更完整的 RPG Maker 菜单、战斗和地图场景验收。
- 评估截图 / 视觉输入，支持纯画面内容。

验收：长任务不会无限运行；切换游戏不串上下文；重启 App 后可恢复历史；危险操作未经确认不会执行。

## 12. 验收清单

- [ ] 侧栏打开、关闭和拖动宽度不遮挡关键控件或改变游戏布局尺寸。
- [ ] 输入聚焦时不会误操作游戏，关闭后焦点恢复。
- [ ] Ollama 不在线、模型不存在、模型不支持工具调用都有明确状态。
- [ ] 问询模式不会执行写操作或按键。
- [ ] 游玩模式操作前观察、操作后验证。
- [ ] 停止后不再启动新工具。
- [ ] 达到步数、时间或无进展上限时正确结束。
- [ ] 工具参数通过既有 schema 校验，模型输出不能直接执行 JS。
- [ ] demo 指定选项任务端到端通过。
- [ ] Edge 明确提示该能力需要 App / local，不发起本机 Ollama 请求。
