# 翻译缓存结果窗口跨分片聚合优化需求

- 状态：需求草案，待评审；仅定义后台 seed 补译的纯缓存结果消费，不代表已实现。
- 日期：2026-10-26。
- 关联需求：[翻译缓存批处理性能](translation-cache-batch-performance.md)、[翻译缓存语义分段与优化需求](translation-cache-optimization.md)、[翻译调度基线](translation-scheduling.md)。
- 技术方案：[缓存结果窗口跨分片聚合技术方案](technical/translation-cache-result-window-batching.md)。
- 替代边界：本页细化并收紧[缓存批处理性能](translation-cache-batch-performance.md) §5.3、§9.3.4 中“纯缓存结果聚合”的判定，并澄清[缓存批次设计](technical/translation-cache-optimization.md) §11.2 中“没有更多就绪项”的语义；其他缓存快照、权威校验、回填、失败恢复、缓存优先窗口和引擎调度语义不变。

## 1. 背景

后台 seed 补译已经使用独立缓存 worker、共享 SQLite 索引和 32 项扫描分片。热态缓存查询通常只需毫秒级时间，但实际活动日志仍可能连续出现：

```text
[缓存] #657：1/1 条（12 字符）完成
[缓存] #658：1/1 条（38 字符）完成
[缓存] #659：2/2 条（55 字符）完成
[缓存] #660：1/1 条（62 字符）完成
```

一次本地观测中，115 个结果窗口共消费 163 条、7,168 个源字符，耗时约 75.5 秒，折合约 95 源字符/秒。其中 114 个窗口为纯缓存窗口，平均每个窗口仅 1.42 条、62.3 个字符，27 个窗口只有 1 条。

这组数据不能证明缓存匹配本身只能达到约 95 字符/秒。它首先说明结果窗口被切得过碎，固定开销替代了缓存查询成为主要节奏。

## 2. 问题定义

### 2.1 扫描分片被误当成结果批次

缓存 worker 一次领取 32 项扫描分片，这是 IPC 和内存反压单位，不是用户可见批次，也不是结果提交批次。

当前结果消费在缓存分片结束且即时结果缓冲为空时，可以提前结束一个纯缓存窗口。若该分片只先返回 1～3 条命中，就会形成一个很小的窗口，随后执行回填、状态持久化、日志和下一轮调度。

### 2.2 “没有更多就绪项”缺少时间与工作状态定义

“没有更多就绪项时立即提交”不能等同于“此刻内存中的 completed 数组为空”。下一分片可能已经在 worker 中执行，或仍在待扫描 / 重校验队列中。

因此，判断窗口是否可以结束，必须同时检查：

- 当前已完成的缓存结果；
- 是否有缓存分片在途；
- 是否还有可领取的未扫描任务；
- 是否还有 `RECHECK` 任务；
- 结果缓冲是否在短时间内继续增长。

### 2.3 批次上限没有作为装载容量使用

纯缓存结果窗口已经有 40 项 / 10,000 字符上限，但当前实现可能只装入 1 条就提交。上限成为“允许的上限”，没有成为“尽量装满、达到边界才发车”的装载容量。

### 2.4 固定开销被小窗口反复放大

每个结果窗口至少涉及：

- 结果选择与来源统计；
- 本作缓存回填 flush；
- 作业状态检查和持久化；
- 活动日志写入；
- 下一轮 `fill()` 调度。

当窗口平均只有 1～2 条时，这些固定成本会明显压低端到端吞吐，并让用户误以为缓存匹配变慢。

## 3. 目标

1. 纯缓存结果窗口跨多个 32 项扫描分片持续装载，直到达到容量边界或满足明确的提交条件。
2. 不把“分片完成”当作“批次完成”；分片结束只更新工作状态，不单独触发小批提交。
3. 在存在足够纯缓存结果时，避免稳定出现 1～3 条的小窗口。
4. 保持首批进度可见：单条结果仍可及时更新进度与检查点，不要求用户等到整批提交后才看到变化。
5. 真实引擎结果、暂停、取消、缓存线路故障和任务结束仍及时提交，不为凑满缓存窗口而阻塞。
6. 纯缓存结果不继承真实引擎的自适应条数或字符预算。
7. 保留现有 40 项 / 10,000 字符上限、权威校验、去重、回填和失败恢复语义。
8. 以真实语料回放验证端到端纯缓存吞吐，而不是只报告 SQL 或 worker 单条耗时。

## 4. 非目标

- 不把全部缺失项一次性交给真实翻译引擎。
- 不取消 40 项或 10,000 字符上限。
- 不把 32 项扫描分片直接扩大为无界队列。
- 不改变真实引擎的 4～40 项自适应批次、字符预算、并发和超时策略。
- 不取消文件指纹、`authorityVersion`、共享 revision、人工译文保护和冲突校验。
- 不为普通用户新增缓存批次大小设置。
- 不通过跳过回填、持久化或日志来制造吞吐数字。
- 不承诺所有设备、语料和命中率下固定达到同一吞吐。

## 5. 术语

| 术语     | 定义                                                                     |
| -------- | ------------------------------------------------------------------------ |
| 扫描分片 | cache worker 单次 IPC 领取的扫描工作量，当前最多 32 项。                 |
| 结果窗口 | 主线程一次 `fill()` 消费并向作业层提交的结果集合，对应一次活动日志批次。 |
| 装载容量 | 纯缓存结果窗口最多可容纳的 40 项 / 10,000 字符。                         |
| 静默窗口 | 已无缓存工作可继续装载后，等待新结果进入的短暂时间；默认 250ms。         |
| 工作耗尽 | 无在途分片、无可领取扫描项、无 `RECHECK`、无待消费缓存结果。             |
| 混合窗口 | 同一结果窗口最终包含缓存结果和真实引擎结果的窗口。                       |

## 6. 产品规则

### 6.1 纯缓存窗口按容量装载

- 纯缓存结果窗口最多 40 项、10,000 个源字符。
- 达到任一上限时立即提交。
- 单条结果自身超过 10,000 字符时，允许作为单独窗口提交；不能丢弃或无限等待。
- 字符数按原文 Unicode 码点统计，不按 UTF-16 代码单元统计。
- 未达到上限但仍有缓存工作可继续时，不得仅因扫描分片结束而提交。

### 6.2 允许提交的窗口边界

结果窗口按以下优先级结束：

1. 达到 40 项或已无法继续装入更多条目（`chars >= 10,000` 或加入下一项会超过 10,000 字符）。
2. 出现真实引擎结果，需要及时提交混合窗口。
3. 暂停、取消、任务结束、缓存线路不可用或已无待处理项。
4. 缓存工作耗尽，且连续 250ms 没有新结果进入。
5. 达到安全保持上限 5 秒，且当前已有结果；该条件只用于防止无限等待，不属于正常装载路径。

第 4 条中的“工作耗尽”必须满足第 5 节定义，不能只看瞬时结果数组是否为空。

### 6.3 首批可见性

- 第一条缓存结果到达后，可以立即更新已完成数量、剩余字符和检查点。
- 首批可见性不等于首批必须提交。用户不需要等到 40 项全部完成才看到进度。
- 活动日志按最终提交窗口记录，不按单条缓存结果逐条记录。

### 6.4 混合窗口与真实引擎

- 真实引擎结果到达后，不等待纯缓存窗口装满。
- 已选中的缓存结果可与引擎结果同窗提交。
- 引擎批量和缓存结果窗口仍使用不同预算；纯缓存窗口提交时跳过真实引擎自适应批次预算观察，避免毫秒级纯缓存速度误导真实引擎批次大小。
- 在途真实引擎请求（如重试任务）不阻断纯缓存窗口在工作耗尽后按 250ms 静默窗口收口，避免慢引擎阻塞已完成缓存译文的释放。
- 被缓存撤销的引擎尝试仍按现有结构化来源规则记录，不进入最终来源标签。

### 6.5 暂停、失败与恢复

- 暂停时立即停止领取新缓存工作，并提交当前已选结果。
- 缓存 worker 不可用时提交当前结果，随后按现有软失败策略降级到引擎。
- 正常窗口提交时执行一次批量回填和状态检查点。
- 未完成的回填继续沿用现有持久化待办和重试语义。
- 窗口聚合不得改变每条原文只完成一次的计数规则。

### 6.6 日志与统计

- 一个结果窗口对应一条活动日志批次。
- 日志中的 `total`、`chars`、`success`、`failed`、`cacheHits` 仍按任务条目统计。
- 纯缓存窗口不追加重复的“命中缓存”尾巴。
- 页面上的名义“每段 40”不能作为实际窗口大小的证据；实际大小以活动日志和诊断指标为准。

## 7. 验收标准

### 7.1 正确性

| 场景                                          | 必须结果                                                                         |
| --------------------------------------------- | -------------------------------------------------------------------------------- |
| 96 条纯缓存命中分布在 3 个 32 项分片          | 最多形成 3 个窗口，通常为 40 / 40 / 16；不得按分片返回节奏拆成大量 1～3 条窗口。 |
| 首分片只先返回 1 条，后续仍有在途或待扫描分片 | 不立即提交该 1 条；继续装载。                                                    |
| 39 条纯缓存结果后工作耗尽                     | 等待 250ms 静默窗口后提交一个 39 条窗口。                                        |
| 首批结果已到达但后续分片尚未完成              | 进度可先更新，结果窗口仍可保持打开。                                             |
| 装载中出现真实引擎结果                        | 立即提交混合窗口，不为凑满缓存容量等待。                                         |
| 暂停或缓存线路失败                            | 当前已选结果及时提交，不丢失、不重复计数。                                       |
| 单条原文超过 10,000 字符                      | 作为单独结果提交，并有明确诊断。                                                 |
| 回填与人工修改并发                            | 继续按现有权威版本规则拒绝旧结果，不因窗口聚合放宽校验。                         |
| 同一窗口重复原文                              | 查询与回填去重，完成计数仍按任务条目。                                           |
| 活动日志与窗口结果                            | 一条日志对应一个已提交窗口，统计总和与窗口结果一致。                             |

### 7.2 聚合行为

- 纯缓存工作持续可用时，不允许稳定出现 1～3 条窗口。
- 结果窗口达到容量、出现引擎结果或进入终止状态时，必须立即提交。
- 分片完成事件不得单独作为纯缓存窗口的提交条件。
- 250ms 静默窗口和 5 秒安全上限必须可诊断，不能静默改变结果正确性。

### 7.3 性能

性能验收必须使用固定语料、固定硬件、热态共享索引和同一构建，至少回放 100,000 个源字符。分别报告冷启动与热态，不把首次索引迁移计入热态吞吐。

| 指标                 | 目标                                                                                          |
| -------------------- | --------------------------------------------------------------------------------------------- |
| 热态纯缓存端到端吞吐 | 在基准语料上不低于 1,000 源字符/秒；未达标时报告分阶段瓶颈，不以原始 SQL 耗时替代端到端结果。 |
| 热态查询与安全校验   | 40 项 / 10,000 字符 p95 不高于 50ms，沿用现有目标。                                           |
| 结果窗口领取到可提交 | p95 不高于 300ms，不包含回填 flush、状态写盘和 UI 重绘。                                      |
| 连续纯缓存窗口间隔   | 不得稳定出现 1 秒以上间隔。                                                                   |
| 小窗口比例           | 排除最后排空窗口和单条超长文本后，纯缓存窗口不得稳定低于 16 项。                              |
| 引擎提交             | 100% 缓存命中回放中真实引擎提交数为 0。                                                       |
| 回填与持久化         | 按窗口聚合，不随每条缓存命中线性增长。                                                        |

### 7.4 诊断

至少记录以下窗口级指标：

- 窗口开始、结束和提交原因；
- 提交原因包含 `full-items`、`full-chars`、`oversized-single-item`、`mixed-engine`、`paused`、`closed`、`cache-unavailable`、`work-exhausted`、`safety-timeout`；
- 窗口条数、字符数、是否纯缓存；
- 已完成的扫描分片数；
- 从最后一条结果到提交的等待时间；
- 提交时是否仍有在途分片、待扫描项或 `RECHECK`；
- 回填 flush、状态持久化和日志耗时；
- 实际窗口吞吐与源字符数。

诊断默认不进入用户活动日志。

## 8. 实施优先级

| 优先级 | 工作项                                       | 目的                         |
| ------ | -------------------------------------------- | ---------------------------- |
| P0     | 去掉“分片完成即提交纯缓存窗口”的提前退出     | 恢复跨分片装载               |
| P0     | 明确工作耗尽、250ms 静默窗口和终止边界       | 防止等待无界或再次过碎       |
| P1     | 增加窗口级诊断与聚合回归测试                 | 防止后续回退                 |
| P1     | 使用真实语料回放并对比修复前后窗口数量与吞吐 | 验证实际收益                 |
| P2     | 根据基准结果调整静默窗口和安全上限           | 设备差异调优，不增加用户配置 |

## 9. 风险与约束

- 若把“没有结果”误判为“没有工作”，会重新产生小窗口。
- 若只扩大结果窗口但每条仍单独回填和写状态，吞吐仍会被固定开销限制。
- 若等待时间过长，会延迟日志和最终提交；必须保留首批进度更新和 5 秒安全上限。
- 若为缓存窗口等待而阻塞真实引擎结果，会降低混合任务体验；出现引擎结果时必须及时提交。
- 聚合不能绕过人工译文保护、共享 revision、语言对、去重和冲突校验。
