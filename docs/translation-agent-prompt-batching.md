# 翻译 Agent 单请求多句打包与字符上限需求

- 状态：需求草案，待评审；定义 Agent 引擎的单请求多句打包与配置重定义。
- 日期：2026-10-27。
- 关联需求：[翻译调度基线](translation-scheduling.md)、[翻译缓存结果窗口跨分片聚合需求](translation-cache-result-window-batching.md)、[翻译工具与并发](translation-concurrency-and-badges.md)。
- 技术方案：[Agent 单请求多句打包技术方案](technical/translation-agent-prompt-batching.md)。

## 1. 背景与现状问题

在批量翻译（Seed 补译）流程中，大部分文本行只有几个或十几个字符（例如「70 森３」、「森１５」、「はい」）。当前 Agent 引擎的实现存在以下问题：

1. **逐句调用，网络与 LLM 往返开销极大**：
   调度器将每条待译文本以单项数组 `[src]` 派发给引擎，底层 `agentJaToZh(text)` 每次仅向 Ollama/LLM 发送一条文本的 Prompt。一次 HTTP 往返、Prompt 重复前缀、模型推理启动仅翻译 9～20 个字符，吞吐量极低。
2. **活动日志碎裂刷屏**：
   由于每次仅翻译 1 条文本，活动日志呈现密集的微小记录：
   ```text
   00:23:47 [Agent] #1289：1/1 条（9 字符）完成
   00:23:48 [Agent] #1290：1/1 条（9 字符）完成
   00:23:49 [Agent] #1291：2/2 条（18 字符）完成
   ```
3. **设置项含义误导**：
   在 `/translate/engines` 设置面板中，配置项名称为“并发最多多少个字符（maxConcurrentChars）”，当前底层仅用作全局通道在途字符流控，而非“单次请求允许打包的最大字符数”。用户预期的是“单台货车装满 3000 字符再发车”，实际系统却是一句话跑一趟车。

## 2. 目标与用户体验

1. **单次请求最大字符打包**：
   Agent 引擎支持将多条短文本合并到单次 Prompt 中（如 3000 字符），一次请求完成数十条文本的翻译，成倍提升翻译吞吐。
2. **设置项语义明确**：
   在 `/translate/engines` 面板中，将配置项调整为“单次请求最多字符数”，默认 3000 字符，范围 500～40,000 字符。
3. **自然的批次日志**：
   Agent 翻译完成后，日志整合成完整的批次展示，例如：
   `[Agent] #1289：48/48 条（2,910 字符）完成`。

## 3. 详细需求

### 3.1 引擎设置面板（`/translate/engines`）语义对齐

- 保持“并发请求数上限（concurrencyLimit）”不变：表示同时向该 Agent 实例发起的最大并发 HTTP 请求数。
- 变更“并发最多多少个字符”为“**单次请求最多字符数**”：
  - 标签文案：`单次请求最多字符数`（英文：`Maximum characters per request`）。
  - 说明文案：`单个翻译请求允许打包的字符总数上限（范围 {min}～{max} 字）。`（英文：`Maximum character limit packed into a single translation request ({min}–{max} chars).`）。
  - 默认值：3,000 字符；最小 500，最大 40,000。

### 3.2 贪心打包（Greedy Packing）

- 待译任务按字符预算贪心合并：
  - 当前包累计字符数 + 下一条字符数 $\le$ 单次字符上限：并入当前请求包。
  - 下一条加入会超过上限：结束当前包并发送；超出的一条留给下一个批次。

### 3.3 超长单句拆分（“拆句子，不要断句”）

- 若**单条文本自身字符数就超过了单次字符上限**：
  - 必须按自然语言边界拆分，严禁机械定长截断。
  - **拆分优先级**：
    1. 换行符 `\n`、段落边界；
    2. 句末标点：句号 `。` `.`、感叹号 `！` `!`、问号 `？` `?`、省略号 `……` `...`；
    3. 分句标点：分号 `；` `;`、顿号 `、`、逗号 `，` `,`。
  - **控制码保护红线**：绝不能在 RPG Maker 控制符（如 `\C[3]`、`\N[1]`、`\V[1]`、`__C0__`）内部拆断。
  - 各子句翻译完成后按原标点拼接，还原为整句后再进行格式校验与入库。

### 3.4 错行与校验降级容灾

- 大模型批量翻译可能出现漏行、虚构多行或混淆序号。
- **校验原则**：
  - 响应结果行数必须与请求条数严格 1:1 匹配；
  - 每条译文中的控制占位符 `__C\d+__` 必须完整保留；
- **降级回退机制**：
  - 若整个批次或某些条目解析失败 / 校验不通过，自动将未通过条目**回退为单句逐条重试**，确保系统鲁棒性，杜绝错行、漏译或数据丢失。
