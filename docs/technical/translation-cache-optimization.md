## 2. 不变量

1. 原始 `src` / `zh` 不因索引升级改变。
2. 查询最小单位为完整短句；边界来自保守规则或可信显式分段。
3. 未知换行仅是原始字符，不授权独立提取、组合或补译；**无提取元数据且无人工注解 → 默认 unknown**。
4. 子区间译文只能通过与当前 revision 绑定的可信映射获得。
5. 语气、引用、控件、人工保护、语言对约束在覆盖率排序之前校验。
6. 派生别名与组合结果不写成新定稿。
7. 不修改管线写入秩与双写契约；不把插件渐进替换改成服务端式整段 null。
8. 运行时控制符别名仅由当前缓存行和游戏状态派生：整句展开后做哈希反查，引用值或缓存变化时重建；译文内的控制符优先取名称或值自身的缓存译文，缺失才回退运行时原文，冲突别名不猜测。

## 3. 数据模型

继续使用 SQLite 的原始定稿与可重建索引。新增逻辑概念如下，最终字段名随实现确定。

| 概念         | 内容与约束                                                            |
| ------------ | --------------------------------------------------------------------- |
| 换行注解     | 原始起止偏移、soft / hard / unknown、证据来源、记录 revision          |
| 逻辑正文视图 | 用于分段和匹配的文本，以及到原始文本的可逆位置映射                    |
| 语义边界     | 逻辑位置、原始位置、证据类型及适用规则版本                            |
| 对齐分组     | 连续 source span、连续 target span、边界证据、对齐证据、定稿 revision |
| 候选诊断     | 可确认状态、拒绝原因、规则版本和基准 revision                         |

偏移统一采用 UTF-16 半开区间 `[start,end)`，不允许落在代理对或受保护 token 内部。逻辑正文删除软折行及其排版缩进后，一个逻辑区间可能对应多个原始片段；位置映射须保留这些片段，不能只用固定偏移差。

持久化对齐分组仍可用覆盖软换行的连续原始区间表示，但验证、展示与提取均通过位置映射解释。渲染替换使用原始区间；匹配使用逻辑正文；不把归一化后的字符串写回原文。

### 3.1 边界证据与对齐证据分离

- 边界证据：保守标点规则、明确结构、来源声明或人工确认。
- 对齐证据：人工确认，或受信任导入器提供的明确映射。
- 仅有行号、相同段数、相似标点分布、模型建议，都不足以自动赋予可信提取资格。
- 人工确认允许为无标点正文建立显式完整短句边界；因此后端不应要求这些边界事先能由标点分词器推导。
- 明确映射的导入器须验证版本、偏移和结构；普通 JSON 不能因排列相似而自动推断映射。

## 4. 换行与逻辑正文

### 4.1 分类规则

优先读取与原文精确绑定的提取元数据，再读取人工注解；**没有证据则为 unknown**。一个普通文本 JSON 值中的换行本身不能证明 soft 或 hard。

图鉴 / 匹配对无显式注解的换行使用启发式（MVP）：

- 换行两侧均为词字符（字母 / 数字 / 汉字假名等）且无句末标点 → **推断 soft**，可与连续正文匹配（如 `好きじゃ↵　ない`）。
- 换行紧跟 `。！？` 等句末 → **推断 hard**。
- 其余（逗号等歧义）→ **unknown**；用户仍可在图鉴里覆盖。

显式注解（人工 / 导入适配器）优先于启发式。不能把所有 RPG Maker 文本换行无条件一律 soft。

### 4.2 保守处理

- soft：消除换行及紧随其后的**排版缩进**（行首全角/半角空格、制表符 run）；词间空格按下方语言策略。
- hard：保留结构隔离，连续块不可跨越。
- unknown：保留原始字符；没有其它可信边界时，将相关文本作为完整待处理区域。不能把折行左右两侧直接提升成独立短句。
- URL、HTML、替换槽、Ruby、RM 控制码先识别保护；字面控制序列与真实换行分别解析。
- 未知区域需要补译时扩大到安全边界，必要时放弃其中局部命中，重新翻译完整区域；不能只补译被截断的半句。

**soft 消除后的空白策略（默认，实现锁定）**

设换行两侧在去掉该换行与排版缩进后的邻接字符为 L、R（已跳过受保护 token 边界则不在此合并）。

| 源语言语境                                                                      | 规则                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 日 / 中 / 韩等无空格书写（`src_lang` 为 `ja`/`zh`/`ko`，或正文判定为 CJK 主文） | L 与 R **直接相连**，不插入空格。例：`好きじゃ\n　ない` → 逻辑 `好きじゃない`                                                                                                                                                           |
| 英文及空格书写语言（`en` 等）                                                   | 若 L、R 均为词字符（字母/数字/`'`），则 **插入一个 U+0020**；若任一侧已是空白，或任一侧为标点/括号，则 **不插入**。例：`word\nword` → `word word`；`see.\nNext` → `see.Next` 再由标点规则处理（不在换行步骤插空）；`Hel\nlo` → `Hel lo` |
| 语言对未知                                                                      | 按 **更保守**：当作空格书写语言（可插空格），避免 CJK 误粘英文                                                                                                                                                                          |

说明：词中折行（`Hel\nlo`）在英文 soft 下会得到 `Hel lo` 而非 `Hello`——有意不猜粘连；正确修复依赖更好的提取元数据或人工，而不是自动去空格。

对于案例 `好きじゃ\n　ないんスよ`：unknown 时整体保留；确认 soft 后逻辑正文为 `好きじゃないんスよ`，来源偏移仍指向原始两行。

## 5. 统一分段与候选生成

优化预览、导入校验、服务端与插件共用纯规则层。拆分结果包含位置、语气、结构和证据，不再只返回字符串数组。

1. 构造受保护 token 与换行注解。
2. 生成逻辑正文和位置映射。
3. 合并保守规则边界与可信显式边界，冲突则返回诊断，不静默覆盖。
4. 保留问叹、省略号及引用上下文；安全外壳作为别名描述。
5. 生成待确认对齐候选；数量一致仅可作为提示字段。
6. 调用同一验证函数，显示每项可确认状态。

不自动按日语助词、词尾或任意字符建立可复用边界。模型可作为后续可选建议来源，建议未经人工确认不能进入可信索引。

### 5.1 引用结构

成对最外层 `「……」` 可建立别名；内部 `『……』` 及其说话人、转述尾缀继续保留。去壳不是语义分段，也不需要复制译文。

`おっかないんスよねえ』つって` 是包含引用结束和转述的残片，不能自动等价于裸句。残片记录可保留原始精确查找，但默认不作为去壳或子块提取来源；需结构诊断与单独审校。

## 6. 对齐确认与接口

扩展现有 optimize 接口。当前为 MVP：控制台与 API 同步演进，**不做旧客户端协议兼容层**。

请求需要：父记录、基准 revision、换行注解、显式边界和对齐分组。所有偏移基于请求指定的原始快照。

预校验与提交使用相同验证器，依次检查：

1. 记录身份、语言对、revision 和规则版本一致。
2. 原始区间合法，未截断代理对、控件或受保护 token。
3. 逻辑位置映射有效，soft / hard / unknown 处理符合证据。
4. 边界可被规则解释或有人工确认；不允许只提交任意字符命中率。
5. 原译映射单调、无重叠、不跨硬结构；允许一对多和多对一。
6. 外壳、引用和控件关系可解释；人工保护及现有映射不冲突。

一对多 / 多对一保存为不可随意拆开的整体映射块。只有存在更细可信映射时，才允许从内部提取；不根据句数按比例切译文。

新确认请求按整批原子提交，任一项无效则返回逐项诊断且不写入映射。成功时复用已有版本与事务机制，同时更新映射、索引及失效信息。revision 变化返回冲突，前端保留编辑内容并请求重新校验。

修改定稿与确认映射分开：修改译文成功后所有候选以新 revision 重算，不能沿用旧目标偏移继续确认。

## 7. 匹配与补译

沿用人工保护和冲突策略，在合法候选中优先整段、连续大块、最后单短句。查询与缓存双方都可携带逻辑视图；包含关系必须建立在相同规则与可信边界上。

- 查询 `a,b,c`，缓存 `b,c`：整块使用其译文，安全补译 `a`。
- 查询 `b,c`，缓存 `a,b,c`：只通过可信映射提取；无映射继续查较小记录。
- 未知折行不能用于推导 `a` / `b`，不能跨它制造连续块；已有明确人工分段需先补充相应换行解释。
- 控制符和输出分隔符保持绑定；命中块内部译文不被再次按标点重排。
- 引擎等待后重查依赖版本，失效则重新规划；partial 不写成整段定稿。
- **路径分流**：上述「完整覆盖 / 安全补译」约束 **服务端规划与 live 定稿前查找**。插件 `translateWithLookup` 仍可渐进替换已命中子段（管线 §2）；本期不把插件行为改成整段 null。
- **双写**：live 落库仍走管线 §14.5；共享 `rejected`（低秩）不得写入本作 ndjson。

## 8. 持久化与迁移（MVP）

1. 不更换数据库，不合并原始主键，不自动删除疑似重复或错误记录。
2. 换行及边界注解绑定 revision；正文修改后旧注解和映射失效。
3. 新规则使用独立版本（`SENTENCE_RULE_VERSION`）。与逻辑视图相关的索引随注解写入重建；不把旧换行位置索引直接当成新语义单元。
4. **不做旧客户端 / 旧插件双轨降级**：控制台、共享缓存服务与插件同一规则版本一起升级；无 soft 注解时自然退回整段 / 精确键，这是证据缺失而非兼容层。
5. 本作带来源回填可携带注解、映射和规则版本；服务端与插件共用解析约定。旧对象行和数组行继续可读，但不凭空补可信证据。
6. 历史独立碎片没有足够来源信息时只标记为待审校。列出问题与影响，不自动改译文、删记录或反推父子关系。

## 10. 索引精确查询与性能改造（2026-10-22，首版）

本节收紧 §7 的候选检索方式；保留连续短句、安全提取、人工保护与写入秩。**首版已接入**：缓存命中查询使用等值索引，规则 v10 启动时重建历史键，数字族独立建索引；live 与覆盖核验复用本作候选上下文，共享回填不重复参与本作匹配，空回填及未变化来源不重复读文件。首次加载、外部编辑刷新仍需解析文件；缺口仍独立打开连接，在线影子索引等后续目标不视为本版已完成。 对应需求 §3.6、§6；性能依据见 [调度方案 §13](../translation-scheduling.md#13-批次性能诊断与优化依据)。

### 10.1 当前问题与约束

改造前实测第 534 批 4 条、288 个源字符，总计 3184ms，其中 4 次 cache plan 合计 2048ms。共享库已经存在等值索引查询，不能将瓶颈笼统归因于 LIKE；实际还存在省略号 GLOB 兼容，以及 live 将约 6762 条本作记录逐条传入句段规划的问题。

约束覆盖 live、seed 补译 / 覆盖核验、本作 resolver、共享库候选与插件：

- 不使用 SQL `LIKE`、`GLOB` 或其他模糊检索作为缓存命中方式；禁止回退全库 includes / 正则 / 相似度扫描。单条输入的规范化、token 解析可以使用有界正则，这不属于扫描缓存。
- 所有候选必须由等值索引定位。对索引返回的少量记录校验结构、语气、连续位置和可信映射，不等于模糊搜索。
- 数字族索引增量维护；移除查询时 `src GLOB '*[0-9]'` 捞全库再建模板的路径。
- 不以缩短计时为由删除人工保护、来源秩、语言对或 revision 校验；复杂复用超限可以降级，权威判断不能跳过。

### 10.2 索引键与规范化

继续复用原始定稿表及现有可重建索引，必要时扩展，不建立独立权威译文库。逻辑索引如下，最终列名随实现锁定：

| 查询                | 索引键                                                                                                       | 返回                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------- |
| 原文整段            | `(src_lang, tgt_lang, raw_src)`                                                                              | 定稿引用与来源                    |
| 规范整段 / 安全别名 | `(rule_version, src_lang, tgt_lang, key_kind, normalized_key, tone, control_signature, structure_signature)` | 可能多个定稿引用；不是任选一个    |
| 完整短句            | `(rule_version, src_lang, tgt_lang, unit_key, tone, control_signature, boundary_kind)`                       | 定稿 ID / revision 与原始句段位置 |
| 数字模板            | `(rule_version, src_lang, tgt_lang, template_key, context_signature)`                                        | 已验证的源 / 译模板与依赖引用     |

共享 SQLite 为实际条件建立对应复合索引；本作及插件按相同键组织 Map / 倒排表。索引行引用 `recordId + revision`，既有区间映射仍用原始 UTF-16 偏移。使用哈希压缩键时必须复核完整键，不能把哈希相同直接视为命中。

规范化在写入、索引重建、查询时共用同一纯函数及 `rule_version`。省略号等价变体在索引中一次性收敛到确定键，替代运行时 GLOB 兼容；仍保留位置、语气与结构约束。安全外壳只生成有限别名，不枚举任意删标点组合。问号、感叹号、未知换行、英文词间空格和受保护 token 不随意删除。原始 src / zh、导出及显示不变。

同规范键允许一对多；索引不得因 UNIQUE 约束覆盖定稿。返回候选后沿用权威 / 冲突规则，同权不同译不能挑首条；原文精确命中也须遵守既有等价组与人工保护规则。

### 10.3 查询流程与有界降级

1. 获取当前可用索引快照及保护版本；按既有来源优先级查原文整段等值索引，再查规范 / 安全别名等值索引。不把“本作优先”错误地等同于所有带来源回填都高于共享人工定稿。
2. 对适用的数字文本查模板键，仅有无歧义、依赖有效且数字槽对应明确的模板才还原；保留前导零。无可用模板继续查询，不逐条枚举缓存。
3. 将查询解析成合法完整短句，批量等值查询倒排键。候选上限按整条输入累计，建议初始上限 500，不能每个键各取 500 后无限叠加；高频桶、重复位置和规范化别名也计入预算。
4. 只向覆盖规划器传入索引筛出的候选，复用现有连续区间与映射校验；禁止把整个 localRecords 数组拼入每次 `cache.plan`。没有候选直接返回 miss，不启动全库匹配。
5. 超限返回独立诊断，不将截断后的候选伪装成完整权威集合。保留已确认的整段 / 人工保护，不能因为候选预算耗尽而绕过人工保护去整段覆盖；无法安全确定时返回可解释的 partial / 未完成。
6. 缺口批量补译沿用父上下文，完成后只复核使用过的定稿依赖与相关权威键，发现人工修改则重新规划。partial 不持久化为完整新定稿。

句段层是否启用可根据实测决定；停用该层也必须保留整段、规范键及模板快查。该降级不改变插件渐进显示和服务端 full / partial / miss 契约。

### 10.4 快照、增量写入与初始化

- 每个游戏 / 缓存版本复用记录和索引快照；一次初始加载后，正常批次不重复完整读文件、JSON 解析或重建 resolver。外部修改通过文件签名及权威版本检测，在批次边界刷新受影响内容。
- 缺口子任务复用父任务缓存句柄、规则快照和索引；避免递归再次回填、解析完整文件。实现时明确句柄所有者，子任务不得关闭父句柄。
- 已接受写入在短事务中同步更新定稿、revision、索引及 outbox；批内后续查询可见新增结果。负缓存按语料 / 规则版本失效，不把短暂 miss 永久保存。
- 回填与覆盖核验复用快照和受影响项；保留成功项及时持久化，不为合并写盘扩大故障重跑范围。空回填不能重复解析整个游戏文件。
- 人工定稿或来源依赖修改 / 删除使对应别名、模板、短句索引及回填失效；不能只校验文件时间而忽略共享库 revision。

### 10.5 迁移与验收

1. 固化规范化规则与测试，建立新版本索引；历史记录只重建索引，不改原始正文或人工译文。
2. 将现有 GLOB 省略号兼容和数字全库检索替换为已准备好的键 / 模板索引，并复用本作候选索引；重建操作从查询热路径移出。
3. 沿用管线 §14.7 的版本切换方案，避免查询混用新旧规则；构建失败保留可用旧索引，但不能继续通过旧 GLOB 查询。缺少所需新索引时仅走可验证的原文等值查询；无法核验人工权威时返回未完成，不能伪装普通 miss 并覆盖人工译文。
4. 检查查询计划确实使用对应索引，覆盖精确、规范、省略号、短句及数字模板路径。静态检查缓存查询路径无 LIKE / GLOB，运行测试还须证明不存在全量加载与逐条全库遍历；不得只检查 SQL 字面量。
5. 保留来源优先级、等价冲突、语气差异、控件、未知换行、可信映射、语言对、人工修改 / 删除失效与并发写入回归；服务端及 MV / RGSS 使用同一输入回放。
6. 按需求 §6 的规模与场景测 p50 / p95 / max、候选数量、缓存加载次数、SQL 次数及字数；热态 40 条批次查询及安全验证目标 p95 ≤50ms。初始化 / 重建、模型推理、保存和端到端耗时分别报告；目标未达成则先按阶段日志定位，不通过跳过正确性规则达标。

### 10.6 首版落点与回归

- `lib/translate/sentence-units.ts` / `shared-cache/match-index.ts`：规则 v10 重建原始 / 规范 / 别名和句段位置键；只读连接检查新版本标记，不能用旧 GLOB 兼容绕过迁移。迁移不改原文、译文、定稿 ID / revision 与既有对齐。
- `numeric_label_keys` 按语言对、编号族建立复合索引，写入 / 删除随原有触发器维护；编号族候选超限不学习不完整模板。
- `game-records.ts` / `game-cache-context.ts`：有容量上限的文件快照与本作 Map / resolver。文件身份、修改时间、大小与路径变化触发刷新；共享来源记录由共享索引查询。自身共享回填可推进快照签名，但不得掩盖同期 seed 修改或回退路径变化。
- `backfill.ts`：无任务且无依赖变更时直接返回；文件事件快照按签名复用，只刷新变化的来源。每条成功仍先保存共享 SQLite，文件回填保留原有锁、fsync 与事件幂等性。
- `live-translate.ts` / `fill-missing.ts`：只传入索引选出的本作候选；候选超限不会伪装普通 miss 并调用引擎绕过人工权威，返回明确未完成原因。批后覆盖核验同规则。
- 回归包含查询 SQL 无 LIKE / GLOB、EXPLAIN 确认使用索引、规范标点命中且问叹隔离、历史键重建、编号族隔离、空回填不读文件、共享 revision 修改 / 删除、本作人工覆盖、seed 原子替换、索引快照复用及候选超限不调用引擎。性能样本见需求 §6.1；性能数字使用单独基准记录，不把机器耗时阈值写成易抖动的单元测试。

### 10.7 状态指标与下一步流水线建议

已实现状态栏：剩余时间不足一小时用 `MM:SS`，一小时及以上用 `HH:MM:SS`（小时可超过 24）；速率用源文 Unicode 字符/s。以本次启动后最近 8 个已完成批次的已核验覆盖字符数除以实际批次总耗时，失败批次耗时计入、暂停及首次全量扫描不计入。批次使用单调时钟计时，不受系统时间调整影响。剩余时间统一为当前 `missingChars / charsPerSecond`，不使用任务总字符数、历史 startedAt 或累计会话耗时。暂停时隐藏 ETA；每次恢复（包括磁盘恢复、worker 热更新）清空速率样本，首次有效批次完成前不显示速率与估时；零吞吐及无效采样不显示 ETA。缓存命中也算有效进展，因此这是整条任务的处理速率，不是模型纯推理速率。

状态栏仅在运行且已有有效速率时显示“翻译 · 剩余 MM:SS · 字/s”，停止、暂停、完成或异常时隐藏速度与估时；缓存耗时不在状态栏展示。详细管线与 Apple 计时默认关闭，使用 `CHAYA_TRANSLATE_DEBUG=1` 按需开启，正常日志保留批次摘要和异常。

后台 seed 作业内部诊断的缓存毫秒数为当前进度窗口内 worker 整段 / 句段 / 数字模板匹配累计耗时；不包含 worker 启动、共享库打开 / 迁移、翻译、写入及回填。旧单次补译路径仍统计该批匹配及末尾覆盖校验耗时。两者都不是每条平均耗时，通过结构化回调 / job 快照传递，不从日志解析。

后台 seed 作业已采用独立缓存 worker 与引擎消费线路，缓存属于可跳过的加速步骤，不是派发前置条件。实现与验收以 [调度基线 §14](../translation-scheduling.md#14-非阻塞缓存扫描与翻译派发2026-10-23) 为准：

1. 缓存可扫描全程，IPC 分片 32 项且只有一个分片在途，受结果缓冲反压约束。§12 已接入有界缓存分类窗口：窗口内的未分类任务不得由引擎领取，明确 miss / partial 才进入引擎；缓存不可用或停滞时仍有界降级。当前纯缓存结果消费仍可能提前结束，需继续修复聚合。
2. 不新增完整 L1 正负缓存，继续复用本作上下文和等值索引；索引更新后后续扫描可见。扫描结果接受时核验文件指纹、语料版本和依赖 revision，旧结果可保守放弃。没有把整个共享库加载到内存。
3. 引擎结果先核验相关等值权威键并持久化，再完成任务；不强制重跑整段匹配。成功结果和汇总进度持久化；扫描位置和逐项尝试状态尚不持久化，恢复会重建扫描。
4. 服务端同游戏 / 同配置 / 同语言对 / 同受保护原文的在途请求共享传输 Promise，接受与持久化各自核验；失败不会成为永久 miss。底层未真正结束的不可取消请求仍占配额。
5. 缓存同步 SQLite 查询及匹配在 worker 线程运行；提交、权威核验和回填仍有同步短操作。直接单次补译、CLI 和实时入口尚未迁移独立缓存线路。详细容量、暂停与超时边界见调度方案 §14.3。

当前热缓存实测 40 条约 7–16ms，流水线收益上限主要受这部分占比限制。优先衡量引擎首条 / 完成时间、持久化和回填耗时，再决定实施顺序；不能承诺该调度本身将端到端速度翻倍。

### 11.1 快照版本链与失效判定

现有 `CacheScanResult.stamp` 是扫描当时的 seed / cache 文件身份，主线程只比较当前 stamp。共享回填追加本作 `cache.ndjson` 后 stamp 必然变化，因此后续预扫描命中会被拒绝；但仅放宽 stamp 又会掩盖同期人工修改。

目标设计把“文件发生变化”和“本作权威发生变化”分开：

| 版本                   | 归属              | 变化条件                                                                 | 用途                          |
| ---------------------- | ----------------- | ------------------------------------------------------------------------ | ----------------------------- |
| `fileStamp`            | seed + cache 文件 | 路径、inode、mtime、ctime、size 任一变化                                 | 检测是否有任何文件写入        |
| `authorityVersion`     | 本作缓存上下文    | seed / fallback 身份、非共享来源本作记录或人工屏蔽变化                   | 证明本作有效权威是否变化      |
| `corpusVersion`        | 共享 SQLite       | 共享语料规则 / 索引版本变化                                              | 证明候选规划基于当前共享语料  |
| `recordRevisions`      | 共享 SQLite       | 扫描使用的共享记录 revision 变化或删除                                   | 证明每条命中依赖仍然有效      |
| `ownedFileTransitions` | 当前 seed 会话    | 本任务成功回填前后的一对 `fileStamp`，并绑定追加事件 ID 和受影响记录集合 | 证明 stamp 变化来自可识别回填 |

`authorityVersion` 是每个 `contentRoot` 的内容寻址版本，不写进译文正文。它由 seed / fallback 路径、非共享本作记录和人工屏蔽集合计算哈希；缓存 worker 与主线程分别运行，不能使用各自进程内的单调计数器直接比较。`getGameCacheContext` 因上述权威内容变化而重建时产生新版本；`noteGameSharedBackfill` 只推进文件 stamp，不改变 `authorityVersion`。这样共享镜像追加不会伪装成本作权威变化，人工修改仍会使版本变化。

每次成功回填在持有现有缓存文件锁后执行：

1. 写前读取 `beforeStamp`，并记录本次待追加事件 ID、记录 ID / revision 和根路径。
2. 追加并完成现有 fsync / 幂等确认。
3. 写后读取 `afterStamp`。
4. 仅当写前、写后都能确认 seed 与 fallback 路径未变，且写入前后的行差集、新增事件集合都恰好等于本批共享来源镜像时，向当前会话登记 `ownedFileTransitions[beforeStamp] = afterStamp`。
5. 无法确认来源或登记失败时不建立豁免；宁可让扫描结果重新校验，也不能放宽人工保护。

扫描结果携带 `{ fileStamp, authorityVersion, corpusVersion, recordRevisions }`。接受缓存结果时按以下顺序判定：

1. `corpusVersion` 必须等于当前共享版本。
2. 使用的共享记录必须通过 `current()` revision 校验。
3. 当前 `fileStamp` 等于扫描 stamp，或从扫描 stamp 到当前 stamp 存在完整、连续、未分叉的 `ownedFileTransitions` 链。
4. 当前 `authorityVersion` 必须等于扫描时的 `authorityVersion`。
5. 任一 stamp 变化不在 owned 链中、版本链存在分叉、登记表溢出或无法确认写入来源，均判定为过期。

版本链仅用于当前 seed 会话；进程重启后 worker 和结果缓冲都会重建，不依赖该链恢复正确性。登记表必须有界，超过容量时淘汰旧项并使对应结果保守失效，不能无限增长。

`authorityVersion` 必须由上下文快照统一提供，不能只在回填后修改一个布尔标记。共享记录 revision、人工译文保护、来源优先级和写入秩仍按 §7、§10.4 校验，版本链不能替代这些检查。

### 11.2 批次分层与调度状态

缓存扫描、结果消费和用户日志是三套不同节奏，不能共用 Agent / Apple 的自适应批量：

| 层级           | 首期预算                                                 | 反压 / 边界                                      |
| -------------- | -------------------------------------------------------- | ------------------------------------------------ |
| 扫描 IPC 分片  | 每片最多 32 项，只保留一个在途分片                       | 结果缓冲 64 项；缓冲满时停止领取新分片           |
| partial 计划   | 最多 128 项                                              | 只保存可交给引擎补缺口的计划，不保存完整译文快照 |
| 纯缓存结果批次 | 最多 40 项、10,000 字符                                  | 独立于引擎初始 4 项和 3,000 字符预算             |
| 用户日志窗口   | 以已完成结果聚合；首批最多等待 250ms，避免为凑批无限延迟 | 不反向限制扫描；普通日志保持短小                 |

现有 5 秒批次目标继续只控制引擎派发和返回窗口，不控制纯缓存结果消费。纯缓存结果已就绪时，结果消费者可以一次取走至多 40 项 / 10,000 字符；没有更多就绪项时立即提交已有结果，不为凑满 40 项等待。混合窗口可以同时包含缓存和引擎结果，但两类预算分别计算。

调度状态至少区分：

| 状态                | 含义                                      | 是否允许引擎领取         |
| ------------------- | ----------------------------------------- | ------------------------ |
| `UNKNOWN`           | 尚未扫描，不能冒充 miss                   | 允许，按既有非阻塞竞速   |
| `WAIT_CACHE`        | 已明确等待缓存线路，用于有界兜底          | 不领取，直到结果或超时   |
| `FULL`              | 已得到完整缓存命中                        | 不领取，提交前做版本校验 |
| `PARTIAL`           | 有安全缺口计划                            | 允许，按缺口计划派发     |
| `MISS`              | 缓存明确未命中，或重新扫描后确认 miss     | 允许                     |
| `RECHECK`           | 曾完整命中但快照过期，等待重新校验 / 扫描 | 不允许直接当 `UNKNOWN`   |
| `CACHE_UNAVAILABLE` | 缓存 worker 或权威检查不可用              | 允许，按现有软失败降级   |

`RECHECK` 的转换规则：

1. 先尝试用当前 stamp、owned 链、`authorityVersion` 和共享 revision 做轻量校验。
2. 无法证明有效时，只重新扫描该项或受影响的小范围，不立即把整项转成 `MISS`。
3. 重新扫描明确得到 `MISS` 后才进入引擎队列。
4. 缓存线路不可用或重试超时，转 `CACHE_UNAVAILABLE` 后按既有软失败策略允许引擎继续；不能把它记录成“缓存未命中”。

`RECHECK` 使用有界重扫队列，同一任务最多重试 2 次。重试耗尽后转 `MISS` 并允许引擎继续；缓存线路故障则立即释放队列，避免条目永久停在不可领取状态。

同一扫描窗口内按 `src + 源语言 + 目标语言 + category + 保护签名` 去重。相同键只执行一次缓存查询和一次回填；若对应多个任务条目，查询结果可以 fan-out 到各任务 ID，但完成状态、日志 `total/success/failed/chars` 仍按任务条目计数，缓存查询次数按去重键计数。去重只发生在结果消费层，不改变原文清单和持久化条目的唯一性。

### 11.3 批次日志来源与 i18n

用户日志不能从最终 `item.engine` 反推实际执行路径。批次日志扩展为结构化来源，至少包含：

```ts
type BatchExecutionSource = 'cache' | 'apple' | 'agent' | 'platform' | 'bergamot' | 'ollama' | 'unknown'

type TranslationBatchLog = {
  batch: number
  success: number
  total: number
  failed: number
  chars: number
  cacheHits: number
  submittedSources: BatchExecutionSource[]
  finalSources: BatchExecutionSource[]
  cacheUnavailable: boolean
}
```

字段语义：

- `submittedSources`：本窗口实际提交过请求的真实翻译来源；缓存扫描、缓存重校验和缓存回填不得加入。
- `finalSources`：最终被接受结果的实际来源；采用共享 / 本作缓存时包含 `cache`。每条结果用 `resultSources` 保留组成来源；部分缓存拼接 Apple 补译时为 `cache + live:apple`，不得从兼容字段 `engine: cache:partial` 推断为纯缓存。失败或被权威译文替换的引擎输出不进入最终来源。
- `cacheHits`：最终全文采用缓存权威译文的条目数，不等同于 `submittedSources` 是否为空。部分缓存加引擎补译不计作整条缓存命中。
- `cacheUnavailable`：当前会话缓存线路不可用；与是否有真实引擎结果分别统计。该标记跨结果窗口保留，直到 seed 清单重建或会话重建，避免后续窗口误显示为健康缓存。

`success`、`failed` 只按任务最终结果计数，不按缓存线路健康状态计数。缓存不可用时，有真实引擎结果的条目按结果成功 / 失败；没有真实引擎且未完成的条目计入 `failed`。`cacheUnavailable` 只影响标签和诊断，不得把未完成条目伪装成缓存 miss 或成功。

`onEngineDispatch(engine)` 在实际提交时携带真实引擎 ID，嵌套缺口补译原样向上传递；不得用外层预选引擎代替实际请求引擎。`submittedSources` 按提交所在窗口统计，可能包含仍在执行的其他条目，不能据此推断当前窗口每条缓存结果都调用过引擎。

调度另用每条结果的 `engineWork` 记录是否等待过引擎（含合并等待已有请求、失败尝试和嵌套补译），并跨同一任务的重试保留。只有最终来源全部为缓存且没有引擎等待的结果，才进入独立的纯缓存大窗口；经过引擎后被人工缓存替换的结果仍及时释放，但用户标签只显示最终采用的缓存。旧结果若仅有 `cache:partial` 而无组成来源，按未知来源加缓存保守处理。吞吐统计排除最终全文采用缓存的条目，混合补译计入完成字符数。

缺口补译写入共享库后，再匹配可能立即读到本次新记录，不能把这类自写回读一律改成缓存来源。嵌套调用通过内部 `onCacheWrite` 传递本次接受写入的记录和组成来源；重新匹配按记录 ID + revision 对照，本作镜像按原文、译文和引擎标签对照。只给当前计划真正采用的自写记录保留引擎来源；已有记录或后来产生的人工修订仍归缓存。此关联仅在单次调用内保存，不追溯历史缓存原本由哪个引擎生成。

用户标签由结构化字段投影，不解析英文日志正文。标签只表达最终采用的工具，`submittedSources` 仅作为诊断数据，以及整批失败时的回退来源：

| 条件                                 | 标签            |
| ------------------------------------ | --------------- |
| 最终来源仅缓存                       | `[缓存]`        |
| 最终来源仅 Apple                     | `[Apple]`       |
| 最终来源仅 Agent                     | `[agent]`       |
| 最终来源包含 Apple 和缓存            | `[Apple+缓存]`  |
| 最终来源包含 Agent 和缓存            | `[agent+缓存]`  |
| 最终来源包含多个引擎                 | `[来源1+来源2]` |
| 整批失败且尝试过真实引擎             | `[来源1]`       |
| 无最终来源、无真实来源、缓存线路故障 | `[缓存不可用]`  |

最终来源按固定顺序投影：`apple`、`agent`、`platform`、`bergamot`、`ollama`、其他已知来源，最后才是 `cache`；不按完成时间排序。未知来源保留短名称，不能静默归并到缓存。纯缓存批次不再额外显示“命中缓存”，混合批次才显示缓存命中条数。后端持久化的 `text` 可继续使用英文诊断摘要，但 UI 必须优先使用 `TranslationBatchLog` 和 i18n 键生成用户文案；缺少结构化字段时才回退到 `text`。

i18n 至少提供缓存、缓存不可用、Apple、Agent 和组合连接符的独立键。组合标签中的真实引擎名按现有产品名称本地化，不能用固定中文标点拼出无法换行的长串；容器必须允许自然换行，不能用截断隐藏实际来源。

### 11.4 回填、持久化与去重

回填继续先保存共享 SQLite，再追加本作镜像；本作追加失败不能回滚已确认的共享译文。

- `queueBackfill` 在进入 `game_backfill_tasks` 前按 `(root, src, record_id, revision)` 去重，避免同一批重复扫描生成重复任务。
- 同一 `src` 对应多个任务条目时，共享记录回填一次；完成计数仍按任务条目分别递增。
- 正常暂停、批次结束和正常退出必须执行 `flushBackfill`；flush 成功后才确认任务完成。
- 异常退出时，未确认任务保留在持久化队列，恢复后可重试；不得把“已排队”报告为“已回填”。
- 空队列且没有 revision 失效项时直接返回，不读取或解析整个 `cache.ndjson`。
- 已登记 owned transition 只允许推进文件 stamp，不允许跳过共享 revision 检查；回填后 `authorityVersion` 不变。
- 若回填写入和人工修改并发发生，版本链无法形成完整的 owned 链，后续缓存结果必须重新校验。
- 回填 flush 返回 `{ sharedOnly }`；只有写入内容差集、事件集合、seed / fallback 身份和上下文版本全部可证明时才为 `true`。

#### 原文库存与译文进度的失效边界

存储守护进程的 `materialize()` 在保存译文、写入游戏设置、恢复读视图和重新挂载时都会生成公开文件。生成内容与现有文件相同必须保留原文件的 inode 和时间戳；仅内容变化或文件缺失时才原子替换。否则每次保存译文都会使 `seedFileStamp()` 改变，`seed-session.fill()` 将误判为原文更新，清空完成状态并重建待译队列，导致剩余字符回跳及缓存反复处理。

- 原文内容真正变化时仍更新文件身份，运行中的会话按现有规则重建库存。
- 原文未变、译文变化时，不重置正在执行的会话；暂停后继续或显式刷新必须重新判断待译清单。
- 准备好的库存同时记录 `stamp`（原文）和 `progressStamp`（原文与本作缓存），仅两者均匹配当前文件时才可复用；旧 bundle 缺少进度标记时重新准备。
- 两个标记在读取库存前采集，不能在读取完成后用新标记给旧数据补签；持久化进度沿用这份快照的标记。
- 此处不把共享数据库 WAL 纳入文件标记；共享记录的权威校验仍遵循现有 revision 规则。

回归验证覆盖：追加译文、写入无关设置、修复读视图与守护进程重启不改变未变原文的文件身份；真实更新原文会改变身份，原文视图缺失后可恢复；原文未变但缓存变化时，开始 / 继续和刷新均不得复用旧库存。

| `backfillQueueMs`          | 回填入队耗时                                         |
| `backfillFlushMs`          | 回填追加、fsync 和确认耗时                           |
| `persistMs`                | 作业状态持久化耗时                                   |
| `engineQueueMs`            | 引擎排队时间                                         |
| `engineRunMs`              | 真实引擎执行时间                                     |
| `fileReadCount`            | seed / cache 完整读取次数                            |
| `contextBuildCount`        | 本作上下文和 resolver 重建次数                       |

| `staleRecheckCount`        | 过期结果进入 `RECHECK` 的次数                        |
| `selfBackfillRejectCount`  | 已登记自身回填仍被拒绝的次数，目标为 0               |
| `engineAfterCacheHitCount` | 最终采用缓存但仍提交真实引擎的次数，用于发现错误竞速 |

性能测量口径：

- 50ms 目标只覆盖 40 条 / 10,000 字符的热态查询、候选筛选、安全校验和必要的 revision 检查。
- 300ms 目标覆盖纯缓存结果从主线程领取到可提交，包含轻量校验和结果组装，不包含首次 worker 启动、索引迁移、真实引擎、回填 flush、作业状态写盘和 UI 重绘。
- 回填、持久化和日志回调分别计时并报告；不得把它们隐藏在缓存查询时间之外后仍宣称端到端达标。
- 连续 10 个热态批次中，初始加载后 `fileReadCount` 和 `contextBuildCount` 不随批次数量线性增长；自身回填只允许推进版本，不允许重建完整 resolver。
- 性能样本必须记录共享语料规模、本作记录数、批次条数、字符数、冷 / 热状态、硬件和 p50 / p95 / max。

正确性验收至少覆盖：

1. 首批回填改变 stamp 后，后续已扫描完整命中仍为 `cache:scan`，真实引擎提交数为 0。
2. 自身回填与人工 seed / cache 修改并发时，owned 链不成立，旧结果被拒绝。
3. owned transition 链分叉、登记表淘汰或写入来源不明时，结果保守失效。
4. 完整命中过期进入 `RECHECK`，只有明确 miss 后才进入引擎。
5. 缓存 worker 不可用时进入 `CACHE_UNAVAILABLE`，引擎可继续但日志不标记纯缓存。
6. 40 条纯缓存结果不受引擎 4 条初始批量限制，但受 10,000 字符和 64 项结果缓冲约束。
7. 同一去重键只查询 / 回填一次，日志仍按任务条目计数。
8. 实际提交 Apple / Agent 后采用缓存，日志投影为 `[缓存]`，不展示被撤销的引擎尝试；混合最终来源才投影为 `[agent+缓存]` 等组合标签。
9. 正常结束、暂停和异常退出分别满足 flush、待重试和不谎报完成的语义。

## 12. 缓存优先预取、权重与长驻协调（2026-10-25，主体已接入）

状态：主体已接入，验收未完成。需求契约见 [缓存批处理性能 §9](../translation-cache-batch-performance.md#9-缓存优先预取来源权重与长驻-worker2026-10-25主体已接入验收未完成)。本节补充实现边界，不替代 §11 的快照、`RECHECK`、回填和日志契约。

### 12.1 当前接线与缺口

当前实现已经具备：

- `seed-job` 独立 worker 作为后台作业协调者；
- 独立 `cache-lane` / `cache-worker`，扫描逻辑不阻塞 Next.js；
- 32 项扫描分片、64 项结果缓冲、40 项 / 10,000 字符纯缓存结果批次；
- `cacheEngineRank` 来源权重及写入、查询侧权威选择；
- Apple / Bergamot 长驻子进程，空闲 60 秒回收；
- storage daemon 和回填持久化队列。

仍存在的调度缺口：

1. `seed-session.start()` 启动缓存 lane 后立即 `pump()`；`UNKNOWN` 任务可以被引擎直接领取。
2. 没有缓存 plan 时使用 `cacheMode: 'bypass'`，引擎请求不等待缓存分类。
3. 缓存命中只 abort 已经提交的请求；不可取消适配器仍占用配额直到真正结束。
4. 缓存 worker 在一次 seed session 内长驻，但暂停会关闭；恢复会重新启动并重建索引。
5. 缓存命中逐条 `queueBackfill`，结果窗口结束统一 flush，但事件和文件快照处理仍可能重复。

### 12.2 目标状态机

在现有 `UNKNOWN / MISS / RUNNING / DONE / FAILED / WAIT_CACHE / RECHECK` 之外，引入逻辑状态 `CACHE_PENDING` 和 `PARTIAL`。实现可复用 `UNKNOWN` 加 `cacheDeadline`、`MISS` 加已保存的缺口计划，不必扩展持久化状态位，但调试快照必须能区分 `CACHE_PENDING`、`PARTIAL` 和普通 `MISS`。

`cacheDeadline` 只在任务实际投递给 cache worker 时设置，不从进入缓存优先窗口时开始。等待 worker 空闲的排队时间由 `cacheAdmissionWaitMs` 单独统计，不能算作缓存扫描超时。进入窗口超过 1500ms 仍无法投递时，协调者标记 `cacheAdmissionTimeout` 并允许引擎领取；任务已被领取后不得再投递。

| 状态            | 含义                                 | 可被引擎领取           | 退出条件                                                             |
| --------------- | ------------------------------------ | ---------------------- | -------------------------------------------------------------------- |
| `CACHE_PENDING` | 已进入缓存优先窗口，尚未得到缓存分类 | 分类窗口内否；到期后可 | `full` / `partial` / `miss` / `RECHECK` / `CACHE_UNAVAILABLE` / 超时 |
| `PARTIAL`       | 已保存安全缺口计划，只允许派发缺口   | 是，仅缺口             | 计划消费、任务完成、线路失败或重新校验                               |
| `UNKNOWN`       | 尚未进入缓存优先窗口                 | 仅缓存不可用或停滞兜底 | 进入窗口时转 `CACHE_PENDING`，或由引擎兜底领取                       |
| `WAIT_CACHE`    | 引擎已失败，等待尚未返回的缓存结果   | 否                     | 缓存结果、超时或线路失败                                             |
| `RECHECK`       | 完整命中但快照待复核                 | 否                     | 复核有效、重扫 `miss`、重试耗尽或线路失败                            |

状态转换要求：

1. `CACHE_PENDING -> DONE` 只允许经过 §11.1 的完整校验。
2. `CACHE_PENDING -> MISS` 才能进入普通引擎队列；`CACHE_PENDING -> PARTIAL` 只允许派发缺口，不得派发完整原文。`RECHECK` 不得直接当普通 miss，仅允许重试耗尽后按既有规则降级。
3. 分类窗口到期只解除引擎领取限制，不伪造 `miss`；调试状态记为 `cacheTimedOut`。
4. 超时后缓存结果仍可返回；若任务尚未提交，按缓存优先完成；若引擎已提交，继续按首个有效结果竞争和现有 abort 规则处理。
5. 缓存线路失败时批量释放 `CACHE_PENDING`、`WAIT_CACHE` 和 `RECHECK`，设置会话级 `cacheUnavailable`，不得逐项等待分类超时。
6. 单个任务扫描异常不得返回 `miss`；应保留错误原因并按有界降级规则进入引擎，避免把故障伪装成缓存不存在。
7. `CACHE_PENDING` 达到 64 项且连续 1500ms 没有新的分类结果时，`UNKNOWN` 可以绕过窗口由引擎兜底领取；这不是 `MISS`，也不得参与缓存命中率统计。
8. 分类或准入超时只解除领取限制，不关闭健康 worker；只有 watchdog 无进展、进程退出或协议致命错误才设置 `cacheUnavailable`。
9. `limited` 表示候选或计划超出预算，不是普通 `miss`；允许有界降级到引擎，但提交前必须重新校验当前权威。

### 12.3 缓存优先窗口与领取协议

#### 12.3.1 窗口预算

| 项目            |              首期值 | 约束                                       |
| --------------- | ------------------: | ------------------------------------------ |
| 缓存优先窗口    |               64 项 | 最多 64 项 `CACHE_PENDING`，含在途和待投递 |
| IPC 分片        |               32 项 | 只保留一个在途分片                         |
| 结果缓冲        |               64 项 | 达到阈值停止领取新分片；在途 32 项可收尾   |
| 分类窗口        |              1500ms | 从投递 worker 开始；32 项热态分片约 678ms  |
| worker 准入上限 |              1500ms | 从进入窗口到可投递，超时允许引擎领取       |
| 停滞兜底        |              1500ms | 无分类进展时允许引擎领取窗口外 `UNKNOWN`   |
| 纯缓存消费批次  | 40 项 / 10,000 字符 | 沿用 §11.2，不继承引擎预算                 |

窗口是上限，不是屏障。缓存 worker 已就绪且缓冲未满时持续领取；主线程处理速度不足时通过 `next()` 返回 `null` 形成反压。64 项包含在途和待投递任务，不额外增加第三个队列；慢任务不能阻止已确认的 `miss` 立即派发。结果缓冲达到 64 项后不再领取新分片，但已投递的 32 项分片允许收尾，因此瞬时最多 96 项已分类结果，随后必须消费后再继续。

#### 12.3.2 领取顺序

每次 `next()` 按以下优先级生成任务：

1. `RECHECK` 队列；
2. 已进入缓存优先窗口但尚未提交给 worker 的任务；
3. 新任务，按稳定游标领取；实际投递 worker 时写入 `cacheDeadline = now + 1500ms`；
4. `WAIT_CACHE` 的兜底重扫。

同一任务只能存在一个缓存扫描请求。当前实现尚未合并重复 `src` 的扫描结果；后续共享查询结果时，状态、完成计数和日志字符数仍须按任务条目计算。

#### 12.3.3 worker 消息

目标协议保留逐项进度，同时用分片结束标记维护反压：

```ts
type CacheScanRequest = {
  batchId: number
  leaseId: string
  tasks: Array<{ id: number; src: string }>
}

type CacheScanReady = {
  type: 'ready'
  workerVersion?: string
  /** Required. Absent / 0 is rejected; ready never doubles as batch completion. */
  protocolVersion?: number
}

type CacheScanItem = {
  type: 'item'
  batchId: number
  leaseId: string
  result: CacheScanResult
}

type CacheScanDone = {
  type: 'done'
  batchId: number
  leaseId: string
  elapsedMs: number
}

type CacheScanItemError = {
  type: 'itemError'
  batchId: number
  leaseId: string
  id: number
  src: string
  error: string
}

type CacheStampAdvance = {
  type: 'stampAdvance'
  leaseId: string
  beforeStamp: string
  afterStamp: string
}

type CacheStampAdvanceAck = {
  type: 'stampAdvanced'
  leaseId: string
  beforeStamp: string
  afterStamp: string
  applied: boolean
  reason?: string
}
```

兼容要求：

- 主线程按微任务 / 时间片聚合同一 `batchId` 的结果，不能每条消息都完整执行 `onCache()`、`pump()` 和日志刷新。
- 只有 `done` 才解除在途分片并允许投递下一片；逐项 `item` 可以提前释放完整命中，不等待分片末尾。
- 每个已接受分片必须在所有 `item` / `itemError` 之后收到一次 `done`；致命错误则走线路失败。
- 启动握手 `ready` 只表示初始化，不能作为完成标记；分片完成必须是 `done`。worker 必须发送 `protocolVersion>=1`；缺失或为 0 时直接软失败，不保留无效的旧版完成分支。
- `stampAdvance` 必须由 worker 回 `stampAdvanced`；`applied=false` 时协调者保留原上下文并等待下一次正常重建，不能假定 stamp 已推进。
- 协调者按 `leaseId + batchId` 归属结果；旧租约的结果一律丢弃，不能用任务 ID 代替租约身份。
- 不允许每项都单独回传完整快照或重复 resolver 数据；共享只读上下文可在 worker 内按扫描窗口复用。
- 单项扫描异常发送 `itemError`，不得伪装成 `miss`；该任务保留错误原因并走有界降级。只有 worker 致命错误才关闭整条线路。

### 12.4 调度接线

`seed-session` 的职责调整：

1. `start()` 启动缓存 lane 后不再无条件 `pump()`；先让缓存 lane 领取缓存优先窗口。cache worker 缺失、初始化失败或进入 `CACHE_UNAVAILABLE` 时，立即 `pump()` 走引擎降级。
2. `pump()` 的 `nextTask()` 只允许领取 `MISS`、`PARTIAL`、超时的 `CACHE_PENDING` 和满足停滞兜底的 `UNKNOWN`，不领取窗口内未到期的 `CACHE_PENDING`。
3. 新增 deadline 检查：每次 pump、缓存结果到达和定时唤醒时，释放已到期的 `CACHE_PENDING`。
4. `CACHE_PENDING -> partial` 时先保存 plan，再只派发缺口；不能派发完整原文。
5. 缓存返回 `full` 时取消尚未发送的引擎占位；已发送请求按现有 abort 和配额规则处理。
6. `fill()` 的结果窗口继续按完成项聚合，不等待缓存优先窗口全部完成。

建议使用单个短定时器维护最早的 `cacheDeadline` 和窗口停滞时间，不要为每个任务创建独立 `setTimeout`。定时器只负责唤醒 `pump()` 和 deadline 扫描，不执行缓存查询。

1500ms 分类与准入上限不得直接复用现有 5 秒 watchdog。前者是任务调度放行时间，后者只判断 worker 是否完全无进展；否则慢分片会被误判为线路故障。

### 12.5 权重与权威

权重真源继续为 `lib/translate/cache-engine-rank.ts`。调度、写入和查询不得各自维护另一套权重表。

#### 12.5.1 选择顺序

```text
authority rank desc
  -> exact src match
  -> category match (same rank only)
  -> local record before shared mirror
  -> stable record id (only to order equal translations)
```

- `updated_at` 不参与权威选择，只用于展示、清理策略或诊断。
- 完成时间、缓存命中时间和批次顺序均不参与权威选择。
- 高权重旧记录优先于低权重新记录。
- 本作记录与共享记录必须在同一候选集比较权重；不能因为当前查找先本作后共享，就让低权重本作记录压过高权重共享记录。
- 同权重译文一致时保留现有记录；同权重冲突时先比较精确 `src`，仍冲突再比较 category，之后才允许本作优先。若译文仍不一致，返回冲突，不静默选择；稳定记录 ID 只用于相同译文的确定性排序。`manual` 对同一精确 `src` 的明确改译按现有写入冲突规则处理，不能被“本作优先”或“返回冲突”永久挡住；该例外必须限定到同权重的精确 `src` 人工写入。
- 候选或计划 `limited` 不是普通 miss；应返回 `cacheLimited`，不得通过 bypass 绕过当前权威检查。

建议把本作与共享候选合并封装为一个只读 resolver，供 cache scan、引擎提交前复核和回填共用。它输出 `{ zh, engine, rank, local, recordId, revision }`，调度层不自行复制权重比较逻辑。共享来源镜像仍按 origin / revision 校验，不能用本作镜像绕过共享记录 revision。

#### 12.5.2 引擎结果竞争

引擎结果在持久化前必须复核当前权威：

- 当前存在更高权重权威时，接受高权重译文，拒绝低权重写入；本作低权重记录不能覆盖共享高权重记录；
- 当前权威与引擎结果同权重且冲突时，按现有写入冲突规则处理；普通引擎不得借冲突绕过同权重人工定稿；
- 当前权威 revision 已变化时，重新校验，不得用旧扫描 plan 覆盖；
- 缓存命中只撤销同一任务尚未接受的候选，不全局替换其他任务的引擎结果。

#### 12.5.3 重复与清理

- 重复译文不视为错误；高权重记录可以在前，低权重记录暂时保留。
- 不在本阶段自动删除低权重记录。
- 若后续增加清理，必须是独立需求，并明确人工保护、回滚、备份和审计。

### 12.6 长驻生命周期

#### 12.6.1 协调者与子 worker

```text
seed job worker（唯一协调者）
  -> cache worker（SQLite / 匹配，长驻）
  -> engine adapters（按 miss / partial 调用）
       -> Apple daemon（60s idle）
       -> Bergamot daemon（60s idle）
       -> Agent / platform HTTP
  -> storage daemon（回填 / 文件写入）
```

协调者不把模型推理放入 cache worker，也不让 cache worker 直接提交权威或写本作文件。cache worker 只返回扫描结果和依赖记录。

#### 12.6.2 复用规则

| 事件                       | cache worker         | Apple / Bergamot                |
| -------------------------- | -------------------- | ------------------------------- |
| 批次边界                   | 复用                 | 复用                            |
| 用户暂停                   | 停止领取，保留进程   | 允许在途收尾，空闲后按 TTL 回收 |
| 恢复                       | 优先复用；失效才重建 | 需要时复用或重建                |
| 切换游戏                   | 关闭并重建           | 关闭或按配置重建                |
| worker 代码 / 索引版本更新 | 排空当前分片后重建   | 排空当前请求后重建              |
| 致命错误                   | 关闭并软失败降级     | 对应引擎失败转移                |
| 空闲 TTL                   | 建议 5–10 分钟，可调 | 维持 60 秒                      |

缓存 worker 应由 seed job worker 按 `contentRoot + database` 持有，而不是由单次 `fill()` 会话独占。暂停只释放会话租约，worker 在空闲 TTL 内继续驻留；切换游戏、数据库身份变化或代码版本更新时关闭。这样不需要把旧会话对象永久保留，也不会在暂停后泄漏在途任务。

本作 `ownedFileTransitions` 目前只存在于协调者，缓存 worker 无法据此推进自己的 `getGameCacheContext()`。实现必须把已验证的 `beforeStamp -> afterStamp` 通过 worker 协议同步给 cache worker，并仅在该 worker 自己的当前 stamp 等于 `beforeStamp` 时推进；无法证明归属或出现并发外部变化时仍按现有逻辑重建。否则自身回填后 worker 会反复重建 resolver，抵消长驻收益。

每次会话租约使用新的 `leaseId`；worker 的扫描结果和 `done` 消息必须回传 `leaseId`。协调者丢弃旧租约结果，worker 收到租约释放后停止领取新分片，但允许已投递分片完成并丢弃结果。长驻 worker 不得仅靠任务 ID 判断结果归属，因为恢复后的任务 ID 可能重复。

若实现上必须随会话销毁，应在暂停日志中记录 `cacheWorkerSpawnCount`，并单独报告恢复冷启动耗时；此时需求中的“暂停后复用”视为未达成，不能只在文档中声明。

#### 12.6.3 启动策略

- 首次 `start()` 创建 cache worker 并完成索引打开 / 迁移。
- 纯缓存任务不主动启动 Apple / Bergamot。
- 只有确认 `miss` / `partial` 后才按引擎开关和就绪检查启动相应 daemon。
- Bing / Google 没有本地进程，不能宣称其网络和平台侧缓存可预热。

### 12.7 回填与持久化

#### 12.7.1 批量入队

缓存分片结果先聚合为窗口级候选：

```ts
type BackfillCandidate = {
  root: string
  src: string
  recordId: number
  revision: number
}
```

- 入队键为 `(root, src, recordId, revision)`；事件身份使用 `(database, recordId, revision)`，不能用自增 task id，否则同一 origin 会生成不同事件。事件 ID 还需避开 `game_backfills` 已确认版本和 `translation_outbox` 已排队版本，否则同 revision 删除后重建时可能被旧 `seen` 集合误判为已回填。
- 同一窗口内重复键只保留一次。
- 已存在等价的 `game_backfill_tasks` 或已完成的 `game_backfills` 不重复追加；`queue` 和 `flush` 都要检查。
- 同一 `src` 对应多个任务条目时只回填一次，完成计数仍按任务条目。

#### 12.7.2 flush 边界

- 正常批次边界可以 flush，但必须按窗口合并，不按单条命中 flush。
- 暂停、任务结束和正常退出必须 flush。
- 异常退出允许保留待办，恢复后重试；不得标记为已回填。
- 空队列且无 revision 失效项时直接返回，不读取 `cache.ndjson`。
- flush 后只允许通过 §11.1 的 owned transition 推进 stamp，不能跳过权威和 revision 校验。

#### 12.7.3 文件成本

当前 `flushBackfill()` 在存在待办时会读取并解析本作缓存快照，追加事件后再重新读取核验。优化目标是：

- 维持有界文件快照缓存，文件身份不变时复用；
- 同一窗口的事件合并追加；
- 只有需要确认 owned 写入时才重读差异；
- 避免因不同任务 ID 为同一 origin / revision 反复生成等价事件；
- 保留锁、fsync、幂等和崩溃恢复语义。

### 12.8 指标

新增指标只进入调试日志或诊断界面，默认不展示给普通用户：

| -------------------------------- | -------------------------------------- |

性能口径沿用 §11.5。新增预取后仍需分别报告：

- 冷启动：worker 创建、数据库打开、索引迁移；
- 热查询：32 项分片扫描和 40 项结果消费；
- 分类等待：任务在 `CACHE_PENDING` 的实际等待；
- 引擎：排队、提交、首条结果、全部结束；
- 回填：入队、flush、文件读取和 fsync；
- 持久化：作业状态检查和批次边界写入。

### 12.9 迁移与兼容

1. 先引入 `CACHE_PENDING` 和 deadline，不改变现有持久化状态格式；运行中恢复仍从已完成译文重建。
2. 保留现有 `UNKNOWN` 行为作为 feature flag / 回退路径，确认预取没有降低缓存故障时的吞吐后再移除。
3. 逐项 + `done` 协议要求 `protocolVersion>=1`；未声明版本的 worker 软失败并降级到引擎，不把启动 `ready` 当作分片完成。
4. 暂停复用 cache worker 时，确保旧 generation 的结果被丢弃；复用不能绕过会话代次检查。
5. 回填去重必须使用现有 origin / revision 身份，不能只按 `src` 去重而忽略不同 revision。
6. 日志和 UI 只消费结构化字段，不从新增调试指标反推用户文案。
7. `CACHE_PENDING`、deadline 和缓存优先窗口只保存在协调者内存；暂停恢复或进程重启后从持久化译文重建，不能把 `CACHE_PENDING` 当成失败或 miss 持久化。
8. 新增 worker 消息必须向后兼容：启动 `ready`、结果 `item` / `itemError`、完成 `done` 和 stamp 推进分别处理，不能把任一消息误当成分片完成。

### 12.10 测试矩阵

自动化至少覆盖：

1. 64 项缓存优先窗口全部命中时，引擎提交数为 0；结果缓冲达到 64 项后停止领取新分片，在途 32 项收尾后最多 96 项，内存不得无界增长。
2. 前 3 项命中、后 3 项 miss 时，只有 miss 项提交引擎。
3. 预取结果在 1500ms 内返回，引擎未提前提交。
4. 预取超过 1500ms，任务按 deadline 放行，不等待整个窗口。
5. 缓存 worker 初始化卡住，窗口到期后引擎可继续。
6. 缓存返回 `RECHECK` 时首次不进入普通 miss 队列，重试耗尽后按既有规则降级。
7. 缓存命中 abort 已提交引擎请求后，不重复完成、不重复计数。
8. 高权重旧记录优先于低权重新记录。
9. 低权重本作记录不能压过高权重共享记录。
10. 同权重冲突时精确 `src` 优先，再比较 category；仍冲突时返回冲突，不任意选择。
11. 暂停后恢复复用 cache worker，旧 generation 结果被丢弃。
12. 32 项分片结果只触发一次窗口级回填入队。
13. 同一 origin / revision 的重复候选只追加一次事件。
14. 空回填队列不读取完整 `cache.ndjson`。
15. 回填与人工修改并发时，owned 链不成立，旧结果失效。
16. 纯缓存批次不启动 Apple / Bergamot，也不把缓存扫描计入 `submittedSources`。
17. 缓存线路失败后 `CACHE_PENDING`、`WAIT_CACHE` 和 `RECHECK` 均有界释放。
18. 单个任务扫描异常不会被记录为缓存 miss。
19. 缓存优先窗口无分类进展 1500ms 后，引擎可领取窗口外任务且统计口径不误报缓存命中。
20. worker 准入等待超过 1500ms 时任务可被引擎领取，且不记为缓存 miss。
21. 复用 cache worker 后旧 `leaseId` 的结果和 `done` 被丢弃，不影响新会话计数。
22. 主线程登记自身回填后，worker 接受对应 stamp 推进且不重建 resolver；并发人工修改时仍重建或保守失效。
23. 候选 / 计划 `limited` 不被记录为普通 miss，引擎提交前仍复核权威。
24. 启动 `ready` 不被当作分片完成；未声明版本的 worker 被拒绝并软失败。
25. `stampAdvance` 的 `applied=true / false` 都按确认处理；失败时不得假定 worker 已推进。

性能回归至少记录：

- 40 项 / 10,000 字符热态查询 p50 / p95 / max；
- 64 项缓存优先窗口、32 项分片和 64 / 96 项结果缓冲边界的首条、首批和全部结果时间；
- 连续 10 个纯缓存批次的引擎提交数、批次间隔和回填次数；
- cache worker 启动 / 复用次数；
- 本作记录规模、共享语料规模和硬件信息。

### 12.11 实施顺序

1. **P0：预取门控**
   - 增加 `CACHE_PENDING` / deadline；
   - `pump()` 不领取窗口内任务；
   - 缓存线路失败批量降级。
2. **P0：缓存优先释放**
   - `full` 直接完成；
   - `partial` 只派缺口；
   - `miss` 立即派发；
   - `RECHECK` 继续重扫。
3. **P1：分片协议**
   - 逐项 / 小批结果 + `done` 完成标记；
   - 窗口级校验、去重和日志聚合；
   - 反压按分片而不是逐条消息。
4. **P1：回填聚合**
   - 窗口级 `queueBackfill`；
   - origin / revision 去重；
   - 快照复用和分段计时。
5. **P1：worker 复用**
   - 暂停不销毁 cache worker；
   - 跨 fill 复用；
   - 版本更新、切换游戏和空闲 TTL 明确关闭。
6. **P2：参数与回放**
   - 用真实语料验证 1500ms 分类窗口及其可调范围；
   - 验证 64 项缓存优先窗口和 32 / 64 缓冲边界；
   - 根据指标调优，不为未验证的设备差异增加用户配置。

### 12.12 回滚与边界

- 预取门控可通过开关回退到当前 `UNKNOWN` 直接派发，但回退状态必须保留结构化日志和缓存故障降级。
- 逐项 + `done` 协议异常时可以回退逐项消息；不得同时运行两套提交路径导致重复完成。
- 回填去重错误时优先保守失效和重新校验，不得用删除事件或忽略 revision 的方式修复。
- 任何性能优化都不得绕过人工保护、`authorityVersion`、共享 revision、来源权重或正常退出 flush。

### 一次自动处理的终态失败（2026-10-25）

- 成功译文仍由现有缓存保存；终态失败单独写入 `translate-jobs/<game-key>.failures.ndjson`。原文为键，seed 目标语言固定为简体中文；其它目标语言列表不读取此标记。
- 每条记录使用一次追加写入，保存 `src/error/at`；`error=null` 为手动保存成功后的清除事件。追加日志避免 Web 保存与任务 worker 相互覆盖整个 job JSON。旧 job 的 `failedSources` 作为兼容基线，清除事件优先。
- 调度器在最终结果确认时保存失败，即使结果尚未进入日志汇总窗口，暂停或重启也不会丢失已确认的终态。仅实际触发过翻译、耗尽工具、无暂停/禁用中断的失败可持久化；无工具、缓存错误和中途暂停不作终态失败。
- 库存优先判定有效译文，再判定失败；余下进入 pending。计数满足 `needCount=done+failedCount+missing`，字符数同理。失败不会增加 `done` 或写入成功缓存。任务在 `missing=0` 且无待汇总结果时完成。
- 失败日志文件签名纳入进度与列表准备缓存失效键，不能用频繁更新的 job JSON 签名触发全量扫描。继续任务仍在 worker 内重建库存，HTTP 轮询只读取快照。
- 列表失败标记保持到译文真正保存成功；重新翻译沿用显式 `force=true,persist=false` 预览，再由保存清除标记。失败筛选与未翻译筛选分开，手动重试失败不解除自动任务限制。
- 验证：全工具失败后重建库存不再入队；暂停/无派发不写失败；手动保存清除失败，另一个游戏与其它语言不受影响；成功、失败、剩余统计守恒。
