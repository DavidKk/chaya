# 旅伴核心重构技术方案

> 有效性：实施中；2026-10-29。
> 实现进度：T0–T6 在声明的标准回合战斗与样例范围内完成，逐项证据见文末验收对照。包含本地战斗、统一控制权、记录及有界经历检索、异步快慢判断、独立聊天、模型驻留和分段日志。官方 MV / MZ 样例、真实模型宿主、资源并发、双面板和存储恢复已有实测；构建后的 Next 配置页、API、插件及真实旅伴面板完整链路连续两轮通过。新旧同存档基准包含旧路径失败，不能计算加速倍数；历史暖模型超时仍保留。T7 首增量增加实际 HP 条件经验，见 §8.3；完整经历覆盖标记、其余 T7 和 T8 扩展仍属后续范围。
> 需求与验收：[旅伴核心重构需求](../companion-core-rebuild.md)。
> 有效范围：旅伴的新执行核心、动态战术、统一记录、异步判断与并发协作。沿用现有 UI 和配置入口，不要求首期实现多模型配置面板。
> 替代关系：实施切换后，在旅伴范围内替代[原技术方案](companion.md)中逐步模型执行与相关运行编排；现有授权、输入守卫、事实来源、记忆清理和停止要求继续有效。其他托管入口仍走原执行流程，但必须接入同一控制权仲裁。
> 本页代码摘录用于描述目标接口；实际支持范围、接线和已知限制以文末“当前实现范围”为准。示例接口不代表所有字段或扩展已实现。

## 1. 已核对的基础与缺口

以下记录重构前核对的基础与缺口；本阶段已补齐的接线见文末“当前实现范围”，不将旧文档中的交付状态当作本次实测结果。

| 接点                                                                                        | 当前基础                                             | 重构处理                                                                         |
| ------------------------------------------------------------------------------------------- | ---------------------------------------------------- | -------------------------------------------------------------------------------- |
| `plugins/mv/src/agent/runtime/companion-facts.ts`                                           | 游戏事实、标准事件、实例和现场版本                   | 复用身份与采集，补战斗输入机会、行动关联及能力声明                               |
| `plugins/mv/src/agent/runtime/companion-facts-mechanics.ts`                                 | 攻击、防御、可用技能枚举和有限机制                   | 补当前行动者、目标合法性、治疗效果描述；当前枚举不能直接当作可立即执行的动作列表 |
| `plugins/mv/src/agent/handlers.ts`                                                          | 状态读取、输入守卫、手动输入事件和 `inputOwner` 检查 | 复用普通输入链路，补统一控制权与逐段取消检查                                     |
| `lib/game-agent/runtime/task-controller.ts`                                                 | 操作任务生命周期、输入所有者、任务存档               | 与新协调器共享控制权，避免建立第二套独立操作锁                                   |
| `lib/game-agent/runtime/run-turn.ts`                                                        | 每步等待 `host.model.complete` 后再处理工具          | 新旅伴本地闭环不调用该逐步循环；其他入口继续使用                                 |
| `plugins/mv/src/agent/runtime/companion-chat.ts`                                            | 独立聊天生命周期和有限事实、记忆上下文               | 复用聊天通道，接入当前战术、真实行动原因和新的失效标识                           |
| `lib/game-agent/companion/memory-*`                                                         | 经历归约、行动缓冲、检索、持久化与基础投影           | 复用数据边界，补统一结果投影，不把当前缓冲当完整经验统计                         |
| `services/game-agent/companion-model.server.ts`                                             | 供应商适配、短生成、流式和思考能力处理               | 增加任务角色、战术结构化输出和独立预算                                           |
| `services/game-agent/companion-resource.server.ts`                                          | 按资源分组的有界队列，运行结束后释放占用             | 复用排队机制；容量改由资源配置统一决定，不能由单次请求不断抬高                   |
| `plugins/mv/src/agent/runtime/memory-persistence.ts`、`services/storage/companion-store.ts` | 游戏宿主通过存储服务提交记忆                         | 沿用当前实际接线，新增数据继续走同一持久化边界                                   |

当前本机记忆已有 `services/game-agent/companion-memory-db.ts` 的 SQLite 实现。重构不根据旧文档另建文件库或浏览器库，也不要求每游戏一个数据库。部署环境无法连接既有存储时，以实际能力和有界内存降级，不静默切换到新的长期数据源。

首期技术缺口是：可执行战斗契约、动态战术结构、本地动作选择、统一协调与控制权、模型结果采纳规则。完整经验推导不是本地闭环的依赖。

## 2. 部署与代码职责

### 2.1 三个运行位置

```text
游戏宿主（每个运行实例一份）
  事实适配 → 局势评估 → 本地动作选择 → 普通输入适配 → 结果关联
                    ↑                       ↑
              当前有效战术 ← 旅伴协调器 / 共享控制权
                    ↑              ↓
              判断结果采纳      异步任务、记录和聊天
                                   ↓
应用现有模型服务：任务路由 → 共享资源队列 → 供应商
应用现有存储服务：统一记录批次 → 经历 / 统计 / 经验

现有面板：发送指令、订阅状态与消息；不运行执行循环
```

核心闭环在权威游戏宿主运行，面板隐藏、重开或多个入口订阅不能创建第二份执行器。Cloud 页面通过已有桥接访问同一宿主；服务端不维护一份并行操控游戏的战斗状态。

模型调用、磁盘写入和历史检索是异步效果，不阻塞本地动作选择。引擎 hook 只复制有限事实、结果并发布事件，不能在 hook 内等待模型或数据库。

### 2.2 拟定落点

| 职责                                                 | 落点与边界                                                                    |
| ---------------------------------------------------- | ----------------------------------------------------------------------------- |
| 新核心契约、局势评估、战术校验、动作选择、纯状态归约 | `lib/game-agent/companion/core/`，注入事实、时钟和能力，不访问引擎或 Node I/O |
| 战斗输入机会、命令适配、结果关联和宿主运行协调       | `plugins/mv/src/agent/runtime/companion-core/`，只在这里接触引擎              |
| 模型任务适配和资源调度                               | 现有 `services/game-agent/companion-*.server.ts`，规模增长时按职责拆分        |
| 经历、统计和经验的读写                               | 现有 `lib/game-agent/companion/memory-*` 契约与 `services/storage/` 适配      |
| 跨入口消息                                           | `lib/runtime/companion-protocol.ts` 及对应校验，按协议版本扩展                |
| 面板接线                                             | 现有 `components/game-agent/`，本次不预设界面改版                             |

不为每个逻辑服务建立一个顶层模块。共享控制权需要从现有宿主与控制器中抽取或注入同一实例；新协调器不能只写自己的 `busy` 标记。

## 3. 身份、版本与控制权

复用 `RuntimeScope`、`ContextStamp`，保留游戏、数据版本、周目、实例与读档分段。补充以下运行标识，各有独立语义：

| 标识                               | 变化时机                                  | 用途                            |
| ---------------------------------- | ----------------------------------------- | ------------------------------- |
| `contextEpoch`                     | 读档开始、现场失去可信性或宿主重建        | 阻止旧现场结果生效              |
| `goalRevision`                     | 新目标、目标替换或约束变更                | 阻止旧目标分析覆盖新要求        |
| `controlGeneration`                | 取得、撤销或移交控制权                    | 在最终输入派发处拒绝旧控制者    |
| `tacticRevision`                   | 战术修改被采纳，或有效临时规则增加 / 失效 | 保守拒绝并发旧战术修改          |
| `memoryEpoch`、`recordingRevision` | 清理记忆、切换记录状态                    | 拒绝旧读取结果或待写批次        |
| `decisionGeneration`               | 同范围判断任务被替代或取消                | 即使底层未取消，也拒绝其结果    |
| `opportunityId`                    | 出现新的可输入命令槽或旧槽失效            | 防止同一角色 / 多行动槽重复确认 |

`factsRevision` 用于观察与诊断，不能要求所有模型结果与最新值相等。每次 HP 变化都使深入分析作废，会重新引入反复思考；应检查该分析真正依赖的条件。

### 3.1 一个控制权来源

拟定宿主内接口：

```ts
type ControlLease = {
  runtimeInstanceId: string
  ownerId: string
  generation: number
}

type ControlArbiter = {
  acquire(input: AuthorizedControlRequest): ControlLease
  assertCurrent(lease: ControlLease): void
  revoke(lease: ControlLease, reason: ControlRevocationReason): void
  release(lease: ControlLease): void
}
```

`AuthorizedControlRequest` 来自现有经过授权校验的入口，不接受模型自报授权。操作目标的 scope、lifetime 和可用动作保持显式。

旅伴、原托管、宏或其他可发送输入的入口，最终均需通过同一派发守卫。读档、移动等能改变现场的写操作也参与协调；不能只保护键盘输入而放任另一入口同时读档。

移交顺序为：撤销旧 generation → 取消后续输入与释放按键 → 使旧待执行计划失效 → 确认不再发送输入 → 新控制者取得权利。`revoke / release` 都比较完整 lease，旧控制者的异步回调不能撤销或清除新 lease，即使新旧任务复用了同一 ownerId。玩家停止、暂停或手动接管由宿主解析当前 lease 后撤销，不使用模型返回的控制标识。已经提交给引擎的战斗行动可能仍会结算，应保留关联，但不继续导航。

手动接管立即撤销自动输入资格，人类输入不等待租约释放。自动输入清理未确认时，暂不允许新的自动控制者进入。

## 4. 事实与战斗适配契约

### 4.1 区分动作可用与当前能否输入

现有 `legalActions` 表示角色具备的候选能力，不表示此刻可以任意给角色提交命令。新增战斗视图：

```ts
type BattleFrame = {
  stamp: ContextStamp
  encounterId: string
  phase: 'party_command' | 'actor_command' | 'resolving' | 'result' | 'blocked'
  opportunity: CommandOpportunity | null
  offers: ActionOffer[]
  capabilitiesRevision: number
}

type CommandOpportunity = {
  opportunityId: string
  actor: FactEntityRef | null
  actionSlot: number | null
  kind: 'party' | 'actor'
}

type ActionOffer = {
  actionKey: string
  actor: FactEntityRef | null
  kind: 'attack' | 'guard' | 'skill' | 'item' | 'escape'
  abilityId?: number
  targetRule: SupportedTargetRule
  costs: KnownActionCosts
  effect: ObservedOrDeclaredEffect
}
```

`SupportedTargetRule` 明确单体 / 全体、敌我、存活 / 倒下、自身 / 无目标等区别。随机目标、特殊范围或插件效果在未适配时标为 unsupported，不能将未知范围默认成单体敌人。首期只选已支持范围的动作。

`KnownActionCosts` 包含当前可读取消耗和未知项。`ObservedOrDeclaredEffect` 区分普通伤害、可识别治疗、防御、其他与未知，记录机制来源；不执行任意伤害公式来预测结果。

实体绑定使用遭遇内稳定实例 ID，不能只保存数组下标。首期适配需补可用治疗技能或道具的事实、目标、成本与结果，至少验证一种生存手段；不是仅凭技能名称判断“治疗”。

### 4.2 首期适配范围

- MV / MZ 标准回合战斗，分别验证普通攻击、防御和至少一种治疗路径。
- `party_command` 作为已授权战斗内的导航阶段，按当前目标进入角色命令；不为一次“战斗”菜单选择调用模型。
- `actor_command` 只对当前可输入槽选择、导航并确认支持的动作；TPB 或自定义阶段未验证前不报告完整支持。
- `resolving` 等待引擎推进；`result` 读取结算，结算确认只允许在授权范围内进行，结束后不得把确认键发送到地图。
- 未知窗口、剧情选择和不支持的目标规则返回明确阻塞原因，不以连续按确认兜底。

能力表至少分别声明 `battle.observe`、`battle.command`、`battle.result` 及各动作与目标范围的支持程度。宿主只有三项基础能力及当前样例所需动作都满足时才能启动对应自动战斗。

### 4.3 命令提交与战斗结算分开

```text
选定角色 A 的命令 → 导航 → 确认提交 A → 进入 B 的命令槽
选定角色 B 的命令 → 导航 → 确认提交 B → 全队命令提交完毕
引擎执行回合 → A / B 或敌方实际行动 → 多段 / 多目标结果 → 结算
```

**不能提交 A 后一直等待 A 造成伤害才处理 B。** 标准回合战斗可能需要先输入全队命令才能结算。

输入导航管线一次只处理一个命令，但允许多个已提交、尚未结算的命令存在。其数量受当前引擎实际命令槽与固定容量限制。新战术只改变未提交命令；首期不自动撤回已经确认的全队计划。

## 5. 本地选择、执行与验证

### 5.1 核心接口与运行方式

| 接口                              | 输入 → 输出                               | 是否阻塞本地闭环               |
| --------------------------------- | ----------------------------------------- | ------------------------------ |
| `facts.readBattle`                | 当前能力 → `BattleFrame`                  | 只做有界同步读取               |
| `situation.evaluate`              | 事实、近期结果、约束 → 风险与变化         | 纯计算                         |
| `tactics.current / validatePatch` | 当前战术 / 调整建议 → 版本视图 / 校验结果 | 纯计算                         |
| `selector.choose`                 | 战斗视图、局势、战术 → 命令意图或等待原因 | 纯计算                         |
| `executor.submit`                 | 命令意图、lease、取消信号 → 提交状态事件  | 异步推进，不阻塞协调器处理停止 |
| `results.ingest`                  | 引擎结果 → 关联结果、投影效果             | 有界归约                       |
| `decision.request`                | 明确问题和上下文 → 请求句柄、异步建议     | 不等待返回再执行普通动作       |
| `memory.query / enqueue`          | 有限查询 / 记录批次 → 证据 / 提交状态     | 不进入动作关键路径             |

协调器使用串行事件归约更新内存状态，归约步骤内部不 `await` 外部调用。模型、导航和存储在外部执行，将完成事件送回协调器；这能保证采纳战术的原子性，又不让慢请求挡住停止。

事件唤醒时合并重复状态变化，只维护一个执行 pump。需要等待动画时订阅阶段变化，并设置有界看门狗；退避轮询作为补充，不能每帧重算全场、查询历史或请求模型。

### 5.2 动作生命周期

```text
planned → navigating → committed → observed
    └─────────→ rejected / cancelled
             navigating / committed → unknown
```

- `planned`：本地选出动作，尚未输入。
- `navigating`：进入菜单、选择技能或目标；每段短输入前检查 lease、现场、当前窗口和取消信号。
- `committed`：确认命令槽已消费或引擎接受。单次按键成功返回不构成提交证据。
- `observed`：收到可关联引擎结果或明确未执行的原因。包含命中、未命中、无效果、资源不足等结果，不将零伤害自动判为输入失败。
- `unknown`：提交与否或实际结果无法证明，例如最终确认已派发后断连、提交证据缺失或适配缺口。区分提交未知与已提交但结果未知，不自动重放。

最终确认派发前先在运行时标记该机会正在确认。确认已派发但没有提交证据时，占住该 `opportunityId`，只观察和核对，不因超时重新确认。仅在能证明该槽仍未接受命令、无输入在途且已恢复已知窗口后才允许重选；无法证明则暂停相关执行。普通导航取消不能将这种状态重新归类为“尚未发出”。

导航每次推进都检查 UI 是否前进；无进展超过次数或时间上限则停止该计划并重新观察，不能无限按键。实施时为不同阶段设置可配置上限，并通过样例测量调整。

命令意图绑定选定时的战术版本。战术在导航期间变化时，最终确认前重新选择并比较：动作与目标仍一致则更新校验依据后继续；不一致则取消旧导航，在可验证的窗口恢复后重新规划。不能只替换内存中的目标却沿用旧菜单位置；无法可靠恢复时暂停。尚未开始导航的旧计划直接失效，已提交命令不撤回。

用 `commandId` 标记旅伴命令，保留引擎事件的 `actionId / resultId`。只有在行动者、槽位或适配 hook 可以证明关联时建立映射；反击、反射和强制行动不因时间相邻就归到某条命令。一个行动可能对应多个结果，也可能未执行。

资源预算需考虑已提交待结算命令的预期消耗；这只是本地预留，不修改真实库存。实际执行仍可能因敌方行动或引擎规则失败，最终以结果为准。

### 5.3 运行状态

| 状态                               | 进入原因                           | 后续行为                         |
| ---------------------------------- | ---------------------------------- | -------------------------------- |
| `idle`                             | 未授权或尚无目标                   | 可采集、聊天                     |
| `running`                          | 目标有效且持有控制权               | 执行本地闭环                     |
| `waiting_game`                     | 动画、提交后等待阶段变化           | 等待游戏，不请求模型解释正常动画 |
| `waiting_decision`                 | 没有能继续使用的战术，需要判断     | 有界等待，可聊天和停止           |
| `paused`                           | 游戏暂停、明确暂停或需要玩家处理   | 不发新输入，恢复重新观察         |
| `stopping`                         | 停止、手动接管、读档或替换目标     | 即刻撤销资格并清理导航           |
| `completed / interrupted / failed` | 已验证完成、现场中断或不可恢复失败 | 不自动恢复执行                   |

普通模型故障不使 `running` 自动变成 `waiting_decision`。只有缺乏有效行为时才等待；无法识别机制需要区分模型判断不足与引擎能力不足，后者不会靠重复分析解决。

`paused` 同样是输入版本屏障：立即撤销 lease，使未提交计划与相关判断 ticket 失效，取消导航并释放按键。暂停期间可以接收已提交行动的结果，不能继续派发输入或因模型完成自行恢复。显式恢复必须重新读取事实、确认目标有效并取得新 lease，不能续跑旧导航。游戏暂停状态也在每段输入的最终守卫处检查。

## 6. 动态战术与调整协议

### 6.1 采用声明式战术

首期提供有限的具名规则和参数，随后扩展。规则支持角色条件、风险条件、资源预算、目标偏好和技能偏好，不提供任意代码、任意属性路径或脚本执行。

```ts
type TacticPlan = {
  schemaVersion: 1
  revision: number
  rules: TacticRule[]
}

type TacticRule = {
  id: string
  priority: number
  when: TacticCondition
  prefer: SupportedActionPreference
  lifetime: RuleLifetime
}

type TacticPatch = {
  operations: TacticOperation[]
  reason: string
  evidenceRefs: string[]
}
```

`TacticCondition` 是白名单联合：例如 `hp_ratio_below`、`observed_hit_margin_below`、`resource_below`、`has_state`，以及有深度和数量限制的 `all / any`。各类型定义明确参数、单位和适用角色。未知指标求值为 unknown，不能直接视作满足；规则可显式指定受支持的未知情况回退。

`observed_hit_margin_below` 只引用匹配条件的已观察伤害估计，携带样本数、时间窗口与证据完整度，不保证代表下一击。角色、敌人、装备或阶段变化会降低适用性。首期可以先支持基础血线和资源规则，伤害条件在可验证的事实能力具备后接入。

`TacticOperation` 限定为增加规则、替换具名规则、删除规则或修改受支持参数。限制条数、字符串、阈值区间和可引用能力；一个 patch 全部校验成功才提交。不能用通用 JSON Patch 修改控制权、目标或记忆。

规则按明确优先级选择，冲突时采用稳定的次序与最新合法事实筛选。玩家禁止使用的物品属于目标约束，不是模型可以提高优先级绕过的普通偏好。默认生存规则仍是可调整战术，不能变成硬编码的全角色固定百分比。

### 6.2 临时调整与持续调整

`RuleLifetime` 支持当前遭遇、明确命令机会、下一次匹配行动或其他已实现的有界期限。临时规则必须绑定实体和消费条件，不能用模糊的“下一回合”跨角色误用。

临时规则增加、消费或到期都会更新有效战术版本。结果可能因此被保守拒绝，这是首期采用整份战术版本比较的取舍；只在相关问题仍存在时合并触发重新分析，不立即无条件重试。

### 6.3 判断结果只提交建议

模型只输出 `TacticPatch`。宿主保留不可由模型覆盖的请求信封：

```ts
type DecisionTicket = {
  requestId: string
  stamp: ContextStamp
  encounterId: string
  goalRevision: number
  controlGeneration: number
  baseTacticRevision: number
  decisionGeneration: number
  capabilitiesRevision: number
  memoryEpoch: number
  recordingRevision: number
  expiresAt: number
  dependencies: DecisionDependency[]
}
```

`DecisionDependency` 是宿主按问题生成的具名条件，例如目标仍存在、关键状态仍成立、特定命令机会未结束或资源区间仍适用。不能依靠模型在结果中自报“条件仍然满足”。

采纳顺序：

1. 确认请求仍有效，实例、现场、遭遇、目标和控制权未失效，且未超时。
2. 比较当前判断 generation，拒绝被替代任务；使用过记忆的请求检查记忆和记录版本。
3. 要求 `baseTacticRevision` 与当前值相等，首期不自动合并并发战术修改。
4. 校验依赖条件、当前能力、实体、参数、规则上限及玩家约束。
5. 原子提交新战术修订，发布采纳事件；新命令在下一个可输入边界使用。

拒绝时记录 `STALE_CONTEXT / STALE_GOAL / STALE_TACTIC / SUPERSEDED / CONDITION_CHANGED / CAPABILITY_UNSUPPORTED / INVALID_PATCH` 等原因。未知内容或无效 JSON 不触发逐动作旧 Agent 兜底；保留已有战术，必要时等待玩家。

同一遭遇首期只保留一个有效战术分析任务。普通变化合并到待分析问题；重大变化使旧 ticket 失效并尝试取消，再提交新任务。聊天、经验候选和战术分析可以同时存在，但没有第二个战术写入方。

替代任务按实例与遭遇的整个战术判断范围合并为一个待执行请求，快速与深入判断共用此合并边界，不积累多份旧上下文。正在运行且无法取消的旧请求继续占用资源；新请求出队时重新检查现场和有效期，失效则移除或重组上下文。触发需有问题指纹、冷却和失败退避，明确区分普通变化与重大变化，避免每次 HP 更新都替代推理，导致始终没有结果可采纳。

## 7. 模型任务、并发与上下文

### 7.1 任务角色与预算

| 角色           | 触发                         | 输入与输出                                   | 调度方向                             |
| -------------- | ---------------------------- | -------------------------------------------- | ------------------------------------ |
| `chat`         | 玩家发言、值得交流的事件     | 原文、有限对话、事实和经历 → 回复 / 意图候选 | 交互任务，可流式，默认不请求深入思考 |
| `tactic_quick` | 局部异常、明确调整要求       | 一个问题、相关能力和证据 → 小范围 patch      | 交互判断，限制输入输出               |
| `tactic_deep`  | 新阶段、持续无进展或复杂取舍 | 更多相关证据 → 战术 patch                    | 明确触发，可延后                     |
| `experience`   | 结算、证据更新且有整理价值   | 经历与统计 → 结论候选                        | 后台，可跳过或延期                   |

每类任务分别配置输入预算、输出上限、总截止时间与是否请求思考。首期复用现有预算类型，新增角色预算后通过基准调整；不把当前服务中 `control` 的长超时直接用于快速判断。总时限包含排队，供应商支持时再区分首段与执行时限。

上下文优先保留目标约束、问题、相关事实、当前战术和允许修改项，再加入相关证据、必要近期对话。不能裁掉关键约束后继续要求模型输出；必需信息放不下时应缩小问题或返回预算不足。

聊天不需要整套战术 DSL，战术判断不需要完整闲聊，经验整理不需要游戏工具。游戏台词和历史内容作为带来源资料，不能变成控制指令。显式停止、确认卡片等确定指令直接路由，不额外调用分类模型。

玩家意图走独立的受校验命令入口：宿主在接收原文时绑定消息 ID、输入顺序、现场、目标版本和控制 generation，模型只能提出类型受限的意图候选。协调器核对来源原文、时效、目标、授权和最新约束；同一消息幂等处理，较旧候选不能反转已采纳的新要求。普通闲聊不推进目标版本。停止或接管后的旧候选即使表示“继续打”，也不能重新申请控制权。

明确且在授权内的约束调整提交后递增 `goalRevision`，使旧策略结果失效；含糊或扩权请求沿用现有澄清与授权入口。若当前战术因此不再满足约束，立即停止派发不合规动作，重新选择或等待判断，不能等聊天回复完成才执行约束。`chat` 的回复文本与意图候选分别处理，不把生成中的半截输出当作命令；候选解析失败不扩大权限。

### 7.2 资源并发与决策并发分开

```text
任务 role → 模型选择 → 资源池队列（容量 N）→ 供应商请求
                                           ↓
                聊天展示 / 战术校验 / 经验候选归约
```

首期所有角色可映射到现有同一 profile / model，但使用独立 conversation key。key 至少区分实例、角色、会话及相关模型配置修订；不得复用供应商的有状态聊天会话来混放策略和闲聊。

资源池由可信配置决定容量，单次请求不能随意抬高容量。当前相同 host 或本机资源的保守分组可继续作为默认值，后续再细化资源池映射；不同模型不能自动视为不同 GPU 或配额。

同一资源池的调用必须进入同一个调度权威，包括仍使用旧执行循环的模型请求。现有队列是进程内状态，部署多 worker 时不能各自把容量 N 当作全局 N；首期应将该资源池集中到一个现有模型服务调度实例。无法统一的外部调用不计入可保证的容量范围，诊断中说明此边界。

容量为一时，聊天与判断公平轮转，后台只使用可用余量。容量大于一时允许真实请求重叠。队列有总量、后台量和每实例的限制，重复问题合并；一个实例不能持续灌入判断请求占满公共资源。

取消必须区分：

- 业务取消：立刻使结果失去采纳资格、更新可见状态，并向上游传递取消信号。
- 资源结束：底层请求真正完成或确认终止后，才释放正在运行的占用。

无法中断上游时，显示该资源仍在收尾，不假装释放容量。高优先级只能影响后续出队，不能承诺抢占已运行请求；长分析拆分或延后，不能用新增“紧急通道”绕过真实容量。

Ollama 驻留与启动：

- `services/game-agent/companion-ollama.ts` 在资源槽位内查询 `/api/ps`，检查模型名称及当前 16,384 上下文配置。已驻留则复用；确认缺失或上下文不同，先发送空 `messages` 的 `/api/chat` 进行加载，再开始短生成。预加载和后续生成都发送数值 `keep_alive: -1`。完成、取消和释放资源槽位不发送卸载请求，也不关闭服务。外部客户端、系统资源管理或服务重启仍可能导致模型不再驻留。
- 探测最多 1 秒；不支持探测时标为 `unknown`，不虚构冷启动。确认冷启动通过 `model.status` 发送 `loading` / `ready`，宿主按请求、会话及现场转发；面板只更新当前请求进度，不写成聊天回复。取消或现场变化后，加载完成不能继续旧路由或取得控制权。
- 普通路由、聊天和准备请求获得最多 60 秒独立启动额度，队列准入仍受原短预算限制。快速、深入战术判断保留原总时限；加载中断仍等待上游结算后释放槽位。路由先完成加载，再创建有效期 10 秒的战斗意图凭证。桌面与浏览器的路由传输上限统一为 140 秒，覆盖预热、重新检查时可能发生的再次加载及短生成，不改变战术时限。
- 桌面复用服务日志，浏览器宿主复用插件日志，来源均为 `companion-model`。记录 `requestId`、模型、用途、资源及 `accepted / queued / loading / ready / completed / failed` 中适用的阶段；浏览器队列耗时在完成或失败记录中体现。完成记录区分 `contextMs / queueMs / startupMs / generationMs / firstTokenMs / totalMs`，并保留供应商 token 与纳秒级推理计时。`loadMs` 是正式生成请求的原生加载计时；预加载响应提供加载计时时另记 `startupLoadMs`，缺失不填零。失败记录保留实际已等待的启动耗时；日志不包含提示词、聊天正文或凭据。
- `startupMs` 包含驻留探测和预加载等待；`firstTokenMs` 从请求发送起计，包含排队和启动等待，首段超时预算在加载结束后开始。`unknown` 模式不能保证代理后的启动等待与生成分离，错误照实上报。

### 7.3 多模型只预留映射

预留 `resolveModel(role, settings)`，首期返回既有选择；后续按角色覆盖 profile / model，并继续映射真实 `resourcePoolId`。不要求首期新增独立配置页、自动挑选最强模型或 Agent 编排框架。

模型替换使对应会话与请求失效，不更改已授权目标。多模型扩展仍遵守单一战术采纳入口，不使用“多个模型投票后直接发送操作”的机制。

## 8. 统一事件、记忆与经验

### 8.1 一份来源事件，多个投影

复用现有 `SourceGameEvent` 身份和生产者游标，新增具名事件：命令计划、命令提交、命令状态变化、战术采纳 / 拒绝与模型任务状态。实际引擎行动仍使用事实适配器事件，不将模型工具返回再写为第二份战斗事实。

源事件有独立稳定 `eventId`；同事件重试不改变 ID，同 ID 不同内容返回冲突。多段 / 多目标按现有 `resultId` 分别记录，不能按 `actionId` 去重掉合法命中。事件乱序时做有界关联，缺失就标注缺口。

| 投影         | 来源                         | 持久化要求                          |
| ------------ | ---------------------------- | ----------------------------------- |
| 当前行动账本 | 命令事件与可验证的引擎关联   | 运行时有界维护，重要结果留证据      |
| 经历         | 遭遇、击倒、结算、保存与读档 | 沿用记忆批次和完整度                |
| 基础统计     | 已去重的引擎结果与遭遇结算   | 增量提交，不由模型更新计数          |
| 经验候选     | 相关经历、统计和模型假设     | 与确定事实分开，带证据和适用条件    |
| 活动诊断     | 行动、战术和任务状态         | 引用相同来源 ID，不复制全部事实快照 |

统计至少区分遭遇次数、胜败、伤害样本、实际恢复与资源消耗。多目标结果不能重复计算一次 MP 或道具消耗；无法可靠归因的消耗和结果进入未知项，不硬凑总数。并非首期必须实现全部统计项，已交付项需有明确归约定义。

首期至少交付遭遇次数与结局分类：胜、败、逃跑、中断、未知。按实例、读档分段和遭遇身份去重，一个实际遭遇只计一次；结局未确认时不能推定胜败。迟到证据将未知更新为已知时，在同一事务内调整分类，不增加遭遇总数。伤害与资源等细分统计在能够可靠关联后逐项增加。

### 8.2 提交、重放与多实例

源游标去重、批次幂等与统计投影在同一存储事务边界提交，保证重试不双计数。当前 `MemoryBackend` 若不足以携带新增投影，按 schema 版本扩展现有批次，不额外开一条无事务的统计写通道。

同一游戏的多个实例提交到同一服务，由服务归约增量，或进行带 generation 的比较更新。禁止各自计算完整快照再互相覆盖。持久化 checkpoint 之前的内存投影不宣称已保存；崩溃恢复只重放可验证的已提交来源，不伪造丢失事件。

原始细节有保留上限，因此累计统计不保证永远可以从剩余细节完整重建。保留投影版本、覆盖范围和证据完整度；算法升级无法重算缺失历史时开启新统计版本或标注缺口。

清理与关闭记录沿用版本屏障。关闭记录仍允许有界实时状态供执行，但不新增长期经历、统计或经验；清空未提交记录并使旧写任务失效。经验模型也不能绕过开关写回。

`memoryEpoch / recordingRevision` 沿用按游戏管理的持久化范围，由存储服务的管理事务分配；多个宿主不能各自递增后通过普通批次抬高服务端版本。普通写批次必须精确匹配服务端版本与记录状态，管理命令使用请求幂等和版本比较提交。清理事务同时处理经历、证据、统计、关联和经验候选；偏好仅按玩家指定范围删除。

各宿主收到屏障或重连时先同步管理版本，清空旧缓存与待写记录，作废使用已删证据的检索、回复和判断；不得给旧批次重新贴版本后提交。未同步实例的旧写入由服务端拒绝，不能依赖广播一定到达。管理操作提交失败显示未完成，并继续阻止本实例旧批次写入，不宣称其他窗口已完成清理。重新开启记录从最新事实建立基线，标注关闭区间的缺口，不回填该期间缓存；已有经历检索和明确偏好修改仍可用。

### 8.3 经验结论与首增量

经验条目至少包含：游戏与数据版本、实体和条件范围、结论状态、证据引用、反例引用、样本量、更新时间及记忆版本。

结论状态区分观察摘要、待验证假设、受条件支持、存在反例与不适用。状态变更依赖定义好的归约规则，模型不得单凭一句“确定有效”升级可信度。跨周目可检索符合条件的经验，但不合并周目统计。

复杂条件如何分组、最小样本与结论演进规则，在经验阶段单独细化，不在首期实现通用自动反思。

2026-10-30 的首增量已实现[实际 HP 条件经验](companion-experience.md)：从已确认记录归约条件、样本量、方向与反例，供战术和聊天引用，没有新写通道或模型调用。仅覆盖保留观察，同游戏 / 版本 / 周目隔离；不跨周目复用，不确认机制，不代表完整 T7。测试游戏启动器默认静音，结束时关闭游戏与测试服务，保留推理服务及模型驻留。

## 9. 桥接、兼容与切换

复用 `agent.companion.*` 请求、事件订阅和模型服务。扩展核心版本、战斗能力、执行状态、战术摘要、活动请求及排队状态；只暴露受控操作，不提供远程调用任意内部方法的接口。

宿主协商确认支持新核心后，旅伴已授权战斗目标进入新执行器。其他类型目标明确走现有支持路径或报告暂不支持，不在战斗失败时静默切回逐步模型循环。

请求按 `requestId + payload fingerprint` 幂等；相同 ID 不同参数报冲突。订阅重连只补状态与有限事件，不重新启动目标或重发动作。旧面板和旧宿主不能默认为支持新核心。

沿用面板已有角色、语言与 profile 选择，新增状态尽量映射现有任务展示。聊天、停止回复、停止执行、记录开关分别管理，不由一个全局取消信号混在一起。

旧记忆保留并执行版本迁移；新增字段缺失时标为未知。临时战术、控制 lease 和待执行动作不在重启后自动恢复。旧执行器与新执行器可按明确运行模式选择，但同一目标只能绑定一个执行器。

### 当前实现范围（2026-10-29）

`lib/game-agent/companion/core/` 提供局势评估、本地选择、声明式战术、patch 原子校验、临时规则、租约和有界行动账本。`plugins/mv/src/agent/runtime/companion-core/` 负责引擎观察、普通命令导航、提交与结果关联，以及战斗任务编排。

**宿主接线和生命周期**

- `host.ts` 创建共享 `ControlArbiter`，由 `control.ts` / `task-control.ts` 连接旅伴、其他托管及所有写命令；读档、游戏编辑和输入也检查当前所有者。`inputOwner` 与完整 lease 一同校验，旧任务的迟到清理不能撤销新所有者。
- 旅伴可信控制票据中的 `battle` / `open` 进入 `battle-host.ts` / `battle-task.ts`，不调用原逐步 `runAgentTurn`。其余目标沿用既有路径。接手前核对标准 MV / MZ 回合引擎、必要窗口接口及当前战斗现场。
- 输入仍走 `game.state` / `input.press`，逐段检查租约、现场和战术；不直接设置行动、目标或窗口状态。导航期间战术变化会重新校验动作；无法确认最终提交时占住槽位并暂停，不重复派发确认。
- 长于两帧的受控按键，在名义按住时长后最多等待一秒，确认引擎 `_previousState` 已采样按下，再在 `finally` 中释放；释放后同样有界确认引擎采样归零。只读采样状态，不调用额外的引擎更新。超时分别报告 `INPUT_NOT_OBSERVED` / `INPUT_RELEASE_UNCONFIRMED`；失去控制权时立即释放，不等待采样预算耗尽。
- 胜利或逃跑在 `goal` 生命周期下结束任务；`until_stopped` 保持等待，但不自动移动到下一场战斗。失败、中断、不支持现场或连续判断失败进入玩家确认。读档和手动接管终止等待，不需要先回复继续卡片。恢复前等待旧导航及控制清理完成并重新观察。
- 战斗中连续缺少可信事实 30 秒会暂停；可信的地图、菜单、商店或存档场景中没有遭遇时，按跨战斗等候处理并重置看门狗，不因长时间等下一场战斗误暂停。快速判断失败采用有界退避，耗尽三次后暂停；可用本地规则不依赖聊天或后台模型完成。
- 连续三个实际回合仅提交默认保命防御、没有其他队员进攻或治疗时，触发深入复核；累计六个回合仍未脱困，在下一命令机会暂停并说明原因。统计依据实际提交，在下一输入阶段结算上一回合，兼容引擎先增加结算回合数、再返回最后一名角色提交确认的顺序；自定义防御规则不按默认保命停滞处理。

| 实际动作范围          | 当前状态                                                             |
| --------------------- | -------------------------------------------------------------------- |
| 普通攻击、防御        | 已接线，遵守引擎成本和目标可用性                                     |
| 技能                  | 当前角色可用技能；单敌、全敌、单活队友、全活队友、自身及无需目标范围 |
| 治疗                  | 依据 HP Recover 或明确 HP 恢复效果识别，不执行伤害公式预测恢复量     |
| 物品、复活、主动逃跑  | 尚未由新执行器派发；可以观察既有菜单逃跑结果                         |
| TPB、自定义战斗、RGSS | 拒绝作为已支持的本地战斗启动                                         |

结果沿用事实生产者事件，只将最终确认绑定的同一 `Game_Action` 归入命令；多目标使用各自结果 ID，反击、反射不归入原命令。敌方可见性与原始 troop index 分开处理；不以空敌人数组推断胜利，不把内部敌方 HP 当作已知策略依据。

**动态判断、玩家约束和聊天**

`battle-decisions.ts` 将目标、当前事实、有效战术、约束、近期结果及最多三条检索经历组装成独立请求。局部阻塞触发快速判断，需复核的局势在仍可本地执行时触发深入判断；普通动作不逐个触发模型。同一战斗任务仅保留一个判断调用，重复问题合并，不因上次超时而并行重开上游。

模型只返回最多四个战术操作及原因和证据；无操作建议合法且不增加战术版本。`tactic-references.ts` 核对模型实际收到的技能、状态、实体、机会和经历 ID，协调器再核对最新现场、请求信封、作用域、机会、目标、能力、战术和记忆版本，最终原子采纳。不同请求共享一个采纳入口。

`battle-intents.ts` 绑定玩家原文、消息身份与顺序、现场、目标、控制版本和时限。首个约束在任何输入前校验；战斗中的后续约束走现有语义路由。最多八项候选支持禁用技能、禁用物品（0 代表全部）、集中攻击指定敌人和保留绝对 MP 数量。引用必须来自原文且实体已知；具体对象还须在引用中出现其非空名称或独立数字 ID，MP 数值须与引用中的完整数字一致，不能从 100 提取成 10。别名或无法对应当前名称的请求会要求澄清。此检查限制凭空生成对象，不代表代码能完整证明自然语言中的禁止语义；全物品禁用仍依赖模型提取。整批校验后提交，不支持提取式扩大权限、删除约束或自动恢复。约束达到容量时拒绝新增，不挤掉先前的禁令。

聊天继续使用独立 `CompanionChatSlot`，上下文加入实际战术、当前动作和选择原因。路由、聊天、后台表达、快慢判断各用独立 conversation key；新路由、读档、接管和记忆管理版本变化使旧控制票据失效。记忆重载后，旧聊天的后续 delta / 完成结果不展示，旧对话与表达候选不进入下一次上下文。

| 用途                    | 输出上限（token） | 总时限（含排队）     | 思考     |
| ----------------------- | ----------------- | -------------------- | -------- |
| 语义路由 / 初次约束提取 | 128               | 5 秒                 | 默认关闭 |
| 聊天                    | 256               | 15 秒；流式首段 5 秒 | 默认关闭 |
| 后台表达候选            | 384               | 10 秒                | 默认关闭 |
| 快速战术判断            | 768               | 6 秒                 | 默认关闭 |
| 深入战术判断            | 768               | 25 秒                | 请求开启 |

这些是预算和超时界限，不是实测响应承诺。Ollama 使用显式 `think`；其他供应商根据能力发送提示或报告不支持，不声称已强制控制思考。原始 CLI 路径的输出 token 限制仍只有提示约束。协调器 quick / deep 票据分别有效 8 / 30 秒。

上下文字符预算为 12000。服务端和浏览器直连共用 `model-context.ts`，保留完整 system 和最新请求，只移除整条旧消息；必需信息超限返回预算错误。战术组装先裁可选经历和近期结果，保留目标与约束，并为供应商提示留余量；不能用截断 JSON 来满足预算。

**模型资源边界**

`companion-resource.server.ts` 按真实资源键调度，默认容量一。`GAME_AGENT_DIR/companion-resources.json` 是可信本机配置，示例：

```json
{
  "resources": {
    "local-inference": {
      "capacity": 2,
      "maxRunningPerInstance": 1,
      "maxQueuedPerInstance": 4
    }
  }
}
```

容量范围 1–8；每实例运行上限不超过容量，每实例排队默认四、最多十六，总队列十六，后台最多一条。配置在后续调度或结束时生效，降低容量不取消既有运行请求。交互与判断按实例公平轮转，后台使用余量；既有模型调用也进入共享调度。取消立即失去业务资格，但运行占用等上游实际结束再释放。

此服务端调度是进程内权威，不保证多个独立 worker 或外部程序共享总容量。浏览器直连 Ollama 使用 `lib/browser/companion-model-resource.ts` 的同源 IndexedDB 事务租约与 Web Locks，当前固定容量一；按 deadline 加回收窗口处理失联，并以活跃 Web Lock 防止标签页暂停心跳后重复运行。不支持 Web Locks 时明确拒绝直连调度。浏览器进程已退出、外部推理仍继续的情况无法保证物理算力已停止，不能宣称全机器级 GPU 锁。

多模型目前预留任务角色和独立调用边界；聊天、快速、深入判断仍采用现有选择，不新增配置面板或自动模型路由。

### 统一记录和记忆管理（2026-10-28）

`MemoryWriteBatch` 保持 schema 1，新增独立版本的 `battleRecording: { schemaVersion: 1, events }` 扩展，单批最多 128 个事件。目前持久化首次观察、命令确认提交、引擎行动结果和遭遇结局；计划、完整命令生命周期、战术和模型任务事件仍主要用于运行诊断，未全部持久化。

- 宿主通过 `memory-persistence.ts` 创建 writer，等待其管理状态初始化，再将协调器 `onRecord` 注入 `CompanionRecordingWriter.enqueue`。异步队列最多 256 条 / 1 MiB，溢出丢新增并报告 `dropped`；失败保留原批次身份，有界自动重试后可显式刷新或同步恢复。尚未获得管理状态时不补录事件。
- 继续使用已有存储服务和 SQLite。来源指纹、批次身份、明细、遭遇投影及既有记忆集合在同一事务提交；冲突整批回滚。新增表按游戏隔离，不另建每游戏数据库；纯内存临时后端明确拒绝战斗持久化扩展。
- 来源按完整 scope、遭遇、事件类型与事件 ID 去重，多目标使用各自 `resultId`。遭遇按游戏、数据版本、周目、实例、分段和遭遇 ID 归约，统计按游戏、数据版本和周目汇总。首次事件可建立未知遭遇，已知结局晚到可升级但不增加总数，矛盾已知结局报冲突。
- 当前累计指标只有遭遇总数和胜、败、逃跑、中断、未知分类。`projectionVersion: 1` / `coverage: 'observed_only'` 不代表完整历史。每游戏保留最近 512 条明细，`detailsTrimmed` 标明裁剪；去重身份及投影继续保留并计入容量，容量耗尽拒绝写入，不丢去重身份继续计数。尚无伤害或恢复累计投影。
- `action_result` 可携带同一事实生产者的实际来源、目标、技能、HP 前后和状态证据；旧记录缺少该字段仍有效，不从伤害数字倒推 HP。共享校验检查证据与结果的身份一致性。
- `memory-recording.ts` 从已确认的事件生成战斗结局和实际 HP 归零经历，供现有记忆查询、聊天及战术上下文使用。启动时从快照恢复，运行中仅在 canonical writer 获得存储 ACK 后发布；失败、未确认和旧管理版本批次不进入读投影。不新增经历持久化流或重复累计统计。
- 读投影最多缓存 512 条事件 / 1 MiB，每份经历证据与来源引用最多 64 条。按完整 scope 和遭遇分组，公开引用使用确定性 ID 并检测冲突；与已提交旧经历重叠时保留其 ID、合并证据，不纳入未提交旧细节。同遭遇存在矛盾结局时返回一份结局未知经历。胜败经历一律保守标为 `partial`，详情裁剪时标注；归零经历只声明实际观察到的 HP 变化，不推断战斗胜利或技能抗性。
- `companion.manage` 在管理事务内按预期 `memoryEpoch / recordingRevision` 比较更新，分配版本并保存幂等结果。普通写入只能精确匹配当前版本，不能自行清理、切换记录或抬高版本。关闭记录拒绝新增经历与战斗记录，明确偏好修改仍可提交；清理删除投影、来源和明细，默认保留偏好。
- `memory-sync.ts` 每两秒及在线恢复时使用轻量 `companion.state` 探测管理版本，仅变更时重载 store 和 writer，丢旧覆盖层与旧批次；普通事件写入不反复全量重载。管理失败时阻止本实例继续写入，可原请求重试；定时同步失败在下一次重试。插件离线队列丢弃失效批次，传输故障保留原条目。

跨窗口同步存在轮询窗口；存储端从管理事务提交起即拒绝旧版本写入。此机制只同步清理和记录开关，不持续导入其他实例的普通经历。重新开启记录从当前状态继续，不给旧内容更换版本。有界事件能够生成可检索的观察经历，但不能还原完整历史；记录关闭区间的详细覆盖标记、条件经验和结论仍待专项实现。

### 验证状态和后续验收

本地执行诊断通过任务 `progress.updated` 的 `diagnostic` 字段查询，复用任务已有的最近 200 条事件上限。`selection` 分别记录局势评估、动作选择和总耗时；`navigation` 关联实际命令和提交结果；`engine_wait` 合并一次引擎结算阶段的等待，在阶段变化、现场丢失或停止时结束；`result` 记录去重后的结果关联耗时。事件携带现场版本、遭遇、命令、输入机会、规则与战术版本等适用字段；导航中的重复校验不重复产生选择日志，诊断回调异常不影响游戏操作。

T0 的旧路径基线包含六次未完成战斗的记录；T6 按实际结局标记失败，没有把任务 `completed` 当作胜利。r7 旧路径轨迹中，模型在战斗场景调用地图交互工具，得到错误后以“等待战斗结束”回答；旧工具循环允许已调用工具后的普通回答返回 `answered`，未核对战斗胜利。本批保留此失败原因，不修改旧循环以制造双方获胜样本。新路径两次实际获胜足以验证本地闭环；由于旧路径没有成功样本，不提供有效加速倍数。
