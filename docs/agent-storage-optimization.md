> 有效范围：本机 Storage Daemon 管理的 Agent Trace、旅伴记忆、对话及角色配置；Cloud 经已连接游戏访问本机存储的场景一并考虑。

## 1. 背景与问题

项目已经使用 SQLite、运行时内存和文件配置。当前问题集中在数据读写粒度、查询范围和配置所有权，并非缺少某一种存储技术。

| 对象                 | 当前工作区实现                                                   | 待解决问题                                                                 |
| -------------------- | ---------------------------------------------------------------- | -------------------------------------------------------------------------- |
| 数据库所有权         | 本机独立 Storage Daemon 持有 `shared.sqlite`、`companion.sqlite` | 保留单写入所有者，避免优化引入插件直连和多进程抢库                         |
| Trace 与游戏来源事件 | JSON 摘要、JSONL 事件；追加前读已有事件做去重                    | 追加成本随历史长度增加；列表和任务读取需要文件扫描                         |
| 经历、证据和偏好     | SQLite 结构表与完整记忆 JSON 快照并存                            | 有效批次仍加载完整快照、删除并重插该游戏全部经历及证据                     |
| 对话与卡片           | SQLite 的 JSON 文档；旅伴对话消息与活动各保留最近 200 条         | 文档整份更新；写入后调用公共文件视图刷新，涉及无关翻译数据                 |
| 当前游戏事实         | 引擎内存与共享事实适配器                                         | 已有合理所有权，应避免为了增加缓存而复制第二份当前世界                     |
| Agent 设置、Skills   | JSON 设置文件、项目 `SKILL.md`                                   | 延续可编辑文件与受控写入机制                                               |
| 角色和工作区         | 当前工作区新增实现使用 localStorage 保存角色及 Markdown 字符串   | 浏览器仍持有权威配置；尚不是真实文件工作区，也不能据此认定已完成运行时接入 |
| 文本检索             | 未发现业务 FTS5 建表和查询                                       | 先有结构化范围查询；长期文本回忆单独建设                                   |

以上是代码路径判断，尚不能据此认定线上卡顿的原因或承诺具体提速比例。代码定位见技术方案 §2。

## 2. 目标与非目标

### 2.1 目标

1. 新增少量事件或记忆时，只处理相关变更，减少与历史总量相关的扫描和重写。
2. 日志、经历和可选长期对话能够按范围分页读取，不依赖全量装入前端或插件。
3. 数据持久化成功、仅进入内存、文件视图待刷新三种状态可区分。
4. 浏览器清站点数据后，已提交的角色、人设和台词仍能从本机恢复。
5. 优化后继续满足事件去重、冲突检测、周目隔离、清理屏障和容量管理。
6. 用相同机器、数据集和负载前后对比；将排队、执行和投影耗时分开记录。

### 2.2 非目标

- 不引入云端数据库、向量数据库或独立外部搜索服务。
- 不合并现有翻译库与旅伴库，不改变游戏原生存档的存储所有权。
- 不逐帧保存地图、战斗、变量、截图或完整游戏状态。
- 不把 Trace 全量复制进旅伴记忆，也不将全文匹配解释成经验推理。
- 不在本轮扩展非标准引擎采集能力，不自动上传游戏文本和轨迹。
- 不要求将最近 200 条对话自动扩展成永久聊天档案。

## 3. 存储分层与所有权

| 层                   | 负责什么                                                           | 不承担什么                                 |
| -------------------- | ------------------------------------------------------------------ | ------------------------------------------ |
| SQLite               | 结构化事实、经历与证据、偏好、事件索引、提交回执；按需保存长期对话 | 每帧状态和大型媒体文件                     |
| 内存                 | 引擎当前事实、有界待写队列、近期对话、可失效查询结果               | 已确认持久化数据的唯一副本                 |
| Markdown / JSON 文件 | 人设、性格规则、可编辑 Skills、台词模板、导出归档                  | 与数据库并列且互相覆盖的第二份历史事实真源 |

Storage Daemon 继续统一管理耐久数据。Local 服务可直接调用它；Cloud 中的游戏入口通过已有连接交给本机插件，再调用 Daemon。未连接本机运行时的 Cloud 页面不得显示“已保存到本机”。

记忆快照只用于检查点与恢复。原生游戏存档、截图和其他大文件维持既有体系，数据库按需保存身份、路径和关联信息。

## 4. 功能需求

### F01. Trace 增量归档与有界读取

- 追加单个事件不读取、解析该任务或运行实例的完整历史。
- 同一事件重试不重复计数；同键不同内容返回明确冲突，不能静默覆盖。
- 支持按游戏、运行实例、任务和时间范围查询，返回稳定顺序、分页游标和覆盖信息。
- 游戏事实保持来源身份；一个来源事件可关联多个任务，不为每个任务复制正文。
- 新增任务关联不改写来源事件的原始内容和关联字段；分页同时约束事件与关联水位，避免翻页期间遗漏或混入新关联。
- 沿用现有日志导出格式，并对导出大小、取消和失败设置边界。
- 删除任务、清理日志和清理旅伴记忆维持各自范围；不能互相扩大删除。
- 复用当前日志保留策略，补齐来源事件、去重元数据和活动任务的容量约束。

### F02. 记忆增量写入与范围查询

- 经历、证据、偏好、存读档关联和统计按稳定身份增量更新。
- 一个批次内的去重、经历变更、证据变更、统计和提交确认保持原子性。
- 查询先限制游戏、数据修订、周目及必要的遭遇或分段，再返回有上限的结果。
- 仅有明确读档来源关联时沿用现有 linked-load 例外；不借优化放宽跨周目匹配。
- 保留 `memoryEpoch`、`recordingRevision`、完整度、来源引用和 pending 标记。
- 清空、关闭记录或容量裁剪后，旧队列、旧查询结果和旧索引不能恢复已删除数据。
- 快照可用于恢复，不作为每次普通提交必须同步重写的完整副本。

### F03. 对话写入与公共文件视图解耦

- 只修改对话或卡片时，不重建、扫描或重写无关翻译文件视图。
- 保持当前近期消息与活动各 200 条、接口总量限制及恢复行为。
- 文件视图刷新失败不能把已提交数据库事务误报为“完全未保存”，应明确待恢复状态。
- 卡片状态按稳定消息或卡片身份更新；重试不能恢复已回答卡片或重复触发动作。
- 长期历史按 F05 单独启用，不以改变存储格式为由默认延长保留时间。

### F04. 角色、性格与台词工作区持久化

- 用户保存的角色、Markdown 内容和台词由本机持有，可备份和恢复；浏览器只保留视图或草稿。
- 保留现有 Agent 设置同步机制，不再建立一套供应商凭据或模型配置副本。
- 并发编辑有版本冲突提示，不能后写静默覆盖；失败时保留未提交草稿。
- 旧 localStorage 数据通过用户可见的导入过程迁移；提交成功前不能删除原数据。
- 默认模板中的虚构历险和玩家偏好不得作为实际经历或明确用户偏好自动入库。
- 保存到工作区与参与模型执行分别报告状态；只有确实接入后才声明“已生效”。
- 编辑规则文件不扩大工具权限，不改变真实游戏事实的来源。

### F05. 可选长期对话与文本回忆

- 在近期对话之外，需要长期回忆时单独定义保留开关、容量、清理和导出入口。
- 消息、卡片可逐条保存和分页；旧文档仅迁移实际保留的内容，不承诺恢复更早历史。
- 首先支持实体和结构化范围查询；全文索引用于补充文本匹配。
- 中文、日文短人名与英文独立词均有验收样例；不能只验证英文长词。
- 返回来源、范围、完整度和索引覆盖；索引未就绪不能冒充“历史中没有发生过”。

### F06. 有界内存与缓存失效

- 只缓存可重建的热点查询或派生结果；当前事实继续由引擎提供。
- 每类缓存同时限制数量和字节，访问命中可更新 LRU 次序。
- 读档、运行实例切换、配置修订、记忆清空和记录状态变化触发相应失效。
- 待写队列、去重仲裁和删除屏障沿用自己的可靠性机制，不能当普通 LRU 淘汰。

### F07. 迁移、恢复与可观测性

- 明确每类数据切换前后的唯一权威来源；禁止无期限双写。
- 迁移可中断、可续传，验证数据数量、身份、关联和内容指纹后才切换。
- 迁移期间的新增、更新和删除都须纳入校验；无法完整追踪变化时，在有界冻结内重读该范围，超时则取消切换。
- 迁移失败保留原始数据；切换后新增写入不能因简单回退旧文件而丢失。
- 统计排队时间、执行时间、读写条数和字节、视图刷新、缓存占用及迁移进度。
- 容量统计包含索引、回执和必要元数据；不得通过无限增长的去重表规避预算。

## 6. 验收标准

| 编号 | 场景                             | 通过条件                                                                                         |
| ---- | -------------------------------- | ------------------------------------------------------------------------------------------------ |
| A01  | 连续追加与重复发送 Trace         | 无完整日志重读；相同事件一次计数，冲突内容被拒绝                                                 |
| A02  | 多任务关联同一来源事件           | 正文只有一份，原文不被任务序号改写；关联增删期间分页不漏读或混入，删除其中一个任务不影响其余引用 |
| A03  | 新增一条经历或偏好               | 只更新相关行及必要元数据；不整游戏删除重插、不同步重写完整快照                                   |
| A04  | 批次中断、重放和清理竞争         | 不产生半批次、重复统计或已删内容复活；错误重放有明确结果                                         |
| A05  | 相同敌人、不同周目与读档分段     | 默认隔离，仅可验证读档关联按原规则补充历史                                                       |
| A06  | 保存对话、回答卡片               | 不刷新翻译视图；近期数量上限有效；重试不回滚卡片状态或重执行动作                                 |
| A07  | 数据库已提交但视图刷新失败       | 显示可恢复状态；重启可补齐视图，提交结果不产生歧义                                               |
| A08  | 角色保存、清浏览器数据与并发编辑 | 从本机恢复已提交内容；冲突可见，断连不伪报持久化成功                                             |
| A09  | 旧数据迁移中止、损坏与并发变更   | 可继续或保持旧源可读；新增、更新和删除均校验，损坏有报告，不静默跳过并宣布成功                   |
| A10  | 中文、日文短名和英文文本回忆     | 范围正确、来源明确；索引缺失和真实无匹配可区分                                                   |
| A11  | 长时间运行、缓存失效与容量裁剪   | 内存和持久预算受控，清理后旧结果不能再次进入上下文                                               |
| A12  | 翻译、Trace、记忆混合负载        | 固定负载前后比较 p50/p95、最大排队和占用；不得出现无界阻塞或未解释的退化                         |

性能验收同时检查算法和实测：固定新增批次，比较 N 与 10N 历史下的处理行数和字节；普通增量路径不得随总历史重写。容量回收、索引重建等维护任务独立记录。绝对延迟门槛在 M0 固定设备和负载后写入验收记录，不在没有基线时承诺毫秒数或提速比例。
