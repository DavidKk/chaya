## 1. 目标与边界

作为独立记忆模块，记录玩家真实经历，供陪玩与托管只读查询，供旅伴回答「上次被谁、用什么招式打倒」「读档前发生过什么」，并在再次遇到同一敌人时引用证据。采集覆盖手动游玩与 Agent 操作，不依赖旅伴面板打开或模型在线。

采集、归约、存储与按实体检索均不需要模型或向量库。当前事实和技能机制由共享游戏事实接口提供，记忆不重复维护第二份当前世界。自然语言建议与措辞由陪玩负责；显式用户偏好属于记忆，近期对话与可丢弃措辞候选属于陪玩，不将全部聊天永久写入。

## 2. 记录什么：事件，不是每帧状态

读取当前状态不等于保存历史。正常游玩只在有意义的事件发生时提取少量必要字段，不定时保存整份游戏快照，不记录逐帧 HP、全部变量、逐格移动或画面视频。

| 数据                     | 平时如何处理                                     | 何时持久保存                                                             |
| ------------------------ | ------------------------------------------------ | ------------------------------------------------------------------------ |
| 当前场景、位置、队伍状态 | 内存中维护当前值，旧值由新值替代                 | 战斗开始、结束或读档时取必要摘要                                         |
| 行动及伤害结果           | 每次实际结算后记录紧凑事件，放入有上限的内存缓冲 | 击倒、战败时冻结相关片段；`defense_attempt` 已在契约中，当前尚未单独落盘 |
| 战斗结果                 | 记录胜利、战败、逃跑、剧情允许失败等不同结果     | 每场一条紧凑摘要；普通战斗不保留全部行动                                 |
| 保存 / 读取进度          | 记录来源类型、稳定存档身份和现场摘要             | 操作成功后提交；失败不能冒充成功                                         |
| 奖励、等级变化           | 合并一次结算中的重复通知                         | 确认获得或升级后保存紧凑里程碑                                           |
| 技术诊断、完整状态、截图 | 沿用各自日志能力                                 | 默认不复制进旅伴记忆                                                     |

内存缓冲按事件数量和字节双重限制，长期记忆有单游戏 / 数据版本和全局容量限制，偏好、索引和统计也计入相应预算；具体默认值统一见技术文档。容量达到上限后保留可容纳摘要、裁剪较早的详细证据，标明缺口，不让记录无限增长。用户可查看实际占用与清理。

## 3. 最终交付中的记忆闭环

1. 采集到敌人某技能实际命中我方，记录行动前后 HP、结算伤害和关键状态变化。
2. 我方被击倒或战败时，保存当次遭遇和相关行动证据；不能把整场失败武断归因于最后一下。
3. 玩家成功读档，创建新的游玩分段，保留过去经历，重置当前观察与即时提示上下文。
4. 再遇同一敌人时，按游戏与敌人稳定 ID 查询经历，可直接提醒「上次这招打倒了某队员」。
5. 之后获胜会更新战斗结果，避免旅伴只记得失败。防御目前只作为未验证尝试进入建议措辞；尚未单独采集「防御时实际挨打」证据，也不把护盾 / 缴械写成已证明有效。

## 4. 事实、统计和策略假设分离

| 层       | 内容                                     | 约束                                                          |
| -------- | ---------------------------------------- | ------------------------------------------------------------- |
| 经历     | 某次行动、击倒、战斗结果、读档           | 稳定事件身份与来源引用；不被聚合覆盖                          |
| 统计     | 遇到次数、战败次数、某技能已观察伤害范围 | 从经历派生；同一事件重复处理不能重复计数                      |
| 策略假设 | 可能先防御、使用某个减伤技能             | 由陪玩 / 托管消费层提出，不自动写成事实；实际尝试结果另记经历 |

不能把「逃跑失败」记为死亡，也不能把剧情允许的战败等同于 Game Over。持续伤害、即死、自伤、强制结算或自定义插件无法可靠归因时记未知 / 部分已知，不猜攻击者或技能。

「被超杀击倒」只证明该招在当时造成了危险，不能直接证明缴械、封技或护盾有效。具体建议需结合当前可用能力、已知免疫和实际尝试结果；一次有效也不等于在所有装备、阶段和难度下有效。未观察到的 BOSS、稀有度、任务或技能机制不编造。

## 5. 读档与游玩分段

- 覆盖原生读档、Chaya 快速 / 自动存档恢复及其失败回滚路径，不只监听 `DataManager.loadGame`。
- 读档开始前记录 `from`；恢复成功且新游戏对象就绪后读取 `to`，不等待下一次 `Game_Map.setup`。
- 每次成功读档创建新 `segmentId`。保存现实发生顺序，读档不会删除旧经历；当前游戏事实重新建立，旧提示和临时战斗上下文失效。
- `from` 引用读档前当前分段中的相关经历，不机械绑定全局最近一次死亡。主动读档、连续读档和没有死亡的读档都必须正确。
- 原生槽位、快速槽位可能被覆盖，需区分存档来源与版本 / 条目身份。能可靠关联时记录保存时的分段和事件引用；外部导入或旧存档无法关联时标未知。
- 新游戏建立新周目身份；游戏进程重启与新周目不是一回事。无法确认周目归属时不得仅凭标题或槽位合并。

## 6. 查询与使用

精确匹配优先使用游戏数据版本、敌人 ID、技能 ID；地图作为场景条件，名称仅展示。默认查询当前周目；其它周目只在用户明确要求或启用相应设置时返回，并标注来源，不混入当前周目的次数。相关记录不足时返回空或部分证据，不按同名实体猜测。

本次成功读档的 from 是显式上下文关联：即使目标为缺少周目元数据的旧存档，也可引用同游戏 / 修订、明确关联的读档前经历，标为「读档前那次」。这不证明两端属于同周目，不合并统计，也不放开全库跨周目检索。

查询返回最近经历、相关胜败摘要、证据引用、已知缺口和情境差异；不把整份历史注入模型。「刚才怎么死的」优先绑定当前遭遇 / 分段，刚读档后可沿本次 load 的 from 引用查询前一相关遭遇；没有明确候选就消歧，不回退为全局最后一次死亡。自动提醒优先本地生成，主动追问由陪玩模块使用结构化结果回答；托管使用同一只读查询，仍必须重新观察和验证动作。

## 7. 生命周期与存储

采集在游戏宿主中运行，与 React 面板和托管模块解耦。采集 hook 只做轻量读取与入队；异步批量持久化，失败不阻断游戏。失败须有一次可见的降级状态，重试有上限，不能无界积压。

每条事件可幂等去重，区分库游戏、周目、运行实例、分段和战斗实例。不同窗口写入同一游戏时不能整份互相覆盖。存储支持查询、清理和容量维护；不承诺无限保存或绝不丢失尚未写盘的数据。

## 8. 验收

1. 不配置模型、关闭旅伴面板、由玩家手动游玩时，采集仍工作。
2. 同一 BOSS 技能击倒队员后，记录技能身份、目标、前后 HP 与相关状态；未知原因不被写成确定技能。
3. 原生 / 快速 / 自动读档都保留旧经历并开始新分段；失败恢复不误提交，重复成功通知只提交一次。
4. 同地图读档无需等待切图即可得到目标现场；连续读档不会串用上一个分段的死亡。
5. 同一事件重试不增加战败计数；同名不同 ID、不同游戏和不同实例不串记录。
6. 逃跑失败、剧情允许战败、普通击倒和 Game Over 能区分；后续胜利可被检索。
7. 长时间普通移动不产生逐帧 / 逐格持久记录，战斗缓冲和长期存储均有上限。
8. 超容量裁剪、存储失败和重启恢复有明确行为；缺少证据时旅伴不声称记得完整过程。
9. 采集和归约的测试覆盖事件顺序、重复消费、缓冲裁剪、读档回滚与失败归因，无需模型参与。

## 9. 非目标

本次不录制完整战斗回放、所有按键或全量存档；不推断隐藏脚本机制；不做向量库、自动模型反思、云端同步和独立进程服务。基础摘要和统计由规则整理，陪玩可以基于新证据生成表达候选，但不能反写为战斗事实。防御建议的生成质量另行验收，不能以采集成功代替策略正确。

## 10. 显式偏好与作用域（F13）

支持结构化的提醒频率、剧透偏好、表达风格等白名单字段。每项带用户来源、更新时间、作用域和修订号；当前明确设置优先于游戏偏好，再优先于用户默认。用户本轮表达可以影响本次对话，只有明确希望持续生效的偏好才长期保存；歧义需澄清。

偏好不绑定现实身份画像，不把模型推断的性格 / 情绪当事实。角色改变不删除玩家偏好，但角色人设不能覆盖明确偏好；不同用户存储空间必须隔离。游戏经历按游戏 / 数据版本 / 周目组织，用户默认偏好独立于周目。

## 11. 查看、暂停、清理与恢复（F13–F14）

- 查看：提供记忆摘要、证据完整度、使用容量、记录开关和当前持久化状态；不要求用户理解底层日志。
- 暂停记录：清空尚未提交的经历片段并使旧写队列失效，停止新增游戏长期经历；保留已有记忆和偏好，实时事实 / 本地反应继续。再次开启从当前现场建立新采集基线，不补录暂停期间。
- 清理：按游戏删除经历 / 统计 / 存档关联，偏好有单独删除范围。清理完成前建立版本屏障，取消相关查询、候选与待写数据；清理后的新事件可以继续记录，不能被旧重试或旧日志回填。
- 恢复：只恢复已提交记录和可验证存档关联；强退可能丢失未提交片段，不能承诺绝不丢失。升级 / 损坏时保留原数据并明确降级，不能静默清库。
- 边界：记忆清理不等同于删除 Agent 活动日志、游戏存档或供应商会话；界面说明删除范围，各自按原能力管理。已删除记忆不能自动从残留活动日志再导入。

专项补充验收：偏好优先级、删除时并发写入 / 查询 / 模型返回、暂停记录后重新启用、不同用户 / 周目隔离、全局容量维护、原数据保留迁移与跨窗口清理均有固定样例。实施归入总体 T2 / T5 / T7 / T8，不另起不兼容记忆模块。
