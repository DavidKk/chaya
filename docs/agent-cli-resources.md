# CLI 按需启动与空闲资源回收

> 有效性：现行需求；实现进度：已实现，相关测试、构建与 CR 已完成；全仓测试有 2 项已复现的原有失败，详见验收记录。
> 日期：2026-11-01。
> 范围：当前文本模型接入路径中的 Cursor / Codex 空闲池，以及 `/logs/cli` 进程列表。
> 替代关系：本页明确 [CLI 接入](agent-cli-providers.md) §6.8、§12 的空闲资源策略；不实现旧方案中的完整 CLI Run / MCP 会话池与运行并发限制。
> 技术方案：[CLI 资源管理](technical/agent-cli-resources.md)。

## 1. 问题与基线

当前实现已经在第一次模型调用时创建 Cursor / Codex 子进程，并在成功调用后保温 5 分钟；Gemini 每轮新建并收尾。保温减少连续聊天的冷启动开销，并非服务启动即预热。

仍需解决两个问题：不同实例或代理配置的空闲进程可以累积；日志页默认全机扫描，并曾按命令行中的供应商名称误收桌面应用辅助进程，容易误认为全部由 Chaya 启动。列表减少不代表其他应用的实际内存减少。

## 2. 交付要求

1. 不调用模型时不预启动保温进程。成功调用后保温 5 分钟，再次调用从完成时重新计时；运行中的任务不受空闲定时器影响。
2. 当前 Chaya 服务的空闲池最多保留 2 个进程，同一供应商的同一实例最多 1 个。达到上限时先释放最久未使用的空闲进程；同实例配置变化时释放旧配置的空闲进程。
3. 失败、死亡、授权变化的进程不再复用。回收沿用已有进程关闭、临时目录删除与凭证租约释放，不删除其他并发调用使用中的凭证目录。
4. 日志页默认只显示当前 Chaya 服务登记的进程，并说明按需启动、5 分钟保温和最多 2 个空闲进程。其他本机 CLI 通过显式切换查看，标明不由当前 Chaya 服务管理，不能自动回收它们。
5. 默认列表无登记进程时不启动 `ps`；有登记时只采样这些 PID。用户启用本机 CLI 扫描后才执行全机扫描。轮询间隔 10 秒，页面隐藏时暂停采样，返回前台刷新。
6. 扫描以实际可执行文件及已知 Node CLI 入口识别，排除 Codex 桌面主进程、渲染器和辅助服务。外部进程结束操作继续校验目标。

## 3. 边界与取舍

- 2 个是空闲保温上限，不是运行任务并发上限；不因回收策略中断正在执行的模型请求。
- 池属于当前服务进程，不是整台机器的跨服务配额。另一个 Chaya 服务及 ChatGPT / Cursor 的 CLI 属于外部来源，不能据此判定为孤儿进程。
- 保持 5 分钟，避免在没有真实冷启动收益测量时缩短既有窗口。首次调用及被淘汰后的调用仍有冷启动成本。
- 本期不新增设置项、不购买或调用模型进行验收、不修改授权协议。操作系统强杀、忽略 SIGTERM 的 CLI 以及跨进程池统一管理不属于本次保证。

## 4. 验收

- 用受控时钟验证从零启动、超时释放、复用重置、忙碌保护、并发返回、授权变化、失败释放与 LRU 淘汰。
- 验证同实例配置切换回收旧空闲进程；忙碌进程保留至调用结束。
- 验证默认列表不会全机扫描、无登记时不会启动 `ps`，扫描失败仍保留活着的登记进程。
- 验证 CLI 分类排除桌面进程，包含路径有空格的真实 CLI。
- 执行类型、格式、lint、测试及构建检查；CR 后修复发现并提交本地版本。
