# 旅伴记忆技术设计

> 状态：功能已落地，作用域 format / lint / typecheck 已通过；真实引擎、存储故障与容量验收未做；2026-10-24。
> 需求：[`../companion-memory.md`](../companion-memory.md)
> 总体接口、并发、任务：[`companion.md`](./companion.md)，本模块归入 T0 / T1 / T2 / T8。
> 事件所有权：[`agent-activity-log.md`](./agent-activity-log.md)；已有轨迹范围：[`../agent-gameplay-trace.md`](../agent-gameplay-trace.md)。本文定义新增领域能力，不声明旧轨迹已具有记忆字段。

## 1. 分层、所有权与数据流

```text
共享事实适配器 → 来源事件 → memory.ingest → 有界行动缓冲
                                             ↓ 关键证据冻结 / 战斗结算
                                       经历批次 → 异步提交
                                             ↓
                                  统计投影 / 实体索引 / 有限查询
                                             ↓
                                  陪玩与托管的只读证据上下文

用户明确偏好 / 清理 / 记录设置 → 入口验证 → 记忆管理事务
```

事实适配器唯一负责引擎读取与事件生产；记忆拥有经历、证据、投影、偏好及容量维护。沿用既有 SourceGameEvent 生产者、来源身份与 actionId，不重新解释模型工具返回来制造游戏事实。相同原始事件可被日志和记忆分别引用；记忆只保留必要证据摘录，不复制全部任务轨迹或截图。

适配器做 I/O，纯归约器显式接收状态、事件、时间 / 身份和配置，输出状态与待提交效果。不得从 300 条滚动文本反复猜死亡现场，也不把 UI 是否打开作为记录生命周期。

## 2. 采集、留存与默认容量

不是每帧录制。标准行动入口提取实际结果，对 HP / 关键状态变化、击倒保留紧凑事件。当前位置、资源等只更新当前值；普通移动不写历史。每场战斗有一条摘要，普通胜利不持久保存全部行动；击倒发生时立即冻结直接证据，不等最终战败才回找。`defense_attempt` 是契约预留，当前采集管线尚未单独产出该经历。

| 数据                       | 默认预算                                  | 超出行为                                                          |
| -------------------------- | ----------------------------------------- | ----------------------------------------------------------------- |
| 每实例行动缓冲             | 256 条且最多 256 KiB                      | 覆盖最早部分，保留缺口                                            |
| 单个关键经历证据片段       | 64 条且最多 64 KiB                        | 优先直接击倒 / 尝试证据及临近行动，标 partial                     |
| 每实例待写队列，含冻结片段 | 256 项且最多 1 MiB                        | 优先关键摘要，淘汰低优先级细节、记录降级；不额外挂无界冻结副本    |
| 单游戏 / 数据版本持久记录  | 20 MiB 逻辑预算                           | 经历、证据、存档关联、索引 / 投影、元数据预留均计入，先回收旧细节 |
| 当前用户全部记忆           | 200 MiB 逻辑预算，包含偏好                | 同样按旧细节 → 旧经历维护；不承诺每游戏都能同时占满 20 MiB        |
| 当前用户偏好               | 256 项且最多 128 KiB                      | 合并同键修订；超过上限需清理 / 拒绝新增，不无限扩张               |
| 检索结果                   | 默认 3 条，摘要与直接证据默认共 2000 字符 | 返回完整度和后续查询标识，避免截断后声称完整                      |

这些是可调实施起点，不是实测。字符串、数组、状态数量和单项 payload 均需字段级上限，按序列化 UTF-8 字节计数，并为索引 / 元数据保守预留。实际数据库配额不足时提前降级。普通配置不进入全量游戏状态日志。

本机压缩整理临时副本另有最多 20 MiB 工作空间，所有游戏串行压缩，目标峰值为全局逻辑预算加该工作空间和固定元数据预留；实际文件系统开销不承诺精确相等。空间不足则先降级，不能为整理无限复制文件。浏览器内部实现的物理开销由配额检测和失败恢复处理。

## 3. 身份、事件与证据

复用总体 `RuntimeScope`、`ContextStamp`。数据版本无法验证时使用显式 unknown / 未验证修订身份；不能把所有 unknown 当成可跨运行合并的同版本。显式建立周目，重启不是新游戏；无法确认时建立未关联周目，之后只有可验证存档元数据或用户明确绑定才关联。

```ts
type MemoryInput = {
  source: SourceGameEvent
  stamp: ContextStamp
  memoryEpoch: number
  recordingRevision: number
  coveredSourceCursor: SourceCursor
}

type ActionEvidence = {
  actionId: string
  resultId: string
  source: { kind: 'actor' | 'enemy' | 'unknown'; id?: number; instance?: string }
  target: { kind: 'actor' | 'enemy'; id: number; instance: string }
  ability?: { kind: 'skill' | 'item'; id: number; name?: string }
  hpBefore: number | null
  hpAfter: number | null
  reportedHpDamage: number | null
  hpMax?: number
  stateIdsBefore?: number[]
  stateIdsAfter?: number[]
  attribution: 'observed_action' | 'unknown'
}

type MemoryEvidence = {
  episodeId: string
  scope: RuntimeScope
  encounterId?: string
  sourceRefs: string[]
  completeness: 'complete_for_claim' | 'partial' | 'unknown'
  persistence: 'pending' | 'committed'
  summary: string
  evidence: ActionEvidence[]
  memoryEpoch: number
}
```

这是接口语义示例；实际输入按事件 kind 定义可区分联合，包括 action、knockout、battle_result、save、load、milestone 和管理事务，不用任意 payload 作为稳定实现契约。实体 ID 是数据表身份，instance 区分同类敌人的不同个体；显示名或译名不参与主键。

同一次行动共享 actionId，每个目标 / 每次多段命中有独立 resultId；重试不变，合法重复命中不能被去重吞掉。击倒按存活 → 倒下转换记录；复活后再次倒下是新击倒，不能与重复通知混淆。

来源稳定键为既有 `eventId`；相同 ID 不同内容返回冲突并隔离，不静默覆盖。producer epoch / sourceSeq 保留，不能被 taskSeq 替代。来源序号包含与记忆无关的事件，因此使用覆盖游标确认已消费 / 主动跳过的范围，不把每一个数字间隔误报为丢失。确实缺失则标 gap；来源失效 / 已退休后拒绝旧重放，不长期保留无界去重集合。

## 4. 标准战斗与机制采集（F02–F03、F05）

- 遭遇开始生成跨实例不冲突的 encounterId，读取当时地图、敌群 / 敌人 ID 与必要队伍摘要，不能依赖上次切图缓存。
- `Game_Action.apply` 原方法前复制 HP / 状态，之后立刻读取目标 `result()` 及新状态；返回值不是结算结果。只复制可序列化字段，不持有会被下一行动覆盖的引擎对象。
- 普通攻击、反击、反射、多段分别验证调用链。反射时 subject 不一定等于实际反射来源；无法证明就 unknown。结算报告伤害和 HP 差分开，溢出伤害不冒充实际损失。
- 击倒立即冻结相关证据；战败在引擎可能复活队伍 / 切场景前冻结现场，结束补结算。允许失败、Game Over、逃跑与逃跑失败分开。
- 持续伤害、即死、脚本 / 外部修改按可观测来源记录，不能凭最近一次攻击猜原因。绕过标准入口的插件报告能力不足。
- 胜败使用同一遭遇身份。每个敌人定义在一次遭遇中只计一次「遭遇次数」，敌人实例数量单独记录；战败次数按遭遇结算计，不按我方倒下人数计。

当前技能 / 状态机制通过共享事实接口提供，保存经历时只冻结理解该次结果所需摘要与来源。没有可靠机制时不把技能称为超杀、不推断可缴械 / 必然被护盾抵挡，也不根据先后相邻证明减伤因果。

## 5. 保存与加载生命周期（F04）

统一使用 `begin → commit | rollback`，操作 ID 跨原生 / Chaya 嵌套入口传递；每个成功操作只提交一次。

1. begin 必须在替换全局对象前冻结 from / 当前分段 / 遭遇，递增 contextEpoch，阻止旧模型和动作继续派发。
2. 原生 `DataManager.loadGame` 按真实同步 / Promise 契约处理；Chaya 接 `restoreSave` / controller 的恢复与回滚。单独监听 `extractSaveContents` 不能证明最终成功。
3. 恢复确认成功后直接读 to；对象 / 地图未就绪时有界等待 / 超时，不依赖下一次 `Game_Map.setup`。成功建立新 segmentId、提交 load 关联，再发布新基线。
4. rollback 不切有效 segment、不提交成功 load；重读现场，新 epoch 下再观察，不能恢复旧异步结果。无法确认时将现场标 unavailable，停止依赖该现场的操作。
5. begin 期间必要事件暂存到操作级有界缓冲；恢复过程的物品 / 等级差异只用于基线，不产生奖励。commit / rollback 后按确定结果一次释放或丢弃，不能跨分段混写。

存档关联包括 native / quick / auto、槽位或条目、可验证修订、保存时周目 / 分段 / 水位。原生存档可携带有命名空间与版本的 Chaya 来源元数据；不改游戏剧情变量。Chaya 条目可使用其受控元数据；只有实际保存成功才提交关联，加载失败不能污染存档身份。

外部导入、旧存档或覆盖后无法验证元数据时 origin=unknown，不凭文件名、槽位或游戏时长猜父节点。内嵌元数据也必须与当前库游戏 / 数据版本匹配，克隆存档不能跨游戏自动合并；不可验证时降级。本次不建立完整分支树，但保留保存来源边以支持后续扩展。

外部加载中断托管；托管自身获授权加载时沿用 operationId，在动作回读时按原任务边界验证 / 完成。记忆只发布加载事实，不决定是否继续任务。

## 6. 经历、统计、查询与一致性（F03、F05–F06）

`reduceMemory(state, input)` 产生经历、证据和投影变更；同一批次包含稳定键去重、经历与统计更新。经历不是聚合文本的覆盖对象，详细证据可按容量裁剪；统计是可重建投影，不是必胜策略。

投影键包含游戏 / 数据版本 / 周目 / 敌人定义及可选技能，地图和装备 / 阶段作为条件。保存覆盖范围和来源水位；压缩时保留受预算约束的统计基点，或重建剩余经历并标覆盖起点，不能重放旧经历双计数。状态统计键、修订和来源游标同样受容量管理，不以「只有统计很小」为由无限增长。

查询默认当前周目，优先当前明确遭遇 / 分段，再按实体匹配；主动查更早经历可显式扩展分段范围。跨周目需要用户要求或设置并标明来源；数据修订不兼容时不自动合并。没有匹配返回空，多个模糊候选返回待消歧，不能以全局最近一次死亡兜底。

查询意图区分 current_encounter、recent_death、rematch 与 explicit_history。recent_death 先查当前遭遇和分段；当前没有新击倒且存在最近一次成功加载关联时，只沿该 load.from 的明确遭遇 / 经历引用查询，不扫描全库最后死亡。关联缺失或多人 / 多次经历无法对应用户指代时返回候选供澄清。读取这一关联不等于将旧分段当成当前游戏事实。

周目元数据未知的旧存档也必须保留该上下文边。rematch 可以补充本次 load.from 明确关联的同游戏 / 修订证据，输出 origin=linked_load_context 并标为「读档前那次」；这不是跨周目同一性的证明，不合并两端统计。只有明确这条关联才能走该例外，不能将周目未知扩大为任意旧经历都可匹配。

当前运行的未提交经历允许从内存投影读取，但标 pending，不能宣称已跨重启保存。持久记录与内存 overlay 通过稳定 ID 合并，不重复返回；清理 / epoch 变化后 overlay 立即失效。查询以 memoryEpoch 和索引水位固定一次视图，跨窗口新提交可刷新；模型发送前校验未被清理。

## 7. 存储选型与提交契约（T2）

确定使用两种现有宿主形态的适配，不新增数据库服务或原生 SQLite 依赖：

| 环境           | 存储所有者                             | 提交方式                                                                  |
| -------------- | -------------------------------------- | ------------------------------------------------------------------------- |
| Cloud / 浏览器 | 同源 IndexedDB；页面宿主通过 port 代理 | 独立记忆 stores，单个 readwrite 事务原子更新经历、证据、去重 / 水位与投影 |
| App / local    | 现有本地应用服务；游戏插件只提交事件   | 每游戏 / 修订串行写入有界日志批次 + 检查点，受控原子切换存储代次          |

浏览器候选 stores 为 metadata、episodes、evidence、projections、saveLinks、preferences。索引覆盖游戏修订 / 周目 / 敌人 / 技能 / 时间；禁止一次 getAll 全库再筛选。跨窗口以数据库事务作仲裁，Promise 只能在 transaction.complete 后表示提交，不能在单个 request.success 时提前确认。事务不能等待网络或模型。

本机适配由一个数据目录写入所有者处理，已有服务多入口归并到它；第二服务进程无法取得目录写锁时拒绝写入并报告，不允许两进程各自靠内存队列覆盖文件。每批记录包含 schema、批次 ID、epoch、来源水位、经历 / 证据和管理变更；完成写入与异步 flush 后确认提交，投影可以从已提交检查点与后续批次重建。

启动忽略不完整尾批次并报告缺口，保留原文件供恢复。压缩在单写入队列中完成新代次检查点与必要记录，完整写入后原子切换 manifest，最后回收旧代次；崩溃后只选择完整有效代次，不把新旧批次重复消费。读写、重放、索引与容量维护都通过 MemoryStore，不由 UI 直接改文件。

hook 只做轻量复制和入队；普通数据短批次合并，关键经历优先提交。退出仅尽力刷新，不承诺强退前未提交数据不丢失。无 IndexedDB / 服务断连 / 写锁失败时使用有界内存并显示降级，不能回退为无限 localStorage 或伪报保存成功。

## 8. 显式偏好与删除屏障（F13）

偏好按用户存储空间隔离，可选 libraryGameId，具有 key / value / revision / sourceUserMessageId / updatedAt。入口只接受白名单字段和真实用户设置 / 指令；模型建议不是新的用户来源。设置解析歧义先澄清；本轮临时表达不自动提升为永久偏好。

`memoryEpoch` 为持久化范围版本，删除和记录开关有原子更新。所有 ingest、批次、查询、候选与模型上下文携带该版本；写入检查当前 epoch / recordingRevision，不接受旧值。

清理流程：协调器取得对应范围管理事务 → 升 epoch 并广播 barrier → 清空 / 作废旧缓冲和待写队列 → 删除指定经历 / 证据 / 统计 / 存档关联 → 提交 → 通知消费者丢旧检索 / 候选。偏好仅按用户选择的范围删除，游戏存档和活动日志不受该动作删除。

活动运行实例必须确认新版本后才能继续提交新事件；离线生产者重连先握手，旧队列不能在服务端被重新贴上新 epoch。清理保留所需删除版本 / 来源水位，历史归档不自动导入，因此不会把已删内容恢复。正在生成且使用已删证据的回复取消；已显示历史消息不自动重写，管理界面说明此范围。

关闭记录同样提升记录修订并作废旧队列，只停止新的游戏经历；实时事实、已有记忆查询和用户主动修改偏好仍可用。重新开启从当前基线记录，不追补暂停区间，必要时显示缺口。

## 9. 失败、迁移与恢复（F14）

| 失败                  | 行为                                                                 |
| --------------------- | -------------------------------------------------------------------- |
| 短暂写失败            | 最多 2 次带退避的重试，受队列和期限限制；一次可见降级，不阻塞游戏    |
| 配额 / 磁盘不足       | 先按策略回收可裁剪数据，再尝试一次；仍失败保留关键摘要到有界内存     |
| 来源重复 / 冲突       | 同 ID 同内容忽略；同 ID 异内容隔离并记录诊断，不能覆盖事实           |
| 序号缺口 / 缓冲淘汰   | 记录覆盖范围和 partial；不编造完整过程                               |
| 本机服务 / 浏览器关闭 | 重启只恢复已提交批次，未提交片段可丢；不恢复游戏输入                 |
| schema 升级           | 版本化迁移先验证，成功后切换；失败保留旧版只读与原数据，禁止清库重试 |
| 旧文本 / 旧任务       | 只读兼容；不能补写不存在的技能、攻击者或周目关系                     |

重试 timer 隶属宿主取消信号，读档 / 清理后不重试旧队列。重建投影必须使用未删除且在当前有效版本内的经历；裁剪 / 删除后不能从残留诊断日志回填。

## 10. 验证与实施交付

T0 固定事件、scope、epoch、完整度、存储错误码与事务契约；T1 提供真实标准行动 / 加载来源；T2 完成归约、两种存储、查询与管理；T8 验证旧配置、存档元数据、迁移和跨模块取消。

必须包含以下固定样例，并映射总体 A01–A04、A10–A11：

1. 行动前后 HP / 状态、溢出伤害、群攻 / 多段身份、反击 / 反射与未知归因；复活再倒下不被去重吞掉。
2. 允许失败时复活前冻结、逃跑失败不计死亡、同类多个敌人 / 多名我方倒下不重复计战败。
3. 原生同步 / 异步、快速 / 自动、同地图 / 连续加载、嵌套入口和失败回滚；load 结果重复提交仍只有一条。
4. 无模型、面板隐藏、普通移动与手动游玩；原生 / Chaya 保存成功元数据可关联，旧或外部存档保持 unknown，但明确 load.from 关联仍可用于读档前经历提醒，不错误合并周目。
5. 同事件重试不双计数、主动过滤的序号不误报缺口、乱序 / 冲突处理、多实例 / 用户 / 周目隔离。
6. 环形缓冲和队列的数量 / 字节封顶，单游戏与全局回收，统计基点 / 缺口、压缩峰值和空间不足。
7. IndexedDB 的请求成功后事务失败、本机尾批次不完整、检查点切换时崩溃、第二写进程、多窗口同时清理与写入。
8. 暂停记录、删除时存在旧 ingest / 查询 / 模型返回、生产者离线重连，以及从旧日志自动回填被禁止。
9. schema 升级失败原数据仍在，已提交记录可恢复，未提交丢失如实标记；只读消费者不会取得写工具。

引擎接点在实际支持的 MV / MZ 版本和插件组合中验证，不能以 MV 标准源码推断任意自定义系统。背景设计采用事件 / 投影分层、事务和幂等原则，不引入完整事件溯源框架或依赖模型反思才能运行。
