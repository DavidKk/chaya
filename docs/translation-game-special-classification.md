## 1. 背景与核心痛点

当前游戏本地翻译系统主要面向 RPG Maker、Galgame 等日语游戏，通过本地翻译模型完成游戏文本的批量翻译。随着翻译规模不断扩大，现有方案在翻译质量、处理速度和特殊文本适配方面逐渐暴露出瓶颈：

### 1.1 翻译质量不足

传统机器翻译模型偏向通用文本，对游戏特有的语言表达支持有限：

- **人物对白**：口语化表达、角色语气、敬语及复杂情绪变化。
- **特殊发声**：角色受伤或濒死时的惨叫、喘息、呻吟、咳嗽、哭泣等非标准日语词汇。
- **拟声拟态**：动作音效、环境声音、大量重复音节（如「あっ……」「う、うそ……っ」）。
- **复杂上下文**：省略主谓、隐含语义、高度依赖当前剧情的表达。
- **游戏特殊格式**：控制码（如 `\V[n]`、`\N[n]`、`\C[n]`）、特殊占位符及换行排版。

此类文本若仅靠通用分词或词典匹配极易崩溃，且同一段文本往往同时包含痛苦、恐惧等复合情绪，无法简单归入单一类别。

### 1.2 翻译速度与质量难以兼顾

全量文本使用大参数语言模型会急剧增加计算资源消耗与耗时，对于动辄数万至数十万条文本的游戏脚本而言不可承受：

- 必须保持本地低资源占用，保证高吞吐批量翻译。
- 避免所有文本都经过复杂模型进行二次处理，必须分流。

### 1.3 翻译异常缺少系统化积累

- 当前翻译流程中的漏译、误译和格式损坏尚未形成闭环的数据反馈机制。
- 单次单点修复无法阻止同类问题在后续游戏中重复发生。
- 高质量日中游戏语料（特别是特殊发声与情绪对白）人工采集成本极高，急需在日常翻译中实现自动化结构化沉淀。

## 2. 总体目标与核心原则

### 2.1 四大核心目标

1. **提升当前翻译质量与性能**：第一阶段优先通过外置资源直接匹配语气词、拟声与纯发声，减少机翻调用，完善格式保护与异常采集；后续再开展新模型选型与推理优化。
2. **建立独立的多维文本分类系统**：构建模型驱动的文本理解与打标模块，对游戏文本输出结构化多维标签。
3. **建立持续的数据积累机制**：以沉淀资产为核心，持续记录原文、译文、上下文、多维标签及置信度。
4. **为未来模型优化提供基础**：为后续动态示例检索（Few-Shot）、小模型微调（LoRA）及第三方协同提供数据基础。

### 2.2 核心设计原则

- **性能优先**：主翻译流程坚决不因分类、打标、审核或修正任务而发生阻塞。
- **直接匹配优先**：在保护已有定稿的前提下，优先使用外置完整译例与受限发声模板；未命中、存在歧义或不支持的语言对回退到现有引擎。
- **模型分类**：文本语义、情绪、发声及表达特征由模型统一识别，不依赖僵化关键词词典。
- **多维多标签（Multi-label）**：允许单文本同时挂载多个维度标签，真实还原复杂语境。
- **数据优先**：M1 完成资源外置与异常采集，M2 再进行模型分类与标签沉淀，不以训练新模型作为前置条件。
- **双轨解耦**：分类系统与主翻译流程彻底解耦，支持离线、增量与批量执行。

## 3. 多维文本分类打标体系（Schema 规范）

分类系统面向所有游戏文本设计，初期优先处理异常与高风险文本，后续逐步扩展。

### 3.1 分类维度定义

| 分类维度                           | 涵盖范围与示例                                                            |
| :--------------------------------- | :------------------------------------------------------------------------ |
| **文本类型 (text_type)**           | 对白（Dialogue）、旁白（Narration）、系统UI/菜单、动作/心理描写、环境音效 |
| **情绪 (emotion)**                 | 愤怒、恐惧、喜悦、悲伤、痛苦、羞耻、冷漠、温柔（支持复合多选）            |
| **语气 (tone)**                    | 命令、疑问、恳求、讽刺、撒娇、敬语、粗鲁、傲娇、迟疑                      |
| **声音类型 (voice_type)**          | 惨叫、喘息、呻吟、哭泣、咳嗽、狂笑、呢喃、叹息                            |
| **表达特征 (expression_feature)**  | 重复音节、拖音（〜/ー）、停顿（……）、结巴/短促（っ/ッ）、省略             |
| **翻译风险 (translation_risk)**    | 语义歧义、高度依赖上下文、特殊双关/俚语、非标准假名发音                   |
| **翻译异常 (translation_anomaly)** | 疑似漏译、源语言残留、误译、语气/情感丢失、控制码/变量损坏、模型复读      |

### 3.2 语料存储元数据 Schema

沉淀的数据保留文本身份与可取得的上下文；实时模式缺少下文时允许为空，并记录缺失情况，不为补齐上下文等待或虚构内容：

- `sample_id` / `source_revision` / `translation_revision`: 稳定样本标识与原译版本
- `source_language` / `target_language`: 明确的有向语言对
- `original_text`: 原文（不限于日语）
- `translated_text`: 目标语言译文（若已翻译）
- `context`:
  - `speaker`: 发言角色名称 / ID
  - `scene_id`: 地图 ID 或场景编号
  - `prev_lines`: 上文 1~2 句文本
  - `next_lines`: 下文 1~2 句文本
- `labels`: 多维标签键值对（支持每类多个值）
- `model_meta`: 打标模型名称、版本、标签置信度（允许为空）、简短判定依据、标签及提示词版本。模型自报置信度不等于经过校准的准确率
- `status`: 采集、分类、审核各自记录状态；模型打标不自动升级为人工已审核
- 语义类标签绑定原文与上下文版本；翻译异常标签还需绑定译文版本。更新译文后保留旧结果用于追溯，并将旧异常标签标为过期，等待重打标。

## 4. 实施范围、分期规划与里程碑验收（Milestones & DoD）

按**“固基 -> 闭环 -> 资产 -> 反哺”**递进演进，前一阶段达到验收准则后开启下一阶段。

```
M1: 外置资源与直接匹配翻译（P0 / 第一版）
       │ 交付物：多语言资源包、短语/发声直接匹配、格式保护、异常采集与基线报告
       ▼
M2: 独立多维分类引擎与打标闭环（P1 阶段）
       │ 交付物：7 维多标签体系、异步解耦调度器、首批异常样本打标
       ▼
M3: 数据资产化管理与流转体系（P2 阶段）
       │ 交付物：多维数据筛选、标准导出导入、第三方/人工处理对接
       ▼
M4: 知识反哺与场景增强（进阶阶段）
       │ 交付物：动态 Few-Shot 示例检索、高频口癖规则库、微调数据集自动化生成
```

---

### Milestone 1: 外置资源与直接匹配翻译（P0 / 第一版）

- **目标**：以“外置数据 + 代码匹配”为第一阶段主线，优先覆盖已确认的术语、固定短语、语气词、拟声与纯发声，命中后跳过机翻；未覆盖文本沿用现有引擎，同时完成格式保护和异常采集。M1 与 §7–9 的第一版范围、验收一致。
- **核心交付物**：
  1. **多语言外置资源包**：迁出 `GAME_TERMS`、`FIXED_PHRASES`、发声映射和称呼译文；按显式语言对隔离，支持校验、预览、导入、更新、停用与恢复上一版本，不要求改代码或重新构建。
  2. **统一直接匹配路径**：保护已有定稿后，先尝试完整译例，再对整条符合限定形式的纯发声执行受限模板；统一 CLI、批量、实时及导出相关入口。混合对白、歧义和未知形式回退到现有引擎，不用逐字发声映射吞掉普通语义。
  3. **格式保护与还原**：匹配和机翻两条路径共用控制码、变量、换行及表达结构保护与校验；未定义的促音、拖音处理不静默删除，格式破损结果不发布。
  4. **基础检查与异常采集**：记录引擎失败、空译、格式异常及语言相关疑似问题，保存可用上下文、版本和来源，支持重放与最小 JSONL 导出；基础规则不宣称确认了语义误译。
  5. **效果与性能报告**：使用现有引擎对照直接匹配前后效果，分别统计完整译例、发声模板、缓存和机翻回退的覆盖量、人工合格率、请求数与耗时。
- **阶段边界**：独立模型分类从 M2 开始；新增 2~3 款轻量模型的选型作为后续优化，不是 M1 的交付前置条件。M1 的本地资源管理不包含 GitHub 下载和算法动态加载，独立分发按更新项目 U0/U1/U2a/U2b 另行交付，不扩张到整个翻译模块。
- **验收准则（DoD）**：
  - [ ] 外置资源的导入、更新、停用、恢复与新增测试语言可在不改源码、不重新构建的情况下完成；错误包不改变有效版本，版本变化后依赖缓存正确失效。
  - [ ] 已确认的语气词、拟声与纯发声用例能直接得到译文，命中项引擎调用数为 0；混合对白、歧义、未知形式及不支持方向正确回退，各入口行为一致。
  - [ ] 语言对互不串用，人工定稿、受保护导入和删除标记不被匹配或自动纠偏绕过。
  - [ ] 完成一份 3~5 万行脚本的端到端测试，受支持控制码测试集全部通过，检测到的破损译文不发布；重复、停顿、促音和拖音正反例按已定义策略处理。
  - [ ] 注入失败、空译、格式损坏与采集故障可追溯，具备补采或明确缺口记录；未运行分类模型时翻译照常执行。
  - [ ] 固定语料、硬件与配置，提交覆盖率、人工合格率、机翻调用减少量、吞吐、P50/P95、内存和错误率报告，并通过 §9 全部验收；不得只以不含假名判断质量。

### Milestone 2: 独立多维分类引擎与打标闭环（P1）

- **目标**：建立与主流程完全解耦的模型驱动分类管道，完成首批异常文本与高风险文本的自动化结构化打标。
- **核心交付物**：
  1. **分类体系 Schema 固化**：正式固化 7 大维度枚举与 JSON Schema 输出约束。
  2. **独立异步分类任务调度器**：支持离线、增量、批量拉取未打标记录，调用指定分类模型进行多标签打标。
  3. **多标签存储结构设计**：持久化保存包含原文、上下文、多维标签、模型版本、置信度的完整结构。
  4. **首期定向打标验证**：针对 M1 积累的异常库，执行全量自动化打标与准确性验证。
- **验收准则（DoD）**：
  - [ ] 分类服务可作为独立命令行或后台 Job 运行，支持断点续打、重试与速率控制。
  - [ ] 抽样评估 200 条典型发声、情绪对白与异常句子，模型的标签打标合理率（人工判定）≥ 85%。
  - [ ] 分类结果与翻译表解耦存储，翻译结果更新时保留旧标签历史，并按 §3.2 标记依赖旧版本的结果过期。

### Milestone 3: 数据资产化管理与流转体系（P2）

- **目标**：让沉淀的数据“可看、可查、可导、可流转”，为第三方协作与人工微调提供完备工具链。
- **核心交付物**：
  1. **数据检索与多维筛选器**：支持按情绪、声音类型、翻译异常等多维度交叉过滤查询。
  2. **标准化数据导出导入套件**：
     - 导出为标准格式（JSONL / CSV），携带完整上下文元数据。
     - 支持导出为 Prompt-ready 标注模板或第三方大模型修复任务输入格式。
     - 支持外部人工标注/第三方修复结果的结构化二次导入与增量合并。
  3. **数据清洗与去重工具**：仅合并同语言对、同上下文身份与版本的重复采集事件；不同角色、情绪、重复次数的拟声词保留，不全局删重。
- **验收准则（DoD）**：
  - [ ] 能一键导出特定标签集（例如：`声音类型=呻吟/喘息 AND 异常=漏译`）用于分析或外部批量修复。
  - [ ] 外部修改后的 JSONL 经校验、版本冲突预览与显式应用后更新系统；不得自动覆盖人工定稿。
  - [ ] 积累 1,000+ 条可追溯的对齐样本，分别统计未审核与已审核数量；训练可用性另行评估。

### Milestone 4: 知识反哺与场景增强（进阶演进）

- **目标**：将积累的数据资产反哺回翻译系统，不训练全量模型也能显著改善特殊文本表现。
- **核心交付物**：
  1. **动态 Few-Shot 示例检索（RAG 增强）**：基于 M3 沉淀的高分打标对齐样本，在主流程遇到高风险文本时，动态检索 2~3 个同类型优质译例注入 Prompt。
  2. **高频特殊发声/口癖映射表自动生成**：从样本生成待审核候选，经确认后纳入具有语言对和场景约束的外置译文包；不得用于代替模型语义分类或自动套用未审核声音译法。
  3. **微调（SFT / LoRA）训练集自动化生成器**：一键生成符合主流微调框架指令格式的训练/评估集。
- **验收准则（DoD）**：
  - [ ] 特殊发声与语气词在引入动态示例后，在固定留出集上比较增强前后的一次翻译合格率，报告百分点变化及回归项；目标待基线建立后确定。
  - [ ] 成功产出首批可直接供轻量小模型 LoRA 训练的格式化数据集。

### 4.5 现阶段明确暂不纳入的范围（Out of Scope）

为保证前期专注，以下特性暂不在当前交付周期内：

- 全自动复杂文本在线实时二次修正。
- 大规模人工标注与外包审核流程接入。
- 独立端侧分类模型的正式预训练。
- 翻译模型全量参数微调。
- 第三方付费商业翻译 API 的自动化代付流转。

## 5. 双轨系统架构与数据流转

系统严格采用主翻译流程与数据处理流程分离的架构设计：

```text
【主翻译流程（不等待分类或审核）】
游戏文本提取
    ↓
文本预处理 (控制码占位化、标点归一)
    ↓
受保护译文 / 缓存查询 → 外置短语与发声规则匹配
    ├── 命中 → 还原与校验
    └── 未命中 / 歧义 → 现有本地翻译引擎 → 还原与校验
    ↓
确定性质量检测 (启发式规则)
    ├── 正常 ────────────→ 保存译文，继续后续翻译
    └── 失败 / 疑似异常 ──→ 持久化采集事件（携带可用上下文）
                            ↓
【独立数据处理流程 (异步 / 离线 / 资产化)】
待处理数据池 (已译文本 / 异常记录)
    ↓
独立调度器 (速率控制、批处理)
    ↓
模型多维打标 (7 维度多标签识别)
    ↓
结构化存储 (解耦独立存储，避免覆盖译文)
    ↓
多维筛选与格式导出 (JSONL / 外部处理)
    ↓
第三方修复 / 人工审核回填 (M3)
    ↓
动态 Few-Shot 检索 / LoRA 语料沉淀 (M4)
```

## 6. 预期成果与系统愿景

1. **更高效的本地翻译能力**：在低资源消耗下，消除控制码损毁，提高整包游戏吞吐量。
2. **可扩展的游戏文本理解体系**：建立针对对白、语气、情绪、特殊发声的标准多维标签能力。
3. **高复用性本地语料数据资产**：从日常游戏中自发沉淀高价值游戏语料，告别高昂的人工收集成本。
4. **平滑的未来模型迭代通路**：通过从规则到示例增强，再到模型微调的平滑过渡，持续提升复杂发声与口语对白的本地化品质。

## 7. 第一版交付范围

## 8. 多语言与外置译文需求

### 8.1 语言对

- 表现性文本的源语言建设优先级为 **日语 > 英语 > 俄语 > 韩语 > 其他语言**；优先评估各源语言到中文的方向，其他目标语言仍须独立提供资源。该顺序用于资源建设与验收，不是运行时猜测语言或跨语言回退的顺序。
- 使用显式、有向的 `source_language → target_language`；翻转方向不自动反用译文。
- 首批回归覆盖现有 `ja / en / zh / ko / ru` 标识，以 `ja→zh` 为主要质量集，增加 `en→zh` 和 `ja→en` 的端到端用例；机器翻译用例仅在引擎支持时启用，缺失能力必须明确报告。
- 新语言通过数据配置注册。语言标识遵循 BCP 47，保留 `zh` 等历史代码的兼容身份；简繁体和地区变体不静默合并，不把 `zh-Hant` 写到 `zh` 分区。
- 只在历史记录或用户未指定时使用原有默认规则。用户显式传入非法、未知代码必须报错，不能回退为日译中。短句、纯汉字等无法可靠识别时使用游戏配置或要求选择语言。
- 自动检测、分词与质量检查可逐步增加语言能力；不支持的语言不套用日语假名规则。所有引擎输入、缓存查询及返回结果携带语言对。

### 8.2 译文数据与代码分离

- 本作人工译文、共享翻译记忆继续存放在现有翻译存储中。新增术语、固定菜单译文和经确认的特殊译例使用外置数据包，不通过修改函数或重新打包应用添加。
- 应用附带的初始数据包由现有 `GAME_TERMS`、`FIXED_PHRASES`、发声字符映射和 `HONORIFICS` 迁移；保留译文、语言对、别名及纠偏候选信息。代码只负责解析、匹配、保护和冲突处理，不机械继承可能丢失语气的历史规则。
- 包内记录使用稳定 ID、语言对、适用范围、来源和审核状态。支持全局或本作范围；对上下文敏感的译例要求可验证的上下文条件。条件不足则跳过，交给正常翻译流程。
- 完整标签和已确认的完整文本优先；纯发声可使用 §8.5 的受限模板。不将「喘息」「惨叫」等关键词映射当作语义分类，不做普通对白中的任意子串替换。
- 缺少目标译文时正常走现有缓存与引擎流程，不跨语言借用中文，也不依据反向译文推导结果。

### 8.3 动态更新与权威保护

- 第一版支持版本化 UTF-8 JSONL 数据包，经导入入口完成校验、预览、应用。直接编辑导出文件后需重新导入，不监控任意文件变化自动生效。
- 导入预览列出新增、修改、删除、冲突及无效行；默认全包校验通过后原子激活。重复提交同一版本内容不会生成重复记录，同版本不同内容拒绝覆盖。
- 数据包的全局默认条目不能覆盖本作有效定稿；任何自动纠偏不能修改已有人工或受保护导入译文。同范围同条件的异译冲突不自动选一个，保留现有结果或交给引擎。
- 未审核的模型生成结果仅存为候选，不自动成为运行时可用译文。包中自报 `reviewed` 不自动取得人工定稿权威。
- 更新、停用和恢复上一版本均更新版本号并失效依赖缓存。连接中的进程在下次请求前完成版本检查；离线进程使用最后确认快照，重连后同步。
- 已经显式保存的人工译文不随包变更而改写；包派生的运行时结果需带来源和版本，不能伪装成人工或普通无来源导入。

### 8.4 持续采集

每次失败或疑似异常记录样本身份、原译文与版本、语言对、引擎和错误码、检查依据、可用上下文、重试次数及时间。控制码损坏的译文作为候选保留，禁止用于渲染或有效缓存。

主流程不等待分类。采集成功需有持久化回执；队列满、写盘失败时记录任务的采集不完整状态和可重放游标，不能静默丢弃或宣称全部采集成功。本版以异常优先采集，后续分类任务可通过快照增量读取全量文本。

### 8.5 表现性文本的直接翻译

第一阶段采用「外置数据 + 代码匹配」优先策略，沿用现有机翻作为未覆盖文本的回退，不要求先接入新模型或先分类再翻译。

统一将语气词、感叹词、角色发声及拟声拟态表达称为「表现性文本」；重复、拖音、停顿、结巴属于表达特征。游戏术语和普通对白分别管理。

1. **完整表达优先**：将已确认的短语、语气词、喘息、哭声、惨叫和环境音效等以完整译例保存，按语言对及必要场景条件匹配。类别描述用于组织资源，不等于代码产生了语义分类标签。
2. **纯发声模板补充覆盖**：没有完整译例时，允许按已审核的音节映射、重复与拖音模板生成译文。仅对整条满足限定形式的文本启用；模板所用音节、目标字形和变体均外置，不能见到假名就逐字转换。
3. **保留表达结构**：重复、停顿、促音、拖音、疑问和控制码需要明确的还原策略；不能沿用旧规则直接删除促音或称呼。尚未定义或无法无损处理时，跳过匹配。
4. **混合对白回退**：如 `はぁ……もう歩けない` 这样的完整对白，不能整句套发声字符表；`えっ？` 等存在多种译法的短句优先使用已确认译例，无法消歧则走现有引擎。
5. **语言对独立**：日中音节规则不用于日英或其他方向。新目标语言可以增加完整译例和已支持模板的数据，不要求改匹配代码；没有该方向资源时正常回退。
6. **可解释与可统计**：结果记录资源条目、匹配方式和版本，分别统计完整短语命中、发声模板命中、歧义跳过及引擎请求数；不把「未调用模型」等同于译文正确。
7. **标点与数量变体**：匹配副本可按资源明确声明的策略解析 `...`、`.........`、`…`、`……`、连续 `! / ！`、逗号及重复发声，保留原始片段、数量和位置。完整译例先匹配，再尝试结构模板；不全局删除标点或压缩重复。输出按声明策略还原，未定义的变体回退引擎。
8. **按语言配置模板**：共享解析、重复计数和标点处理机制，各源语言独立配置单元、别名、边界和允许的修饰。英语不逐字母转中文，俄语不套拉丁字母近形匹配，韩语不套假名映射。新增语言能以现有模板表达时只加数据；需要新结构时再扩展代码，不承诺所有语言均可只靠资源覆盖。

M1 优先完成日语资源和质量验证，随后按上述顺序扩充英文、俄文、韩文资源。各语言独立报告正反例、命中率及人工合格率；尚未验证的模板保持禁用，注册或完整译例可用不等于该语言的模板已经完成。

## 9. 第一版验收与评估口径

1. **数据驱动扩展**：不改 TS/Swift、不重新构建，注册一个测试语言并导入对应目标译文；查询、导出和缓存均使用正确语言对。未支持该方向的引擎返回明确能力提示。
2. **语言隔离**：同原文在 `ja→zh`、`ja→en`、`en→zh` 下互不串用；`zh` 与 `zh-Hant` 分开；显式未知代码、反向方向、缺少目标条目覆盖测试。
3. **热更新闭环**：完成预览、应用、重复导入、更新、停用和恢复上一版本；错误包不改变当前有效版本；连接进程下次请求使用新快照，旧版本派生结果不重新覆盖新译文。
4. **权威保护**：本作人工定稿、受保护导入、删除标记均不被包或自动纠偏绕过；两个包的等条件异译保持冲突可见。
5. **格式与采集**：受支持控制码集合含重复变量、换行、空白和 Ruby 等现有格式；注入空译、引擎超时、控制码损坏、写盘失败及任务重启，可确认拦截、记录或补采。重复音节和合法同文译文不被强制清除。
6. **性能**：固定硬件与配置，使用同一份 3–5 万行脚本，区分冷/热缓存；至少重复 3 次。记录吞吐、端到端 P50/P95、峰值内存、失败率及采集积压。相对现行流程，新增数据查询与采集开销导致的吞吐下降不超过 5%、P95 增长不超过 10%；未达到时记录瓶颈，不能以关闭采集作为通过。
7. **质量**：冻结至少 200 条含普通对白、特殊发声、菜单与格式文本的评估集，报告各类人工合格数和总合格率。新默认模型须总体不低于现行基线、特殊文本合格率提升且格式保护全部通过；不满足则保留现行默认模型。未测试的语言不继承日译中的质量结论。
8. **交付证据**：保存模型与量化配置、语言能力矩阵、数据包样例、迁移/恢复记录及性能质量对照报告。本文约定目标，不表示上述能力已经实现。
9. **直接匹配**：冻结短语、语气词、纯发声及混合对白正反例集。符合规则且不被有效定稿覆盖的命中项，引擎调用数为 0；混合对白不整句音节替换，未定义变体和不支持方向回退。报告现有基线、完整匹配及模板各自的人工合格率、覆盖率与机翻请求减少量，不以扩大误匹配换覆盖率。

2. 数据与算法分别发布：资源包提供译文与受限模板声明；匹配能力包提供表现性文本匹配算法。改词条不重下算法，改兼容算法不重装 App。
3. 首次使用随应用附带的基础算法和资源；已有内容不重复下载。离线、GitHub 不可达或新版失败时继续使用本地可用组合。
4. 不把整个翻译服务下载化：调度、引擎调用、缓存、存储、保护和校验、采集及提取回写留在宿主。
5. 一次任务固定算法与资源组合，下一批才启用新版。算法版本、资源版本和来源可追溯，派生结果不能因只比较资源版本而误用旧算法缓存。
6. 算法通过稳定接口接收原文、明确语言对及必要上下文，返回命中或未命中。宿主验证结果并掌握回退，算法不得绕过人工定稿和格式保护。
7. 已有用户需要一次含能力加载器的新 App。此后符合协议与运行环境要求的资源和匹配算法可独立更新；不兼容宿主变更仍更新 App。

验收分别对应更新 U2a/U2b：实际从 GitHub 安装两个数据版本及两个算法版本，验证无整 App 更新、无 Vercel 转发、已有内容不重下、旧任务组合保持、下一批切换、失败恢复、缓存正确性及匹配性能。该验收不替代本文 §9 的翻译质量验收。
