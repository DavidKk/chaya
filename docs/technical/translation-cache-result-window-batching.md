# 翻译缓存结果窗口跨分片聚合技术方案

- 状态：技术方案草案，待评审；尚未实施。
- 日期：2026-10-26。
- 需求：[翻译缓存结果窗口跨分片聚合优化需求](../translation-cache-result-window-batching.md)。
- 关联设计：[缓存快照、批次与回填版本链](translation-cache-optimization.md#11-缓存批次快照回填与用户日志2026-10-25)、[非阻塞缓存扫描与翻译派发](../translation-scheduling.md#14-非阻塞缓存扫描与翻译派发2026-10-23)。
- 适用范围：后台 seed 补译的纯缓存结果窗口。缓存优先预取、32 项扫描分片、真实引擎批量和回填持久化契约保持原样。

## 1. 结论

需求成立，但根因不是“每批只能查 12 个字符”，而是结果窗口的提交条件把扫描分片的结束误当成了结果批次的结束：

```ts
const cacheShardSettled = cacheBatchDoneSeq > cacheDoneAtStart && completed.length === 0
if (selected.length > 0 && window.cacheOnly() && cacheShardSettled) break
```

`cacheShardSettled` 只说明当前 32 项分片已收尾，且瞬时 `completed` 为空；它不说明没有下一分片、待扫描任务或 `RECHECK`。当 worker 先返回 1 条命中、其余项稍后返回时，`fill()` 会立即提交这个 1 条窗口。下一次调用再从剩余任务开始，于是形成大量 1～3 条日志批次。

修复方向是**跨分片装满结果窗口**，而不是把全部待译文本一次性交给真实引擎。结果窗口沿用 40 项 / 10,000 字符容量；达到容量、出现真实引擎结果或进入终止状态时提交。只有真正没有可继续的缓存工作时，才允许用 250ms 静默窗口收口。

## 2. 当前调用链

### 2.1 三层不同节奏

| 层级     | 当前实现                                            | 职责                             | 不应被谁限制                          |
| -------- | --------------------------------------------------- | -------------------------------- | ------------------------------------- |
| 扫描分片 | `CACHE_SHARD = 32`，同一时间一个在途                | worker IPC、查询和反压单位       | 不应决定活动日志批次                  |
| 结果窗口 | `createResultWindow()` 选择本轮 `fill()` 返回的条目 | 主线程提交、日志和作业层观察单位 | 不应继承真实引擎的 4～40 项自适应预算 |
| 引擎批次 | `cap()` 与 `maxChars` 控制真实引擎派发              | 控制真实请求耗时和并发           | 不应限制纯缓存结果装载                |

`fill()` 每次返回一个结果窗口。`seed-job-runtime` 根据 `result.items` 写一条活动日志；因此结果窗口过早收口，会同时放大日志、回填 flush、状态持久化和下一轮调度的固定成本。

### 2.2 纯缓存结果如何到达

1. `cacheNext()` 从 `cachePending` 和 `recheckQueue` 领取最多 32 项，加入 `cacheInFlight` 后交给 worker。
2. `onResult()` 校验缓存结果；完整命中调用 `finish()`，把条目放入 `completed` 并立即更新内存进度。
3. `finish()` 只在 `completed` 达到当前 `cap()` 或任务结束时唤醒等待者，否则启动一个 250ms 唤醒定时器。
4. `fill()` 用 `createResultWindow()` 从 `completed` 取结果；`onItem()` 在窗口取走条目时调用。纯缓存窗口允许到 40 项，字符上限为 10,000。
5. 当前代码在 `onBatchDone()` 后看到 `completed.length === 0`，就可能提交已选纯缓存结果。

### 2.3 提前退出的精确缺口

`cacheBatchDoneSeq > cacheDoneAtStart` 是“本窗口期间至少有一个分片完成”的序号判断，不是“缓存工作已耗尽”。`completed.length === 0` 只表示主线程此刻没有尚未取走的完成项；worker 仍可能处理下一分片，`scanCursor` 仍可能未到末尾，`recheckQueue` 仍可能有任务。

因此当前条件会错误覆盖以下情况：

- 当前分片只先返回 1 条完整命中，其余结果尚未到达；
- 当前分片结束后，下一分片已具备领取条件；
- 还有 `RECHECK` 等待重新扫描；
- 仍有 `UNKNOWN` 任务尚未扫描；
- 缓存 worker 仍健康，只是当前微任务队列暂时为空。

这不是缓存查询慢，而是结果消费者在错误的时间点收口。

## 3. 目标状态机

### 3.1 窗口状态

建议把结果窗口的收口逻辑显式建模为以下状态，实际可以用函数和局部变量实现，不要求新增持久化状态：

| 状态       | 含义                                                 | 是否继续装载     |
| ---------- | ---------------------------------------------------- | ---------------- |
| `OPEN`     | 已有结果，未达到容量，缓存工作仍可能继续             | 是               |
| `FULL`     | 达到 40 项，或加入下一条纯缓存结果会超过 10,000 字符 | 否，立即提交     |
| `MIXED`    | 出现真实引擎结果，或窗口不再满足 `cacheOnly()`       | 否，立即提交     |
| `DRAINING` | 工作已耗尽，等待 250ms 静默窗口确认没有新结果        | 仅吸收已到达结果 |
| `CLOSED`   | 已提交或会话终止                                     | 否               |

`DRAINING` 是唯一允许“已有结果但暂不提交”的非容量状态；它必须有截止时间，不能无限等待。

### 3.2 工作耗尽谓词

`cacheWorkExhausted()` 必须同时满足以下条件：

```ts
const cacheWorkExhausted = () =>
  !paused && !closed && cacheAvailable && cachePending.size === 0 && cacheInFlight.size === 0 && recheckQueue.length === 0 && scanCursor >= states.length
```

实现时还须确认以下边界：

- `completed` 为空不能单独作为耗尽证据；应先由 `window.take(completed)` 消费当前结果。
- `cachePending` 包含已进入缓存优先窗口但尚未投递 worker 的任务；不能只看 `cacheInFlight`。
- `scanCursor >= states.length` 只说明没有新的稳定游标可领取；已存在的 `RECHECK` 和待重试项仍算未耗尽。
- `WAIT_CACHE` 是已结束本轮引擎尝试、等待缓存兜底的独立任务状态，不是缓存扫描工作。它不阻塞当前纯缓存窗口收口，但必须保持未完成，由后续会话继续处理；不得因谓词成立而把它当成 `DONE` 或 `FAILED`。
- `active.size > 0` 引擎在途与纯缓存窗口：当 `window.cacheOnly()` 且 `cacheWorkExhausted()` 成立时，纯缓存窗口不应被慢引擎长连接阻断；250ms 静默窗口到期后应正常提交纯缓存结果并释放进度，在途引擎任务保留在后台并在后续轮次收口，防止个别慢引擎拖死整个纯缓存吞吐。
- `cacheAvailable === false` 属于终止/降级路径，不进入正常 `DRAINING` 等待。
- 会话暂停或关闭时直接走终止提交，不等待 250ms。
- 若后续引入独立的缓存工作队列，必须把该队列纳入同一谓词，不能只补一个新集合而遗漏其他入口。

建议把该谓词做成单一函数，并在以下事件后重新求值：`onResult`、`onBatchDone`、`onItemError`、`cacheNext` 改变状态后、`releaseToEngine`、暂停和关闭。

### 3.3 提交优先级

窗口按以下优先级收口：

1. `MIXED`：出现真实引擎结果，或窗口已包含非纯缓存结果。
2. `FULL`：达到 40 项，或已无法继续装入更多条目（`chars >= 10,000` 或下一条会超过 10,000 字符）。
3. 终止：暂停、取消、关闭、缓存线路不可用或任务完成。
4. `DRAINING`：工作耗尽后连续 250ms 没有新结果。
5. 安全上限：已有结果且窗口打开满 5 秒，强制提交并记录原因。

**驱动机制与唤醒定时器（Wake-up Timers）**：

主循环等待依赖 `resolveWait` 与 `notify()`。当工作真正耗尽（`cacheWorkExhausted()`）且无新事件时，Worker 与引擎均不会再触发事件，系统不能陷入永久等待。必须由状态机主动调度定时器：

- `drainTimer`：当判定 `cacheWorkExhausted() && selected.length > 0` 成立时启动 250ms 静默定时器调用 `notify()`；若期间有新缓存结果到达，则重置或清理该定时器。
- `safetyTimer`：窗口打开时启动 5 秒兜底定时器调用 `notify()`，防止任何意外阻塞。
- 窗口收口提交时清理所有局部定时器，防止定时器泄漏。

第 5 条只防死锁，不是正常批次策略。若 5 秒内仍持续有结果进入但未达到容量，优先继续装载；只有窗口无法继续推进或没有新的工作事件时才触发安全上限。实现需要区分“窗口存活时间”和“最后一条结果时间”，避免健康的大窗口被固定时间粗暴截断。

## 4. 容量与装载规则

### 4.1 纯缓存窗口

- 条数上限：40 项。
- 字符上限：10,000 个源文 Unicode 码点。
- 达到任一上限：立即提交。
- 下一条加入后会超过字符上限：保留该条给下一窗口，窗口视为已满并立即提交当前窗口。`result-window.ts` 的 `full()` 需涵盖字符容量与因超限无法继续装入的边界。
- 单条自身超过 10,000 字符：允许作为单独窗口提交，并记录 `oversized-single-item`。
- 纯缓存窗口不读取真实引擎的 `cap()`、初始 4 项或 3,000 字符预算。

### 4.2 混合窗口

真实引擎结果出现后立即提交当前窗口，不为纯缓存容量等待。混合窗口的条数和字符统计按实际任务条目计算；真实引擎批次预算不变。

### 4.3 去重与计数

结果窗口聚合只改变提交时机，不改变以下语义：

- 同一窗口内相同查询键仍只查询和回填一次；
- 相同原文 fan-out 到多个任务条目时，完成计数仍按任务条目；
- `total`、`success`、`failed`、`chars`、`cacheHits` 仍由窗口条目计算；
- 一个已提交窗口对应一条活动日志批次；
- 回填去重键继续使用 `(root, src, record_id, revision)` 等现有身份，不按窗口序号去重。

## 5. 进度与提交解耦

当前 `finish()` 已在结果进入 `completed` 时更新内存 `progress`；`fill()` 取走结果时再调用 `onItem()`，让作业层更新速率与检查点。这一分工必须保留：

- 第一条缓存结果到达后，内存中的已完成数量和剩余字符即可更新；作业层通过现有 250ms 唤醒或窗口取走结果获得速率样本和检查点回调；
- `onItem()` 可以按现有 250ms 节流持久化，不要求等到窗口提交；
- 活动日志、最终 `result.items`、批量回填 flush 和作业轮次统计仍按已提交窗口生成；
- 不得为了聚合窗口而把 `onItem()` 推迟到 40 条之后。

换言之，“首批可见”与“首批提交”是两个不同契约。前者保持即时，后者按容量和工作状态决定。

## 6. 回填、持久化与失败恢复

每个已提交结果窗口执行一次批量回填和状态检查点：

1. 窗口选择完成后，把窗口内所有 `records` 去重合并到 `pendingBackfill`。
2. 调用一次 `queueBackfill()`。
3. 调用一次 `flushBackfill()`；失败时保留待办并按现有重试语义处理。
4. 作业层在窗口返回后写一条批次日志并持久化汇总进度。

`onItem()` 的 250ms 检查点仍可独立发生，因此“窗口未提交”不等于“进度未持久化”。正常暂停、结束和退出继续执行 flush；异常退出允许待回填任务恢复后重试，不能把已排队报告为已回填。

窗口聚合不得绕过 `authorityVersion`、文件 stamp、owned transition、共享 revision、人工译文保护或来源权重。若窗口内任一条结果校验失败，按现有规则拒绝该条，而不是拒绝整个窗口或放宽校验。

## 8. 诊断

窗口级诊断默认不进入用户活动日志。至少记录：

| 指标                                                         | 说明                                                                                                                                             |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| `windowId`                                                   | 本次结果窗口的单调序号                                                                                                                           |
| `windowStartedAt` / `windowClosedAt`                         | 窗口生命周期                                                                                                                                     |
| `windowCloseReason`                                          | `full-items`、`full-chars`、`oversized-single-item`、`mixed-engine`、`paused`、`closed`、`cache-unavailable`、`work-exhausted`、`safety-timeout` |
| `windowItems` / `windowChars`                                | 实际提交条数和源文字符数                                                                                                                         |
| `cacheOnly`                                                  | 提交时是否为纯缓存窗口                                                                                                                           |
| `completedShards`                                            | 窗口期间完成的分片数                                                                                                                             |
| `lastResultToCloseMs`                                        | 最后一条结果到窗口提交的时间                                                                                                                     |
| `pendingCacheAtClose` / `inFlightAtClose` / `recheckAtClose` | 提交时是否仍有缓存工作                                                                                                                           |
| `backfillFlushMs` / `persistMs` / `logMs`                    | 固定开销分段                                                                                                                                     |
| `windowSourceCharsPerSecond`                                 | 按端到端窗口耗时计算的吞吐                                                                                                                       |

提交原因必须是单一枚举，不能只记录“没有更多就绪项”这类无法区分工作耗尽和瞬时空数组的文本。

## 9. 测试矩阵

### 9.1 单元测试

1. 32 项分片先返回 1 条完整命中，分片随后返回剩余命中：窗口继续装载，直到 40 项或工作耗尽。
2. 三个连续 32 项分片全部命中：形成 40 / 40 / 16 等容量窗口，而不是按分片返回节奏拆成小窗口。
3. 当前分片 `done` 且 `completed` 瞬时为空，但 `scanCursor` 未到末尾：不得提交已有结果。
4. `cachePending`、`cacheInFlight`、`recheckQueue` 任一非空：不得判定工作耗尽。
5. 工作真正耗尽后，250ms 内没有新结果：提交现有窗口。
6. 工作耗尽但 250ms 内又到达新结果：取消静默提交，继续装载。
7. 达到 40 项或 10,000 字符：立即提交。
8. 单条超过 10,000 字符：单独提交并记录原因。
9. 纯缓存窗口中出现真实引擎结果：立即提交混合窗口。
10. 暂停、关闭、缓存线路失败：提交已有结果并停止领取新缓存工作。
11. `WAIT_CACHE` 非空不阻止当前窗口收口，但对应任务保持未完成，不能在进度中计为成功或失败。
12. 首条结果进入 `completed` 后，内存进度立即变化，`onItem()` 最多经过一个现有 250ms 唤醒周期被调用，但窗口尚未提交；日志和批量回填仍只在提交时发生。

### 9.2 集成测试

使用真实打包 cache worker 和模拟翻译适配器，至少覆盖：

- 96 条热缓存命中跨 3 个分片，验证窗口条数、日志条数、回填 flush 次数和引擎提交数为 0；
- 先命中 1 条、随后命中大量条目，验证不会产生 1 条日志批次；
- 工作耗尽后的 250ms 静默提交，验证没有无限等待；
- 混合窗口中缓存和 Apple / Agent 结果只完成一次计数；
- 人工修改与回填并发，旧缓存结果仍被拒绝；
- 暂停恢复、worker 重启和旧租约 `done` 不影响新窗口。

### 9.3 性能基准

固定语料、硬件、共享索引和构建，至少回放 100,000 个源字符。分别报告冷启动和热态，热态吞吐以窗口端到端耗时为分母，不以 SQL 查询耗时替代。验收指标见需求 §7.3。

## 10. 实施顺序

1. **P0：修正收口条件**
   - 新增 `cacheWorkExhausted()`；
   - 删除 `cacheShardSettled` 作为纯缓存窗口提交条件；
   - 增加 250ms 静默窗口和 5 秒安全上限；
   - 保持混合窗口、暂停和缓存故障的立即提交。
2. **P0：保持进度与提交解耦**
   - 保留首条结果到达后的现有 250ms 唤醒，不把 `onItem()` 推迟到窗口提交；
   - 确认检查点不依赖窗口提交。
3. **P1：窗口诊断**
   - 记录关闭原因、最后结果到提交的时间、提交时剩余工作；
   - 区分窗口条数、字符数和分片数。
4. **P1：回归与回放**
   - 增加跨分片、静默窗口、混合窗口和终止状态测试；
   - 对比修复前后的窗口数量、平均条数、字符数和端到端吞吐。
5. **P2：参数调优**
   - 根据基准调整 250ms 静默窗口和 5 秒安全上限；
   - 不增加普通用户配置。

## 11. 风险与回滚

- 若只删除 `cacheShardSettled` 而不增加工作耗尽判定，窗口可能无限等待；必须同时实现静默窗口和安全上限。
- 若只扩大 32 项分片，IPC 和查询反压会变差，且不能解决结果窗口提前收口。
- 若把全部缺失项一次性交给真实引擎，会放大长尾和失败面；本方案明确不这样做。
- 若窗口聚合阻塞真实引擎结果，混合任务体验会下降；出现引擎结果必须立即提交。
- 若为吞吐跳过回填、持久化、人工保护或 revision 校验，结果不可接受。
- 回滚时应恢复原窗口收口逻辑，但保留诊断指标和正确性测试；不能用关闭测试或删除日志来掩盖回归。

## 12. 不变量

1. 一个连续 seed 作业可以包含多个内部结果窗口，窗口不是用户手动发起的独立翻译任务。
2. 扫描分片、结果窗口和引擎批次是三个独立预算。
3. 纯缓存窗口最多 40 项、10,000 个源文字符。
4. 真实引擎结果、暂停、取消、关闭和缓存线路失败可以提前结束窗口。
5. “没有更多就绪项”必须由工作耗尽谓词证明，不能只看瞬时结果数组。
6. 首条结果可以立即更新进度，但日志和批量提交按窗口发生。
7. 窗口提交执行一次批量回填和状态检查点，不改变既有恢复语义。
8. 任何性能优化不得绕过权威版本、revision、人工保护、去重或失败恢复。
