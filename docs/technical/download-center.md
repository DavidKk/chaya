# 下载中心（右上角统一下载管理）需求

> 状态：**已实施**（已按部署平台 CR，见 §9；决策见 §10）。`deployment-optimization.md` 的 O3 / O4 已并入本文；技术方案见 [`download-center-design.md`](./download-center-design.md)。

## 1. 背景与目标

现在「下载 / 升级 NW.js」「浏览器模式装壳」都是同步阻塞：服务端请求要等下载、解压、安装全部完成才返回，期间确认弹窗关不掉；浏览器模式装壳则锁住整张游戏卡片。下载没有进度，失败后只能从头再下。

目标：

1. 右上角固定一个**下载中心**，所有由应用管理且能观测状态的异步下载统一在这里展示，可以同时容纳多个任务。交给终端或浏览器原生下载、应用无法观测的任务明确排除。
2. 触发按钮显示简短摘要；下拉框列出每个任务的进度、阶段和操作。
3. 下载放到后台，不阻塞页面其它操作。
4. **尽量支持断点续传**（参照 bash 脚本的 `.part` + `curl --continue-at -`）；目标不支持的就明确不支持。

不在范围内：macOS 的 bash 安装命令（终端自带进度与续传）。

## 2. 两种下载通道

只有两种，按当前服务形态二选一：

| 通道             | 适用                                     | 谁执行下载                  | 进度来源               | 刷新页面后                                     |
| ---------------- | ---------------------------------------- | --------------------------- | ---------------------- | ---------------------------------------------- |
| **服务端任务**   | 能写盘的模式（`canUseDisk`：本地 / App） | Node 进程后台下载到 `data/` | **SSE 推送**           | 任务继续，重新连接后恢复显示                   |
| **浏览器内任务** | 浏览器模式（Vercel 等）                  | 当前页面自己处理            | 页面内存（不经服务端） | 任务状态丢失；已完成的部分保留，重新发起会续上 |

edge 构建不包含服务端下载接口，页面在浏览器模式下也不连 SSE。同一个页面只会启用一种通道（dev 切换器切换会整页刷新）。

## 3. 服务端任务

### 3.1 任务模型

进程内注册表（`services/downloads/jobs.ts`）。同一种类同时只跑一个，重复发起直接返回正在跑的任务。结束的任务保留 1 小时、最多 20 条，用于页面重连时补发结束提示（下载中心只展示进行中的任务）。用户不能取消或移除任务：下载中心只是告诉用户当前有东西在下载，不是下载器。

服务端任务下载的是所有游戏共用的壳，不属于某个游戏，任务上不显示游戏名。

```ts
type ServerDownloadJob = {
  id: string
  kind: 'nw-shell' // 以后的下载在这里加种类
  status: 'running' | 'done' | 'error' | 'canceled'
  phase: 'resolve' | 'download' | 'extract' | 'install'
  version?: string
  receivedBytes?: number
  totalBytes?: number // 来自 Content-Length / Content-Range，可能缺失
  resumedFrom?: number // 本次从多少字节续传，0 表示从头
  error?: string
  startedAt: number
  finishedAt?: number
  result?: Record<string, unknown>
}
```

标题和阶段文案由前端按 `kind` / `phase` 本地化，服务端不下发展示文本。

### 3.2 接口

| 接口                                                   | 行为                                                                                                                     |
| ------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------ |
| `POST /api/shell { fetchLatest: true }`                | 启动后台任务，立即返回 `202 { job, reused }`；已有运行中的任务时 `reused: true` 并返回它                                 |
| `POST /api/shell { fetchLatest: true, wait: true }`    | 等任务结束再返回结果（给 MCP 这类不会订阅进度的调用方，保持原有同步语义）                                                |
| `GET /api/downloads/stream`（SSE）                     | 连接时推 `snapshot`（全部任务），之后任务变化推 `job`，15 秒一次 `ping` 保活                                             |
| `GET /api/downloads`                                   | 一次性列表（给不能用 SSE 的调用方，例如只有 Bearer 的脚本；以及测试）                                                    |
| `POST /api/shell { shellSource }`、`DELETE /api/shell` | NW.js 任务运行中返回 `409 SHELL_JOB_RUNNING`，避免和后台安装同时改 `data/shell`（界面已禁用按钮，这里防 MCP / 其它页面） |

进度推送节流：同一任务最多每 250 ms 推一次，阶段变化和结束立即推。鉴权沿用 `defineApiRoute`：需要管理 Cookie（`EventSource` 不能带自定义请求头，和日志 SSE 一样靠 Cookie）；游戏的 launch token 不在放行名单里，读不到下载列表。

**页面何时连 SSE**：`BUILD_TARGET !== 'edge'`，且首次 `/api/status` 已返回 `canUseDisk = true` 才连接。dev 切换器切换后整页刷新，挂载时判断一次即可。不能只看 `GameLinkProvider` 的 `browserMode`：它首次拿到状态前默认是 `false`，edge 构建会白白请求一个 404。

**后台标签页断开 SSE**：本地服务是 `http://localhost`（HTTP/1.1），浏览器对同一主机最多保持 6 个连接；每个标签页一条下载 SSE、日志页再一条，开几个标签页就会把连接占满，其它请求卡住。所以标签页隐藏时关闭 SSE，重新可见时重连，靠首帧快照补齐期间的变化（含任务结束提示）。

### 3.3 断点续传（对齐 bash）

| 情况                                                                                                   | 处理                                                                                                                                                                            |
| ------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 开始下载时已有 `<zip>.part`                                                                            | 带 `Range: bytes=<已有大小>-` 请求                                                                                                                                              |
| 返回 `206`                                                                                             | 追加写入 `.part`，进度从已有大小起算，`resumedFrom` 记录起点                                                                                                                    |
| 返回 `206` 但 `Content-Range` 缺失或非法（未带 Range 却收到 206 时，起点必须为 0，否则同样按非法处理） | 不追加（会拼坏文件）：删除 `.part`，不带 Range 从头请求一次。起点必须等于 `.part` 大小，结束不得小于起点，总长必须大于结束                                                      |
| 返回 `200`（源站不支持 Range）                                                                         | 清空 `.part` 从头下载（不支持就不续传）                                                                                                                                         |
| 返回 `416`                                                                                             | 必须解析 `Content-Range: bytes */<总长>` 且 `.part` 大小等于总长，才可能已完整；有校验值则再校验。缺失或长度不等时删除 `.part` 并不带 Range 从头请求一次                        |
| 网络错误 / 60 秒无数据                                                                                 | **保留 `.part`**，任务标记失败；重新下载即续传                                                                                                                                  |
| 流结束但字节数少于总长                                                                                 | 保留 `.part`，报"下载不完整"；重新下载即续传                                                                                                                                    |
| 下载完成                                                                                               | 校验：有 `SHASUMS256.txt` 时比对 SHA-256，没有则以解压成功为准；不通过删除 `.part` 并报错                                                                                       |
| 校验通过                                                                                               | `.part` 改名为压缩包 → 解压 → 删除压缩包（现有逻辑）                                                                                                                            |
| 解压被中止（服务内部中止）                                                                             | 只删除解压目录，**保留压缩包**，重新下载时直接解压                                                                                                                              |
| 解压失败（非中止）                                                                                     | 删除解压目录；压缩包**没经过 SHA-256 校验**的一并删除（否则下次跳过下载、反复解压同一个坏包）；校验过的保留（这时失败多半是环境问题，如缺 `unzip`、磁盘满），提示里带上原始错误 |
| 已有同版本解压结果                                                                                     | 跳过下载和解压，直接进入安装（现有逻辑）                                                                                                                                        |
| 已有完整压缩包（上次解压被中止）                                                                       | 有校验值则先校验，通过直接解压，不符删除后重新下载                                                                                                                              |

- 实测（2026-10-03，v0.117.0，用 `curl` 验证）：`dl.nwjs.io` 302 跳到 `dl.node-webkit.org`，带 Range 返回 `206` + `Content-Range: bytes 100-199/215951728` + `Accept-Ranges: bytes`；`SHASUMS256.txt` 同样经跳转可取，含三平台包的 SHA-256。Node `fetch`（undici）跨域跳转只去掉凭据类请求头，Range 应保留；实施时用一次真实请求确认，不成立就改为手动跟随跳转并重带 Range。
- 总大小：`206` 取 `Content-Range` 的总长，`200` 取 `Content-Length`。
- 版本清单和校验值请求同时受任务的中止信号（服务内部使用，界面不提供取消）与各自超时控制。校验值从 `https://dl.nwjs.io/<版本>/SHASUMS256.txt` 按文件名匹配；取不到或没有该文件时不阻塞下载，退回"以解压成功为准"。
- `.part` 路径按版本区分（`data/shell-cache/<version>-<fileKey>/`），同一版本的包不会变，不额外做 `If-Range`，内容不符由 SHA-256 兜底。
- 进程重启 / App 退出任务会丢失，但 `.part` 留在磁盘上，重新发起即可续传。**不再**在启动时清理 `.part`（覆盖 O3 原设计）。
- 安装成功后，删除 `shell-cache` 下**其它版本**残留的 `.part` 和压缩包（每个约 200 MB）；各版本的解压目录维持现状不动。
- 假设同一 `data/` 目录只有一个服务进程在用（App 用独立的 `userData`）。同一目录起两个本地服务同时下载不在支持范围内。
- 任务中止时结束解压子进程（`spawn` 传 `signal`，Windows 为 PowerShell `Expand-Archive`）。

### 3.4 安装：暂存后整体替换

现有 `installShell({ force: true })` 先 `rmSync` 删除 `data/shell/<壳>` 再复制。后台下载要好几分钟，期间用户可能已经启动游戏；Windows 上被占用的文件删不掉，壳会只删掉一半而损坏。改为：

0. 安装、启动、读取状态前都先执行恢复检查：如果正式目录不是可用壳（不存在、失效符号链接或残缺目录）而 `.<壳名>.old` 是可用壳（上次替换或回滚中途进程退出），先把占位的正式路径挪开，再把 `.old` 改回正式目录；恢复失败则报错并保留 `.old`，不继续安装或启动。恢复必须在**解析游戏状态之前**执行：启动接口先看"是否已装壳"，正式目录缺失时会直接返回"尚未安装壳"，走不到后面的重链步骤。
1. 复制新壳到同级暂存目录 `data/shell/.<壳名>.staging`（macOS 在暂存目录里建好 `app.nw` 链接）。
2. 旧壳整体改名为 `.<壳名>.old`。Windows 上游戏正在运行时这一步会失败（`EPERM` / `EBUSY`），此时删除暂存目录，旧壳原样保留，任务失败并提示"游戏正在运行，退出后重新下载"。
3. 暂存目录改名为正式目录；失败则把旧壳改名回来。如果回滚也失败，保留 `.old` 和恢复路径，任务报错；下次安装、启动或读取状态时按第 0 步恢复。
4. 只有正式目录是可用壳时才删除 `.old`（失败不影响已安装结果，下次安装再清理）。`.staging` 可在下次安装开始时直接清理，`.old` 不可在正式目录缺失时盲目删除。

- 改名在同一目录内完成，单次改名是原子操作；正常失败路径会回滚到旧壳。极端情况下回滚也可能失败，此时依靠保留的 `.old` 和安装 / 启动 / 读取状态前恢复，不承诺跨多步的绝对原子性。
- macOS / Linux 运行中也能改名，正在运行的游戏继续使用旧文件，下次启动用新壳。
- Windows 刚复制完的文件可能被杀毒软件短暂占用：改名失败时间隔 200 ms 重试 3 次，仍失败再报错。
- 不用心跳在线检测（`getGamePresence`）做前置判断：它只记一个"当前游戏"、15 秒心跳窗口，刚启动未发心跳的游戏查不到，远程连入的游戏也会被误判为占用。
- 这一改动在 `services/game/shell.ts`，所有装壳路径（手动指定壳源、下载最新版、MCP）都受益。
- 整个替换（复制 + 两次改名 + 重试等待）在服务进程里**同步执行**，同一进程的启动、状态请求不会插在中间，所以不存在"正式目录短暂缺失时被启动"的情况，也不需要加锁。只有进程在替换中途崩溃才会留下待恢复状态，由第 0 步处理。
- "存在"分两种判断：路径是否被占用（用 `lstat`，失效符号链接也算占用，用于改名前挪开）；是否是可用壳（能找到壳可执行文件，用于决定是否恢复、能否删 `.old`、是否已装壳）。正式路径是失效链接而 `.old` 可用时，必须恢复，不能当作"已存在"跳过。
- **顺带修复现有缺陷（Linux）**：`installShell` 与启动前的 `ensureShellLinkedToContent` 只判断"是否 Windows"，Linux 被当成 macOS 去找 `Contents/Resources`，复制完壳后报"壳结构异常"，启动也会失败。Linux 和 Windows 一样由启动参数传内容根（`services/platform/host/linux.ts`），不需要 `app.nw`；改为只有 macOS 建 `app.nw` 链接。

### 3.5 页面行为

下文按钮名以游戏卡片壳菜单（「更多」）为准：

- 「安装壳」/「卸载壳」：按当前游戏状态二选一，没装壳显示安装（用设置里的壳源），装了显示卸载。
- 「下载最新壳」/「更新壳」：本方案的后台任务，下载到工具共用的 `data/shell`，与当前游戏是否装壳无关，**Local 模式下一直显示**（游戏自带壳也显示）；检测到新版本时文案变为「更新壳」；已比对过版本且当前壳就是最新时显示「已是最新壳」并置灰；打开菜单后首次检测出结果前显示转圈 +「正在检测」并置灰（之后每 3 秒的复检保留上次结果，不再闪回检测中）；未装壳或检测失败时为「下载最新壳」。游戏运行中置灰。

- 确认弹窗点「下载并升级 / 下载并安装」后**立即关闭**，任务出现在下载中心并自动展开一次；请求本身失败（例如未选游戏）时直接提示错误。
- 确认弹窗文案去掉"请先退出游戏"，改为"安装时如果游戏正在运行（Windows）会失败，退出后再点一次即可"。
- 任务启动时记下当时游戏的内容根，只用于 macOS 的 `app.nw` 链接；中途切换游戏不影响，启动游戏时会按当前游戏重链（现有逻辑）。
- 失败后没有「重试」按钮：用户在壳菜单再点一次「下载最新」，会接着 `.part` 续传。
- 任务结束：成功提示版本；失败提示原因（提示里说明"重新下载会接着上次进度"）。任务结束后从下载中心消失，结果只靠通知。**结束提示由全站外壳统一发出**（挂在 `AppShell`，用户在日志页、营销首页等其它页面也能看到）；游戏库页订阅下载存储的"任务结束"事件再刷新状态（成功和失败都刷新，失败时壳可能处于恢复后的状态），不在发起处等待结果。
- 任务进行中，卡片上禁用「安装 / 下载最新 / 升级 / 卸载」；「开始游戏」保持可点：安装阶段之前用旧壳；替换是同步完成的，不会启动到半个壳；遇到崩溃遗留的待恢复状态，启动前会先自动恢复（见 §3.4）。
- MCP 以 `wait: true` 发起时，MCP 请求中断不会中止任务；任务照常出现在下载中心。

## 4. 浏览器内任务

### 4.1 能做到什么、做不到什么

实测（2026-10-03）：`nwjs.io/versions.json` 返回 `Access-Control-Allow-Origin: *`，页面可直接拉版本；压缩包的 `dl.nwjs.io` 与跳转后的 `dl.node-webkit.org` 都没有 CORS 头，页面无法用 `fetch` 读取压缩包，只能让 Chrome 自己下载，再由用户选择下载好的文件。因此：

| 环节                       | 谁处理        | 续传                                                      | 下载中心显示                         |
| -------------------------- | ------------- | --------------------------------------------------------- | ------------------------------------ |
| 下载约 200 MB 压缩包       | Chrome 下载栏 | Chrome 自带（下载栏里"继续"）                             | 只显示"等待浏览器下载完成"，无百分比 |
| 读取压缩包并写入 OPFS 缓存 | 页面          | 缓存命中即跳过下载                                        | 读取中                               |
| 解压并逐个写入游戏目录     | 页面          | **已支持**：同名同大小文件跳过（`writeZipEntriesResume`） | `写入 123/456`，有百分比             |

不经本站代理下载（避免 Vercel 流量费用，也不让本站成为二进制分发点）。

### 4.2 流程

1. 用户在游戏卡片点「安装壳」：在这次点击里**先**请求目录写权限（`requestPermission` 需要用户手势，必须在任何其它 `await` 之前），然后立即在下载中心创建任务（缓存是否命中都创建，后面的写入进度要在这里显示），阶段"准备中"：拉版本、查 OPFS 缓存。
2. 缓存命中：直接进入第 5 步。
3. 未命中：阶段变为"等待浏览器下载"，并尝试打开官方下载链接。拉版本有 `await`，超过约 5 秒的用户手势有效期后，新标签页可能被浏览器拦截，所以**游戏卡片**上同时提供「打开官方下载」按钮作为兜底。
4. 游戏卡片操作区提供「选择已下载的压缩包」按钮（下载中心只显示"等待浏览器下载"并提示去卡片上选择），用户点击时才弹文件框，这是一次独立的用户手势（O4 原定的拆分方案）。点击处理里先 `queryPermission`，目录权限丢了就在这次点击里重新请求。
   - 文件名校验：去掉浏览器给重名文件加的 ` (1)` 后缀后，必须等于期望的压缩包名（含版本与架构，如 `nwjs-v0.117.0-win-x64.zip`），否则提示"请选择 {期望文件名}"，任务停在这一步。页面拿不到校验文件（同样没有 CORS），只能靠文件名 + 解压后检查 `nw.exe`。
5. 读取、写缓存、解压写入，进度在下载中心更新。OPFS 缓存的压缩包解压失败（缓存损坏）时，删除该缓存并回到第 3 步。

### 4.3 页面行为

- 不再设置全局 `busy`，整张卡片不锁；任务期间禁用该游戏的「安装壳」，「连接」只在排队 / 读取 / 写入阶段禁用（等待选文件时不动游戏目录，仍可连接；否则用户放弃选文件后要刷新才能连接）。
- 切换游戏不打断写入（写入持有原游戏的目录句柄）。
- 同一个游戏在两个标签页同时装壳会互相覆盖文件：用 Web Locks（`navigator.locks`，Chromium 支持），按游戏 id 加锁，拿不到锁提示"另一个页面正在为此游戏安装壳"。
- 浏览器任务只存在当前标签页的内存里，其它标签页看不到（服务端任务各标签页都能看到）。
- 没有取消：任务一直等到用户选文件或写完。刷新页面会中断任务，已写完的文件保留，下次安装续上。
- 多个游戏同时装壳时，"读取 / 写入"两个阶段在**当前标签页内**排队逐个执行（显示"排队中"；不同标签页各自排队，互不等待）：每个任务要把约 216 MB 压缩包整个读进内存再解压，并行容易把标签页内存撑爆。等待选文件可以同时进行。
- 失败后没有「重试」按钮：在卡片上再点「安装壳」即可（同样先请求目录权限）。
- 任务进行中该游戏被移出游戏库：任务照常结束，但不再把结果写回游戏库（不会把它加回来）。
- 有任务写入中时关闭页面，弹浏览器自带的离开确认。
- Linux 的"下载链接"由浏览器原生下载，无法观测，**不进**下载中心，维持现状。

## 5. 下载中心界面

位置：`AppTopBar` 右上角，顺序为开发切换（server / edge，仅 dev，永远第一个）→ `end` 插槽 → 下载中心 → 语言切换。

**只读**：下载中心只说明"当前有东西在下载"，以后 App 更新等任务也由它承载。没有任何操作按钮（无取消、重试、移除、清除）；需要用户手势的步骤（浏览器选压缩包）放在游戏卡片上。

**触发按钮**

- 只有存在进行中的任务时才显示；没有时整块隐藏。
- 下载图标右上角显示进行中任务数的角标（超过 99 显示 `99+`）。
- 营销首页不显示顶栏：任务照常运行，结束提示照常弹出（同步与提示挂在全站外壳 `AppShell` 上，不依赖下载中心组件是否渲染）。

**下拉框**（沿用 `dropdownMenu.ts` 的样式与 `LocaleSwitcher` 的弹层定位，宽约 22rem）

- 用 base-ui **Popover**（只读面板，点开不移动焦点；程序化展开时不抢焦点）。弹层在有 ShadowRoot 时挂进 ShadowRoot。
- 只列进行中的任务，按开始时间倒序，一行一个：
  - 标题：如"NW.js 0.117.0"，版本未知（还在查询版本）时只显示"NW.js"；副标题标注"服务端"或"浏览器"，浏览器任务再加游戏名。
  - 阶段文案：查询版本 / 下载中 / 解压中 / 安装中 / 准备中 / 等待浏览器下载 / 排队中 / 读取中 / 写入中。
  - 进度条：有总大小时显示确定进度，否则显示不确定进度。
  - 大小与速度：`45.2 / 216 MB · 3.1 MB/s · 剩余约 55 秒`（无总大小时不显示剩余时间），续传时标注"从 30 MB 续传"。速度只按本次实际收到的字节推算（不把续传起点算进去）并做平滑；浏览器写入阶段按文件数计，不显示速度。
  - 浏览器任务等待选文件时显示"浏览器下载完 {文件名} 后，在游戏卡片点「选择已下载的压缩包」"。
- **自动清除**：任务结束（成功 / 失败）即从下载中心消失，结果用通知提示；最后一个任务结束后整块隐藏。服务端结束任务在服务端保留 1 小时（用于重连补发提示），本页的浏览器任务和服务重启合成的中断项 1 小时后从内存移除。
- 结束提示规则：打开页面时第一份快照里已经结束的任务不弹提示；此后（含标签页回到前台重连）凡是本页之前看到在进行中、或之前从未见过的任务以结束状态出现，都补弹一次。例如标签页在后台时 MCP 发起并完成的任务，回到前台会提示，游戏库页也会据此刷新。
- 文案全部走 i18n（中 / 英 / 日 / 韩），独立文件 `lib/i18n/messages/parts/downloads.ts`，避免继续撑大 `types.ts`。

## 6. 以后新增下载的接入约定

- **浏览器**：用统一的浏览器任务运行器启动；需要用户手势的步骤放在发起处（如游戏卡片）承接，下载中心保持只读。

## 8. 验收

- 服务端：点确认后弹窗 1 秒内关闭；进度实时更新；下载到一半断网，60 秒内报错，恢复网络后再点「下载最新」，从断点继续（日志与界面显示续传起点）；刷新页面进行中的任务仍在显示；任务结束后从下载中心消失并弹通知，没有任务时右上角不显示下载图标。
- 服务端：源站返回 200（不支持 Range）时从头下载；`.part` 损坏时校验失败、删除并提示重新下载。
- MCP `chaya_game_shell_install` 仍同步返回结果，且任务同时出现在页面的下载中心。
- 浏览器：装壳期间可装插件、改窗口配置、切换游戏；拉版本人为延迟 6 秒，游戏卡片上的「选择已下载的压缩包」仍能弹出文件框；写入中途刷新页面，再次安装跳过已写文件。
- 服务端 · Windows：下载中启动游戏，任务到安装阶段失败并提示退出游戏，旧壳完好可继续玩；退出后重新下载几秒完成（直接用已下载的包）。
- 服务端 · macOS：游戏运行中完成升级，游戏不受影响，下次启动为新版本。
- 服务端：未校验的压缩包解压失败后被删除，再次下载会重新下载。
- 服务端 · Linux：「下载最新」装壳成功，「开始游戏」能启动（修复现有缺陷后）。
- 服务端：任务运行中，经 MCP 调「安装」（指定壳源）或「卸载」返回 409。
- 服务端：开 4 个标签页，只有前台标签页保持下载 SSE；切回其它标签页后进度立即补齐，期间结束的任务补弹提示；刷新页面时已结束的任务不弹提示。
- 浏览器：选错压缩包（其它版本 / 架构 / 非 NW.js）被拒绝并提示期望文件名。
- 浏览器：同一游戏两个标签页同时装壳，第二个被拦下并提示。
- 多任务：浏览器模式下，两个不同游戏的装壳任务可同时出现在列表里，读取 / 写入阶段排队执行；服务端模式下，NW.js 任务与以后新增的服务端任务可同时出现。两种通道不会同时出现在同一个页面。
- 构建：`pnpm check:edge` 通过，edge 产物里不含 `/api/downloads*`。
- 测试：任务状态机（成功 / 失败 / 重复发起）、Range 206 / 200 / 416 分支（含 206 起点不符、416 总长不符）、字节数不足保留 `.part`、SHA-256 不符删除 `.part`、空闲超时保留 `.part`、暂存替换（改名失败回滚、回滚失败后恢复、残留清理）、SSE 首帧快照、前端存储合并。

## 9. 平台核对（2026-10-03 CR）

对照 `deployment-platforms.md` §3 部署矩阵逐项核对：

| 部署方式                        | 用哪种通道 | 能否跑通 | 关键点                                                                                                                                 |
| ------------------------------- | ---------- | -------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| 本地 server · Windows           | 服务端     | 能       | 解压用 PowerShell `Expand-Archive`；游戏运行中改名会失败，靠暂存替换保证旧壳不坏（§3.4）                                               |
| 本地 server · macOS             | 服务端     | 能       | `unzip` 解压、装成 `data/shell/Chaya.app`；运行中也能替换                                                                              |
| 本地 server · Linux             | 服务端     | 修复后能 | `tar -xzf`；需系统有 `tar`。**现有缺陷**：装壳与启动把 Linux 当 macOS 处理，现在跑不通，本方案一并修（§3.4）                           |
| App（Electron）                 | 服务端     | 能       | 内置服务是常驻 Node 进程，请求返回后后台任务继续；`data/` 在 `userData`，可写；退出 App 时任务中断、`.part` 保留                       |
| Vercel                          | 浏览器     | 能       | edge 构建不含 `/api/downloads*` 和服务端装壳；页面不连 SSE；**下载中心和浏览器装壳流程本身**不依赖服务端信令，但游戏连接仍受多实例限制 |
| 自托管 Node（edge 构建）        | 浏览器     | 有前提   | 同 Vercel；部署方必须启用 HTTPS（`localhost` 按浏览器规则可视为安全上下文），否则 FSA / OPFS / Web Locks 不保证可用                    |
| dev                             | 随切换器   | 能       | 两种通道都在；切换器切换后整页刷新，按新模式启用对应通道；服务端注册表挂在 `globalThis` 上，热更新不丢                                 |
| 局域网他人访问本地 server       | 服务端     | 能       | 需管理授权 Cookie；多个已授权页面看到同一份任务列表（只读）                                                                            |
| 远程游戏连入（`status.remote`） | —          | 不适用   | 服务端装壳本来就拒绝远程条目（`REMOTE_READ_ONLY`），没有下载任务                                                                       |

浏览器侧三平台：

| 浏览器模式 · 平台 | 下载中心任务                                     |
| ----------------- | ------------------------------------------------ |
| Windows           | 有：等待下载 → 选文件 → 写入（本方案主体）       |
| macOS             | 无：走终端命令（bash 自带进度与续传）            |
| Linux             | 无：只给下载链接，由浏览器原生下载，页面观测不到 |

已有问题，不在本次范围：

- 服务端下载用 Node 自带的 `fetch`，默认不读 `HTTP(S)_PROXY` 环境变量。需要代理的网络环境，现在同步下载也一样失败；后续可以在启动脚本里设 `NODE_USE_ENV_PROXY=1`（较新的 Node 版本支持），或给下载单独接代理。
- 磁盘写满时任务报错，`.part` 保留；空间不够的话再次下载仍会失败，提示里直接带上系统错误。

## 10. 已确认

1. 入口常驻。
2. 中断（断网、超时、服务重启）时保留 `.part`，再次下载续传（与 bash 一致）。用户不能取消（2026-10-03 改为只读下载中心）。
3. 浏览器模式维持"Chrome 下载 + 用户选文件"，不做本站代理下载。
4. 任务行显示速度和剩余时间；下载中心只读，只在有进行中任务时显示，角标为任务数，结束即自动清除并用通知提示。
5. 安装改为暂存后整体替换，不依赖心跳在线检测（CR 后采纳，§3.4）。
6. 需求、技术方案与部署矩阵对齐 review（2026-10-03）后补充：后台标签页断开 SSE、409 互斥、解压失败按是否校验决定删包、浏览器读写排队、文件名校验、Linux 装壳缺陷、Range 严格校验和替换失败恢复。
