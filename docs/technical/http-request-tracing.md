# HTTP 请求耗时与关联日志

- **状态**：现行实现说明
- **适用范围**：本机 Next 服务的页面与 API 请求；不覆盖浏览器渲染、游戏插件帧耗时或跨进程完整分布式追踪。

## 请求 ID

页面与 API 响应返回 `X-Chaya-Request-Id`。在浏览器 Network 面板打开慢请求，复制该响应头；本机结构化日志使用同一个值作为 `meta.operationId`。

```sh
curl -sS -o /dev/null -D - \
  -w 'total=%{time_total}s\n' \
  'http://127.0.0.1:3000/game?game=YOUR_GAME_ID'
```

可传入 `X-Chaya-Request-Id` 请求头辅助复现。仅接受 1–100 个字母、数字、冒号、下划线或连字符，其他值自动替换为 UUID。

默认日志位于 `logs/plugins/YYYY-MM-DD.ndjson`；设置 `CHAYA_LOG_DIR` 时以该目录为准。慢阶段和失败默认落盘，正常的 debug 阶段只保留在各进程最近 2000 条内存记录和实时订阅中，不写入磁盘；设置 `CHAYA_LOG_LEVEL=debug` 也不会恢复 DEBUG 落盘。按 ID 查找（包含轮转文件）：

```sh
rg -F 'COPIED_REQUEST_ID' logs/plugins/*.ndjson
```

## 集中查看慢请求

默认阈值为 **1000 ms**。尚未结束的请求达到阈值就输出英文 `[Chaya HTTP SLOW] ... running ... requestId=...` 并保存预警；完成、失败或连接断开时补齐最终耗时和状态。事件循环阻塞导致定时器来不及执行时，完成回调仍会根据实际耗时补记慢请求。

优先读取精简汇总，无需扫描普通插件日志：

```sh
curl -sS 'http://127.0.0.1:3000/api/logs?view=slow'
curl -sS 'http://127.0.0.1:3000/api/logs?view=slow&minMs=5000&limit=10'
curl -sS 'http://127.0.0.1:3000/api/logs?view=slow&requestId=COPIED_REQUEST_ID'
```

响应包含阈值、匹配数、运行中数量、前 10 个路径的次数及最大耗时，以及默认最多 20 条请求（`limit` 上限 100）。支持 `since`（请求开始时间的 Unix 毫秒值）、`minMs`（最小 1000）、`requestId`。同次请求的预警与完成合并为一条；客户端复用 request ID 的不同请求仍分别计数。运行中请求优先，其余按开始时间倒序排列。

慢请求单独保存在 `logs/plugins/slow-http/YYYY-MM-DD.ndjson`，不占普通日志缓冲区。汇总读取 14 天内最新最多 2000 条事件，所有文件合计最多读取 4 MiB；一个慢请求通常有预警和完成两条事件。返回的次数只针对该读取窗口，不代表全历史总数。当前进程另保留最近最多 256 条运行中的慢请求，优先并入汇总。仅有预警、缺少完成记录且不在运行索引中的请求标为 `unfinished`，保留最后一次已记录耗时；可能来自服务重启或运行索引超限淘汰，不能据此断言请求已经结束。超过索引上限的请求结束时仍尝试保存完成记录。`DELETE /api/logs` 同时清空普通和慢请求历史，保留运行索引中的请求。

覆盖页面、API、静态资源及日志接口的原生请求。SSE 仅计算建立连接前的耗时，已成功建立的长连接不因存活时间而报警；WebSocket 升级请求不计入。HTML 流式响应仍计算至响应结束。查询串不落日志，记录中保留方法、路径、request ID、状态与耗时。Cloud / 浏览器模式不开放本机慢请求历史。

## 阶段含义

| operation      | 含义                                                                  |
| -------------- | --------------------------------------------------------------------- |
| `http.server`  | Node 接收请求到响应结束或连接中断，包含开发编译和流式响应的等待。     |
| `http.proxy`   | 页面代理处理；`sinceArrivalMs` 表示从原生 HTTP 接收至代理执行的时间。 |
| `http.locale`  | 服务端布局的语言 cookie / 请求头解析。                                |
| `http.request` | API 控制器执行；API 的 `Server-Timing: handler` 也提供这一层耗时。    |

`http.server` 在 `instrumentation.ts` 的 Node 启动阶段注册。修改后需要重新启动 Next 服务才能确保启用；仅靠 HMR 更新页面不能确认原生观察器已注册。大于等于 1 秒或状态码大于等于 500 的请求还会在终端打印 `[Chaya HTTP] ... requestId=...`。

`/api/logs` 及其子路径不写入普通请求阶段日志，避免日志订阅自身产生循环；超过阈值时仍写入独立慢请求汇总。Cloud 模式不注册本机原生 HTTP 观察器。

这些阶段用于缩小范围：原生到代理的间隔较大时结合 Next 的开发编译日志及 `.next/dev/trace` 检查；代理结束后到响应结束较慢时继续检查服务端渲染与事件循环阻塞。语言解析只是布局中的一个阶段，不能代表全部 application-code 耗时。当前没有自动关联浏览器后续请求或所有后台进程。

源码注释、后台日志和接口机器文本遵循现有 `docs/technical/api-and-logs-standard.md` 的英文规范；界面文案仍由多语言词典提供。

## 首次日志恢复

日志总线首次使用时恢复最近最多 2000 条记录。从最新日期文件尾部向前读取，每次 64 KiB，所有文件共享 4 MiB 上限；遇到损坏记录或超大行时可能少于 2000 条。恢复读取之后执行磁盘保留策略，清理和缩减超限历史文件。

2026-10-31 排查发现本地日志约 2.2 GB，旧实现会同步读取、解析保留期内的完整文件后再截取 2000 条，可能阻塞同进程页面请求。新实现对这些实际文件恢复 2000 条约耗时 23 ms。这证实消除了无界扫描，并不能反推此前某次 23 秒 application-code 全部由它造成；历史请求没有足够的关联阶段数据。

## 日志大小、保留与写入

普通插件 / 服务日志按 UTC 日期分文件。当前文件将超过单文件上限时，先重命名为 `YYYY-MM-DD.<timestamp>-<uuid>.ndjson`，再写入新的日期文件。启动恢复、批量写入和大小查询都会执行自动清理：删除 UTC 日期早于 14 天前的文件，再按日期和轮转顺序删除最旧文件，直到总量不超过上限。容量优先于保留天数，高流量下历史不足 14 天。清理以 UTC 日期为单位，截止日当天的文件可能保留到次日清理。

| 项目                | 当前配置                                                                                                                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| 普通日志磁盘级别    | `CHAYA_LOG_LEVEL`，默认 `info`；支持 `info`、`ok`、`warn`、`fail`，`error` 是 `fail` 的别名；`debug` 按 `info` 处理，DEBUG 始终不落盘 |
| 普通日志大小        | 单文件 32 MiB，总量 256 MiB，保留 14 天                                                                                               |
| 慢请求日志大小      | 独立目录，单文件 4 MiB，总量 32 MiB，保留 14 天；不受普通日志级别过滤                                                                 |
| 普通日志内存 / 订阅 | 保留全部级别，内存最多 2000 条且不超过 8 MiB 序列化体积；进程重启后仅能恢复已落盘记录                                                 |
| 单条记录            | 最多 16 KiB；消息最多 2000 字符；元数据限制深度、键数、数组长度和字符串总长度，优先保留请求 ID、操作 ID、状态和耗时                   |
| 批量写入            | 每 100 ms 合并写盘；单文件待写内容达到 64 KiB 时提前写盘；跨进程目录锁协调轮转和清理                                                  |
| 手动清空            | 日志面板清空按钮 / `DELETE /api/logs`，清除普通与慢请求历史；慢请求仍保留运行中项目                                                   |
| 大小与策略查询      | `GET /api/logs?limit=1` 的 `stats.file` 和 `stats.slowFile`，分别包含普通日志与慢请求日志大小及 `policy`                              |

内存限制也覆盖异常路径：

- 普通日志每个总线实例最多 2000 条且不超过 8 MiB 序列化体积，超限淘汰最旧记录。单条记录在进入内存前就执行 16 KiB 限制和元数据截短，复制后不再引用原始大对象。
- 待写队列每个进程最多 1 MiB、2000 条、32 个目标文件。写锁持续被占用时淘汰最旧待写记录，避免重试队列无限增长；`stats.file.pending` 暴露当前体积、条数和累计丢弃数。
- `stats.memory` 暴露普通缓冲区的序列化体积、上限和淘汰数。该体积是日志载荷预算，不是 JavaScript 堆占用或进程 RSS；对象、索引和短时处理开销另计。
- 日志 SSE 每个总线最多 64 个订阅者，单连接应用队列最多 64 KiB。慢读客户端队列满时丢弃新事件，取消、断线或已中止请求均释放订阅和心跳。
- 浏览器日志保留最近 1000 条，上传等待队列最多 500 条，每批最多 100 条；这些记录同样在保留前截短到每条最多 16 KiB。

两类受管理日志的合计上限为 **288 MiB**。自动清理只管理符合上述日期命名的文件；活动记录、游戏操作轨迹、Next 开发日志及自定义命名文件属于其他存储，不在该上限内，也不属于本节自动清理范围。手动清空会删除目标日志目录内全部 `.ndjson` 文件。

DEBUG 的亚毫秒存储操作和正常请求阶段不再逐条写盘，可以减少磁盘增长与同步文件操作。查询和正常进程退出前会尝试刷出待写内容；其他进程占用写锁时保留批次等待下次重试。清空会丢弃本进程尚未写出的旧记录，避免计时器将它们重新写回。写入仍是同步批量操作；强制终止进程、崩溃、断电或退出时写锁仍被占用，可能丢失尚未写盘的记录。

已有超大文件会在策略执行时缩减：每个文件最多读取末尾 4 MiB，仅保留其中最近、有效、非 DEBUG 的完整记录，再执行总量限制。文件更早部分会删除，不做全量扫描；已有未超单文件上限的历史 DEBUG 随文件到期或容量清理删除，不额外扫描重写。
