# Agent 活动记录需求

> 状态：v2 核心实现已完成；多领域审计扩展与长期索引按后续迭代推进
> 日期：2026-10-09 · 方案修订：2026-10-13
> 技术方案：[`technical/agent-activity-log.md`](./technical/agent-activity-log.md)
> 关联：[`game-agent.md`](./game-agent.md)、[`game-assistance.md`](./game-assistance.md)、[`agent-gameplay-trace.md`](./agent-gameplay-trace.md)

## 1. 背景与目标

当前侧栏和陪玩面板只能显示少量阶段文案或持续 loading。玩家无法确认 Agent 正在观察什么、调用了哪些工具、为何继续或停止；日志页也无法回溯一次任务的提示词、操作和结果。

本需求建立一份跨入口共享的 Agent 活动记录。侧栏、陪玩面板和日志页读取同一任务记录，不各自维护互相冲突的历史。

目标：

- 运行中持续展示可理解的活动，不让玩家面对无信息的 loading。
- 记录用户提示词、实际系统提示词、公开判断摘要、模型回复、工具调用和 token 用量。
- 陪玩迷你面板提供“聊天 / 思考过程”两个 Tab。
- 日志页提供“运行日志 / Agent 活动”两个二级页面。
- 同一任务的成功、失败、停止或上限提示只产生一份最终结果。
- 挂机任务遇到单周期工具调用上限或当前目标完成时保存进度并进入下一周期；正常情况下只有玩家主动点击停止才结束，不可恢复错误可以被迫终止。

## 2. 记录边界

“思考过程”是面向玩家和开发调试的结构化活动摘要，不是模型隐藏思维链。系统不得请求、保存或展示原始 chain-of-thought。可记录的公开阶段包括：

- `observation`：本轮读取到的关键事实。
- `decision`：选择当前动作的简短理由。
- `plan`：下一步计划。
- `action`：正在或已经调用的工具。
- `result`：工具或模型返回的可验证结果。
- `next`：继续、等待玩家或结束的原因。

记录内容：

| 类别     | 必须记录                                                                                      |
| -------- | --------------------------------------------------------------------------------------------- |
| 任务     | task id、game id、会话、入口、能力、Agent 配置、模型、状态、开始和结束时间                    |
| 提示词   | 用户原始提示词、实际生效的系统提示词、玩家后续回复                                            |
| 模型     | 请求开始、公开活动摘要、最终回复、失败信息、耗时                                              |
| 工具     | 名称、脱敏后的参数、开始时间、脱敏后的结果或错误、耗时、状态                                  |
| 用量     | provider 提供的 input、output、reasoning、cached input、total token；未提供时显示未知，不估算 |
| 生命周期 | 阶段变化、进度、等待玩家、停止、完成、失败、重载中断和历史缺口                                |

Agent 操作游戏时产生的观察、结构化决策、工具调用会进入 Agent 任务轨迹；寻路、对话、选项、奖励、地图切换等游戏事实由游戏插件产生，再通过关联标识投影到同一时间线。具体范围与展示要求见 [`agent-gameplay-trace.md`](./agent-gameplay-trace.md)。统一展示不代表由同一个服务写入，也不允许协调服务复制或推测游戏事实。

凭证、Authorization、cookie、token、secret、password、API key、用户主目录及绝对本地路径必须在写入前脱敏。UI 再做防御性脱敏，但不能把只在展示层遮盖当作安全保证。

### 2.1 日志类型与所有权

| 日志类型       | 内容                                           | 权威生产者                         |
| -------------- | ---------------------------------------------- | ---------------------------------- |
| Agent 任务轨迹 | 用户目标、公开决策、工具调用、验证和任务结果   | Agent 协调服务                     |
| 游戏运行日志   | 地图、寻路、对话、选择、战斗、奖励和运行时变化 | 游戏插件                           |
| 操作审计日志   | 设置、插件、存档、翻译等实际执行的持久化变更   | 实际执行该变更的领域服务或游戏插件 |
| 技术运行日志   | HTTP、连接、重试、异常和性能                   | 各服务自身                         |

“游戏统一由插件写入”指逻辑生产者和权威事实源唯一：只有插件可以确认 `game.dialogue`、`game.choice_selected`、`game.chest_opened` 等游戏事件。服务不能因为工具返回成功就自行生成游戏结果。本地服务可以作为物理存储代理把插件事件追加到文件，Cloud 页面可以作为存储代理写入 IndexedDB，但二者都必须保留 `producer.kind=game_plugin`，不得改写来源。

操作审计再按实际执行域细分：游戏启动配置由游戏配置服务写，插件安装、启停和卸载由插件管理服务写，翻译资源变更由翻译服务写，Agent 配置由 Agent 设置服务写；存档文件由谁实际写入就由谁审计——服务直接修改时归存档服务，必须在游戏内完成时归游戏插件。一个服务不得为了让时间线“完整”而代替其它领域补写结果。

一次用户任务可以跨多个领域。例如“当前立即全屏，而且以后启动也全屏”会产生：Agent 协调服务的任务决策、游戏配置服务的下次启动配置审计，以及插件确认的当前窗口变化。三者通过 `taskId`、`actionId`、`parentActionId`、`toolCallId` 关联，不复制同一个事件；任一子动作失败时任务可结束为 `partially_completed`。

### 2.2 执行者与目标身份

每个任务必须记录 `coordinator`、`initiatedFrom`、`primaryDomain` 和 `targets`；每条事件必须区分 `producer`、`execution` 与 `classification`。不能只使用含义混杂的 `gameId`：

- `libraryGameId`：游戏库中的稳定身份，用于下次启动配置和跨运行记录归类。
- `runtimeInstanceId`：一次正在运行的游戏实例，用于当前窗口和局内行为。
- `pluginInstanceId`：实际观察与操作该运行实例的插件身份。
- `connectionId`：一次插件到服务或页面的连接。
- `taskId`、`conversationId`：一次任务和连续对话身份。

同一游戏可以同时存在多个运行实例。当前窗口变化必须绑定明确的 `runtimeInstanceId`，不能仅凭游戏名称或 `libraryGameId` 选择；批量任务只保存一份任务，每个目标分别生成 action，并独立记录结果。

## 3. 统一任务与互斥

- 同一 `runtimeInstanceId` 同一时间只允许一个 Agent 任务运行。侧栏、陪玩聊天、自动陪玩和其它入口共享这把锁；同一个库游戏的不同运行实例互不误锁。
- 任一入口启动任务后，其它入口显示同一个进行中任务和停止按钮，不能再次启动冲突任务。
- 关闭面板、切换 Tab、SSE 断开或完成一个阶段目标都不会停止挂机任务。正常情况下只有玩家点击停止才结束；游戏断连或不可恢复错误可以被迫终止。
- 刷新或重新打开面板后，从持久化事件序号恢复活动记录；历史被裁剪时明确显示缺口。

## 4. 各界面行为

### 4.1 Agent 侧栏

- 运行中的 Agent 回复区域展示当前公开活动摘要和工具调用。
- 新活动实时追加；工具行显示运行中、成功或失败以及耗时，可展开查看脱敏参数和结果。
- 最终回复到达后替换“正在思考”主显示；此前活动默认折叠在该回复下，可展开回看。
- 等待玩家时保留活动历史，并在输入区显示具体问题。

### 4.2 陪玩迷你面板

- 内容区顶部提供“聊天”和“思考过程”两个 Tab，默认进入聊天。
- 聊天继续展示玩家与陪玩回复；思考过程展示当前共享任务的活动时间线、工具调用与状态。
- 切换 Tab 不影响任务运行。任务从侧栏发起时，陪玩思考 Tab 仍显示同一记录。
- 自动陪玩提示也走统一 Agent Turn，不再调用独立、已不存在的接口。

### 4.3 日志页

- 日志页提供“运行日志”和“Agent 活动”两个二级页面，URL 可直接表达当前页面。
- 两个二级页面使用与辅助、设置、翻译和集成页面一致的侧栏导航；窄屏完全隐藏页面内二级导航，并将一级、二级入口统一收进右上角导航菜单。
- Agent 活动页按任务倒序展示，可选择任务并查看详情。
- 详情按时间展示完整记录，包含提示词、公开活动、工具参数与结果、最终回复、用量和耗时。
- 空态、连接失败、历史缺口和仍在运行使用独立明确状态；错误不挤进滚动内容底部。

## 5. 连续挂机与终态

- 单周期仍保留模型循环和工具调用硬上限，防止一次请求失控。
- 挂机任务达到单周期上限时写入进度事件和 `next` 摘要，等待短间隔后启动下一周期；不写 `failed`，不向聊天追加“操作未完成”。
- 每个新周期携带原始目标、最新公开进度和必要历史，重新观察后再行动。
- 当前目标已经完成时先输出阶段结果，再进入监看周期；没有新动作可做时保持低频观察，不以成功终态退出挂机。
- 玩家点击停止后不再开始下一周期，当前短动作结束或取消后写入一个 `stopped` 终态。
- 完成、失败和停止由任务控制器各写一次。聊天 UI 只从任务终态生成最终消息，不再额外追加同文错误，因此不得出现 `Yui:` 与 `!:` 两条相同上限提示。
- 连续任务仍受任务级安全边界约束：游戏断连、重复不可恢复错误、权限拒绝或数据损坏会终止并说明原因。

## 6. 保留与降级

- 延续现有任务存储：最多 20 个任务、单任务最多 200 个事件、任务最长保留 7 天；达到边界时裁剪最旧记录。
- 长期 Agent 游戏轨迹按任务追加保存，默认保留 30 天或最多 100 MB；达到任一上限时只清理最旧的已结束任务，运行中的任务不会被自动删除。
- App / local 模式把长期记录写入本地文件；Cloud 模式写入 IndexedDB，并提供脱敏后的版本化 JSONL 导出。内存只保留有限实时窗口，不承担长期归档。
- 不同类型写入各自目录或对象仓库：Agent 任务轨迹、游戏运行日志、领域审计和技术日志互不冒充。游戏运行日志在本地由插件产生、服务代理落盘，在 Cloud 由插件产生、页面代理写入 IndexedDB。
- Agent 活动页支持按任务读取、搜索当前任务事件、导出版本化 JSONL，以及经确认后删除单条或清空全部长期轨迹。清理近期聊天任务不会默认删除长期轨迹。
- MCP / WebMCP 的 `chaya_logs_query` 保持默认查询运行日志；传入 `view: "agent"` 后可读取 Agent 任务摘要或指定 `taskId` 的结构化事件，并可按 `gameId`、`runtimeInstanceId`、`eventType` 和关键词筛选。该入口只读，返回前再次脱敏并限制数量。
- 同一任务只保存一份权威任务记录，不为多个游戏或实例复制；按游戏、实例、会话和领域建立可重建索引。
- 插件来源事件以 `pluginInstanceId + producerEpoch + producerSeq` 幂等去重；任务事件以 `taskId + seq` 去重。插件重启提升 epoch，同一实例出现新活动连接时旧写入租约失效。同一唯一键携带不同内容时拒绝写入并记录 `GAME_LOG_EVENT_CONFLICT`。
- 持久化失败时任务可以继续运行，但必须产生可见的“记录未持久化”警告；不得因写日志失败卡死游戏操作。
- 不支持记录的 provider 字段保持为空，不影响任务继续。

## 7. 验收标准

1. 从侧栏发起任务，侧栏和陪玩思考 Tab 同时看到相同阶段与工具调用，且另一个入口不能再启动任务。
2. 最终回复出现后，活动记录自动收起，可展开查看工具参数、结果、耗时和 token 用量。
3. 陪玩面板具有“聊天 / 思考过程”两个可键盘访问的 Tab，切换不会中止任务。
4. 日志页可在“运行日志 / Agent 活动”间切换；刷新后仍能打开最近任务及其提示词、活动、工具和回复。
5. 系统提示词会记录，但凭证、敏感字段和绝对本地路径不会以明文落盘或显示。
6. provider 返回 token 统计时正确汇总；未返回时显示未知且任务正常完成。
7. 达到单周期工具调用上限或完成当前阶段目标的挂机任务记录进度后继续监看，正常情况下直到玩家点击停止才结束。
8. 同一终态只显示一次，不再出现角色回复和错误行内容相同的重复输出。
9. SSE 断线、面板关闭和页面刷新不停止任务；重连按事件序号恢复且不重复渲染。
10. 记录写入失败、单个事件损坏或历史被裁剪时均有降级提示，界面和任务不会卡死。
11. 本地模式重启后可从文件恢复记录；Cloud 模式刷新后可从 IndexedDB 恢复并导出，且不会把大体积轨迹写入 `localStorage`。
12. 服务工具返回成功但插件没有确认游戏状态变化时，不产生游戏成功事实，任务验证保持未通过或未知。
13. 同一游戏的多个运行实例同时在线时，事件按 `runtimeInstanceId` 和 `pluginInstanceId` 隔离，不会串到另一个实例。
14. 插件重连和网络重试不会产生重复事件；旧连接继续写入会被租约拒绝，内容冲突可被明确诊断。
15. 跨服务任务能在一个 Agent 活动时间线中聚合查看，但导出数据仍可识别每条事件的生产者、执行者、领域和目标。
16. 没有关联 Agent 任务的游戏运行事件仍可按运行实例查看，不会因为缺少 `taskId` 被丢弃或伪造归因。
17. 删除任务、游戏或运行实例时，删除范围分别明确，不会误删其它游戏实例或无关领域审计日志。
