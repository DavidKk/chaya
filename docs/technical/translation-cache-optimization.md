## 2. 不变量

1. 原始 `src` / `zh` 不因索引升级改变。
2. 查询最小单位为完整短句；边界来自保守规则或可信显式分段。
3. 未知换行仅是原始字符，不授权独立提取、组合或补译；**无提取元数据且无人工注解 → 默认 unknown**。
4. 子区间译文只能通过与当前 revision 绑定的可信映射获得。
5. 语气、引用、控件、人工保护、语言对约束在覆盖率排序之前校验。
6. 派生别名与组合结果不写成新定稿。
7. 不修改管线写入秩与双写契约；不把插件渐进替换改成服务端式整段 null。

## 3. 数据模型

继续使用 SQLite 的原始定稿与可重建索引。新增逻辑概念如下，最终字段名随实现确定。

| 概念         | 内容与约束                                                            |
| ------------ | --------------------------------------------------------------------- |
| 换行注解     | 原始起止偏移、soft / hard / unknown、证据来源、记录 revision          |
| 逻辑正文视图 | 用于分段和匹配的文本，以及到原始文本的可逆位置映射                    |
| 语义边界     | 逻辑位置、原始位置、证据类型及适用规则版本                            |
| 对齐分组     | 连续 source span、连续 target span、边界证据、对齐证据、定稿 revision |
| 候选诊断     | 可确认状态、拒绝原因、规则版本和基准 revision                         |

偏移统一采用 UTF-16 半开区间 `[start,end)`，不允许落在代理对或受保护 token 内部。逻辑正文删除软折行及其排版缩进后，一个逻辑区间可能对应多个原始片段；位置映射须保留这些片段，不能只用固定偏移差。

持久化对齐分组仍可用覆盖软换行的连续原始区间表示，但验证、展示与提取均通过位置映射解释。渲染替换使用原始区间；匹配使用逻辑正文；不把归一化后的字符串写回原文。

### 3.1 边界证据与对齐证据分离

- 边界证据：保守标点规则、明确结构、来源声明或人工确认。
- 对齐证据：人工确认，或受信任导入器提供的明确映射。
- 仅有行号、相同段数、相似标点分布、模型建议，都不足以自动赋予可信提取资格。
- 人工确认允许为无标点正文建立显式完整短句边界；因此后端不应要求这些边界事先能由标点分词器推导。
- 明确映射的导入器须验证版本、偏移和结构；普通 JSON 不能因排列相似而自动推断映射。

## 4. 换行与逻辑正文

### 4.1 分类规则

优先读取与原文精确绑定的提取元数据，再读取人工注解；**没有证据则为 unknown**。一个普通文本 JSON 值中的换行本身不能证明 soft 或 hard。

图鉴 / 匹配对无显式注解的换行使用启发式（MVP）：

- 换行两侧均为词字符（字母 / 数字 / 汉字假名等）且无句末标点 → **推断 soft**，可与连续正文匹配（如 `好きじゃ↵　ない`）。
- 换行紧跟 `。！？` 等句末 → **推断 hard**。
- 其余（逗号等歧义）→ **unknown**；用户仍可在图鉴里覆盖。

显式注解（人工 / 导入适配器）优先于启发式。不能把所有 RPG Maker 文本换行无条件一律 soft。

### 4.2 保守处理

- soft：消除换行及紧随其后的**排版缩进**（行首全角/半角空格、制表符 run）；词间空格按下方语言策略。
- hard：保留结构隔离，连续块不可跨越。
- unknown：保留原始字符；没有其它可信边界时，将相关文本作为完整待处理区域。不能把折行左右两侧直接提升成独立短句。
- URL、HTML、替换槽、Ruby、RM 控制码先识别保护；字面控制序列与真实换行分别解析。
- 未知区域需要补译时扩大到安全边界，必要时放弃其中局部命中，重新翻译完整区域；不能只补译被截断的半句。

**soft 消除后的空白策略（默认，实现锁定）**

设换行两侧在去掉该换行与排版缩进后的邻接字符为 L、R（已跳过受保护 token 边界则不在此合并）。

| 源语言语境                                                                      | 规则                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 日 / 中 / 韩等无空格书写（`src_lang` 为 `ja`/`zh`/`ko`，或正文判定为 CJK 主文） | L 与 R **直接相连**，不插入空格。例：`好きじゃ\n　ない` → 逻辑 `好きじゃない`                                                                                                                                                           |
| 英文及空格书写语言（`en` 等）                                                   | 若 L、R 均为词字符（字母/数字/`'`），则 **插入一个 U+0020**；若任一侧已是空白，或任一侧为标点/括号，则 **不插入**。例：`word\nword` → `word word`；`see.\nNext` → `see.Next` 再由标点规则处理（不在换行步骤插空）；`Hel\nlo` → `Hel lo` |
| 语言对未知                                                                      | 按 **更保守**：当作空格书写语言（可插空格），避免 CJK 误粘英文                                                                                                                                                                          |

说明：词中折行（`Hel\nlo`）在英文 soft 下会得到 `Hel lo` 而非 `Hello`——有意不猜粘连；正确修复依赖更好的提取元数据或人工，而不是自动去空格。

对于案例 `好きじゃ\n　ないんスよ`：unknown 时整体保留；确认 soft 后逻辑正文为 `好きじゃないんスよ`，来源偏移仍指向原始两行。

## 5. 统一分段与候选生成

优化预览、导入校验、服务端与插件共用纯规则层。拆分结果包含位置、语气、结构和证据，不再只返回字符串数组。

1. 构造受保护 token 与换行注解。
2. 生成逻辑正文和位置映射。
3. 合并保守规则边界与可信显式边界，冲突则返回诊断，不静默覆盖。
4. 保留问叹、省略号及引用上下文；安全外壳作为别名描述。
5. 生成待确认对齐候选；数量一致仅可作为提示字段。
6. 调用同一验证函数，显示每项可确认状态。

不自动按日语助词、词尾或任意字符建立可复用边界。模型可作为后续可选建议来源，建议未经人工确认不能进入可信索引。

### 5.1 引用结构

成对最外层 `「……」` 可建立别名；内部 `『……』` 及其说话人、转述尾缀继续保留。去壳不是语义分段，也不需要复制译文。

`おっかないんスよねえ』つって` 是包含引用结束和转述的残片，不能自动等价于裸句。残片记录可保留原始精确查找，但默认不作为去壳或子块提取来源；需结构诊断与单独审校。

## 6. 对齐确认与接口

扩展现有 optimize 接口。当前为 MVP：控制台与 API 同步演进，**不做旧客户端协议兼容层**。

请求需要：父记录、基准 revision、换行注解、显式边界和对齐分组。所有偏移基于请求指定的原始快照。

预校验与提交使用相同验证器，依次检查：

1. 记录身份、语言对、revision 和规则版本一致。
2. 原始区间合法，未截断代理对、控件或受保护 token。
3. 逻辑位置映射有效，soft / hard / unknown 处理符合证据。
4. 边界可被规则解释或有人工确认；不允许只提交任意字符命中率。
5. 原译映射单调、无重叠、不跨硬结构；允许一对多和多对一。
6. 外壳、引用和控件关系可解释；人工保护及现有映射不冲突。

一对多 / 多对一保存为不可随意拆开的整体映射块。只有存在更细可信映射时，才允许从内部提取；不根据句数按比例切译文。

新确认请求按整批原子提交，任一项无效则返回逐项诊断且不写入映射。成功时复用已有版本与事务机制，同时更新映射、索引及失效信息。revision 变化返回冲突，前端保留编辑内容并请求重新校验。

修改定稿与确认映射分开：修改译文成功后所有候选以新 revision 重算，不能沿用旧目标偏移继续确认。

## 7. 匹配与补译

沿用人工保护和冲突策略，在合法候选中优先整段、连续大块、最后单短句。查询与缓存双方都可携带逻辑视图；包含关系必须建立在相同规则与可信边界上。

- 查询 `a,b,c`，缓存 `b,c`：整块使用其译文，安全补译 `a`。
- 查询 `b,c`，缓存 `a,b,c`：只通过可信映射提取；无映射继续查较小记录。
- 未知折行不能用于推导 `a` / `b`，不能跨它制造连续块；已有明确人工分段需先补充相应换行解释。
- 控制符和输出分隔符保持绑定；命中块内部译文不被再次按标点重排。
- 引擎等待后重查依赖版本，失效则重新规划；partial 不写成整段定稿。
- **路径分流**：上述「完整覆盖 / 安全补译」约束 **服务端规划与 live 定稿前查找**。插件 `translateWithLookup` 仍可渐进替换已命中子段（管线 §2）；本期不把插件行为改成整段 null。
- **双写**：live 落库仍走管线 §14.5；共享 `rejected`（低秩）不得写入本作 ndjson。

## 8. 持久化与迁移（MVP）

1. 不更换数据库，不合并原始主键，不自动删除疑似重复或错误记录。
2. 换行及边界注解绑定 revision；正文修改后旧注解和映射失效。
3. 新规则使用独立版本（`SENTENCE_RULE_VERSION`）。与逻辑视图相关的索引随注解写入重建；不把旧换行位置索引直接当成新语义单元。
4. **不做旧客户端 / 旧插件双轨降级**：控制台、共享缓存服务与插件同一规则版本一起升级；无 soft 注解时自然退回整段 / 精确键，这是证据缺失而非兼容层。
5. 本作带来源回填可携带注解、映射和规则版本；服务端与插件共用解析约定。旧对象行和数组行继续可读，但不凭空补可信证据。
6. 历史独立碎片没有足够来源信息时只标记为待审校。列出问题与影响，不自动改译文、删记录或反推父子关系。

## 10. 索引精确查询与性能改造（2026-10-22，首版）

本节收紧 §7 的候选检索方式；保留连续短句、安全提取、人工保护与写入秩。**首版已接入**：缓存命中查询使用等值索引，规则 v10 启动时重建历史键，数字族独立建索引；live 与覆盖核验复用本作候选上下文，共享回填不重复参与本作匹配，空回填及未变化来源不重复读文件。首次加载、外部编辑刷新仍需解析文件；缺口仍独立打开连接，在线影子索引等后续目标不视为本版已完成。 对应需求 §3.6、§6；性能依据见 [调度方案 §13](../translation-scheduling.md#13-批次性能诊断与优化依据)。

### 10.1 当前问题与约束

改造前实测第 534 批 4 条、288 个源字符，总计 3184ms，其中 4 次 cache plan 合计 2048ms。共享库已经存在等值索引查询，不能将瓶颈笼统归因于 LIKE；实际还存在省略号 GLOB 兼容，以及 live 将约 6762 条本作记录逐条传入句段规划的问题。

约束覆盖 live、seed 补译 / 覆盖核验、本作 resolver、共享库候选与插件：

- 不使用 SQL `LIKE`、`GLOB` 或其他模糊检索作为缓存命中方式；禁止回退全库 includes / 正则 / 相似度扫描。单条输入的规范化、token 解析可以使用有界正则，这不属于扫描缓存。
- 所有候选必须由等值索引定位。对索引返回的少量记录校验结构、语气、连续位置和可信映射，不等于模糊搜索。
- 数字族索引增量维护；移除查询时 `src GLOB '*[0-9]'` 捞全库再建模板的路径。
- 不以缩短计时为由删除人工保护、来源秩、语言对或 revision 校验；复杂复用超限可以降级，权威判断不能跳过。

### 10.2 索引键与规范化

继续复用原始定稿表及现有可重建索引，必要时扩展，不建立独立权威译文库。逻辑索引如下，最终列名随实现锁定：

| 查询                | 索引键                                                                                                       | 返回                              |
| ------------------- | ------------------------------------------------------------------------------------------------------------ | --------------------------------- |
| 原文整段            | `(src_lang, tgt_lang, raw_src)`                                                                              | 定稿引用与来源                    |
| 规范整段 / 安全别名 | `(rule_version, src_lang, tgt_lang, key_kind, normalized_key, tone, control_signature, structure_signature)` | 可能多个定稿引用；不是任选一个    |
| 完整短句            | `(rule_version, src_lang, tgt_lang, unit_key, tone, control_signature, boundary_kind)`                       | 定稿 ID / revision 与原始句段位置 |
| 数字模板            | `(rule_version, src_lang, tgt_lang, template_key, context_signature)`                                        | 已验证的源 / 译模板与依赖引用     |

共享 SQLite 为实际条件建立对应复合索引；本作及插件按相同键组织 Map / 倒排表。索引行引用 `recordId + revision`，既有区间映射仍用原始 UTF-16 偏移。使用哈希压缩键时必须复核完整键，不能把哈希相同直接视为命中。

规范化在写入、索引重建、查询时共用同一纯函数及 `rule_version`。省略号等价变体在索引中一次性收敛到确定键，替代运行时 GLOB 兼容；仍保留位置、语气与结构约束。安全外壳只生成有限别名，不枚举任意删标点组合。问号、感叹号、未知换行、英文词间空格和受保护 token 不随意删除。原始 src / zh、导出及显示不变。

同规范键允许一对多；索引不得因 UNIQUE 约束覆盖定稿。返回候选后沿用权威 / 冲突规则，同权不同译不能挑首条；原文精确命中也须遵守既有等价组与人工保护规则。

### 10.3 查询流程与有界降级

1. 获取当前可用索引快照及保护版本；按既有来源优先级查原文整段等值索引，再查规范 / 安全别名等值索引。不把“本作优先”错误地等同于所有带来源回填都高于共享人工定稿。
2. 对适用的数字文本查模板键，仅有无歧义、依赖有效且数字槽对应明确的模板才还原；保留前导零。无可用模板继续查询，不逐条枚举缓存。
3. 将查询解析成合法完整短句，批量等值查询倒排键。候选上限按整条输入累计，建议初始上限 500，不能每个键各取 500 后无限叠加；高频桶、重复位置和规范化别名也计入预算。
4. 只向覆盖规划器传入索引筛出的候选，复用现有连续区间与映射校验；禁止把整个 localRecords 数组拼入每次 `cache.plan`。没有候选直接返回 miss，不启动全库匹配。
5. 超限返回独立诊断，不将截断后的候选伪装成完整权威集合。保留已确认的整段 / 人工保护，不能因为候选预算耗尽而绕过人工保护去整段覆盖；无法安全确定时返回可解释的 partial / 未完成。
6. 缺口批量补译沿用父上下文，完成后只复核使用过的定稿依赖与相关权威键，发现人工修改则重新规划。partial 不持久化为完整新定稿。

句段层是否启用可根据实测决定；停用该层也必须保留整段、规范键及模板快查。该降级不改变插件渐进显示和服务端 full / partial / miss 契约。

### 10.4 快照、增量写入与初始化

- 每个游戏 / 缓存版本复用记录和索引快照；一次初始加载后，正常批次不重复完整读文件、JSON 解析或重建 resolver。外部修改通过文件签名及权威版本检测，在批次边界刷新受影响内容。
- 缺口子任务复用父任务缓存句柄、规则快照和索引；避免递归再次回填、解析完整文件。实现时明确句柄所有者，子任务不得关闭父句柄。
- 已接受写入在短事务中同步更新定稿、revision、索引及 outbox；批内后续查询可见新增结果。负缓存按语料 / 规则版本失效，不把短暂 miss 永久保存。
- 回填与覆盖核验复用快照和受影响项；保留成功项及时持久化，不为合并写盘扩大故障重跑范围。空回填不能重复解析整个游戏文件。
- 人工定稿或来源依赖修改 / 删除使对应别名、模板、短句索引及回填失效；不能只校验文件时间而忽略共享库 revision。

### 10.5 迁移与验收

1. 固化规范化规则与测试，建立新版本索引；历史记录只重建索引，不改原始正文或人工译文。
2. 将现有 GLOB 省略号兼容和数字全库检索替换为已准备好的键 / 模板索引，并复用本作候选索引；重建操作从查询热路径移出。
3. 沿用管线 §14.7 的版本切换方案，避免查询混用新旧规则；构建失败保留可用旧索引，但不能继续通过旧 GLOB 查询。缺少所需新索引时仅走可验证的原文等值查询；无法核验人工权威时返回未完成，不能伪装普通 miss 并覆盖人工译文。
4. 检查查询计划确实使用对应索引，覆盖精确、规范、省略号、短句及数字模板路径。静态检查缓存查询路径无 LIKE / GLOB，运行测试还须证明不存在全量加载与逐条全库遍历；不得只检查 SQL 字面量。
5. 保留来源优先级、等价冲突、语气差异、控件、未知换行、可信映射、语言对、人工修改 / 删除失效与并发写入回归；服务端及 MV / RGSS 使用同一输入回放。
6. 按需求 §6 的规模与场景测 p50 / p95 / max、候选数量、缓存加载次数、SQL 次数及字数；热态 40 条批次查询及安全验证目标 p95 ≤50ms。初始化 / 重建、模型推理、保存和端到端耗时分别报告；目标未达成则先按阶段日志定位，不通过跳过正确性规则达标。

### 10.6 首版落点与回归

- `lib/translate/sentence-units.ts` / `shared-cache/match-index.ts`：规则 v10 重建原始 / 规范 / 别名和句段位置键；只读连接检查新版本标记，不能用旧 GLOB 兼容绕过迁移。迁移不改原文、译文、定稿 ID / revision 与既有对齐。
- `numeric_label_keys` 按语言对、编号族建立复合索引，写入 / 删除随原有触发器维护；编号族候选超限不学习不完整模板。
- `game-records.ts` / `game-cache-context.ts`：有容量上限的文件快照与本作 Map / resolver。文件身份、修改时间、大小与路径变化触发刷新；共享来源记录由共享索引查询。自身共享回填可推进快照签名，但不得掩盖同期 seed 修改或回退路径变化。
- `backfill.ts`：无任务且无依赖变更时直接返回；文件事件快照按签名复用，只刷新变化的来源。每条成功仍先保存共享 SQLite，文件回填保留原有锁、fsync 与事件幂等性。
- `live-translate.ts` / `fill-missing.ts`：只传入索引选出的本作候选；候选超限不会伪装普通 miss 并调用引擎绕过人工权威，返回明确未完成原因。批后覆盖核验同规则。
- 回归包含查询 SQL 无 LIKE / GLOB、EXPLAIN 确认使用索引、规范标点命中且问叹隔离、历史键重建、编号族隔离、空回填不读文件、共享 revision 修改 / 删除、本作人工覆盖、seed 原子替换、索引快照复用及候选超限不调用引擎。性能样本见需求 §6.1；性能数字使用单独基准记录，不把机器耗时阈值写成易抖动的单元测试。

### 10.7 状态指标与下一步流水线建议

已实现状态栏：剩余时间不足一小时用 `MM:SS`，一小时及以上用 `HH:MM:SS`（小时可超过 24）；速率用源文 Unicode 字符/s。以本次启动后最近 8 个已完成批次的已核验覆盖字符数除以实际批次总耗时，失败批次耗时计入、暂停及首次全量扫描不计入。批次使用单调时钟计时，不受系统时间调整影响。剩余时间统一为当前 `missingChars / charsPerSecond`，不使用任务总字符数、历史 startedAt 或累计会话耗时。暂停时隐藏 ETA；每次恢复（包括磁盘恢复、worker 热更新）清空速率样本，首次有效批次完成前不显示速率与估时；零吞吐及无效采样不显示 ETA。缓存命中也算有效进展，因此这是整条任务的处理速率，不是模型纯推理速率。

状态栏仅在运行且已有有效速率时显示“翻译 · 剩余 MM:SS · 字/s”，停止、暂停、完成或异常时隐藏速度与估时；缓存耗时不在状态栏展示。详细管线与 Apple 计时默认关闭，使用 `CHAYA_TRANSLATE_DEBUG=1` 按需开启，正常日志保留批次摘要和异常。

后台 seed 作业内部诊断的缓存毫秒数为当前进度窗口内 worker 整段 / 句段 / 数字模板匹配累计耗时；不包含 worker 启动、共享库打开 / 迁移、翻译、写入及回填。旧单次补译路径仍统计该批匹配及末尾覆盖校验耗时。两者都不是每条平均耗时，通过结构化回调 / job 快照传递，不从日志解析。

后台 seed 作业已采用独立缓存 worker 与引擎消费线路，缓存属于可跳过的加速步骤，不是派发前置条件。实现与验收以 [调度基线 §14](../translation-scheduling.md#14-非阻塞缓存扫描与翻译派发2026-10-23) 为准：

1. 缓存可扫描全程，IPC 分片 32 项且只有一个分片在途，受结果缓冲反压约束。引擎有空位优先领取已知缺口 / miss，没有就直接领取尚未扫描的文本，不等待初始化、全量扫描或旧批次最慢项。
2. 不新增完整 L1 正负缓存，继续复用本作上下文和等值索引；索引更新后后续扫描可见。扫描结果接受时核验文件指纹、语料版本和依赖 revision，旧结果可保守放弃。没有把整个共享库加载到内存。
3. 引擎结果先核验相关等值权威键并持久化，再完成任务；不强制重跑整段匹配。成功结果和汇总进度持久化；扫描位置和逐项尝试状态尚不持久化，恢复会重建扫描。
4. 服务端同游戏 / 同配置 / 同语言对 / 同受保护原文的在途请求共享传输 Promise，接受与持久化各自核验；失败不会成为永久 miss。底层未真正结束的不可取消请求仍占配额。
5. 缓存同步 SQLite 查询及匹配在 worker 线程运行；提交、权威核验和回填仍有同步短操作。直接单次补译、CLI 和实时入口尚未迁移独立缓存线路。详细容量、暂停与超时边界见调度方案 §14.3。

当前热缓存实测 40 条约 7–16ms，流水线收益上限主要受这部分占比限制。优先衡量引擎首条 / 完成时间、持久化和回填耗时，再决定实施顺序；不能承诺该调度本身将端到端速度翻倍。
