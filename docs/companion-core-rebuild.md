# 旅伴核心重构需求

> 有效性：实施中；2026-10-29。
> 实现进度：阶段一、二在下文声明的标准回合战斗与样例范围内完成实现和验证，包含本地执行、异步快慢判断、独立聊天、共享控制权、记录持久化、基础结局统计与有界经历检索。官方 MV / MZ 样例、真实模型宿主、资源并发、双面板及存储断连恢复已有实测；构建后的 Next 配置页、API、插件及真实旅伴面板完整链路连续两轮通过。模型驻留、冷启动进度及分段日志已接入。旧路径未完成同存档战斗，保留失败基线，不提供加速倍数；历史路由超时仍保留。阶段三首增量已实现有界的实际 HP 条件经验；更复杂的经验和按角色选择模型继续按阶段三、四推进。
> 技术方案与实施任务：[旅伴核心重构技术方案](technical/companion-core-rebuild.md)。
> 有效范围：旅伴核心执行、动态战术、游戏经历与经验、聊天协作、并发控制和模型扩展。沿用现有 UI 面板、角色、模型配置与可复用基础设施，允许重写核心执行逻辑。
> 替代关系：在已实现的旅伴战斗范围内，替代旧方案中依赖逐步模型决策的执行方式，以及限制新核心职责拆分的约定；具体切换范围见第 11 节。原有授权、普通游戏操作边界、停止、验证与数据隔离要求继续有效，其他助手与托管入口保留原执行流程。
> 现有基线：[旅伴](companion.md)、[游玩记忆](companion-memory.md)、[旅伴实现](technical/companion.md)。旧文档中的交付状态和性能目标不能直接当作本次重构的验收结果。

## 1. 问题与目标

当前旅伴体验更接近侧栏 Agent。用户反馈，在逐步等待模型判断的使用方式下，一场战斗可能耗时大半小时，思考等待明显打断陪玩体验。具体耗时分布仍需测量，不能仅凭现象认定全部由模型推理造成。

重构后的旅伴应持续观察游戏、执行已经理解的常规行动，在需要判断时调整战术，同时能与玩家聊天、引用共同经历。战斗节奏不应由每一步模型调用决定。

本次目标：

1. 常规行动通过本地执行闭环完成，模型不必逐次批准按键或每回合动作。
2. 战术随角色、敌人、资源和局势变化，由模型提出调整，系统校验并应用。
3. 聊天与操作分别推进，旅伴能解释实际行为、回应玩家和适时交流。
4. 系统负责采集、保存、检索和组织记忆；模型按任务获得必要上下文。
5. 支持单模型使用，预留按任务选择不同模型的能力；本机小模型是持续优化方向。

不要求最优解或每次判断都正确。验收关注行为是否符合已采纳的战术、是否有真实结果反馈、是否可以持续调整。

## 2. 重构与复用范围

| 部分                         | 本次方向                                             |
| ---------------------------- | ---------------------------------------------------- |
| 面板、角色、语言与基础配置   | 沿用现有入口和视觉结构，按新运行状态做必要接线       |
| 模型供应商与凭据             | 复用现有适配和配置，不要求更换模型或安装本机模型     |
| 核心执行                     | 允许重写，不以兼容旧逐步模型循环为前提               |
| 游戏事实、输入守卫、动作回读 | 评估后复用，缺失能力按真实支持范围补齐               |
| 记忆采集与存储               | 复用可验证的数据和接口，补充统一行动结果及作用域     |
| 经验统计与结论               | 独立设计、分阶段交付，不把已有战败计数等同于经验系统 |
| 其他助手与托管模式           | 保留现有产品行为；与旅伴共用游戏控制权仲裁           |

首期以 MV / MZ 标准战斗的一条完整流程为落点。具体动作集合由能力核对后确定，必须同时覆盖造成伤害和至少一种实际可验证的生存调整，才能验证动态战术。自定义战斗、RGSS 以及未知机制按能力降级，不假定自动兼容。

首期不要求通用探索、完整任务规划、所有技能机制、多模型配置面板、模型训练或复杂自动经验推导。它们不能成为本地战斗闭环的前置条件。

## 3. 需要搭建的基础能力

下列“服务”表示逻辑职责，可以在现有宿主和应用服务内实现，不要求各自部署进程、数据库或网络服务。具体代码目录与接口留给技术方案确定。

| 基础能力           | 负责什么                                             | 主要交互                                 |
| ------------------ | ---------------------------------------------------- | ---------------------------------------- |
| 游戏事实与能力     | 提供当前状态、行动阶段、合法动作、已知机制和未知项   | 给执行、评估和上下文组装提供同一事实来源 |
| 事件与经历记录     | 关联行动意图、实际执行和结果，保存关键经历并支持检索 | 接收游戏事件，向统计、回忆和诊断提供证据 |
| 经验统计与结论     | 按条件累计结果，组织带证据和适用范围的经验           | 消费统一记录，给判断提供统计和有条件结论 |
| 局势评估           | 计算资源变化、近期伤害、风险和战术进展               | 为本地动作选择和模型触发提供输入         |
| 动态战术管理       | 保存当前有效战术、修订和适用条件                     | 接收受校验的调整，提供给执行器           |
| 本地动作选择       | 结合最新事实和有效战术选择动作与目标                 | 提交动作意图和简短选择原因               |
| 执行与结果验证     | 通过普通游戏操作执行，确认真实结果、失败或未知       | 独占派发操作，回流结果事件               |
| 决策上下文组装     | 为一个明确问题检索相关状态、记忆、经验与可调能力     | 给模型提供有限且有来源的上下文           |
| 模型任务与资源调度 | 管理触发、快慢任务、队列、预算、取消及未来路由       | 提交独立请求，把结果送回对应业务入口     |
| 聊天与表达         | 接收玩家原文，基于真实经历与行为交流                 | 输出聊天，向协调器提交玩家意图           |
| 旅伴运行协调       | 管理实例、目标、控制权、战术采纳及生命周期           | 统一协调执行、聊天和异步判断             |

运行协调器先用代码落实确定的规则，不增加一个模型专门裁决其他模型。聊天、记忆和模型适配都不直接持有游戏操作权限。

## 4. 服务如何协作

### 4.1 开始与常规执行

```text
玩家授权目标 → 建立实例与控制权 → 读取当前事实和能力
                                      ↓
                         加载基础战术与相关经历
                                      ↓
        观察 → 局势评估 → 本地选动作 → 执行 → 验证
          ↑                                     ↓
          └────────── 新事实与结果事件 ──────────┘
```

开始执行时必须有可用基础战术，不等待模型为每个普通动作生成指令。模型可以在目标建立或情况变化时补充判断。

已验证的有效战术允许本地闭环继续运行。动画、行动阶段和输入窗口由游戏状态驱动等待，不能靠持续快速按键推进。无合法动作、授权失效或现场不可信时，进入对应等待、暂停或结束状态。

### 4.2 遇到需要判断的情况

```text
重要变化 / 特殊情况 / 玩家要求
           ↓
去重与合并 → 组装问题、相关证据和可调能力 → 快速判断或深入分析
                                                      ↓
当前战术 ← 协调器校验并采纳调整 ← 结构化建议与适用条件
```

模型调用不进入每次动作的必经路径。同一问题未变化时，不因轮询反复发起分析。模型忙、超时或失败时，有效本地战术继续生效；只有缺少可继续执行的有效策略或能力时才等待或暂停。

### 4.3 聊天与经历反馈

```text
真实事件 / 玩家聊天 → 当前事实 + 相关经历 + 实际行动原因 → 表达或回复
玩家提出操作意图 ───────────────────────────────→ 协调器
行动与结果事件 → 统一记录 → 增量统计 → 相关经验供后续检索
```

不把每次动作播报一遍。主动表达根据事件价值、近期发言和玩家偏好合并、限频；聊天中可以解释为什么刚才治疗，也可以讨论其他内容。尚未执行的计划不能说成已经完成的动作。

聊天中的操作意图必须关联玩家原文、当前目标与现场，由协调器校验后生效。在已有授权范围内，明确调整可以直接应用；含糊或超出授权范围时沿用澄清与授权流程。停止、接管或更新要求之后，迟到的旧聊天解析不能重启操作、恢复旧约束或自行取得控制权。普通聊天不因回复较慢而阻塞执行。

## 5. 动态战术要求

基础战术只是起点，不能把调整能力限制为几种固定姿态。系统逐步提供可理解、可校验、可执行的调控能力。

| 调控方向 | 示例                                                        |
| -------- | ----------------------------------------------------------- |
| 生存条件 | 结合当前 HP、可知伤害、状态和治疗能力决定治疗时机           |
| 资源预算 | 保留一定 MP、限制稀有道具、允许在特定情况下突破普通消耗预算 |
| 目标选择 | 调整敌人优先级、集中攻击或处理特殊目标                      |
| 技能偏好 | 根据已知机制选择技能，限制重复无效尝试                      |
| 重评条件 | 新阶段、连续无效行动、关键资源变化时重新请求判断            |

例如“低于 30% HP 就治疗”可以作为初始规则，但不能成为不可调整的通用结论。当前角色是否还能承受一次已观察攻击、是否存在持续伤害、治疗是否来得及，都可能影响战术。缺少机制信息时保持不确定，不要求首期准确模拟全部伤害。

模型输出受支持的战术变更及适用条件，不生成任意可执行脚本。系统计算可确定的状态量，校验动作和参数；模型负责在已有能力内选择、调整条件。未知能力不会因模型提出而自动获得支持。

临时应对与持续战术分开：本回合优先治疗可以在完成后失效；长期治疗条件的修改需要形成新的战术修订。玩家当前明确约束优先，调整不能自行扩大操作授权。

## 6. 统一记录、经验与存储范围

### 6.1 一次记录，按职责消费

行动、结果和关键事件使用统一身份关联，不能让统计、聊天和记忆各记一套互不一致的事实。

| 数据               | 保存方式与用途                                             |
| ------------------ | ---------------------------------------------------------- |
| 当前事实           | 维护实时状态，不逐帧持久化                                 |
| 行动意图与实际结果 | 同一行动关联记录，区分未发出、已发出、失败、成功与结果未知 |
| 关键经历           | 保存遭遇、击倒、胜败、读档等片段及必要证据                 |
| 统计               | 从同源结果增量计算，重复事件不能双计数                     |
| 经验结论           | 保存适用条件、证据、反例与不确定性，和事实分别表达         |
| 当前战术           | 按实例维护运行状态；可复用部分另行明确保存                 |

详细记录和缓存必须有容量与保留策略。原始证据被裁剪后，摘要和统计应标识可追溯程度，不能声称保留完整战斗过程。

首期建立关键记录、相关经历检索和可核对的基础统计；复杂经验结论单独推进。一次零伤害不能直接推导敌人免疫，先击倒某敌人后获胜也不能直接证明该顺序导致胜利。模型可以提出假设，不能将其直接记为确定机制。

基础统计的最小交付为实际遭遇次数与结局分类：胜、败、逃跑、中断、未知；没有结算证据不能归为胜或败。伤害分布、治疗效率和条件经验可后续增加。

### 6.2 共享服务，隔离数据

| 范围                               | 隔离要求                                                       |
| ---------------------------------- | -------------------------------------------------------------- |
| 当前事实、战术、待执行动作、控制权 | 游戏运行实例；同一游戏的两个窗口相互独立                       |
| 经历与事件                         | 游戏、数据版本、周目和读档分段；多个实例的事件身份不能冲突     |
| 经验                               | 游戏、数据版本与适用条件；允许有条件复用，不合并不同周目的统计 |
| 游戏偏好                           | 玩家与游戏                                                     |
| 角色和通用表达偏好                 | 玩家与角色，可按明确设置跨游戏使用                             |
| 聊天上下文                         | 运行实例与会话，角色或模型切换正确隔离                         |
| 模型资源                           | 可跨实例共享调度，不能因此共享游戏控制权或会话                 |

可以共享一个物理存储后端，无需每个游戏单独部署服务。不同游戏的同名敌人、技能不能自动合并；旧数据版本经验需要重新检查适用性。读档保留历史经历，但旧现场的待执行动作和异步结果失效。

沿用现有按游戏管理记录开关与经历清理的范围，同一游戏多个窗口共享管理状态；经历本身仍按上述作用域隔离。管理结果以存储服务提交为准，各窗口同步版本后才恢复写入，不能各自增加本地版本绕过清理。重新开启记录只从当前状态开始，不补录关闭期间的实时缓存。明确修改偏好不受游戏经历记录开关影响。

## 7. 并发与多模型预留

### 7.1 首期必须建立的并发边界

**可以并发思考，但每个实例只有一个战术采纳入口和一个游戏操作派发入口。**

1. 聊天与战术请求拥有独立上下文、输出和取消状态，即使用同一个模型也不能混用会话。
2. 聊天模型只输出回复和玩家意图；战术模型提交调整建议；经验任务提交结论候选，各自进入对应的受校验入口。
3. 当前战术只有协调器可以提交修改，本地执行器只读取已采纳版本并执行。其他助手入口与旅伴争用同一控制权，不能各自操控。
4. 每个调整携带实例、现场标识、依据的战术版本、修改范围及适用条件。采纳前检查相关状态，不以最后返回者为准。
5. 同一战术范围同时最多一个有效分析任务。重复触发合并；需要新任务替代时，使旧任务失去采纳资格。
6. 首期可按整份战术版本保守拒绝过期调整，不要求自动合并并发修改。后续支持不相交范围合并时，也必须校验组合后的整体一致性。
7. 普通事实更新不一律使建议过期；按依赖条件判断。读档、停止、目标替换、战斗结束和控制权变化必须使相关旧任务失效。
8. 已经发出的动作不能被新的建议追溯修改。新战术在可操作边界生效，执行前再次检查最新事实与授权。

例如：策略分析期间角色遭到重击，本地执行器按当前生存条件喝药。稍后返回的“当前无需治疗”不能覆盖已发生的结果；其中针对后续资源分配的建议，只有仍满足版本及条件时才可以采纳。

停止和手动接管不等待模型返回。迟到结果不能重新启动操作；删除记忆后的迟到写入也不能恢复被删除内容。

### 7.2 同一模型的资源并发

业务任务可以同时存在，实际推理并发按供应商和运行时能力配置。首期必须区分排队与运行，支持并发上限、任务优先级、超时和取消；后端支持时允许同模型多请求，否则排队。

聊天、快速判断和后台任务有各自预算。快速判断不默认开启深度推理；深入分析按问题明确触发，可以等待或延后。不能靠不断重试制造更多排队。

高优先级不能保证打断已经运行的推理。取消请求后，只有底层任务结束或确认取消，才能释放对应占用；旧任务无法被采纳，不代表实际算力已释放。

本地 Ollama 模型首次加载后保持驻留。单次请求结束、停止托管、取消聊天和关闭面板均不主动卸载模型或停止推理服务。每次取得资源槽位后检查真实驻留状态；确认需要重新加载时，面板显示“模型需要冷启动，正在加载，首次使用可能较慢…”，加载完成后继续原请求。模型被外部程序卸载、切换或服务重启后重新检查，不以进程内缓存保证常驻。

冷启动单独计时并设置有界等待，不挤占普通交互的短生成预算，也不扩大快速与深入战术判断的时限。日志按请求关联上下文整理、排队、加载、首段和生成耗时，区分冷、暖及无法确认驻留的状态。日志用于后续优化，不用一次简短回复的耗时代表整场战斗速度。

### 7.3 后续多模型扩展

首期允许所有任务使用同一现有模型配置，保留任务角色和模型选择的扩展点。后续可分别配置聊天、快速判断、深入策略和经验整理的模型，不要求首期完成配置 UI 或复杂路由。

任务触发、模型选择与资源调度分别处理。不同模型可能共享设备资源或服务配额，不能仅按模型名称推定独立容量。扩展多模型时继续沿用同一战术采纳和操作控制边界。

## 8. 生命周期与降级

- 玩家手动游玩时可以继续采集和聊天；未经授权不自动接管。
- 关闭面板不等于停止游戏执行或记录，沿用明确的产品生命周期；聊天取消与停止操作分别处理。
- 暂停立即撤销当前自动输入资格，取消导航并释放按键；旧计划和相关判断失效。恢复先重新观察并取得新控制版本，不复用旧导航；读档和目标替换同样使旧现场相关任务失效。
- 手动接管、停止和断连禁止继续派发动作，已发出动作尽力确认结果；重连不自动恢复旧操作。
- 模型不可用时，已有有效战术与本地反应继续；没有模型支持的聊天明确显示不可用。
- 记录失败采用有界缓冲并展示持久化状态，不阻塞动作，也不宣称已经跨重启保存。
- 引擎能力缺失时缩小执行范围或暂停相关目标，不通过模型猜测或修改数据绕过限制。

## 10. 验收与观测要求

| 验收项       | 需要证明的行为                                                                           |
| ------------ | ---------------------------------------------------------------------------------------- |

| 聊天协作     | 执行期间可聊天；旧意图迟到不覆盖新要求或重启已停止目标，主动评论不逐动作刷屏             |

| 模型生命周期 | 连续请求复用已加载模型；确认冷启动时提示，记录加载耗时；完成或取消不主动卸载             |

| 控制权       | 冲突操作入口共用仲裁；停止或暂停后无新自动输入，旧控制者的迟到清理不能撤销新控制者       |
| 记忆与隔离   | 重复事件不双计数，跨游戏与实例不串数据；跨窗口清理后旧数据不复活，开启记录不追补关闭区间 |
| 降级         | 模型、存储和引擎能力分别失败时行为可解释，已有有效本地闭环不被无关故障阻塞               |

诊断至少关联：实例与遭遇、事件与行动、有效战术版本、动作选择原因、实际结果、模型触发原因、结果采纳或拒绝原因，以及任务排队和运行耗时。

性能验收使用固定游戏样例、模型、设备、推理配置和网络条件，分别测量本地决策、游戏动画或合法操作等待、模型排队、推理、聊天首段与完整回复耗时。与旧运行方式比较整场耗时和模型调用次数，查明等待来源。

本页不承诺固定战斗时长或任意模型的响应速度。首期建立基线测量，再在对应实现方案中确定数值目标；不能用“关闭深度思考”“换小模型”或单元测试通过替代实机验证。

## 11. 当前交付范围（2026-10-29）

现有旅伴入口将已授权的连续战斗目标（`battle` / `open`）交给新本地执行器；单步操作、其他目标和普通托管保留既有路径，共用同一控制仲裁。首次接手前提取并校验玩家约束，常规命令不再等待逐步模型回复。

当前支持标准回合战斗中的攻击、防御，以及受支持目标范围的技能和可识别治疗技能。物品自动使用、复活、主动逃跑策略、TPB、自定义战斗与 RGSS 尚未接入新闭环。遇到不支持的现场、无法确认的提交或持续缺失事实会暂停，不连续重试确认键。开始接手需要处于战斗中；持续托管不自动规划地图移动或寻找下一场战斗。

模型按问题触发快慢判断，以声明式战术修改影响后续本地行动。聊天使用独立会话，并获得当前战术、行动及原因；玩家可追加禁用技能、禁用物品、集中攻击指定敌人、保留绝对 MP 数量等受支持约束。含糊请求要求澄清，旧候选不能覆盖新要求或重启停止的任务。物品禁用约束已预留，但当前执行器不会自动使用物品。

记录继续使用已有存储服务。已确认持久化的战斗结果和实际 HP 归零事实可进入经历检索，供聊天和战术判断引用；从同一事件记录生成有界读投影，不增加另一份经历写入。记录缺失或裁剪时明确表示仅覆盖已观察内容，不推断完整历史、抗性或获胜规律。与旧经历重叠时合并证据，保留已有引用；相互矛盾的结局标为未知。

每两秒及恢复在线时探测同一游戏的记忆管理版本；发现其他窗口清理或切换记录后，重载管理状态并丢弃旧待写内容。同步后，基于旧版本生成中的聊天、策略和缓存失去采用资格。此机制同步管理屏障，不实时合并所有窗口的普通经历；清理事务在存储端持续拒绝旧版本写入。

同模型请求由共享资源队列调度；服务端容量可由可信配置设置，默认一，允许在后端支持时增大。浏览器直连采用同源串行调度；多模型选择入口预留，尚无独立角色配置界面。取消使业务结果立即失效，上游请求实际结束后才释放运行占用。

Ollama 模型加载后保持驻留，完成、停止和取消请求不卸载模型或关闭服务。每次调用检查实际驻留状态；确认需要冷启动时，在现有进度区域提示用户并记录加载耗时。日志区分上下文整理、排队、启动、生成、首段及总耗时，为后续优化保留依据；其他客户端或服务重启仍可能使模型需要重新加载。

自动化验证覆盖本地执行、动态调整、停止与接管、聊天失效、单资源排队及多容量重叠、存储事务和跨连接屏障。官方 MV《LivingShipCowboy》和 MZ《ウェスプラウ戦記》样例已验证普通战斗、治疗、缺 MP、单场任务退出、停止和手动接管，实际调用游戏引擎并回读行动及 HP / MP；真实模型宿主另通过战斗中聊天、两次胜利、地图等待 65 秒、停止和存储确认。补充 MV 受伤队伍实测中，真实治疗后追加资源保留要求，下一战停止消耗 MP 并继续胜利，动态约束已证明影响实际行为。真实模型服务另通过容量一排队、容量二请求重叠和会话独立取消；本机推理后端仍按串行计算，不能据此宣称算力并行。

真实宿主补充验证了模型不可用时本地战斗继续、超时和迟到结果拒绝、模型请求中停止及手动接管。第二个认证存储客户端清理记忆后，旧聊天和战术失效；关闭记录期间继续战斗但不写入，重开不补录。另在隔离测试页复用现有管理组件，实际打开两个浏览器面板连接同一游戏宿主，开关同步通过。切断宿主到存储的实际连接期间战斗继续；另一客户端清理并关闭记录后，重连同步新版本，旧记录没有重新写回。随后使用构建后的 Next 配置页、API、插件与真实游戏内面板，连续两轮验证启用旅伴、战斗中聊天、胜利、停止及记录开关同步，补齐完整页面桥接。

样例、测试配置和逐项验收证据见技术方案。测试隔离了第三方插件，并为治疗和故障场景设置内存中的受伤队伍及敌人 HP，不能视为原游戏完整通关。同存档基准保留路由超时与提交未确认的失败记录；补上引擎按键采样确认后，最新一批本地闭环两次实际胜利，总耗时约 7.6 / 13.1 秒，执行阶段均未逐步调用模型，接手前各有两次路由生成。旧路径均未取得战斗结局，不能计算完成同一场战斗的加速倍数。最新生产链路中的六条暖模型路由全部正确，端到端约 1.7–2.8 秒；此前发生过 5 秒生成超时，仍保留该限制。

阶段一、二的完成结论限定于上述能力与已测样例，包含新旧路径基线和失败原因记录，不包含固定响应速度、所有游戏兼容性或长期稳定性保证。后续性能优化依据分段日志推进；经验结论推导与模型角色映射按阶段三、四继续单独推进。

2026-10-30 的阶段三首增量从同一批已确认战斗记录归纳[实际 HP 条件经验](technical/companion-experience.md)，携带适用条件、独立行动与遭遇数、实际变化区间及反例，供战术和聊天检索。代码负责归约与引用校验，不增加逐步模型调用，也不把保留窗口视为完整历史。跨周目复用、资源效率、通用机制假设和更多战术能力仍待后续交付。
