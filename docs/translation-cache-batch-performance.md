## 1. 背景

后台补译已经使用共享 SQLite 等值索引和独立缓存 worker。热缓存查询本身通常只需要毫秒级时间，理论上全缓存命中的批次应明显快于 Apple、Agent 等真实翻译引擎。

实际运行中出现了以下日志：

```text
[缓存] #9288：4/4 条（121 字符）完成（4 条命中缓存）
[缓存] #9289：5/5 条（228 字符）完成（5 条命中缓存）
[缓存] #9290：7/7 条（273 字符）完成（7 条命中缓存）
```

相邻批次间隔约 2～3 秒。字符数只有约 200，但耗时接近一次真实翻译请求，与本地索引查询的预期不符。

排查确认：

1. 第一批由缓存扫描直接完成，结果来源为 `cache:scan`。
2. 第一批结束时，共享缓存命中会回填到本作缓存文件，文件签名发生变化。
3. 缓存 worker 已提前扫描的后续结果仍携带旧文件签名，因此被主线程判定为过期。
4. 完整命中结果失效后没有立即重新校验，而是落回普通引擎调度。
5. Agent 或 Apple 完成请求后，管线再次发现共享缓存中的权威译文，最终结果被记录为 `cache:remote`。

因此日志显示“缓存命中”，并不代表该任务只执行了本地缓存查询。当前主要耗时来自不必要的真实引擎请求，以及小批次回填、校验和持久化产生的固定开销。

## 2. 问题定义

### 2.1 自身回填造成假性过期

缓存结果需要在使用前校验本作文件签名、共享语料版本和记录 revision。这些校验用于防止用户修改、删除或替换译文后继续使用旧结果，本身是必要的。

但当前无法区分以下两种变化：

- 外部权威变化：用户修改 seed、本作人工译文或共享缓存记录，旧结果确实需要失效。
- 任务自身回填：系统把已经命中的共享译文镜像到本作缓存文件，译文权威和匹配依赖没有变化。

第二种变化不应使同一轮已经完成的缓存扫描失效。

“自身回填”必须是可证明的连续版本变化，而不是仅凭写入者标签推断。若扫描期间同时发生人工修改，或无法证明中间没有其他写入，旧结果仍须失效。实现契约见[技术方案 §11.1](technical/translation-cache-optimization.md#111-快照版本链与失效判定)。

### 2.2 过期的完整命中错误落回引擎

完整缓存命中即使因版本变化无法直接采用，也仍然是“需要重新校验”的任务，不等同于缓存未命中。

当前过期结果可能重新进入普通任务队列，触发 Agent、Apple 或其他引擎。这样既浪费时间和算力，也可能让本地缓存任务受到引擎并发、排队和超时影响。

### 2.3 缓存批量继承了引擎批量

Agent 与 Apple 同时启用时，后台任务从较小批量开始，并按约 5 秒的目标时长自适应。该策略适合控制真实翻译引擎的长尾，但不适合毫秒级缓存查询。

全缓存任务因此可能每次只返回 4～7 条，并在每个小批次执行汇总、状态持久化和回填，固定开销被反复放大。

### 2.4 用户日志无法反映真实执行路径

只要最终采用了缓存权威译文，日志就可能显示为“缓存”。即使中间已经执行了 Agent 或 Apple，用户仍会误认为 2～3 秒全部花在本地缓存查询上。

## 3. 优化目标

1. 全缓存命中时不调用任何真实翻译引擎。
2. 任务自身产生的共享缓存回填不使同一轮缓存扫描结果失效。
3. 真正过期的缓存结果先重新校验或重新扫描，不直接按缓存 miss 处理。
4. 缓存扫描批量与引擎翻译批量相互独立，各自按成本特征调度。
5. 减少缓存批次的重复回填、状态持久化和上下文重建。
6. 用户日志准确区分纯缓存完成、缓存重新校验和执行过真实引擎的任务。
7. 保留现有人工译文保护、来源优先级、语言对、revision 和冲突校验，不以性能优化降低正确性。

运行中的同一份原文库存不得因保存译文或游戏设置而重新开始处理；只有原文实际变化才允许重建队列。暂停后继续或刷新时，必须同时校验原文和本作译文的版本，避免复用过期的待译清单。验收需检查真实引擎写入后剩余字符不因队列误重置而回跳，具体失效边界见技术方案 §11.4。

### 一次自动处理与失败恢复

- 每条原文在自动任务中只进行一次完整处理：可按现有顺序尝试可用工具；全部失败即结束该条处理。
- 成功与终态失败都计入处理进度。成功数仅计算有效译文；失败数单列，失败不写入译文缓存。
- 失败状态按游戏和原文持久保存。继续任务、重启、切换工具、刷新进度均不得自动重试失败项。新增原文仍正常处理。
- 暂停、取消、工具被禁用或尚未触发任何翻译工具，不属于“所有工具失败”，保留未处理状态。
- `/translate/list` 提供失败筛选、失败标记和重新翻译按钮。用户主动重试可以绕过自动任务的失败限制；重试成功后按现有流程保存译文才清除失败标记，预览与再次失败不清除。
- 自动任务中没有待处理项即完成，允许存在失败。完成率使用成功加失败，不能以成功率代替；页面提供失败列表入口。所有新增用户文案支持现有语言。

## 4. 非目标

- 不取消缓存结果的版本与 revision 校验。
- 不把整个共享缓存加载到内存。
- 不恢复 `LIKE`、`GLOB`、全文扫描或模糊匹配。
- 不改变原始 `src`、译文正文、人工保护或写入秩。
- 不要求用户手动配置普通游戏的缓存性能参数。
- 不因缓存优化阻塞真实未命中任务；缓存 worker 异常时仍允许引擎继续工作。

## 5. 优化需求

### 5.1 区分真实过期与自身回填

缓存结果校验必须区分变更来源：

| 变化                             | 处理要求                                        |
| -------------------------------- | ----------------------------------------------- |
| 当前任务把共享命中回填到本作缓存 | 不使同轮扫描结果失效；继续校验共享记录 revision |
| 用户修改 seed 或本作人工译文     | 旧结果失效，重新扫描                            |
| 本作缓存被其他任务或外部程序修改 | 旧结果失效，重新扫描                            |
| 共享缓存记录 revision 更新或删除 | 旧结果失效，重新查询权威记录                    |
| 共享语料规则或索引版本切换       | 旧结果失效，使用新版本重新规划                  |

自身回填豁免只能覆盖系统能够确认的同任务写入，不能通过忽略文件签名掩盖同时发生的人工修改。

### 5.2 为过期结果增加重新校验状态

调度状态需要区分：

- 缓存未扫描；
- 缓存完整命中；
- 缓存部分命中；
- 缓存明确未命中；
- 缓存结果待重新校验；
- 缓存不可用。

完整命中结果过期时：

1. 优先按当前文件签名和共享 revision 重新校验。
2. 无法增量确认时，仅重新扫描该项或受影响的小范围。
3. 重新扫描确认 miss 后，才允许进入真实引擎队列。
4. 重新校验期间不得把任务当作普通 `UNKNOWN` 项抢先派发。

重新扫描最多重试 2 次；仍无法得到当前快照时降级到引擎，缓存线路故障则立即降级，均不得让条目永久停在 `RECHECK`。

### 5.3 缓存与引擎使用独立批量

缓存扫描、缓存结果消费和用户日志不得继承 Agent、Apple 的自适应批量。三者分别定义：

| 层级           | 作用                                   | 预算来源                                         |
| -------------- | -------------------------------------- | ------------------------------------------------ |
| 缓存扫描分片   | worker 单次 IPC 领取与返回的扫描工作量 | 现有 32 项分片；受 worker 在途和结果缓冲反压约束 |
| 纯缓存结果批次 | 主线程一次消费并提交的缓存结果数量     | 独立条数与字符预算，不受引擎初始批量限制         |
| 用户日志窗口   | 一次汇总展示的任务集合                 | 已完成结果按短时间窗口聚合，不反向限制扫描       |

- 缓存扫描窗口可以持续预取，但必须受结果缓冲上限约束。
- 纯缓存结果按独立条数、字符数和明确的工作耗尽边界聚合，一次消费较大批次。
- 引擎批量继续按引擎耗时、失败率和字符预算自适应。
- 混合窗口可以分别消费缓存结果和引擎结果，不要求等待最慢引擎才能提交已经确认的缓存命中。
- 首期采用内部自动参数，不增加用户设置项；后续只有在不同设备差异无法自动适配时才考虑高级设置。
- 纯缓存结果批次首期建议最多 40 条、合计不超过 10,000 字符；这是结果消费上限，不改变现有 32 项扫描分片、64 项结果缓冲或 128 项 partial 计划缓冲。
- 纯缓存批次不得因 Agent+Apple 的初始 4 条限制而拆成小批；同时不得为了凑满批次延迟首批展示。
- 扫描分片完成不等于结果窗口完成；只有达到容量、出现真实引擎结果、进入终止状态，或缓存工作真正耗尽并经过 250ms 静默窗口，才提交纯缓存窗口。工作耗尽判定见[结果窗口聚合需求 §5](translation-cache-result-window-batching.md#5-术语)。
- 用户日志窗口可以包含纯缓存、混合和纯引擎结果，但必须按实际执行来源统计，不得把被缓存撤销的引擎任务算成缓存查询。

批次预算和状态转换契约见[技术方案 §11.2](technical/translation-cache-optimization.md#112-批次分层与调度状态)。

### 5.4 合并回填与持久化

- 共享缓存命中仍可回填本作缓存，但应按独立阈值或批次合并处理。
- 暂停、任务结束和进程正常退出前必须提交待回填数据；异常退出允许保留持久化待办，但恢复前不得宣称对应回填已完成。
- 回填失败不得丢失共享缓存中的权威译文；记录错误并允许后续重试。
- 同一批重复命中的记录只回填一次。
- 回填完成后，缓存 worker 与主线程应共享可识别的版本推进信息，避免重复解析整个本作缓存；推进信息不得跳过同时发生的人工修改。
- 状态持久化保持可恢复性，但不应按每条缓存命中重复写入完整任务快照。

### 5.5 缓存优先但不阻塞真实 miss

- 缓存 worker 健康且已有扫描结果时，引擎优先消费明确 miss 或确认需要补译的缺口。
- 尚未扫描的任务可以设置很短的缓存判定窗口，避免本地命中与真实引擎无意义竞速。
- 缓存初始化、扫描或重新校验超过预算时，引擎仍可继续处理，不能让全任务等待缓存。
- 缓存 worker 不可用时维持现有软失败行为，并在日志中明确标记缓存线路不可用。

### 5.6 用户日志必须反映实际成本

面向用户的批次日志继续使用已确认格式：

```text
[{engine}] #{batch}：{success}/{total} 条（{chars} 字符）完成（{cache} 条命中缓存）
[{engine}] #{batch}：{success}/{total} 条（{chars} 字符）成功，{failed} 条失败{cache_info}
[{engine}] #{batch}：全部失败（共 {total} 条 / {chars} 字符）
```

引擎标签使用固定来源枚举，不允许用自由文本表达组合语义：

| 批次最终来源 | 用户标签          | 判定规则                                             |
| ------------ | ----------------- | ---------------------------------------------------- |
| 仅缓存       | `[缓存]`          | 本窗口接受的译文全部来自缓存，不再重复显示“命中缓存” |
| 仅 Apple     | `[Apple]`         | 本窗口接受的译文全部来自 Apple                       |
| 仅 Agent     | `[agent]`         | 本窗口接受的译文全部来自 Agent                       |
| 缓存与引擎   | `[agent+缓存]` 等 | 按最终被接受的来源拼接；顺序固定，不按完成先后       |
| 整批失败     | `[Apple]` 等      | 没有最终来源时回退展示本批尝试过的真实引擎           |
| 缓存线路故障 | `[缓存不可用]`    | 本窗口没有最终来源、也没有真实引擎尝试时显示         |

- 标签只表达最终采用的工具，不展示已被缓存撤销或没有产出结果的尝试。
- 纯缓存批次不再追加“命中缓存”尾巴，避免标签与统计重复。
- 混合批次仍显示缓存命中条数；它统计最终采用缓存译文的条目，不替代最终来源标签。
- 调试数据必须分别记录缓存查询、引擎提交和最终来源，用户标签只是结构化来源的投影。
- 缓存线路不可用不单独决定条目成功或失败：有真实引擎结果时按该结果计数；没有真实引擎且未完成时计入 `failed`，不得伪装为缓存未命中或成功。
- 缓存线路故障不会叠加最终来源；有最终来源时标签只展示最终采用的工具。

详细诊断默认不展示给普通用户，但调试信息至少记录：

- 缓存查询耗时；
- 重新校验耗时和原因；
- 引擎排队及执行耗时；
- 回填耗时；
- 任务自身回填导致的签名变化次数；
- 过期结果重新扫描次数；
- 缓存命中后仍触发引擎的次数。

日志来源与 i18n 契约见[技术方案 §11.3](technical/translation-cache-optimization.md#113-批次日志来源与-i18n)。

## 6. 验收标准

### 6.1 正确性

| 场景                       | 必须结果                                       |
| -------------------------- | ---------------------------------------------- |
| 100% 共享缓存命中          | 不调用 Agent、Apple、Google、Bing 等翻译引擎   |
| 首批命中后发生本任务回填   | 后续已扫描命中继续有效，或仅做轻量重新校验     |
| 自身回填与人工修改并发发生 | 不得因自身回填豁免接受人工修改前的旧结果       |
| 用户在扫描期间修改 seed    | 旧结果不采用，按新内容重新扫描                 |
| 用户修改本作人工译文       | 人工译文保持最高有效权威，不被旧扫描覆盖       |
| 共享记录被更新或删除       | 旧 revision 不采用，重新查询当前权威           |
| 缓存 worker 异常           | 任务可降级到引擎，并明确记录缓存线路异常       |
| 正常结束或暂停时存在待回填 | 待回填数据已提交，或明确记录为待重试           |
| 异常退出时存在待回填数据   | 已确认结果可恢复，待回填任务可重试且不谎报完成 |
| 同一原文在一个窗口重复出现 | 只执行一次缓存查询和回填；统计按任务条目数计   |

### 6.2 性能

在记录硬件、共享语料规模、本作记录规模、冷/热状态和样本批次的前提下验收：

| 指标               | 目标或判定                                                                 |
| ------------------ | -------------------------------------------------------------------------- |
| 热态查询与安全校验 | 40 条、合计不超过 10,000 字符，p95 不高于 50ms                             |
| 热态纯缓存端到端   | 结果批次从主线程领取到全部结果可提交，p95 不高于 300ms                     |
| 连续纯缓存间隔     | 不得稳定出现 1 秒以上间隔                                                  |
| 真实引擎提交       | 100% 缓存命中回放中必须为 0                                                |
| 自身回填误拒绝     | 必须为 0                                                                   |
| 文件与上下文解析   | 连续 N 批的 seed/cache 文件读取次数和上下文重建次数不随批次线性增长        |
| 分段耗时           | 分别记录冷启动、热查询、重新校验、回填、状态持久化和日志回调，不只报告 SQL |

“热态纯缓存端到端”包含主线程领取结果、提交结果和必要的轻量校验，不包含首次 worker 启动、索引迁移、真实引擎请求和用户界面重绘。回填与任务状态持久化单独报告，不能隐藏在 300ms 目标内，也不能通过跳过它们来达标。

### 6.3 日志

- 用户看到 `[缓存]` 时，可以确认该批没有执行真实翻译引擎。
- 用户看到 `[agent+缓存]` 等组合标签时，可以确认本批最终同时采用了对应引擎和缓存译文。
- 字符数统计为本批原文 Unicode 字符数，不作为缓存查询成本的唯一解释。
- 多语言文案允许自然换行，不依赖固定单行宽度。
- 普通日志保持短小；耗时拆分只进入调试日志或诊断界面。

## 7. 实施优先级

| 优先级 | 需求                                   | 目的                             |
| ------ | -------------------------------------- | -------------------------------- |
| P0     | 修复自身回填导致的假性过期             | 停止全缓存任务落回真实引擎       |
| P0     | 过期完整命中先重新校验，不直接进入引擎 | 保证缓存优先和结果正确性         |
| P1     | 缓存批量与引擎批量分离                 | 提高纯缓存吞吐，减少小批固定开销 |
| P1     | 合并回填并同步版本推进                 | 避免重复写盘和上下文重建         |
| P1     | 用户日志反映真实执行引擎               | 避免把引擎耗时误认为缓存耗时     |
| P2     | 补充结构化性能指标和诊断               | 支持后续规模回放与回归定位       |

## 8. 回归要求

新增自动化用例至少覆盖：

1. cache worker 预扫描多项，首批回填改变文件签名，后续命中仍不调用引擎。
2. 同期发生人工 seed 修改时，自身回填豁免不能错误接受旧结果。
3. 共享记录 revision 在扫描后变化，旧结果被拒绝并重新查询。
4. 40 条纯缓存命中不受 Agent+Apple 初始批量限制。
5. 缓存重新校验失败后只有明确 miss 才进入引擎。
6. 日志标签只反映最终采用的结果来源；被缓存撤销的引擎尝试不会出现在标签中。
7. 自身回填与人工修改并发时，人工修改优先且旧结果被拒绝。
8. 同一原文重复出现时，只查询和回填一次，日志按任务条目计数。
9. 暂停、恢复和 worker 重启后不重复计数、不丢失已确认结果。
10. 正常结束、暂停和异常退出分别满足对应的回填提交或待重试语义。

性能测试与正确性测试分开：单元测试验证状态、调用次数和来源枚举；基准测试记录 p50、p95、最大值、查询次数、文件读取次数、上下文重建次数、引擎提交数、回填次数和日志回调次数。绝对耗时只写入基准记录，不写入易受机器波动影响的普通单元测试。

## 9. 缓存优先预取、来源权重与长驻 worker（2026-10-25，主体已接入，验收未完成）

本节补充并细化 §5.2–5.5 中关于“未扫描任务直接进入引擎”的边界。缓存仍不是引擎的前置条件，但 seed 作业应先给缓存一个很短的分类窗口，避免明明能命中的任务先被提交到真实引擎。

### 9.1 背景

当前 seed 会话启动缓存 lane 后会立即调用引擎调度；尚未扫描的任务以 `cacheMode: 'bypass'` 直接提交。缓存稍后命中时只能撤销已经发出的请求，无法保证“零引擎调用”。

因此用户看到 `[缓存]` 批次时，实际可能已经提交过 Apple、Agent 或 Bergamot。共享 SQLite 查询通常是毫秒级，剩余耗时主要来自：

- 未扫描任务先进入引擎，慢请求形成长尾；
- 每个缓存命中分别入队回填，批次结束时再次读取和解析本作缓存文件；
- 批次边界的状态持久化、结果校验和上下文重建；
- 引擎取消后仍占用实际在途配额，直到适配器真正结束。

这不是单纯继续优化 SQLite 索引可以解决的问题。

### 9.2 目标

1. 缓存结果足以完成的任务，在正常热态下不提交任何真实翻译引擎。
2. 缓存明确未命中或部分命中时，只把缺口交给引擎，不等待整个缓存优先窗口结束。
3. 缓存慢、初始化失败或 worker 不可用时，仍能在有界等待后降级到引擎，不能让作业卡死。
4. 来源权重决定最终权威，不按完成先后、更新时间或日志展示顺序覆盖高权重译文；本作与共享候选使用同一权重顺序。
5. 缓存扫描和引擎守护进程跨批次复用，避免每个 fill 批次重复冷启动。
6. 回填、持久化和诊断指标按窗口聚合，保留现有 revision、人工保护和崩溃恢复语义。

### 9.3 缓存优先预取

#### 9.3.1 缓存优先窗口

- 每个 seed 作业协调者（seed job worker）最多维护 64 项 `CACHE_PENDING`，包含已投递 worker 和等待下一分片的任务；不新增独立的等待队列。
- worker 仍按 32 项分片领取，同一时间最多 32 项在途；已分类但未消费的结果另受 64 项结果缓冲约束。
- 缓存优先窗口的稳态预算为 64 项 `CACHE_PENDING` + 64 项已分类结果；结果缓冲达到 64 项后停止领取新分片，已投递的 32 项分片允许收尾，因此已分类结果瞬时最多 96 项，之后必须先消费再继续，不允许无限预取。
- 部分命中计划沿用 §11.2 的独立预算，最多 128 项，不并入 `CACHE_PENDING` 窗口。
- 缓存优先窗口只覆盖尚未分类的任务，不重复扫描 `DONE`、`FAILED`、`RECHECK` 已在队列中的任务。
- 同一窗口内可按 `src + 源语言 + 目标语言 + category + 保护签名` 合并查询；当前实现仍按任务 ID 逐项扫描，结果 fan-out 与查询去重列为后续优化，完成计数始终按任务条目计算。

#### 9.3.2 缓存优先判定窗口

新发现的任务先进入 `CACHE_PENDING`，默认给缓存 1500ms 分类窗口。32 项热态分片实测约 678ms，原 100ms 会在结果返回前把任务交给真实引擎；1500ms 保留约一倍余量，同时仍是任务级放行上限，不是完整窗口屏障。该窗口从任务实际提交给 cache worker 时开始计时，不从进入缓存优先窗口时开始，避免排队本身被误判为缓存超时。

从进入缓存优先窗口起，等待 worker 可投递的准入时间同样受 1500ms 上限约束。到期仍无法投递时，任务可被引擎领取并标记为 `cacheAdmissionTimeout`；这不是 `MISS`，也不得把排队时间计入缓存查询耗时。若任务已被领取后 worker 才空闲，协调者不得再投递旧任务；已投递任务的结果仍按下面的竞速规则处理。

| 缓存结果                 | 处理                                                               |
| ------------------------ | ------------------------------------------------------------------ |
| 完整命中 `full`          | 校验通过后直接完成，不提交引擎                                     |
| 部分命中 `partial`       | 保留命中计划，只把安全缺口交给引擎                                 |
| 明确未命中 `miss`        | 立即进入引擎队列                                                   |
| 需要重新校验 `RECHECK`   | 继续重新扫描，不得当作普通 `UNKNOWN` 或 `MISS`                     |
| 候选或计划超限 `limited` | 标记为 `cacheLimited`，不得伪装成普通 `miss`；保留提交前权威复核   |
| 分类窗口到期仍无结果     | 标记为缓存超时，允许进入引擎；缓存稍后返回时按现有规则竞争或撤销   |
| worker 准入等待超时      | 标记为 `cacheAdmissionTimeout`，允许进入引擎；不得伪装成缓存未命中 |
| 缓存线路不可用           | 立即按软失败降级到引擎，并记录 `cacheUnavailable`                  |

分类窗口按任务实际投递 cache worker 的时间计时，准入等待另按 `cacheAdmissionWaitMs` 统计；不等待整个缓存优先窗口全部返回。缓存结果逐个或按小批释放，已确认的完整命中可以立即提交。

用户日志必须区分完整缓存命中与部分缓存补译。部分缓存加 Apple 补译的最终标签为 `[Apple+缓存]`，不能因为拼接结果的内部标记是 `cache:partial` 就显示成 `[缓存]`，也不能计入整条缓存命中数。多个缺口采用不同引擎时保留所有被采用的来源；尝试失败或被高权重缓存替换的输出只留在请求诊断中。

纯缓存大窗口仅接纳全文来自缓存且未等待过引擎的结果。补译完成或等待引擎后改用人工缓存的条目，应及时释放完成进度，不得因缓存标签继续等待纯缓存大窗口凑满。缓存分片 `done` 只结束一个扫描分片，不结束结果窗口；窗口只有在工作真正耗尽后才进入 250ms 静默收口。最终标签与实际请求记录分别保存，以便判断延迟来自缓存查找还是补译等待。

1500ms 是任务分类和准入的服务目标，不是缓存 worker 的致命超时。worker 仍需保留独立的粗粒度健康 watchdog；只有真正无进展或进程退出时才关闭整条缓存线路。

#### 9.3.3 不允许完整屏障

- 不要求缓存先扫描完整库存，也不要求整个缓存优先窗口全部返回后才派发引擎。
- 已知 `miss` / `partial` 可以立即使用引擎空位；缓存慢时不会因为预取而空转。
- 只有尚未分类的任务在窗口内短暂等待；窗口到期后按现有非阻塞策略放行。
- 缓存优先窗口可以在当前结果消费尚未结束时继续补充，但受结果缓冲和内存上限约束。
- `CACHE_PENDING` 已达 64 项且缓存连续 1500ms 没有分类进展时，允许引擎兜底领取窗口外 `UNKNOWN` 任务，避免缓存线路变慢后所有引擎一起空转；缓存恢复进展后重新收紧窗口。
- 这里的 1500ms 是全局停滞兜底，不是单任务分类窗口，也不改变“未确认任务不得伪装成 miss”的规则。

#### 9.3.4 缓存 worker 返回形态

目标形态是逐项或小批返回结果，并用独立完成标记结束分片，而不是每条结果都单独触发一次完整主线程调度：

- 结果至少包含任务 ID、原文、plan、快照版本和分片耗时；
- worker 启动时发送一次 `ready` 握手，只表示已初始化，不表示分片完成；
- worker 必须发送 `protocolVersion>=1`；未声明版本的 worker 直接软失败，不猜测旧版完成语义；
- worker 可发送多个逐项 / 小批结果，最后发送带同一 `batchId` 的 `done` 完成标记；
- 每次 seed 会话租约携带独立 `leaseId`；复用长驻 worker 时，旧租约的结果必须丢弃；
- 主线程可向 worker 发送已验证的 `stampAdvance`，携带 `leaseId`、`beforeStamp` 和 `afterStamp`；worker 只在自身 stamp 匹配时推进，并回传 `stampAdvanced` 确认是否生效；
- 每个已接受分片都必须在所有 `item` / `itemError` 之后收到一次 `done`；致命错误则走线路失败；
- 主线程按微任务或时间片合并同一小批结果，完成校验、去重和提交；
- 完整命中可以在分片结束前提交，不能等待分片末尾慢项；
- 主线程按 `leaseId + batchId` 接收逐项消息，并在 `done` 后聚合同一批结果，避免每条消息都触发完整调度。

### 9.4 来源权重与冲突

来源权重必须独立于新旧和完成时间。现有权重继续作为唯一来源权威：

| 来源                                                | 权重 | 说明                     |
| --------------------------------------------------- | ---: | ------------------------ |
| `manual`                                            |    4 | 人工译文，最高权威       |
| `import` / `import:*`                               |    3 | 受信任导入               |
| `live:optimize` / `live:optimize:*` / `live:agent*` |    2 | 优化或 Agent 结果        |
| 普通 `live:*`                                       |    1 | 普通实时引擎结果         |
| `manual:optimize`                                   |    0 | 旧标签，不作为新写入来源 |

选择规则：

1. 先取最高权重，不因高权重记录较旧而改用较新的低权重记录。
2. 同权重且译文一致，可以保留重复记录；重复本身不是冲突。
3. 同一权重内优先精确 `src`。
4. 精确 `src` 无法区分时再比较 category；类别匹配不能跨越权重。
5. 精确 `src` 与 category 都相同且译文一致时，才按本作记录优先于共享镜像；稳定记录 ID 只用于让相同译文的重复候选具有确定性顺序。
6. 若候选译文仍不一致，返回冲突，不静默选择；不能用稳定记录 ID 或本作优先强行消除译文冲突。`manual` 对同一精确 `src` 的明确改译属于写入冲突规则，不能被通用读取冲突永久挡住；普通引擎不得借冲突绕过同权重人工定稿。
7. 低权重旧记录可以暂时保留作为审计或回退，但不得覆盖、降级或抢占高权重记录。
8. 引擎结果提交前仍要做一次当前权威复核；高权重缓存可以在提交前替换低权重引擎结果。

候选集必须同时包含本作记录和共享记录。本作优先只能在权重、精确 `src` 和 category 比较之后执行；不能因为当前实现先查本作或先过滤 local，就让低权重本作记录压过高权重共享记录。`lookupGameTranslation()`、句子计划选择、缓存扫描和提交前复核都应使用同一权威顺序。本次优化不引入自动清理低权重记录；需要清理时另立需求，并保留人工保护和可追溯性。

候选或计划因预算超限返回 `limited` 时，不得把它计为普通 miss 后用 bypass 方式覆盖权威；应返回明确的 `cacheLimited` 原因，允许按有界降级进入引擎，但提交前仍必须执行当前权威复核。

### 9.5 长驻 worker 与冷启动

#### 9.5.1 唯一协调者

继续使用现有 seed job worker 作为唯一作业协调者，不再新增第三个总控 worker。协调者负责：

- 维护缓存优先窗口、任务状态、优先级和引擎空位；
- 接收缓存分片结果并完成权威校验；
- 把确认 miss / partial 分发给不同引擎；
- 聚合回填和状态持久化；
- 维护暂停、恢复、切换游戏和版本更新边界。

缓存扫描继续运行在独立子 worker 中，SQLite 索引和匹配逻辑不阻塞主线程。缓存 worker 不承担 Apple / Bergamot 模型推理。

#### 9.5.2 生命周期

- 缓存 worker 由 seed job worker 按 `contentRoot + database` 持有，在首次需要时创建并预热，跨多个 fill 窗口复用。
- 暂停时停止新扫描和新引擎派发，但不因暂停销毁缓存 worker；恢复时优先复用，暂停只释放会话租约。
- seed job 结束、切换游戏 / 数据库、代码 / worker 版本更新、致命错误或空闲 TTL 到期时才关闭。
- 不得在每个 fill 批次、每次日志窗口或每次暂停时重建缓存 worker。
- 主线程确认的自身回填 owned transition 必须同步给缓存 worker，使其推进本作上下文 stamp 而不重建 resolver；无法证明归属时仍保守重建。
- 启动、索引迁移和首次打开数据库的耗时单独记录，不混入热态缓存查询耗时。

#### 9.5.3 引擎守护进程

- Apple 和 Bergamot 继续使用各自长驻子进程，空闲 60 秒后回收，不按请求冷启动。
- 只有确认存在 `miss` / `partial` 缺口时才启动对应引擎守护进程；纯缓存命中不为了“预热”而启动引擎。
- Bing / Google 属于 HTTP 平台，没有本地翻译进程；连接复用只能尽力而为，不能承诺平台侧缓存或网络冷启动为零。
- 存储写入继续使用现有 storage daemon；缓存 worker 和协调者不直接争抢长期数据库写锁。

### 9.6 回填与持久化

- 每个缓存结果窗口统一调用一次批量 `queueBackfill`；分片结果先聚合，不逐条入队。
- 入队前按 `(root, src, record_id, revision)` 去重；事件身份使用 `(database, recordId, revision)`，同一 origin / revision 已存在时不得重复追加等价事件，也不能使用自增 task ID 作为事件身份。事件 ID 还必须避开已确认版本和 outbox 已排队版本，防止同 revision 删除重建后被旧 seen 集合误判为已回填。
- 正常批次边界、暂停、任务结束和正常退出前执行 `flushBackfill`；异常退出保留待办，恢复后重试。
- 没有待回填任务且没有 revision 失效项时，flush 必须直接返回，不读取、不解析完整 `cache.ndjson`。
- 回填是共享权威译文的本作镜像，其权威仍由共享 origin / revision 决定；镜像不能被当作独立新来源，也不得覆盖更高权重的本作记录。
- 回填失败不回滚已经确认的共享译文；记录错误并允许后续重试，不把“已排队”报告为“已回填”。

### 9.7 非目标

- 不把整个共享缓存加载到内存。
- 不取消文件指纹、`authorityVersion`、共享 revision 和人工保护校验。
- 不因为性能目标删除低权重旧记录或自动解决同权重冲突。
- 不把所有未扫描任务永久挡在缓存之后；缓存故障必须能降级到引擎。
- 不为普通用户新增缓存性能配置项；首期参数由内部根据实测调整。

### 9.8 验收标准

#### 正确性

| 场景                           | 必须结果                                               |
| ------------------------------ | ------------------------------------------------------ |
| 64 项全部热缓存命中            | 引擎提交数为 0，最终来源只有缓存                       |
| 缓存优先窗口内部分命中         | 命中项不提交引擎，只有 miss / partial 缺口进入引擎     |
| 缓存 worker 初始化慢           | 窗口到期后引擎可继续，作业不被全量缓存扫描卡住         |
| 缓存返回 `RECHECK`             | 首次过期不得当作 miss；仅在重试耗尽后按既有规则降级    |
| 单个任务扫描异常               | 不得伪装成缓存 miss，必须记录错误并走有界降级          |
| 候选或计划超限                 | 不得伪装成缓存 miss；提交前仍执行权威复核              |
| 缓存 1500ms 无分类进展         | 引擎可兜底领取窗口外任务，不空转                       |
| 高权重旧记录与低权重新记录并存 | 选择高权重，旧记录可以保留                             |
| 低权重本作记录与高权重共享记录 | 选择高权重共享记录，不因本作优先而反转                 |
| 同权重译文冲突                 | 精确 `src` / category 后仍不一致时返回冲突，不随意选择 |
| 缓存 worker 准入等待超时       | 引擎可领取任务，且不记为缓存 miss                      |
| 暂停后恢复                     | 缓存 worker 可复用，不重复启动和迁移                   |
| 自身回填后继续扫描             | worker 推进已验证 stamp，不重建本作 resolver           |
| 回填与人工修改并发             | 人工修改优先，旧缓存结果保守失效                       |

#### 性能

在记录共享语料规模、本作记录数、硬件和冷 / 热状态的前提下：

- 40 条 / 10,000 字符热态缓存查询与安全校验 p95 不高于 50ms；
- 纯缓存结果从主线程领取到可提交 p95 不高于 300ms；
- 100% 缓存命中回放中真实引擎提交数为 0；
- 连续纯缓存批次不得稳定出现 1 秒以上间隔；
- 缓存优先窗口、缓存分类、引擎提交、回填和状态持久化分别计时，不能只报告 SQL 查询耗时。

#### 诊断

至少记录：

- `cachePendingCount` / `cachePendingPeak`：当前和峰值的 `CACHE_PENDING` 任务数；
- `cacheClassifiedBeforeEngine`：在引擎提交前完成分类的任务数；
- `engineSubmittedBeforeCache`：缓存结果前已提交引擎的任务数；
- `cacheClassifyTimeout`：分类窗口到期仍未返回的任务数；
- `cacheAdmissionWaitMs`：任务在缓存优先窗口内等待投递 worker 的累计时长；
- `cacheAdmissionStallMs`：窗口无分类进展、触发引擎兜底的累计时长；
- `cacheWorkerSpawnCount` / `cacheWorkerReuseCount`：worker 冷启动和复用次数；
- `cacheWorkerContextRebuildCount` / `cacheWorkerStampAdvanceCount`：worker 上下文重建和自身回填 stamp 推进次数；
- `cacheChunkResponseMs`：worker 分片返回耗时；
- `backfillBatchCount` / `backfillFlushMs`：回填聚合和 flush 耗时。

### 9.9 实施优先级

| 优先级 | 工作项                                         | 目的                              |
| ------ | ---------------------------------------------- | --------------------------------- |
| P0     | `CACHE_PENDING` 缓存优先门控与 1500ms 分类窗口 | 首先保证纯缓存命中不提交引擎      |
| P0     | 缓存优先窗口按 32 项分片、结果缓冲反压         | 避免无界扫描和内存增长            |
| P1     | 逐项 / 小批返回、`done` 完成标记与批量校验     | 降低每条结果的调度和 IPC 固定开销 |
| P0     | 纯缓存结果窗口跨分片装载与工作耗尽判定         | 消除 1～3 条小窗口和固定开销      |
| P1     | 批量回填、origin 去重和窗口 flush              | 降低写盘和完整文件解析成本        |
| P1     | 缓存 worker 跨 fill / 暂停复用                 | 消除重复冷启动和索引迁移          |
| P2     | 指标、回放基准和参数调优                       | 验证收益并防止回归                |

任何阶段都不得通过跳过人工保护、共享 revision、权威权重或回填持久化来换取性能数字。
