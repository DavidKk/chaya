# Agent 游戏操作轨迹需求

> 状态：Phase 1 已实现；Phase 2–3 待开发
> 日期：2026-10-12 · 方案修订：2026-10-13
> 依赖：[`agent-activity-log.md`](./agent-activity-log.md)、[`game-agent.md`](./game-agent.md)、[`smart-path.md`](./smart-path.md)

## 1. 背景

Chaya 已有三类与 Agent 游玩相关的记录：

- Agent 活动记录：提示词、公开思考摘要、模型返回、工具调用、耗时与 Token 用量。
- 游戏历史：实际显示的对话、出现的选项、玩家或 Agent 选择的内容、地图切换、战斗与读档。
- 游戏工具结果：事件名称、交互结果、对话、选项、金币与物品变化、最终位置等。

这些记录目前彼此独立。开发者可以看到 Agent 调用了哪个工具，也可以读到游戏历史，但难以直接回答：

- Agent 当时观察到了什么，为什么选择这个目标？
- Agent 为何选择某条路线或某个选项？
- 一次工具调用期间具体发生了哪些游戏事件？
- 寻路在哪一步受阻、是否重新规划、最终为何成功或失败？
- Agent 认为成功的结果是否真的经过游戏状态验证？
- 不同模型或策略在同类任务上的成功率、耗时和成本有什么差异？

本需求建立可关联、可回放、可分析的 Agent 游戏操作轨迹。它不是增加更多无结构文本，而是把“观察 → 决策 → 操作 → 游戏反馈 → 验证”记录为一条统一时间线。

## 2. 目标

| 目标 | 说明                                                         |
| ---- | ------------------------------------------------------------ |
| G1   | 玩家和开发者可以按时间顺序看懂 Agent 如何完成一次游戏任务    |
| G2   | 对话、选项、获得物品等游戏事实与触发它的 Agent 操作直接关联  |
| G3   | 记录结构化决策依据，不依赖或声称提供模型隐藏思维链           |
| G4   | 记录足以分析寻路、目标选择、选项决策、验证与无进展循环的数据 |
| G5   | 游戏内与 Web 日志页读取同一份任务轨迹，不维护相互冲突的历史  |
| G6   | 日志失败或裁剪不能影响游戏运行和 Agent 操作                  |
| G7   | 轨迹默认仅保存在本地，可按任务导出用于后续优化               |

## 3. 非目标

- 不请求、推断或展示模型隐藏 chain-of-thought。
- 不默认记录每一帧、每一个按键持续帧或完整画面视频。
- 不在第一版自动上传轨迹或游戏文本到远端。
- 不在第一版提供跨用户的模型排行榜或云端分析平台。
- 不把 Agent 游戏轨迹复制到通用插件文本日志中。
- 不用日志记录替代操作前后的真实状态验证。

## 4. 核心决策

### 4.1 展示统一，数据分层

游戏内继续复用现有“思考过程”面板，不新增“操作日志”并列面板。面板展示一条统一时间线，依次包含：

1. 观察：Agent 读取到的关键游戏事实。
2. 决策：候选目标、排除项、选择理由和预期结果。
3. 操作：工具调用、移动、按键、互动和等待。
4. 游戏反馈：对话、选项、选择、奖励、地图和战斗变化。
5. 验证：实际结果是否符合目标与预期，下一步为何继续或结束。

底层仍使用不同的事件类型保存这些内容，并通过同一任务和动作标识关联。展示统一不等于把所有内容拼成一段文本。

### 4.2 “思考过程”的边界

“思考过程”是用户当前熟悉的入口名称，内容升级为完整的 Agent 过程。第一版保留该名称和入口，不增加迁移成本；面板标题或空态可以使用更准确的“Agent 过程”。

可记录的决策信息包括：

- 当前目标与约束。
- 观察到的关键事实。
- 候选目标或候选动作。
- 被排除的候选项及原因。
- 最终选择及简短理由。
- 预期结果和验证条件。
- 操作后的实际结果、差异和下一步。

模型供应商若返回独立的公开 reasoning / thought，可作为折叠的调试附件保存；核心时间线不得依赖该字段存在，也不得把它描述为完整内部思维。

### 4.3 多源事实与统一投影

运行中的 `AgentTask` 事件流是 Agent 目标、公开决策、工具调用和任务结果的权威来源；游戏插件事件流是地图、对话、选项、奖励、战斗和运行时变化的权威来源。游戏内思考过程和 Web Agent 活动页按关联 ID 把两类来源投影成一条时间线，但不在写入层复制事件。

- 游戏插件必须在事实发生或被实际观察后生成游戏事件。服务不能根据工具返回值推测 `game.chest_opened`、`game.map_changed` 或奖励事实。
- 工具开始与结束由 Agent 协调服务记录；插件观察到的游戏反馈引用同一个 `actionId` 或 `toolCallId`。没有可靠归因时保留事实并标记 `unattributed`。
- 本地服务可代理插件事件落盘，Cloud 页面可代理写入 IndexedDB；代理不取得事件所有权，必须原样保留插件生产者身份、epoch 和序号。
- 归档失败不得回写或改变实时事件；UI 只显示一次降级告警。
- 实时事件与归档事件使用相同的 schema version、来源事件 ID 和来源序号，恢复时按稳定键去重，不做基于文本或时间的猜测合并。进入 Agent 时间线后的 `taskSeq` 是查询投影字段，不覆盖插件原始 `sourceSeq`。

### 4.4 多实例、重连与冲突

- `libraryGameId` 标识库中游戏，`runtimeInstanceId` 标识一次游戏进程，`pluginInstanceId` 标识插件实例，`connectionId` 标识连接。`gameId` 仅作为旧接口兼容字段，不能承担全部身份语义。
- 同一个库游戏允许同时运行多个实例；每条游戏事件必须绑定唯一运行实例和插件实例。任务未指定唯一实例时应等待用户选择，不能按同名游戏猜测。
- 插件事件唯一键为 `pluginInstanceId + producerEpoch + producerSeq`。重试复用相同键，插件重启增加 epoch。
- 每个插件实例同一时刻只允许一个活动 writer lease；新连接接管后，旧连接的续写被拒绝。
- 同一唯一键重复且内容相同视为幂等成功；内容不同则拒绝并记录 `GAME_LOG_EVENT_CONFLICT`，不得使用最后写入覆盖。

## 5. 使用场景

### 5.1 打开宝箱

玩家要求“打开厨房里的宝箱”。轨迹应完整展示：

```text
观察
  当前地图：厨房；玩家位置：(8, 11)
  发现未处理宝箱事件 #12，距离 9 格

决策
  选择事件 #12
  理由：目标类型匹配、未处理、路径可达
  预期：触发对话、选项或获得物品

寻路
  起点：(8, 11)；目标站位：(14, 9)
  规划 9 步；途中无危险触发事件

游戏反馈
  老人：“这是我年轻时留下的箱子。”
  老人：“里面的东西你可以拿走。”
  选项：打开箱子 / 暂时不打开

决策
  选择“打开箱子”
  理由：符合玩家目标，未发现额外风险

游戏反馈
  获得高级药水 ×1
  宝箱事件页 0 → 1

验证
  背包物品增加，宝箱状态改变；任务成功
```

### 5.2 寻路失败

玩家要求前往一个事件，但角色无法到达。轨迹必须区分：

- 地形不可通行。
- 站位候选全部不可达。
- 被普通事件或动态 NPC 阻挡。
- 被门、传送点或其它触发事件阻挡。
- 搜索预算耗尽。
- 移动过程中地图、场景或目标状态发生变化。
- Agent 重复相同动作且没有新进展。

轨迹应显示选择过的目标站位、阻挡对象、重规划次数、最终停留位置和失败分类，不能只记录一个 `no_path` 字符串。

### 5.3 对话与选择

Agent 推进对话时，轨迹必须保留实际渲染过的原文、可用翻译、说话人、选项列表和最终选择。选择事件必须关联到当时出现的选项，不能只有“按了向下和确认”。

若 Agent 因玩家约束、风险或信息不足而不选择，记录等待原因和向玩家提出的问题。

### 5.4 战斗与菜单

轨迹记录 Agent 观察到的当前行动者、可用命令、选中项和关键战斗状态；记录选择了哪个命令、目标和原因，以及战斗结果。普通方向键过程默认折叠为“从第 1 项移动到第 3 项并确认”，原始按键只在展开详情中提供。

## 6. 轨迹模型

### 6.1 关联层级

所有来源事件必须具备稳定的生产者和运行实例身份；只有进入 Agent 任务时间线的事件才必须具备任务关联：

```text
game session
└── Agent task
    └── turn / cycle
        └── step
            └── action / tool call
                └── game events
```

最少关联字段：

| 字段                | 用途                                      |
| ------------------- | ----------------------------------------- |
| `libraryGameId`     | 标识游戏库中的稳定游戏                    |
| `runtimeInstanceId` | 隔离同一游戏的多个运行实例                |
| `pluginInstanceId`  | 标识产生游戏事实的插件实例                |
| `connectionId`      | 区分一次连接和 writer lease               |
| `conversationId`    | 关联旅伴或 Agent 的连续会话               |
| `taskId`            | 关联玩家发起的一次 Agent 任务，可为空     |
| `turnId` / `cycle`  | 关联一次模型循环或持续任务周期            |
| `stepId`            | 关联一次观察、决策与验证步骤              |
| `actionId`          | 关联工具调用与其间发生的游戏事件          |
| `sourceSeq`         | 保证同一生产者来源流稳定排序与断线恢复    |
| `taskSeq`           | 进入 Agent 任务投影后的任务内排序，可为空 |
| `at`                | 记录实际发生时间并计算耗时                |

### 6.2 必须支持的事件类别

| 类别     | 典型事件                                                                                | 主要内容                                               |
| -------- | --------------------------------------------------------------------------------------- | ------------------------------------------------------ |
| 任务     | `task.started`、`task.completed`、`task.failed`、`task.stopped`                         | 目标、入口、模型、终态、总耗时                         |
| 观察     | `agent.observation`                                                                     | 场景、位置、附近事件、对话、菜单、背包等关键事实或差异 |
| 决策     | `agent.decision`                                                                        | 候选项、排除原因、选择、理由、预期、置信信息           |
| 操作     | `tool.started`、`tool.completed`、`input.sequence`                                      | 工具参数、摘要、结果、错误与耗时                       |
| 寻路     | `navigation.planned`、`navigation.replanned`、`navigation.completed`                    | 起终点、站位、路径长度、阻挡、重规划和结果             |
| 剧情     | `game.dialogue`、`game.choices_shown`、`game.choice_selected`                           | 说话人、文本、选项与选择                               |
| 游戏变化 | `game.inventory_changed`、`game.gold_changed`、`game.map_changed`、`game.event_changed` | 可验证的前后变化                                       |
| 战斗     | `game.battle_started`、`game.battle_action`、`game.battle_completed`                    | 战斗实例、动作、目标与结果                             |
| 验证     | `agent.verification`                                                                    | 目标条件、预期、实际、是否通过、继续或结束原因         |
| 诊断     | `trace.gap`、`trace.degraded`                                                           | 裁剪、丢失、持久化失败与降级                           |

### 6.3 状态记录原则

- 每个任务开始和结束记录一个完整但经过裁剪、脱敏的关键状态检查点。
- 每个动作之间优先记录状态差异，不重复保存完整游戏状态。
- 对话和选项以游戏实际渲染事件为准，不只依赖 Agent 工具返回的摘要。
- 工具完成事件记录该动作覆盖的游戏历史序号范围，或直接引用对应游戏事件。
- 事件顺序以任务内 `seq` 为准；不同来源时间相同时不得依赖毫秒时间排序。

## 7. 结构化决策要求

一次会改变游戏的 Agent 动作，在可获得信息时应产生以下公开决策字段：

```ts
type AgentDecision = {
  goal: string
  observation: string
  candidates?: Array<{
    id: string
    label?: string
    kind?: string
    score?: number
    excluded?: boolean
    reason?: string
  }>
  chosen?: {
    id: string
    action: string
  }
  reason: string
  expected?: string
  verification?: string[]
  confidence?: number
}
```

要求：

- `reason` 必须是面向玩家和开发者的简短依据，不得复制整段系统提示词。
- 有多个可行目标时记录候选项和选择依据。
- 玩家明确排除的人物、入口、危险动作等仍可作为 `excluded` 候选记录，便于判断约束是否正确生效。
- 快速确定性操作可以只记录选择和规则来源，不强制调用模型生成解释。
- 最终验证必须引用实际状态变化；“工具返回成功”本身不能作为任务完成的唯一证据。

## 8. 寻路记录要求

### 8.1 默认摘要

每次寻路至少记录：

- 地图 ID、地图名称与地图尺寸。
- 起点、目标事件、候选站位和最终选择的站位。
- 使用的寻路实现与关键设置。
- 计划路径长度、实际移动步数和耗时。
- 搜索节点数或搜索预算结果。
- 发现的阻挡地形和阻挡事件。
- 是否自动处理途中可打开的门。
- 重规划次数、触发原因和每次重规划后的结果。
- 最终位置及 `arrived`、`nearest`、`blocked`、`timeout`、`transferred`、`interrupted` 等结果。

### 8.2 详细模式

默认不保存逐帧轨迹。满足以下任一条件时可附加详细路径：

- 寻路失败或超时。
- 发生两次及以上重规划。
- 实际步数明显大于计划步数。
- 用户或开发设置显式开启详细诊断。

详细路径可以包含压缩后的坐标序列、每次移动输入和阻挡判断，但必须限制长度，不能让日志增长影响游戏帧率。

## 9. 游戏事件要求

### 9.1 对话

- 记录原始游戏文本、说话人、显示时间和重复次数。
- 有翻译时同时记录翻译文本，但原文仍是事实来源。
- Agent 快进或自动推进的对话同样记录。
- 一次工具调用自动推进多段对话时，每段分别进入时间线。

### 9.2 选项

- 记录完整选项列表、可选状态和默认选中项。
- 选择事件记录索引和文本，并关联对应的选项列表事件。
- 记录选择是由 Agent、玩家还是游戏脚本产生。
- 无法唯一判断时记录等待玩家，而不是伪造 Agent 决策。

### 9.3 奖励与状态变化

- 记录金币、物品、武器、护甲和关键队伍状态变化。
- 记录地图事件消失、事件页变化或当前页无命令等结果。
- 奖励变化应与触发它的 `actionId` 关联；无法可靠归因时标记为 `unattributed`。

## 10. 展示需求

### 10.1 游戏内“思考过程”面板

- 复用现有面板与入口，展示当前共享任务的统一时间线。
- 旅伴发起、Agent 侧栏发起和持续托管任务都进入同一共享任务事件流；旅伴面板显示当前任务，任务结束后显示该游戏最近一次任务。
- 默认显示面向玩家的摘要，不直接铺开 JSON、完整状态或坐标数组。
- 运行中自动追加新事件，但不得强制抢走用户当前阅读位置；用户位于底部时才自动跟随。
- 同一动作按“决策 → 操作 → 游戏反馈 → 验证”形成视觉分组。
- 工具调用、详细路径、原始模型返回和状态差异默认折叠。
- 对话、选项、奖励和失败原因默认可见，不要求展开工具 JSON 才能读到。
- 任务结束后保留记录，可从聊天回复下重新展开。
- 继续沿用当前的键盘访问、滚动和停止任务能力。

第一版提供紧凑筛选：

- 全部
- 决策
- 游戏
- 操作
- 性能

筛选只改变展示，不改变底层事件或正在运行的任务。

### 10.2 Web“Agent 活动”页

- 继续按任务选择记录，默认显示与游戏内一致的统一时间线。
- 提供完整筛选、事件搜索和原始数据展开。
- 任务头部显示游戏、模型、开始时间、终态、总耗时、工具次数与 Token 用量。
- 寻路动作显示计划步数、实际步数、重规划、阻挡和耗时摘要。
- 支持导出当前任务轨迹；导出前沿用统一脱敏。
- 发现历史缺口时在缺口发生的位置显示提示，而不是只在页面顶部告警。

### 10.3 文案规则

用户默认看到游戏语义，不以内部工具名作为主要描述：

| 内部动作              | 默认展示           |
| --------------------- | ------------------ |
| `chaya_live_state`    | 观察当前游戏状态   |
| `chaya_live_interact` | 前往并与“宝箱”互动 |
| `chaya_live_press`    | 选择“打开箱子”     |
| `chaya_live_move_to`  | 前往目标位置       |

内部工具名、参数和结果保留在展开详情中，便于调试。

## 11. 持久化与导出

- Agent 任务状态继续使用现有可恢复任务存储；长期轨迹使用独立的追加式记录，避免受近期任务裁剪影响。
- App / local 模式由插件产生游戏事件，本地服务作为存储代理写入文件；Cloud 模式由插件产生事件，页面作为存储代理写入 IndexedDB。两种模式都不向 `localStorage` 写入大体积轨迹。
- Agent 任务轨迹与游戏运行日志分开保存并通过关联 ID 查询：统一展示不要求共用文件或共用 writer。
- Phase 1 延续近期任务的 20 个任务、单任务 200 个事件和 7 天边界；启用 Phase 2 长期轨迹后，所有长期日志合计默认保留 30 天或最多 100 MB，任一上限触发时按最旧已结束任务清理。
- 玩家可以删除单个任务、清空全部轨迹或导出单个任务。
- 推荐导出格式为版本化 JSONL；另附任务摘要 JSON，便于人工阅读和离线分析。
- 清空陪玩聊天不默认清空长期诊断轨迹，界面必须明确区分；若产品继续沿用“一并清空”，确认文案必须明确说明会删除哪些数据。
- 删除 Agent 任务默认只删除 Agent 任务事件和关联投影，不删除没有任务关联的游戏来源事件；按游戏或运行实例清理时，才按对应范围删除 `sourceEvents`。
- 本地服务是文件唯一物理 writer，Cloud 页面是 IndexedDB 唯一物理 writer；插件通过上报协议写入，不直接竞争归档文件。

## 12. 隐私与安全

- 默认仅本地保存，不自动同步或上传。
- 凭证、Authorization、cookie、token、secret、password、API key 和本机绝对路径必须在写入前脱敏。
- 系统提示词可以按现有活动记录规则保存，但不得包含接入凭证。
- 游戏对话、选择和截图属于用户游戏内容；导出或未来上传前必须由用户主动操作并明确范围。
- 轨迹内容是数据，不得在后续回放或分析时作为系统指令执行。
- 日志不得包含可直接执行的任意脚本或未校验工具调用入口。

## 13. 性能与降级

- 写轨迹不得阻塞游戏主循环；内存排队后异步追加。
- 频繁的移动帧、位置变化和重复对话必须合并或采样。
- 单个事件、数组深度、坐标序列和总文件大小均设置硬上限。
- 持久化失败时 Agent 继续运行，并产生一次可见的 `trace.degraded` 警告。
- 部分游戏 Hook 不可用时继续记录工具层事件，并标记缺失的游戏事件来源。
- 服务或 UI 断线后按 `seq` 补发；被裁剪时产生 `trace.gap`。
- 任意日志异常不得改变游戏状态、按键输入、工具结果或任务终态。

## 14. 分阶段交付

### Phase 1：统一轨迹

- 为任务、步骤、工具调用和游戏事件增加稳定关联 ID。
- 在现有任务事件流中增加观察、决策、游戏反馈和验证事件。
- 工具调用关联调用期间产生的游戏历史序号范围。
- `chaya_live_interact` 输出寻路摘要和可验证状态变化。
- 游戏内思考面板与 Web Agent 活动页展示统一时间线。
- 继续使用现有近期任务存储，先验证事件模型和展示。

### Phase 2：长期记录与导出

- 增加独立追加式轨迹存储。
- 支持 30 天 / 100 MB 保留策略、删除和单任务导出。
- 增加完整筛选、搜索、原始事件详情和任务统计摘要。
- 为失败寻路和多次重规划保存详细路径。

### Phase 3：优化分析

- 统计寻路成功率、平均路径长度、重规划率与失败分类。
- 统计目标选择准确率、选项等待率、验证失败率和无进展循环。
- 对比不同模型、配置和策略的成功率、耗时与 Token 成本。
- 支持选取脱敏任务组成本地回归数据集；任何上传能力另立需求并要求明确授权。

## 15. 验收标准

1. Agent 打开宝箱时，思考过程面板按顺序显示观察、目标选择、寻路、相关对话、选项、选择、奖励和验证结果。
2. 游戏内不新增独立操作日志面板；同一任务的思考与操作在现有思考过程入口统一展示。
3. 时间线默认使用游戏语义描述，工具名和原始 JSON 只在展开详情中显示。
4. 对话和选项以游戏实际渲染记录为准；Agent 自动推进的内容不会丢失。
5. 每个游戏事件可以追溯到任务、步骤和触发它的操作；无法归因时明确标记。
6. 一次寻路可看到起点、目标、候选站位、计划与实际步数、阻挡、重规划、耗时和最终结果。
7. Agent 决策记录候选目标、排除原因、最终选择、简短理由和验证条件，不展示或声称展示隐藏思维链。
8. 工具返回成功但游戏状态未满足目标时，验证显示未通过，任务不会被错误标记为成功。
9. 用户可以按全部、决策、游戏、操作和性能筛选，同一事件不会因切换筛选重复或丢失。
10. 刷新、关闭面板或事件流重连后，仍能按序恢复当前任务轨迹；缺口有明确提示。
11. 日志持久化失败、事件过大或 Hook 缺失时，游戏与 Agent 任务继续运行并显示降级状态。
12. 导出内容不包含凭证和本机绝对路径；默认不会自动上传游戏文本或轨迹。
13. 默认记录不会因逐帧移动或重复对话造成明显游戏卡顿；失败诊断仍能提供足够的详细路径。
14. 长期轨迹达到时间或容量上限时只清理最旧已结束任务，不删除正在运行的任务。
15. 同一个库游戏的多个运行实例同时工作时，时间线不会串实例；无法唯一确定目标实例时任务不会猜测执行。
16. 插件重试、重连和服务代理重放不会产生重复游戏事件；旧租约写入和内容冲突均有明确诊断。
17. 工具返回成功但插件未观察到预期变化时，时间线只显示工具成功，不显示未经确认的游戏结果。
