# 翻译调度优化基线：速度优先，质量持续提升

- 日期：2026-10-22。
- 状态：批量补译后台作业已接入非阻塞缓存与引擎调度；其余差距见第 9 节。
- 目标：先尽快获得有效译文，再按需改善准确度。
- 适用范围：原文批量翻译、缓存缺口补译、游戏内实时翻译；Web 控制台与 MV、VX/VX Ace 插件保持相同行为，入口和运行环境仍各自独立。
- 关联：[翻译管线与缓存规范](technical/translation-pipeline.md)、[历史并发与徽标需求](translation-concurrency-and-badges.md)、[历史并发技术方案](technical/translation-concurrency-and-badges.md)。
- 按需定位：调度差距 §9，性能 §13，非阻塞缓存接线 §14；缓存匹配另见[缓存需求](translation-cache-optimization.md)，不重读整套管线。

**本文件作为后续翻译调度优化的统一入口。** 调整调度、并发、失败转移、重试或质量提升策略时，先更新本文中的规则、场景和验收项，再同步实现与测试。历史文档中“所有引擎立即竞速”的描述不再作为目标；缓存匹配、开关独立和就绪检测仍沿用各自规范。

## 1. 核心决策

采用“独立引擎队列 + 有限并发 + 失败转入队尾 + 按需质量提升”。

1. 缓存非阻塞：已经就绪的完整有效命中直接完成，已知部分命中只补缺口；未完成缓存匹配的文本允许直接翻译，引擎有空位时不等待缓存线路。缓存扫描可独立推进全程，详见第 14 节。
2. 不同引擎同时处理不同文本；每个引擎拥有自己的排队和在途上限。
3. 单条文本正常情况下只由一个引擎处理。失败后释放当前处理位置，再进入下一引擎的队尾，不占着一个批处理工作位置等待整条兜底链。
4. 明显慢于预期时，允许有限的备用请求竞速，避免单条文本长期卡住；不默认向所有引擎重复发送每条文本。
5. 首个通过校验的结果完成快速翻译；Agent 可按需承担后续精翻，不阻塞快速结果。
6. 本轮已经失败的“文本 + 语言对 + 具体引擎配置”不再尝试。seed 自动任务在所有可用工具耗尽后持久标记失败，成功与最终失败都计入处理完成；继续、重启及配置变化均不自动重试。用户在翻译列表主动重译并保存后解除失败标记。
7. 工具开关完全独立，支持全部关闭。关闭、未就绪、被请求白名单排除的引擎不参与首次派发、兜底或精翻。

“快速翻译”和“精翻补全”是两个逻辑阶段，不要求新增两个按钮。后续界面若提供操作入口，应复用现有风格并单独确认交互。

## 2. 首次分配与跨组兜底

### 2.1 首次分配

- 在已开启、就绪且允许接收当前文本的引擎中选择。
- 默认优先使用本地离线工具或免费平台，依据当前排队长度、可用位置、近期成功耗时和成功率估算完成时间，不认定本地一定比平台快。
- 无免费快速通道时，允许直接使用已开启的 Agent；只有单个工具开启时只使用该工具。
- 尚无统计数据时采用保守并发和稳定配置顺序；样本积累后再调整，不依赖未经实测的毫秒数。
- 运行成本和文本可发送范围先作为约束，再在合格引擎中比较速度。Agent 可能使用收费服务，不能默认认定免费。

### 2.2 失败后的顺序

首次选定的引擎决定起始类别。正常失败时，同类未尝试引擎全部失败后才换类：

| 起始类别 | 类别顺序            |
| -------- | ------------------- |
| Agent    | Agent → 平台 → 离线 |
| 平台     | 平台 → Agent → 离线 |
| 离线     | 离线 → Agent → 平台 |

- 同类内按稳定配置顺序选择尚未尝试、可参与的引擎；转移任务进入目标引擎队尾。
- 队列繁忙不算引擎失败；已关闭或不支持该语言对的工具直接排除，不为它无限等待。
- 有在途请求或仍可派发的任务时，不提前标记全部失败。
- 超时备用竞速是第 4 节定义的明确例外，必须单独记录原因，不能隐式退化为全引擎竞速。

示例：文本 A 在 Agent 失败后排入 Google 队尾。Agent 可以继续处理文本 B；Google 完成自己已有任务后再处理 A。若 Google 也失败，则继续同组其他可用平台，平台全部失败后再进入离线队列。

## 3. 独立队列与任务记录

每个具体引擎独立维护队列，而非每个类别只共享一个串行入口。Agent 的实例与模型共同标识配置；本地工具和平台也保留实际配置身份。

每条文本至少记录：

| 信息                                        | 用途                                   |
| ------------------------------------------- | -------------------------------------- |
| 作业 ID、轮次、游戏绑定与内容版本           | 隔离游戏切换、恢复和旧请求             |
| 原文/缺口标识、源语言、目标语言、上下文版本 | 合并真正相同的任务，不误合并不同上下文 |
| 当前阶段、起始类别、当前目标与入队时间      | 明确首次翻译、失败转移或精翻           |
| 已尝试/失败引擎配置集合与原因               | 本轮去重，防止来回循环                 |
| 在途尝试 ID、请求开始时间、截止时间         | 判断备用请求和迟到结果是否有效         |
| 快速结果、精翻状态、缓存来源与依赖版本      | 区分已可用和仍待改善的译文             |

并发约束：

- 同时设置引擎在途上限、作业整体上限和队列容量，防止积压无限增长。
- 初期采用保守上限；当前批内并发 4 仅为已有实现，不等于每个引擎都适合并发 4。
- 本地原生守护进程若实际串行执行，调度上限应匹配其吞吐，避免请求在 stdio 内堆积后一起超时。
- 所有请求路径共享限额，避免批量补译、实时对白和精翻分别计算并发后叠加超限。
- 实时对白优先于后台精翻；同一优先级保持入队顺序，并通过公平调度防止后台长期无法推进。
- 独立文本可乱序完成，对外批量返回仍保持输入顺序。快速完成数与精翻完成数分开统计。

## 4. 超时、故障与有限竞速

正常情况下，每条文本最多一个快速翻译请求在途。预计完成时间明显超出引擎近期正常范围时，可向另一个允许的引擎派发一个备用请求：

- 该文本最多同时存在两个快速翻译尝试；两个请求都计入对应引擎和作业限额。
- 默认备用通道仍优先使用免费、可接收该文本的引擎；收费通道仅在用户授权的策略内参与。
- 尚无足够耗时样本时使用明确配置的保守超时；阈值属于后续压测参数，不在本文虚构固定最优值。
- 第一个有效结果完成快速任务，尚未发出的备用任务立即撤销。
- 已发出的请求在适配器支持时取消；不支持取消时继续计入在途数量，直到实际结束，不能假装已经释放服务资源。
- 迟到结果只能在作业、文本、配置和缓存依赖仍有效时参与候选缓存，不重复计数、不反复替换当前对白。
- 限流、连续超时和服务不可用触发引擎级冷却；冷却期间不派发新请求，不逐条制造相同故障。
- 文本内容错误只影响该文本；不能因为一条特殊文本失败就认定整个引擎不可用。

## 5. 准确度与精翻补全

### 5.1 快速结果校验

非空不等于有效。保留并完善目标语言、原文照抄、控制码、占位符、数字和术语一致性检查。校验失败按本次翻译失败处理，继续排队兜底。

数字、术语等检查须理解游戏转义码和格式，避免把合法的语言表达差异一律判错。校验规则及其误报应有独立测试。

### 5.2 精翻触发

- 对长对白、上下文不足、术语冲突或用户明确选择的内容，可排入已开启 Agent 的精翻队列。
- 精翻继承原文、可用上下文、术语约束和控制码，不把快速译文直接当成唯一源文。
- Agent 没有开启、不就绪或不在本次请求允许列表时，不创建精翻请求。
- 精翻使用剩余资源，不挤占当前对白或尚未补齐的缺词；失败不撤销已经可用的快速译文。
- 精翻也记录尝试集合并遵守同类失败转移规则，不能无限重复调用同一个实例。

### 5.3 缓存择优与显示稳定

- 人工确认的译文优先保护，自动结果不得覆盖人工决定。
- 同时保存来源、语言对、配置版本和校验结果，沿用现有缓存权威与版本规则。
- Agent 来源、耗时更长或返回更晚均不能单独证明更准确。未能证明更优的结果保留为候选，避免自动替换可信定稿。
- 候选精翻结果不会自动成为人工确认结果；比较与提升规则需要独立实施和验收。
- 当前正在显示的对白不因后台结果反复变化；缓存经规则选出的结果用于后续查找、后续渲染或明确刷新。
- 写回前重新检查人工修改、缓存依赖和游戏绑定，不能用迟到结果覆盖新版本。

## 6. 场景与处理方式

| 情况                               | 处理方式                                                                         |
| ---------------------------------- | -------------------------------------------------------------------------------- |
| 人工译文或完整有效缓存命中         | 直接完成，不调用翻译引擎，不自动覆盖                                             |
| 缓存部分命中                       | 保留命中部分，仅为缺口创建任务；组合结果不冒充新的整段定稿                       |
| 没有缓存，多个免费工具可用         | 按预计完成时间首次分配，各工具同时推进自己的队列                                 |
| 当前工具处理正常                   | 其他工具处理其他文本，不重复广播同一条                                           |
| 报错、空译文、照抄原文、控制码缺失 | 记录本次失败，进入同类下一引擎队尾；同类耗尽再换组                               |
| 当前请求明显慢于预期               | 在限额内允许一个备用请求，不等待整组超时才恢复进展                               |
| 平台限流或引擎连续故障             | 冷却该引擎，保留其他工具的吞吐；记录可解释原因                                   |
| 已有快速译文，精翻后来完成         | 校验、检查版本并作为缓存候选；当前画面保持稳定                                   |
| 全部允许引擎耗尽且没有在途请求     | 标记最终失败，保留各次失败原因，不写入伪译文                                     |
| 同一文本再次被发现                 | 复用任务或结果；seed 最终失败跨继续与重启保留，不自动重新派发                    |
| 用户主动重试失败项                 | 在翻译列表显式重译；保存成功后清除失败标记，预览或再次失败仍保留                 |
| 用户暂停                           | 停止派发新任务，保存已完成结果；在途任务按明确的暂停契约收尾                     |
| 用户取消或切换游戏                 | 取消待派发和可取消请求；旧结果不能写入新游戏或新轮次                             |
| 工具在排队期间被关闭               | 撤销该工具未派发任务，转到仍允许的引擎；不隐式重新开启                           |
| 全工具关闭                         | 仅使用缓存；缺词保留待译状态，不启动后台精翻                                     |
| 只有一个工具开启                   | 仅使用该工具；失败后标记失败，不偷偷调用其他工具                                 |
| 敏感文本或请求限制接收范围         | 所有队列、备用请求和精翻统一执行现有发送约束，不能用兜底绕过                     |
| 将来接入收费工具                   | 明确“立即参与/免费通道耗尽后参与/不参与”及成本限制，不因免费通道超时自动授权付费 |

## 7. 生命周期与恢复

- 区分待入队、排队中、执行中、等待转移、快速完成、精翻排队/执行/完成、最终失败、暂停和取消。
- “快速完成”与“精翻待处理”可以同时成立；精翻失败不能把已完成的快速任务改成失败。
- 恢复作业时保留同一轮的尝试记录；对进程退出时仍在途的请求记录中断，不直接伪造成功，也不无限自动重试。
- 用户暂停后的继续属于同一轮；主动重试失败项才开启新轮。配置变化不解除 seed 自动任务的最终失败限制；未实际派发、暂停及取消造成的中断不记为最终失败。
- 收到取消后不得派发下一次兜底；关闭数据库或运行时前等待受管理的在途收尾，避免在途任务操作已释放的资源。
- 调度状态属于作业，不把失败原因或待译状态当译文写进共享缓存。

## 8. 验收与测试矩阵

后续实现必须同时验证服务端和插件路径，不能只测试排序工具函数：

1. 缓存：完整命中零调用；部分命中只补洞；人工更新后迟到结果不能覆盖。
2. 首次派发：依据合格工具的排队和耗时选择；全部关闭、单工具、显式白名单均无越界调用。
3. 队列：同类全部失败后换类；失败进入目标队尾；其他文本继续推进，不被失败链占住工作位置。
4. 去重：本轮每个文本与引擎配置最多正常尝试一次；重复发现、暂停恢复和作业恢复不产生循环。
5. 并发：每个引擎、作业整体和备用请求均遵守上限；批量返回顺序稳定；实时与精翻公平共享资源。
6. 超时：正常请求无额外竞速；超时只增一个备用；首胜后无新派发；不可取消请求仍占在途位置。
7. 故障：限流冷却、单条内容失败、全部失败、空译文、照抄和控制码丢失分别覆盖。
8. 精翻：不开 Agent 不精翻；精翻失败保留快速译文；有效结果仍需遵守缓存权威与版本规则。
9. 生命周期：暂停停止派发；取消不再兜底；切换游戏隔离旧结果；资源释放等待在途收尾。
10. 成本与发送范围：免费/收费资格明确；敏感文本、请求白名单和引擎开关对所有阶段一致生效。

性能验收使用同一语料、同一引擎环境，对比当前实现；同时记录首条有效译文耗时、整批耗时、成功率、队列等待、每引擎请求数、备用请求比例及资源占用。吞吐提高不能以丢失控制码、重复计数或无上限重复请求换取。

## 9. 当前实现与实施顺序

后台 seed 作业已采用独立缓存 worker 与持续补位的引擎调度；直接单次补译、CLI 与实时入口仍沿用原有缓存先行流程。跨请求在途去重与引擎限额由服务端翻译入口共用，插件入口不因此合并。

| 能力                       | 当前情况                                | 后续工作                                 |
| -------------------------- | --------------------------------------- | ---------------------------------------- |
| 非阻塞缓存、部分命中补洞   | seed 作业已接入；提交继续保护人工定稿   | 衡量真实游戏语料吞吐                     |
| 工具开关独立、就绪检测     | 沿用已有过滤，每个进度窗口刷新开关      | 不同配置身份与就绪状态继续按引擎规范处理 |
| 空位补充、失败队尾兜底     | seed 作业内已实现，失败引擎本轮不再尝试 | 直接单次与实时入口后续评估迁移           |
| 跨请求限额及在途去重       | 服务端传输入口已实现                    | 持续观测实际配额与取消行为               |
| 作业级尝试记录与恢复去重   | 尝试记录驻内存，成功译文持久化          | 恢复时重建扫描；尚无逐项失败历史检查点   |
| 预计完成时间首次分配、冷却 | 待实施                                  | 引入观测后逐步启用                       |
| 有限超时竞速               | 待实施                                  | 计入完整资源与取消管理                   |
| 精翻队列、候选译文择优     | 待实施                                  | 先明确缓存候选与提升契约                 |
| 收费策略与预算限制         | 预留                                    | 接入收费工具时独立验收                   |

本轮实现细节和边界见第 14.3 节。前文描述的预计完成时间选引擎、超时备用请求及精翻仍是目标方案，不能视为本版已经上线。

## 11. 批量请求、数字模板与资源过滤补充

### 11.1 现场核对（2026-10-22）

原文页日志每段扫描 40 条，逐行展示其中 6 条译文，再省略余下结果。这种日志展示本身不能证明引擎是否批量调用。

优化前实际链路是：`fillMissingFromSeed` 每批取最多 40 条 → `liveTranslateTexts` 分解为单条任务 → Apple 客户端发送单条 `translate/text` 请求 → Swift 守护进程逐行读取并调用单条 `session.translate(text)`。因此优化前只有作业层批次，Apple 适配器没有真正的数组批量请求；批内有限并发也不等于原生引擎批量翻译。

游戏现场还确认：`Animations.rvdata2` 中 `Thunder5`、`Thunder10`、`Slash9`、`Magic7` 存在于 `RPG::SE` 的 `@name` 字段，且对应 `Audio/SE` 资源文件。不能把这类技术字段当作显示文本，通过数字模板继续翻译。

### 11.2 优化顺序

1. **先修正抽取与回写范围**：根据字段位置和 Ruby 类身份排除音频、图像等资源引用；保留真正的角色名、技能名、物品名与对白。不能仅凭字符串等于某个资源文件名就全局删除，因为玩家可见文本可能恰好同名。
2. **再清理已有任务来源**：从有效显示字段重建待译集合；对旧 seed、旧缓存和旧回写分别核对来源。不要直接清空全局缓存，也不要按文本全局替换或自动回滚人工修改。历史错误资源引用若已回写，需要按原字段与备份核对后修复。
3. **接入真正的引擎批量接口**：有批量能力的适配器一次提交多个独立文本，没有批量能力的工具继续使用受限单条并发。批次大小同时考虑条数、字符数、语言对和引擎限额，不固定认为 40 条适合所有工具。
4. **最后增加受约束的数字模板复用**：只对有明确变量结构或有可靠对齐证据的显示文本复用，不把任意数字差异当作同一句话。

### 11.3 真正的批量接口契约

- Apple 优先评估系统 `TranslationSession` 的批量请求能力，并为 stdio 协议增加数组请求及逐项结果；实际可用性和最低系统版本需实现时验证。
- 同一小批次只包含同一引擎配置、同一语言对及相容的请求约束；每项保留独立 ID，不能依赖结果恰好按输入顺序返回。
- 每项独立校验、计数、写缓存和记录失败；一项失败只转移这一项，不能把已成功的整批重新发送。
- 不用换行符把 40 段拼成一个字符串再拆译文，避免段落错位、丢项与控制码串位。
- 重复任务与安全模板在派发前合并；展示结果仍展开为原始项目。
- 日志区分批次输入数、缓存复用数、实际引擎请求数、实际送译条数、已完成数和仍未解决数。示例译文属于结果摘要，不冒充请求记录。
- 当前日志曾出现 `scanned 40, translated 40, failed 4`，说明“返回有效译文”和“最终缓存覆盖完成”口径可能重叠；后续应分开表达，并测试已完成与未解决集合的核算，不能只改日志数字掩盖缓存未生效。

### 11.4 数字模板的安全边界

| 文本情况                                 | 处理方式                                                             |
| ---------------------------------------- | -------------------------------------------------------------------- |
| 显式变量，例如同一原句中的数量占位符     | 保护变量后翻译模板，按槽位恢复原值                                   |
| 已验证的一一对应数字模板                 | 匹配相同正文、相同数字槽位结构与语言对后复用；保留前导零、符号和格式 |
| 只有一个译例且没有结构证据               | 不直接推断任意数字都可替换；先建立或验证模板                         |
| 型号、版本、日期、序数、专名或多数字重排 | 不默认归并；需要对应规则或显式模板，否则分别翻译                     |
| 同一模板存在冲突译文或数字对齐不明确     | 放弃自动复用，回到正常翻译或人工确认                                 |
| 游戏控制码的数字参数                     | 沿用已有 RM 数字控制码模板，不能和普通正文数字混为一类               |
| 音效、图片等资源标识                     | 从可翻译字段排除，保留原始引用，不进行模板翻译                       |

对于真正显示给玩家且经过模板验证的 `Thunder5 → 雷霆5`，可以建立正文与数字槽位对应，随后得到 `Thunder10 → 雷霆10`，不再调用引擎。但当前现场的音效资源字段应该直接免译。

模板缓存必须包含来源依据、语言对、模板版本和原译文依赖；原译文被人工修订或撤销时，相应模板也要失效。模板复用命中应参与缺词进度统计，否则会出现运行时已经可用、作业仍反复补译的问题。

### 11.5 补充验收

- 原生批量调用验证请求次数、逐项 ID 对应、部分失败、取消、字符限额和小批次切分；不要仅断言作业输入是 40 条。
- 抽取与回写测试覆盖 `RPG::SE/BGM/BGS/ME`、图片引用和相同字符串出现在玩家可见字段的情况；资源引用不改变，可见文本仍可翻译。
- 数字模板测试覆盖单数字、多数字、前导零、负数、小数、数字重排、冲突与人工修改失效；不支持的情况安全退回普通翻译。
- 缓存模板命中后不再产生引擎请求，批内重复模板不重复派发，作业进度与实际完成一致。
- 实测分别统计抽取过滤、批量接口和模板命中带来的收益，不能把删除错误任务的数量误报为翻译吞吐提升。

### 11.6 本轮实施（2026-10-22）

- **Apple 真批量**：Node 客户端在同一微任务内合并相同语言对的请求，一批最多 40 项、40,000 个 UTF-16 字符，单项最多 20,000。Swift 使用 `TranslationSession.translate(batch:)`，每项以独立 ID 流式返回；已成功项不会因随后发生的批次异常被重试。单独启用 Apple 的补译请求最多同时准备 40 项；其他组合仍保留现有 4 条并发与逐条兜底。没有将文本拼成长句再拆分。
- **资源过滤**：RGSS 按 `RPG::AudioFile/SE/BGM/BGS/ME` 类及图片引用字段排除资源，Animation/Tileset 的编辑器名称也不参与抽取。旧 seed 的任务资格由相同显示字段重新计算，以数据文件及备份指纹缓存；不改写 seed、不删除共享缓存。与资源同名的角色/物品等可见字段仍保留。没有自动修复历史上已回写的资源，若存在这类记录，需要按字段与备份另行核对。
- **数字标签复用**：范围限于一个 Latin 单词（可跟一个空格）加末尾 1–6 位数字的完整标签；至少两个不同数字的权威译例同时保留原数字、且中文正文完全一致才复用。冲突、数字丢失/变更、多个数字、换行、控制码均不推断。此为受限标签启发式，不是任意数字文本的语义保证；型号等语义敏感内容应使用明确模板。精确缓存优先，推断结果不写成独立权威译文。请求或插件数据刷新后，从当前权威记录重建依赖；修订/删除译例会失效。服务端补译统计与 MV 本地查询共用规则。
- **计数修复**：`translated` 采用本批在最终缓存检查后已覆盖的项目数，`failed` 采用同批仍未覆盖的项目数，两者互斥且合计等于 `scanned`。
- **页面修复**：RGSS 列表元数据统一返回 `locales.availableLanguages`；选择器兼容缺失、空值及损坏数据。对浏览器扩展注入根节点主题属性的 hydration 提示，只在根 `html` 上使用 `suppressHydrationWarning`。

验证：批量协议覆盖单次数组调用、乱序 ID、逐项失败、整批拒绝、拆批、停止和管道错误；抽取与回写覆盖 VX/VX Ace、音效和可见同名文本；缓存复用覆盖服务端、进度统计与 MV 本地更新失效。macOS 本机仅使用 Apple 实测 40 条简单英文，40/40 返回中文，约 1.14 秒（包含启动；非代表性游戏语料基准）。独立调度与跨请求限额的后续实施见第 14.3 节；超时竞速与精翻队列仍待实施。

## 12. 可恢复的小批次与等待预算（2026-10-22）

本轮优先减少端到端开销，同时限制一次异常影响的范围。独立引擎调度的后续实现见第 14.3 节。

| 项目           | 当前规则                                                                                                               |
| -------------- | ---------------------------------------------------------------------------------------------------------------------- |
| 正常批次目标   | 约 5 秒；依据上一批实际耗时调整，单次最多增长 50%                                                                      |
| 初始批次       | 仅 Apple 时 12 条；其他引擎组合 4 条                                                                                   |
| 数量边界       | 自适应 4–40 条；字符预算可以让实际批次少于 4 条                                                                        |
| 字符预算       | 初始 3,000，范围 500–10,000；单条长文本独立处理，不按任意字符切开控制码或对白                                          |
| 慢项与整批上限 | 单条及整批推理等待约 15 秒；批次超时停止派发，已成功项保留，未完成项记入本轮失败集合                                   |
| 自适应退让     | 耗时过长或存在失败时缩小下一批；正常失败后不再额外等待 1 秒                                                            |
| 保存时机       | 每条有效结果写入 SQLite；缓存补洞也逐个持久化，随后才发出完成回调。作业元数据最多每 250ms 检查点一次，并在批次边界保存 |
| 暂停与恢复     | seed 作业暂停停止新派发、终止缓存扫描并等待在途翻译收尾；恢复从持久化结果重建，缓存可被绕过                            |

开始/恢复时建立一次待译游标，之后每批只核验选中的文本。运行中的状态接口直接返回最近已核验的快照，不因共享库版本变化在每次轮询时扫描整个游戏。源 seed 文件改变时在批次边界重建；到队尾或准备宣布完成时进行完整核对，以发现人工删除或依赖变化。运行中未选中项目的统计是快照，完成状态必须经过最终核验。

5 秒是吞吐与可见反馈之间的目标，15 秒是推理等待预算，均不是操作系统级实时保证；首次准备、最终全量核验以及同步落盘不包含在推理预算中。模型突然变慢时不继续等几分钟，也不把整批成功结果当失败重发。底层无法取消的第三方调用，其迟到响应被丢弃；支持取消的请求传递 AbortSignal。Apple stdio 请求全部取消后终止未完成的原生工作，避免它继续堵住下一批；正常连续批次仍复用进程与 TranslationSession。

缓存补洞改为合批派发；重规划只关注当前文本匹配与依赖变化，不因其他文本的普通写入而误判整份翻译库冲突。原生二进制更新只在当前请求全部收尾后切换；开发热更新中的旧作业停止派发并收尾在途请求，再从持久化译文接续，禁止两个循环同时处理同一个游戏。用户主动暂停优先于自动接续。

验收覆盖：批次增减和边界、条数/字符拆分、中途失败后的恢复、整批超时仍保留成功项、缓存缺口逐项保存、迟到响应不写缓存、人工删除后最终核验、运行中轮询不全量扫描、暂停边界以及原生请求取消/二进制更新。

## 13. 批次性能诊断与优化依据

先记录阶段耗时，再调整批量；不能把整个管线耗时当成模型推理耗时。诊断信息不输出原文或译文，统一使用英文日志。

- 作业日志及服务端 `[translation-timing]`：批次条数、原文 Unicode 码点数 `sourceChars`、用于现有预算的 UTF-16 长度 `budgetUnits`、字符预算，以及配置、打开共享库、回填、加载本作记录/查找表、逐条句段匹配、数字模板查询、引擎请求/返回/失败、共享库写入、进度检查点、最终回填、本批覆盖核验和批次总耗时。
- 服务端 `[apple-timing]`：进程启动、实际发送批次 ID/条数/字符数/语言对/PID、首个结果或错误、批次收尾或中断。选中的作业批次与实际原生批次并非必然一比一：缓存命中不发送，缺口可能递归翻译，不同语言对分别发送。
- 原生 stderr `[apple-native-timing]`：同一个实际批次 ID 的 `received`、`session_ready`、`first_result`、`finished`，包含 session 是否复用、单调时钟耗时和墙钟毫秒。stdout 继续只承载 JSON 协议。Node 派发与原生收到的墙钟差可辅助判断队列等待；原生 `finished - session_ready` 才接近系统翻译 API 的处理时间，仍包含响应编码/发送。

条目之间可以重叠，递归缺口管线包含于父条目的耗时；不能把所有条目的引擎等待时间相加。Node 的“引擎返回”还可能包含事件循环被同步缓存计算阻塞的时间。5 秒预算调整使用整个 fill 的耗时，因此缓存过慢也会使批量缩小，不能据此判断模型吞吐。

### 当前实测与可能原因

2026-10-22 开发环境、正在运行的 Apple 作业第 534 批：4 条、288 个源字符，总计 3184ms。本作记录约 6762 条。

| 阶段              | 实测耗时                       | 判断与后续优化方向                                                                               |
| ----------------- | ------------------------------ | ------------------------------------------------------------------------------------------------ |
| 批前配置/缓存准备 | 313ms                          | 回填 141ms、加载记录 75ms、加载查找表 94ms；本作文件有重复读取和解析，应复用有版本校验的批次快照 |
| 4 条 cache plan   | 516/512/513/507ms，合计 2048ms | 实时路径给每条文本传入完整本作记录，句段算法反复扩展、匹配；优先复用候选索引，避免每条遍历全库   |
| 单条共享库写入    | 1–6ms                          | 当前不是主要瓶颈，保留逐项成功保存能力                                                           |
| 最终回填和关闭库  | 198ms + 11ms                   | 检查空回填是否仍有固定成本、是否重复加载文件；在保持持久化语义下合并重复操作                     |
| 本批覆盖核验      | 388ms                          | 已限定为选中项，但仍需要加载本作记录和构建 resolver；复用同一已校验版本的记录和索引              |
| Apple 实际处理    | 此样本尚无原生分阶段结果       | 不能用逐条 JS Promise 耗时认定模型慢；使用新增原生日志排除 session 准备与原生队列等待            |

同期部分文本会进入缺口子管线，重新打开共享库、回填、加载本作记录/查找表，并在结束后再次回填。应优先考虑复用父管线上下文并汇总缺口批次，同时保留人工修改后的依赖复核、成功即保存与失败隔离。

连续翻译复用进程及同语言对 TranslationSession；空闲超过 60 秒、进程异常、二进制升级或取消所有待完成请求才可能重建。原生主循环等待当前批次完成后才读取下一请求，因此若同一作业被拆成多个原生批次、或多个作业共享 daemon，会产生队列等待。确认这类等待后再评估调度调整，不能直接无限加并发。

优化顺序：整段 / 规范 / 数字模板索引等值快查 → 短句倒排索引限定候选（禁止 LIKE / GLOB 及全库遍历）→ 批内缓存快照复用 → 缺口上下文/批量复用 → 消除空回填与重复核验成本 → 根据纯引擎耗时调优批次。不得为了速度跳过缓存优先级、人工修订校验或持久化检查点。诊断后的索引查询及快照复用首版已接入，缺口连接复用等剩余方向继续以日志验证。

缓存搜索改造的需求与验收以 [缓存优化需求 §3.6、§6](translation-cache-optimization.md#36-缓存搜索只使用索引精确匹配2026-10-22) 为准，具体实现见 [技术方案 §10](technical/translation-cache-optimization.md#10-索引精确查询与性能改造2026-10-22首版)；本节保留性能诊断依据，不另建一套查询规则。

首版效果（2026-10-22）：实际游戏单条 cache plan 从约 500ms 降到 0–5ms，覆盖核验约 5–11ms；40 条热态查询样本 p95 约 16ms。样本规模、冷启动排除项及旧路径误报 miss 的说明见 [缓存优化需求 §6.1](translation-cache-optimization.md#61-首版验证记录2026-10-22)。端到端不承诺固定倍数，继续按批次字符数、成功率及各阶段耗时判断。

## 14. 非阻塞缓存扫描与翻译派发（2026-10-23）

状态：已在后台 seed 批量补译作业接入独立线路调度，具体范围及限制见第 14.3 节。本文该节替代早期“缓存必须先完成”和“仅预查 1–2 批”的建议；不改变引擎开关、请求限额、失败转移及人工定稿保护。

缓存扫描和翻译调度独立推进。首次启动缓存冷、扫描暂时落后、某批查询慢时，均允许尚未匹配缓存的文本直接进入翻译；不能因为缓存尚未返回而空置可用引擎。两条线路不共享整批完成屏障；缓存扫描可以推进到全程结束，以时间片让出事件循环，队列容量 / 内存有界，本版成功结果与汇总进度持久化，扫描游标与逐项尝试状态驻内存；恢复时从持久化结果重建扫描。

> 2026-10-25 设计补充：有界缓存优先预取、来源权重和长驻 worker 的目标契约见[缓存批处理性能 §9](translation-cache-batch-performance.md#9-缓存优先预取来源权重与长驻-worker2026-10-25主体已接入验收未完成)。该节主体已接入，实际能力仍以第 14.3 节为准；纯缓存结果跨分片聚合另见[结果窗口聚合需求](translation-cache-result-window-batching.md)。

### 14.1 任务领取与结果竞争

| 场景                               | 处理                                                                                   |
| ---------------------------------- | -------------------------------------------------------------------------------------- |
| 有已确认缓存未覆盖的任务           | 引擎优先领取已知缺口 / 未命中任务                                                      |
| 引擎空闲，只有未扫描或扫描中的任务 | 原子领取并直接翻译，不等待缓存；缓存状态保留 unknown / scanning，不冒充 miss           |
| 缓存完整命中，翻译尚未发送         | 接受有效缓存、完成任务并撤销待发翻译；不等待凑满批次                                   |
| 缓存部分命中，翻译尚未发送         | 更新为仅翻译缺口；派发时重新核验任务领取版本，避免发送旧整段任务                       |
| 缓存命中时翻译已经发送             | 第一个通过校验并成功接受的结果完成任务；支持取消则尽力取消多余请求，取消不阻塞结果接受 |
| 翻译先完成，缓存尚未扫描 / 返回    | 校验并保存有效翻译，标记完成、更新内存，跳过无必要的后续扫描；不等待缓存线路完成       |
| 任一线路失败                       | 另一条线路继续；缓存不可用不等于全部翻译失败，引擎失败仍执行原有兜底                   |
| 迟到结果或人工修改                 | 复核任务代次及权威 revision；不重复完成 / 计数，不以自动结果覆盖人工定稿               |

“哪个快用哪个”指第一个通过校验且获准接受的结果。缓存与引擎通过任务领取 token / generation 和原子状态更新协调；不会因为两条线路同时返回而同时提交。外部请求不支持取消时仍占用实际在途配额，直到真正结束。迟到结果可按现有候选规则保留，不反复替换已展示结果。

允许跳过的是完整缓存命中搜索，结果提交时仍需使用现有人工保护及相关键 / revision 校验；该检查不得退化为强制全文缓存扫描。已知且有效的人工定稿继续优先；未知缓存状态不能当作数据库不存在记录，不能通过绕过保护的 upsert 覆盖人工数据。

### 14.2 批次、统计与验收

- 各引擎按各自字符预算、批量能力、并发和限流独立组批；无更多就绪任务时可直接发送当前不满批次，不等待缓存批次补齐。
- 纯缓存结果按独立条数和字符预算消费，首期上限为 40 项 / 10,000 字符；不继承引擎初始 4 项或 3,000 字符预算，也不反向限制 32 项扫描分片和 64 项结果缓冲。分片完成不结束纯缓存窗口；工作耗尽、静默收口和容量边界见[结果窗口聚合需求](translation-cache-result-window-batching.md)。
- 相同任务合并在途请求；成功持久化后更新内存及相关 miss 的失效状态，后续未发任务即时受益。
- 记录 cacheHit、cacheMiss、cacheBypassed、cacheCancelled、engineSubmitted、duplicateInFlight，区分未匹配和实际未命中；缓存命中率只按已完成查询统计。
- 用户日志使用结构化 `finalSources` 投影标签，展示最终实际采用的工具；`submittedSources` 仅用于诊断和整批失败回退，不展示已被缓存撤销的引擎尝试。
- 同时记录缓存线路和各引擎线路吞吐；端到端完成量按任务唯一计数，不能相加两条线路的完成回调。缓存绕过耗时不记成缓存匹配耗时。
- 必须覆盖缓存初始化卡住仍能发引擎、扫描慢时批次直接发送、缓存先完成撤销未发任务、引擎先完成无需等待缓存、双方同时完成只记一次、迟到人工命中仍获保护、不可取消请求保留配额、暂停恢复丢弃旧代次，以及全程扫描的内存与队列上限。

### 14.3 本版实施范围与边界

- 后端落点为 `services/translate/scheduler/`；`seed-job` 通过 `createSeedFillSession(..., { nonBlocking: true })` 接入。缓存 worker 单独构建，开发模式监听重建，运行中的缓存线路在已排空 IPC 分片边界加载新 worker；后台作业代码升级则收尾旧会话后恢复。
- 缓存每次 IPC 最多 32 项，只保留一个在途分片；完成结果缓冲 64 项，另允许当前在途分片收尾。部分命中计划最多 128 项、已知 miss 优先队列最多 2,048 项；各引擎预算暂不容纳的任务缓冲最多 64 项，尝试记录达到 64 项时暂停领取新任务，优先消化已有任务。源文清单和紧凑状态数组仍随总量增长，不加载整个共享译文库。
- 每个引擎按单调游标领取新任务，避免每次空位遍历全游戏。失败项进入其他启用引擎队尾，新任务先处理；会话内保存已失败引擎集合，关闭后重新启用也不重复尝试。每个返回进度窗口重新读取开关，已关闭引擎的在途订阅取消。
- 总在途数沿用自适应预算，最多 40，活跃原文合计字符受预算限制；超长文本单独处理。Apple 传输配额 40、Agent 每配置 2、平台 4、Bergamot / Ollama 1；Apple 沿用适配器微任务合批。其余适配器不因此获得新的批量接口。
- 缓存连续 5 秒无进展则关闭该线路，引擎继续。单项翻译沿用 15 秒上限；全部引擎失败时，尚未扫描的任务可暂候缓存，最多 64 项，缓存线路失败则结束这些失败项。此上限也可能截断较慢 Agent，后续须用实测调优。
- 当前版本已接入 `CACHE_PENDING` 分类窗口；暂停会释放会话租约，但缓存 worker 的跨暂停复用仍按 §12.6 的 TTL 和实现状态单独验收。未扫描任务在分类窗口内不由引擎领取，超时或缓存不可用时仍有界降级。实现边界、预算、权重和迁移要求见[缓存批次 §12](technical/translation-cache-optimization.md#12-缓存优先预取权重与长驻协调2026-10-25主体已接入)，实施状态以 §12.1 为准。
- 缓存与引擎按任务状态只完成一次。缓存采用文件指纹、本作权威版本、语料版本和依赖 revision 保守核验；已登记的自身回填只允许沿连续 owned transition 推进 stamp，不得掩盖人工或外部修改。完整命中过期进入 `RECHECK`，重新扫描确认 miss 后才进入引擎；缓存不可用时才按软失败降级。绕过缓存的引擎结果提交时仍做等值权威检查，持久化后才能作为成功结果。详细设计见 [缓存批次 §11](technical/translation-cache-optimization.md#11-缓存批次快照回填与用户日志2026-10-25)。
- 同配置、游戏、语言对及受保护原文的在途传输共享 Promise，各订阅分别接受和持久化；全部订阅取消才取消底层请求。底层不支持取消时仍占配额直到真正结束。数据库写入与回填仍有同步短操作，本版并非所有 SQL 均异步。
- 恢复与非运行态进度统计必须包含本作 `cache.ndjson` 的已保存译文，不能只看 `seed.json`。共享来源镜像通过只读主键 revision 校验，失效或已删除的记录不算完成；整段 / 展示格式的本作等值命中从待译清单剔除。该阶段不迁移共享库、不做共享全文覆盖扫描。进度指纹包含统计规则版本，升级后旧的零进度快照会失效。
- 暂停立即停止新派发并释放缓存 worker 的会话租约，当前会话保留 worker 进程供恢复复用；等待已有受限翻译请求收尾、保存成功结果及刷新回填。恢复使用新租约，旧租约迟到结果和 `done` 必须丢弃；从持久化译文与最终失败记录重建待译状态，不保存逐项扫描游标。正常 `close()`、切换游戏、worker 版本更新或致命错误才终止缓存 worker。最终失败按游戏和原文保存于独立追加日志，中断保持待处理。没有新增完整 L1 正负缓存，继续复用本作上下文、等值索引及在途去重。
- 状态栏缓存时间为当前进度窗口内 worker 累计匹配耗时，不含 worker 启动、迁移及写入；进度窗口按完成项返回，不等待旧批次最慢一项。速率仅使用本次运行的近期完成窗口与实际活跃时间，恢复后清空样本，ETA 使用剩余字符除以该速率。

验证覆盖真实打包 worker 的本地 / 共享 / 数字族命中、全程扫描、缓存卡住时直发、空位持续补充、先完成方唯一计数、人工定稿回填、失败换队尾、引擎切换、字符预算、暂停、在途去重和不可取消请求配额。批次性能补充还须覆盖自身回填后的连续命中、自身回填与人工修改并发、完整命中过期重校验、纯缓存独立批次、结构化日志来源和正常 / 异常退出回填语义，详见 [缓存批次 §11.5](technical/translation-cache-optimization.md#115-指标与验收边界)。集成测试使用真实 SQLite 与 worker、模拟翻译适配器，未调用收费服务，也未恢复用户暂停的真实作业。吞吐收益需要同语料实测，不承诺固定翻倍。
