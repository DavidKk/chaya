## 1. 能力模型

**按「游戏文件由谁读写」区分，而不是按部署平台或执行运行时区分。**

- 服务与游戏在同一台机器 → 服务直接读写游戏、启动游戏（**服务端模式**，`canUseDisk = true`）。
- 服务与游戏不在同一台机器 → 只能由浏览器在用户授权后读写游戏目录（File System Access，下称 **FSA**），用户自己启动游戏（**浏览器模式**，`canUseDisk = false`）。
- 网页不能启动本机进程、不能 `chmod` / 建符号链接 / 签名：这是浏览器硬限制，决定了浏览器模式下壳安装的平台差异（§5）。
- 浏览器模式下，**游戏运行起来之后**，游戏本身（NW.js，具备 Node 文件能力）经 WebRTC 数据通道替页面执行翻译、修改器数据、译文缓存等操作（`components/GameLinkProvider.tsx`、`lib/translate/runtime-api.ts`），不回退到服务器的磁盘接口。所以浏览器模式的分工是：**游戏没运行时靠 FSA，游戏运行后靠游戏连接**。因此游戏连接（WebRTC 信令）是浏览器模式的核心链路（§3.3）。
- `canUseDisk` 目前同时承担「游戏文件由谁读写」与「服务端能否写自己的存储」两层含义；拆分方案见优化方案 O2。

## 2. 构建与运行时模型

三个概念相互独立，不要混用：

| 概念       | 取值                         | 含义                                   | 判定 / 位置                                                                                                                                                              |
| ---------- | ---------------------------- | -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| 构建目标   | `server` / `edge` / `dev`    | 是否剔除 `*.server.*` / `*.dev.*` 路由 | **构建时**：`VERCEL=1` 或 `CHAYA_TARGET=edge` → edge；dev 阶段 → dev；否则 server。写成常量 `NEXT_PUBLIC_CHAYA_TARGET`（`next.config.ts`、`lib/service-mode/target.ts`） |
| 服务形态   | `local` / `app` / `vercel`   | 服务的能力边界                         | edge 构建或 `VERCEL=1` 强制 `vercel`；dev 看右上角切换器（Server / Edge，进程级）；否则看 `CHAYA_SERVICE`（`lib/service-mode/mode.ts`）                                  |
| 执行运行时 | Node.js（Edge Runtime 未用） | Next 路由实际在哪执行                  | 关键 API 显式声明 `runtime = 'nodejs'`，其余沿用 Next.js 默认                                                                                                            |

由服务形态派生：

| 层       | 取值                         | 判定                                                                                                   | 位置                                            |
| -------- | ---------------------------- | ------------------------------------------------------------------------------------------------------ | ----------------------------------------------- |
| 能力     | `canUseDisk`                 | `形态 !== 'vercel'`                                                                                    | `lib/service-mode/mode.ts`                      |
| 界面分支 | `browserMode`                | `/api/status` 返回 `canUseDisk`；Dashboard 中 `browserMode = canUseDisk === false`                     | `components/Dashboard.tsx`                      |
| 操作系统 | `darwin` / `win32` / `linux` | 服务端模式：`process.platform`（经 `status.host.platform`）；浏览器模式：`detectClientOs()`（UA 推断） | `app/api/status/route.ts`、`lib/browser/fsa.ts` |

- 构建目标只在**构建时**生效：只在启动时设 `CHAYA_TARGET` 无效。
- 仅 server 构建的接口文件命名 `route.server.ts`（dev 专用 `route.dev.ts`），edge 构建经 `pageExtensions` 剔除；`pnpm check:edge` 校验产物不含这两类路由。
- 读写用户磁盘的接口用 `requireDisk()`，浏览器模式返回 501。
- 非 `*.server` / `*.dev` 文件不得 import 这两类模块（ESLint `no-restricted-imports`）。

## 3. 部署矩阵

| 部署方式                 | 构建目标                                     | 服务形态 | 服务跑在哪           | 游戏在哪   | 界面模式   | 运行前提                                                                                                  | 状态                                               |
| ------------------------ | -------------------------------------------- | -------- | -------------------- | ---------- | ---------- | --------------------------------------------------------------------------------------------------------- | -------------------------------------------------- |
| 本地 server              | server                                       | `local`  | 用户电脑             | 同一台电脑 | 服务端模式 | Node ≥ 22.19.0；局域网内他人访问需管理授权                                                                | 已实现·有测试                                      |
| App（Electron）          | server（+ standalone）                       | `app`    | 用户电脑（内置服务） | 同一台电脑 | 服务端模式 | 安装包自带运行时                                                                                          | 已实现                                             |
| Vercel                   | edge                                         | `vercel` | Vercel（多实例）     | 用户电脑   | 浏览器模式 | HTTPS（平台自带）；Chromium 桌面浏览器                                                                    | **有部署限制**：信令多实例未解决前为实验性（§3.3） |
| 自托管到远程 Node 服务器 | **edge**（`pnpm build:edge` + `next start`） | `vercel` | 远程服务器           | 用户电脑   | 浏览器模式 | **构建时**设 `CHAYA_TARGET=edge`；Node ≥ 22.19.0；**必须 HTTPS**；**单进程、单副本**；Chromium 桌面浏览器 | 有部署限制：仅单进程                               |

- 局域网里用手机 / 另一台电脑打开本地 server：游戏仍在服务那台机器上，仍是服务端模式（不能按访问 IP 判断）。
- **远程游戏连入**（服务端模式下的特例）：游戏在另一台机器上运行，主动连入本地 server，游戏库记为远程条目（`status.remote`）。服务不能读写它的文件、不能启动它，只能经游戏连接操作；界面不显示绑定状态、操作区换成提示，路径显示 N/A。
- 访问控制：服务端模式由 `proxy.ts` 要求管理授权（启动终端打印的授权链接），防止局域网内他人操作本机磁盘；浏览器模式没有这道门禁。
- App 与 local 代码不分支，区别只是 `data/` 位置：App 由 `electron/main.cjs` 设 `CHAYA_DATA_DIR = userData/data`（安装包资源只读）。

### 3.1 浏览器模式的前提（Vercel 与自托管都适用）

- **安全上下文**：选目录（`showDirectoryPicker`）要求 HTTPS 或 `localhost`；`http://192.168.x.x` 这类局域网 HTTP 页面无法选目录。
- **浏览器**：仅 Chromium 系桌面浏览器（Chrome / Edge）。Safari、Firefox、iOS / Android 浏览器不在当前浏览器模式的支持范围内。
- **路径**：只能拿到目录句柄与目录名，拿不到绝对路径。
- **装壳自动化程度按平台不同**：Windows 页面安装（需用户选中下载好的 zip），macOS 终端命令，Linux 仅下载链接（§5）。
- 不满足前提时目前没有专门提示（优化方案 O10）。

### 3.2 自托管 Node

自托管 Node 使用云端（edge）构建目标，只提供浏览器模式；它仍运行 Node.js API，但主动剔除本机磁盘路由。推荐单进程、固定实例，必须启用 HTTPS。

- **不要**把 server 构建部署到远程：它会被判成 `local`，把壳下载到服务器、读写服务器上的"游戏目录"，是错的。
- 浏览器模式下服务器不收、不存游戏日志（`/api/logs` 在 `canUseDisk = false` 时丢弃上报、读取返回空），自托管也不会把游戏日志写进服务器硬盘。

### 3.3 游戏连接信令与实时日志（部署限制）

- 信令房间存在服务进程内存（`services/runtime/webrtc-signaling.ts`，10 分钟 TTL，最多 5000 个房间）。浏览器模式的日志已不经服务器（§4），不受多实例影响。
- **Vercel**：网页发 offer、游戏取 answer 可能落到不同实例，冷启动后房间消失 → **连不上游戏**（不是偶发丢日志）。在共享存储落地前（优化方案 O6），Vercel 上的浏览器模式视为**实验性，不保证连接**。
- **自托管**：单进程可用当前实现；**禁止多副本 / 负载均衡**。
- **鉴权**（已实现·有测试，`__tests__/app/webrtc-signaling-api.spec.ts`）：
  - 所有请求必须带 `roomId`，不再有公共房间 `'default'`；读取 / 应答不会创建房间。
  - 服务端模式：页面需管理授权，游戏的 launch token 只能读自己的房间并应答（`services/access/api.ts`）。
  - 浏览器模式：页面为每个游戏生成连接令牌（`lib/browser/link-token.ts`，存 localStorage），「连接」时写进游戏 Env（`CHAYA_LINK_TOKEN`）。双方请求信令都带 `X-Chaya-Link-Token`；Web 首次 `reset` / `offer` 时服务器绑定令牌哈希，缺令牌返回 401、令牌不符返回 403，`reset` 保留绑定。
  - 「连接」会同时刷新插件文件，保证游戏侧插件支持令牌。

### 3.4 已定决策：不新增 Node 部署类型（2026-10-03）

远程 Node 与 Vercel 在「游戏文件由浏览器读写」这一能力边界上相同；但运行时稳定性、内存状态、长任务和多实例行为不同（自托管单进程可保留内存状态，Vercel 多实例 / 冷启动不行）。目前没有用到服务端存储、长任务的需求，因此：

- 不新增 `node` 形态；要部署到自己的 Node 服务器，用 **edge 构建**跑在 Node 上（满足 §3 的运行前提）。
- 重新评估的触发条件：要做服务端翻译（服务端模型 key / 批量任务）、跨用户共享译文缓存（`node:sqlite`）、或需要服务端存储的私有化部署。届时方案：新增 `node` 形态，并把 `canUseDisk` 拆成能力层（优化方案 O2），业务代码只看能力不看形态名。

## 4. 能力矩阵

| 能力                         | 服务端模式（local / app）                                      | 浏览器模式（Vercel / 自托管）                                                                                         | 原因                         |
| ---------------------------- | -------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ---------------------------- |
| 选游戏 / 绑定路径            | 系统选目录或手填完整路径                                       | FSA 选目录，只能拿到目录名                                                                                            | 浏览器拿不到绝对路径         |
| 游戏库                       | 服务端配置文件                                                 | 浏览器 IndexedDB（含目录授权句柄），换浏览器 / 设备看不到                                                             | 授权句柄只能存在浏览器本地   |
| 装 / 清除插件                | 服务写 `js/plugins/` 与 `js/plugins.js`                        | 浏览器经 FSA 写入；插件文件从 `GET /api/plugins/:name` 拉                                                             | 普通文件，三平台都能写       |
| 窗口配置（`package.json`）   | `/api/window` 读写                                             | FSA 读写 `<内容根>/package.json`；不存在则不创建                                                                      | 同上                         |
| 信息条统计                   | 服务统计（体积用 `du`，占盘值）                                | 浏览器统计（逐个文件累加逻辑大小，略小于 `du`）                                                                       | 浏览器只能读文件大小         |
| 装壳                         | 下载到 `data/`，所有游戏共用                                   | 写进游戏目录，按平台不同（§5）                                                                                        | 见 §5                        |
| 下载 / 升级 / 卸载共用壳     | 有                                                             | 无（没有共用壳）                                                                                                      | —                            |
| 启动游戏                     | 服务直接启动                                                   | 写连接配置后由用户双击启动                                                                                            | 网页不能启动本机进程         |
| 游戏连回                     | 连回服务（WebRTC，信令走服务内存）                             | 连回打开页面的 origin（信令同样存在该服务的内存里；**有部署限制**，见 §3.3）                                          | —                            |
| 翻译、译文缓存               | 服务端 `/api/translate`、`/api/translate-cache` 读写游戏侧文件 | 游戏连接后由游戏内运行时执行；游戏未连接时不可用                                                                      | 服务器碰不到用户的游戏文件   |
| 修改器数据（catalog）        | 服务端 `/api/game-edit/catalog`                                | 游戏连接后由游戏提供；未连接时不可用                                                                                  | 同上                         |
| 抽取文本 `/api/extract`      | 支持                                                           | 不可用（501）                                                                                                         | 同上                         |
| 跨游戏共享翻译缓存（SQLite） | 支持（`data/` 下）                                             | 不可用                                                                                                                | 需服务端存储与 `node:sqlite` |
| 日志                         | 游戏上报到本机服务，落盘 `logs/plugins`                        | 游戏经数据通道发 `log.batch`，页面内存保存（`lib/log/link-log-store.ts`），只含当前连接的游戏，可清空；服务器不收不存 | 避免日志被其他访问者看到     |
| MCP                          | 服务端 `/api/mcp` + Agent 桥                                   | 无服务端 MCP；页面内 WebMCP 提供库 / 游戏 / 经游戏连接的翻译与修改工具，不可用项见 `lib/webmcp/mode-matrix.ts`        | 服务端工具大多要读写游戏文件 |

## 5. 操作系统 × 部署方式

### 5.1 装壳

| 平台    | 服务端模式（local / app）                                                                                                                                                                                                                                                             | 浏览器模式                                                                                                                                                                                                              |
| ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Windows | 后台任务从 nwjs.io 下载（`.part` + Range 续传、SHA-256 校验，进度经 SSE 显示在下载中心）→ 解压到 `data/shell-cache/[sdk-]<版本>-<fileKey>/extract/`（`fileKey` 含系统与架构，如 `win-x64`、`osx-arm64`；解压后删压缩包）→ 复制到同目录暂存 `.<壳名>.staging` 后整体替换 `data/shell/` | 下载中心任务（只读展示进度）：游戏卡片上「打开官方下载」让浏览器下载到"下载"文件夹 →「选择已下载的压缩包」→ 缓存进 OPFS（下次跳过）→ 页面内排队读取 / 解压写入 `<游戏目录>/<壳目录>/`（可断点续写）→ 写 `Chaya启动.bat` |
| macOS   | 同上，装成 `data/shell/Chaya.app`                                                                                                                                                                                                                                                     | 页面给终端命令（`/sh/mac-shell.sh`）：`curl` 下载（缓存 `/tmp/chaya-nwjs-<uid>/`，可断点续传、校验 SHA256）→ `ditto` 解压 → 建 `app.nw` → `xattr -cr` + `codesign` 重签 → 装成 `<游戏目录>/Chaya.app`（旧的改名备份）   |
| Linux   | 同上（壳目录直接是 NW.js 解压结果，不建 `.app` / `app.nw`）                                                                                                                                                                                                                           | 只给 nwjs.io 下载链接，用户自行解压、`chmod +x` 并启动；不写启动脚本（`writeShellLaunchers` 支持 linux 但未调用）。自动化见优化方案 O7（未实现）                                                                        |

**为什么浏览器模式三平台不同**

| 需要的步骤              | Windows                                                     | macOS                                                  | Linux                                    |
| ----------------------- | ----------------------------------------------------------- | ------------------------------------------------------ | ---------------------------------------- |
| 执行权限                | 不需要                                                      | 需要（`nwjs`），浏览器做不到                           | 需要（`nw`），浏览器做不到               |
| 压缩包内符号链接        | 无                                                          | 有（框架 `Versions/Current` 等），FSA 写不出来，壳会坏 | 未确认                                   |
| 指向游戏的链接 `app.nw` | 不需要（启动脚本传内容根）                                  | 需要，浏览器建不了符号链接                             | 不需要                                   |
| 清隔离标记 + 重签       | 不需要；首次运行可能弹 SmartScreen，点"更多信息 → 仍要运行" | 需要，否则系统拒绝打开                                 | 不需要                                   |
| 结论                    | 浏览器可完成                                                | **必须终端**                                           | 需用户 `chmod`，维持下载链接或改终端命令 |

- dl.nwjs.io 没开 CORS，网页不能 `fetch` 包体，所以 Windows 只能"浏览器正常下载 + 用户选文件"，**无法显示下载进度、无法后台自动下载**。
- 不考虑"浏览器下载 zip 让用户双击解压"：带隔离标记、NW.js 未公证会被拦截，还要用户自己处理链接和签名。
- 可选的 macOS 两段式（浏览器下载、终端只做本地步骤）：收益有限，暂不做。

**下载中心**（已实施，详见 [download-center.md](download-center.md)）：

- 服务端模式是进程内后台任务，通过 SSE 显示进度；`.part` + Range 续传，壳在同目录暂存后整体替换，安装 / 启动 / 读取状态前先恢复上次中断留下的 `.old`。任务在 App 退出或服务进程重启时中断，但 `.part` 保留供下次续传；不是跨进程持久队列。
- 浏览器模式仅 Windows 进入下载中心；Chrome 下载栏仍负责网络下载，页面只能显示“等待浏览器下载”，选文件后才显示读取 / 写入进度。macOS 终端命令与 Linux 原生下载链接不进下载中心。
- 浏览器 Windows 多任务可同时等待选文件，但约 216 MB 压缩包的读取 / 解压 / 写入在页面内串行，避免并发占用过多内存。

## 6. 浏览器模式的数据（`CloudGame`）

存 IndexedDB（`cloudLibraryStorage`），定义见 `lib/browser/cloud-prepare-game.ts`。

| 字段                 | 来源                                                                 | 何时更新                   |
| -------------------- | -------------------------------------------------------------------- | -------------------------- |
| `picked` / `content` | 选目录；`content` 为 `www` 或根                                      | 选游戏                     |
| `existingShell`      | 在游戏目录查找已装壳                                                 | 检测（`inspectCloudGame`） |
| `nwPackage`          | 读 `<内容根>/package.json`（`lib/browser/cloud-window.ts`）          | 检测、改窗口配置           |
| `plugins`            | 跟踪插件逐个状态，判定与服务端共用 `trackedPluginStatuses`           | 检测                       |
| `cacheEntries`       | 游戏侧译文缓存非空行数，候选路径同服务端                             | 检测                       |
| `fingerprint`        | 引擎 / 第三方插件数 / 是否加密（`lib/browser/cloud-fingerprint.ts`） | 检测                       |
| `footprint`          | 内容体积、壳体积（递归累加，较慢）                                   | 后台补算；装壳后置空重算   |

- 检测在选游戏、各操作之后执行；旧条目缺字段时，若目录授权仍有效（`queryPermission === 'granted'`），`useCloudLibrary` 静默补齐，不弹授权。无授权时设置面板显示「授权读取」（`requestPermission` 需用户点击）。
- 游戏库条目由 `withLibraryView` 按服务端同口径生成：名称（`nwGameDisplayName`）、结构标签（`libraryKindLabel`）、壳状态、指纹；目录名放 `pathLabel`。

## 7. 两种模式共用的规则与组件

改 UI 或判定时只改一处，两种模式同时生效。

| 内容                                                                                                     | 共用实现                                                                      |
| -------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------- |
| 游戏显示名：窗口标题 → 包名 → 目录名（去 `.app`）                                                        | `nwGameDisplayName`（`lib/game/nw-window.ts`）                                |
| 游戏库结构标签                                                                                           | `libraryKindLabel`（`lib/game/library-label.ts`）                             |
| 跟踪插件就绪判定（Loader 已注册即全部就绪）                                                              | `trackedPluginStatuses` / `countReadyPlugins`（`lib/game/plugins-status.ts`） |
| 体积文案                                                                                                 | `formatBytes`（`lib/format-bytes.ts`）                                        |
| `package.json` 窗口合并写入                                                                              | `mergeNwPackageWindow`（`lib/game/nw-window.ts`）                             |
| 指纹摘要                                                                                                 | `summarizeFingerprint`（`lib/game/fingerprint`）                              |
| 当前游戏卡片：头部（绑定状态 + 标题 + 信息条）｜快捷入口｜操作区｜补充信息；分隔与间距只在 `CardSection` | `components/dashboard/DashboardGameCard.tsx`                                  |
| 信息条：游戏｜运行环境｜数据，连接状态靠右                                                               | `components/dashboard/DashboardGameMeta.tsx`                                  |
| 设置面板路径行                                                                                           | `PathField`（`components/DashboardSettings.tsx`）                             |

**允许的差异**（其余应保持一致）：

- 操作区按钮：浏览器模式「开始游戏」实为连接，装壳流程不同，无下载 / 升级 / 卸载共用壳。
- 设置面板：浏览器模式游戏目录只读（显示目录名，按钮重新选目录），无壳源行。
- 绑定状态里的壳位置：服务端模式为 `data/shell/...`，浏览器模式为 `<游戏目录>/<壳名>`。
- 远程会话（游戏远程连入）：不显示绑定状态，只显示提示。
